## Pod

### 1. Conceptual Overview

A Pod is the smallest deployable unit in Kubernetes. It represents a single instance of a running process in a cluster and encapsulates one or more containers that share the same network namespace, IPC namespace, and optionally PID namespace.

**What problem it solves:**
Pods provide the abstraction layer between containers and the Kubernetes scheduling and lifecycle machinery. Containers cannot be scheduled directly; the Pod wraps them with metadata, resource specifications, networking configuration, and volume mounts that the kubelet and scheduler consume.

**Where it fits in cluster architecture:**
Pods are the atomic unit the scheduler places onto Nodes. Every higher-level workload controller (Deployment, ReplicaSet, DaemonSet, StatefulSet, Job) ultimately creates Pods. The kubelet on each node is responsible for running and monitoring Pods assigned to that node.

**Which controller manages it:**
Standalone (bare) Pods are not managed by any controller; if deleted or evicted, they are gone. In practice, Pods are managed by their owning controller (ReplicaSet controller, DaemonSet controller, StatefulSet controller, Job controller). The kubelet manages the local lifecycle of Pods assigned to its node.

**How reconciliation works:**
The relevant workload controller watches the Pod API for Pods matching its label selector. It compares the current count/state against the desired spec. If Pods are missing, it creates new ones. If there are excess Pods, it deletes them. For standalone Pods, there is no reconciliation; the kubelet simply runs them.

**Interaction with scheduler:**
When a Pod is created with `spec.nodeName` empty, the kube-scheduler picks it up from the scheduling queue. It runs through filtering (predicates) and scoring (priorities) phases to select a node, then binds the Pod by setting `spec.nodeName`. The kubelet watches for Pods bound to its node and starts them.

**Cloud-provider considerations:**
Cloud providers may inject tolerations (for cloud-specific taints), modify node affinity, or attach cloud-specific volumes. The cloud controller manager handles node lifecycle events that indirectly affect Pod scheduling and eviction. On managed Kubernetes (EKS, GKE, AKS), control plane Pods are hidden; only data plane Pods are visible.

### 4. Complete Field Breakdown

#### metadata

- **name** (string, required)
  - Must be unique within the namespace. DNS subdomain name: max 253 characters, lowercase alphanumeric, `-`, `.`. Immutable after creation. Stored as the key prefix in etcd under `/registry/pods/{namespace}/{name}`. When created by a controller, the name is typically generated with a random suffix from `generateName`.

- **generateName** (string, optional)
  - Prefix for auto-generated names. The API server appends a random 5-character suffix. Used by ReplicaSet/Job controllers. Mutually exclusive in practice with `name` (if `name` is set, `generateName` is ignored). Max 253 chars minus 5 for the suffix.

- **namespace** (string, optional, default: `default`)
  - Must reference an existing Namespace. Immutable after creation. Affects DNS resolution (`{svc}.{namespace}.svc.cluster.local`), RBAC scope, ResourceQuota applicability, and NetworkPolicy matching.

- **labels** (map[string]string, optional)
  - Key-value pairs used for selection by Services, ReplicaSets, NetworkPolicies, PodDisruptionBudgets, and other controllers. Keys follow the `prefix/name` format where prefix is a DNS subdomain (max 253 chars) and name is max 63 chars. Values max 63 chars, must start and end with alphanumeric. Controllers use labels for ownership matching; changing labels on a managed Pod causes the controller to see it as missing and create a replacement while the orphaned Pod continues running.

- **annotations** (map[string]string, optional)
  - Arbitrary non-identifying metadata. Used by tooling (Prometheus scrape config, Istio sidecar injection, Helm metadata, cluster-autoscaler hints). No size limit per annotation but total object size in etcd is capped at 1.5MB. Not used for selection. Commonly used annotations: `kubectl.kubernetes.io/last-applied-configuration` (stores the full last-applied manifest for three-way merge in `kubectl apply`).

- **ownerReferences** ([]OwnerReference, optional)
  - Set by the parent controller (ReplicaSet, StatefulSet, DaemonSet, Job). Contains the owner's `apiVersion`, `kind`, `name`, `uid`, and `blockOwnerDeletion`. When the owner is deleted, the garbage collector cascades deletion to owned Pods. The `controller` boolean field within ownerReferences indicates the managing controller (only one should be `true`). Orphan Pods (ownerReferences removed) persist indefinitely.

- **finalizers** ([]string, optional)
  - Blocks deletion until all finalizers are removed. Used by custom controllers to perform cleanup before a Pod is removed from etcd. The Pod enters a `Terminating` state but the etcd record persists. Common finalizer: `kubernetes.io/pv-protection` on PVs, not typically on Pods directly unless custom controllers are in play.

- **resourceVersion** (string, set by API server)
  - Opaque string representing the etcd revision. Used for optimistic concurrency control. Every update to the object changes this value. When using `kubectl apply` or `replace`, the API server rejects the write if the `resourceVersion` doesn't match the current stored version (HTTP 409 Conflict). Watch events include this for resumption.

- **uid** (string, set by API server)
  - Unique identifier across the entire cluster and across time. UUID format. Used in ownerReferences to precisely identify the parent. Even if a Pod with the same name is recreated, it gets a new UID.

- **generation** (int64, set by API server)
  - Incremented when `spec` changes. For Pods, since spec is mostly immutable, this is typically 0 or 1. More relevant for Deployments, ReplicaSets. Controllers compare `generation` against `status.observedGeneration` to detect whether the latest spec has been processed.

- **creationTimestamp** (Time, set by API server)
  - RFC3339 timestamp of when the object was created in etcd. Immutable. Used for age calculations (`kubectl get pods` shows AGE column derived from this).

- **deletionTimestamp** (Time, set by API server when delete is initiated)
  - Set when a delete request is received. The Pod enters `Terminating` phase. The kubelet begins graceful shutdown. If finalizers exist, the object persists in etcd until all finalizers are removed. Immutable once set.

- **deletionGracePeriodSeconds** (int64, set with deletionTimestamp)
  - The grace period granted for termination. Defaults to `spec.terminationGracePeriodSeconds`. Can be overridden with `kubectl delete --grace-period=N`. Set to 0 for force deletion (dangerous; can leave orphaned container processes).

- **managedFields** ([]ManagedFieldsEntry, set by API server)
  - Server-side apply tracking. Records which field manager owns which fields. Enables conflict detection when multiple controllers or users manage the same object. Each entry contains `manager`, `operation`, `apiVersion`, `time`, and `fieldsV1` (the set of owned fields). Visible with `kubectl get pod -o yaml` but typically large and noisy.

#### spec

##### spec.containers ([]Container, required, minimum 1)

The primary application containers. At least one container is required. Containers within a Pod share the network namespace (same IP, same port space) and can communicate via `localhost`. They share mounted volumes.

- **name** (string, required)
  - Must be unique within the Pod. DNS label: max 63 characters, lowercase alphanumeric and `-`. Immutable. Used in `kubectl logs <pod> -c <name>`, resource references, and status reporting.

- **image** (string, required in practice)
  - Container image reference. Supports `registry/repo:tag` or `registry/repo@sha256:digest`. If no tag is specified, `:latest` is assumed (bad practice in production). The kubelet pulls the image according to `imagePullPolicy`. Immutable in the sense that changing it requires Pod recreation (spec is mostly immutable).

- **imagePullPolicy** (string, optional)
  - Values: `Always`, `IfNotPresent`, `Never`. Default: `Always` if tag is `:latest` or no tag; `IfNotPresent` otherwise. `Always` means the kubelet always contacts the registry (may use cached layers but validates the digest). `IfNotPresent` skips the pull if the image exists locally. `Never` requires the image to be pre-pulled. In production, always use digests or specific tags with `IfNotPresent`.

- **command** ([]string, optional)
  - Overrides the container image's `ENTRYPOINT`. If not set, the image's ENTRYPOINT is used. This is the binary or script that runs as PID 1 inside the container.

- **args** ([]string, optional)
  - Overrides the container image's `CMD`. If `command` is set without `args`, the image CMD is not used. If both are omitted, the image's ENTRYPOINT and CMD are used. Supports `$(VAR_NAME)` expansion from env vars.

- **workingDir** (string, optional)
  - Overrides the image's `WORKDIR`. Must be an absolute path.

- **ports** ([]ContainerPort, optional)
  - Informational. Declaring ports does NOT control whether the port is accessible (the container listens regardless). Useful for documentation, `kubectl port-forward` name-based targeting, and Service `targetPort` name references. `containerPort` is the port number; `name` allows symbolic reference; `protocol` is TCP (default), UDP, or SCTP; `hostPort` maps to the node's port (avoid in production, breaks scheduling flexibility).

- **env** ([]EnvVar, optional)
  - Environment variables injected into the container. Order matters for variable expansion. Sources: literal `value`, `valueFrom.fieldRef` (downward API: `metadata.name`, `metadata.namespace`, `metadata.labels`, `metadata.annotations`, `spec.nodeName`, `spec.serviceAccountName`, `status.podIP`, `status.hostIP`), `valueFrom.resourceFieldRef` (container resource requests/limits), `valueFrom.configMapKeyRef`, `valueFrom.secretKeyRef`. Variables are set at container start and are not updated if the source changes (unlike mounted configMap/secret volumes). Maximum combined env size contributes to the overall Pod object size limit.

- **envFrom** ([]EnvFromSource, optional)
  - Bulk-imports all keys from a ConfigMap or Secret as environment variables. `prefix` adds a prefix to each key. Keys that are not valid env var names are skipped. Conflicts: if multiple sources define the same key, last one wins based on order.

- **resources** (ResourceRequirements, optional but critical)
  - **requests**: The guaranteed minimum resources. The scheduler uses requests for placement decisions. A container without requests has no guaranteed resources and can be OOM-killed first. `cpu` is measured in millicores (1 core = 1000m). `memory` is measured in bytes (Mi, Gi). `ephemeral-storage` limits the total usage of emptyDir volumes, container writable layers, and log files.
  - **limits**: The maximum resource consumption. CPU limits are enforced via CFS throttling (Linux); the container is throttled, not killed. Memory limits are enforced via OOM killer; exceeding the limit triggers an OOM kill (exit code 137). If limits are set without requests, requests default to limits. Best practice: always set both, with requests < limits for burstable workloads or requests == limits for Guaranteed QoS class.
  - **QoS Classes**: `Guaranteed` (all containers have requests == limits for both CPU and memory), `Burstable` (at least one container has a request), `BestEffort` (no requests or limits). QoS class affects OOM score adjustment and eviction priority.

- **volumeMounts** ([]VolumeMount, required for volume access)
  - **name**: Must match a volume defined in `spec.volumes`.
  - **mountPath**: Absolute path inside the container. If the path exists in the image, it is shadowed.
  - **subPath**: Mounts a specific file or directory from the volume instead of the root. Prevents the entire directory from being overwritten. Caveat: subPath volumes do NOT receive updates when the underlying ConfigMap/Secret changes. Use `subPathExpr` for variable expansion.
  - **readOnly**: Boolean, default false. Mount as read-only.
  - **mountPropagation**: `None` (default), `HostToContainer`, or `Bidirectional`. Controls whether mounts made on the host or in other containers are visible. `Bidirectional` is dangerous and requires privileged containers.

- **startupProbe** (Probe, optional)
  - Disables liveness and readiness probes until it succeeds. Designed for slow-starting containers. The container has `failureThreshold * periodSeconds` to start. If the startup probe fails after exhausting retries, the container is killed per `restartPolicy`. Once the startup probe succeeds, it never runs again for that container instance.

- **readinessProbe** (Probe, optional)
  - Determines if the container is ready to receive traffic. Failing the readiness probe removes the Pod's IP from Endpoint/EndpointSlice objects, so Services stop routing to it. The container is NOT restarted. Readiness gates (`spec.readinessGates`) can add additional conditions.

- **livenessProbe** (Probe, optional)
  - Determines if the container is alive. Failing the liveness probe triggers a container restart (per `restartPolicy`). Liveness probes should detect deadlocks and unrecoverable states, not transient errors. Misconfiguring liveness probes (too aggressive, checking dependencies) is one of the most common production issues causing cascading restarts.

- **Probe fields** (common to all probes):
  - `httpGet`: HTTP GET to `path` on `port`. 200-399 is success.
  - `tcpSocket`: TCP connection to `port`. Success if connection established.
  - `exec`: Runs a command. Exit code 0 is success.
  - `grpc`: gRPC health check on `port` with optional `service`.
  - `initialDelaySeconds`: Delay before first probe. Default 0.
  - `periodSeconds`: How often to probe. Default 10.
  - `timeoutSeconds`: Timeout for each probe. Default 1. If the probe doesn't respond within this window, it's considered failed.
  - `successThreshold`: Consecutive successes needed. Default 1. For liveness and startup, must be 1.
  - `failureThreshold`: Consecutive failures before action. Default 3.

- **lifecycle** (Lifecycle, optional)
  - **postStart**: Handler invoked immediately after container creation. Not guaranteed to run before the container's entrypoint. If it fails, the container is killed. Types: `exec`, `httpGet`. Not commonly used in production.
  - **preStop**: Handler invoked before SIGTERM. Blocks the termination sequence until it completes (or `terminationGracePeriodSeconds` expires). Critical for graceful shutdown: the common pattern is `sleep 5-15` to allow endpoints to depopulate before the application begins its shutdown. The SIGTERM is sent AFTER preStop completes.

- **securityContext** (SecurityContext, optional)
  - Container-level security settings that override Pod-level `spec.securityContext` where applicable.
  - **runAsUser** (int64): UID to run the container process. Overrides image USER directive.
  - **runAsGroup** (int64): Primary GID. Files created by the container use this GID.
  - **runAsNonRoot** (bool): If true, kubelet validates that the container doesn't run as UID 0. If the image has USER 0 and no `runAsUser` override, the container fails to start.
  - **readOnlyRootFilesystem** (bool): Mounts the container's root filesystem as read-only. Requires writable volumes for `/tmp`, logs, etc. Strong security practice.
  - **allowPrivilegeEscalation** (bool): Controls whether a process can gain more privileges than its parent. Default is `true` when the container runs as root or has `CAP_SYS_ADMIN`. Set to `false` in production.
  - **capabilities**: `add` and `drop` lists. Best practice: `drop: [ALL]` and selectively add required capabilities. `NET_BIND_SERVICE` allows binding to ports below 1024.
  - **seccompProfile**: `RuntimeDefault` uses the container runtime's default seccomp profile. `Localhost` uses a node-local profile. `Unconfined` disables seccomp (avoid in production).
  - **privileged** (bool): Gives the container full access to the host. Almost never appropriate. Required for some CNI setup containers, node agents.

- **stdin, stdinOnce, tty** (bool, optional)
  - Used for interactive containers (`kubectl run -it`). Not relevant for production workloads.

- **terminationMessagePath** (string, default `/dev/termination-log`)
  - File path inside the container that is read on container termination and placed in `containerStatuses[].lastState.terminated.message`. Max 4096 bytes. Useful for debugging crash causes without looking at full logs.

- **terminationMessagePolicy** (string, default `File`)
  - `File`: Read from `terminationMessagePath`. `FallbackToLogsOnError`: If the termination message file is empty and the container exited with an error, use the last chunk of container log output.

##### spec.initContainers ([]Container, optional)

Init containers run sequentially before any app container starts. Each must complete successfully (exit 0) before the next begins. If an init container fails, the Pod restarts (per `restartPolicy`). Init containers do not support readiness probes (they don't serve traffic). They share volumes with app containers, making them useful for setup tasks (database migrations, config generation, permission fixes).

All container fields apply, except readiness probes which are disallowed.

##### spec.ephemeralContainers ([]EphemeralContainer, optional)

Added via the Pod's ephemeral containers subresource (`kubectl debug`). Cannot be specified at Pod creation time. Lack probes, resource requests/limits, and ports. Used exclusively for debugging running Pods. Once added, they cannot be removed (they persist in the spec). The container runs until it exits or the Pod is deleted.

##### spec.restartPolicy (string, optional)

- Values: `Always` (default), `OnFailure`, `Never`
- `Always`: Kubelet restarts the container on any exit. Used by Deployments, DaemonSets, StatefulSets.
- `OnFailure`: Restart only on non-zero exit. Used by Jobs.
- `Never`: Never restart. Used by Jobs that should not retry.
- Restart backoff: Kubelet uses exponential backoff (10s, 20s, 40s... up to 5 minutes) for container restarts. The backoff resets after 10 minutes of successful running.

##### spec.terminationGracePeriodSeconds (int64, default 30)

Time in seconds the kubelet waits after sending SIGTERM before sending SIGKILL. The sequence is: (1) preStop hook runs, (2) SIGTERM sent, (3) grace period countdown, (4) SIGKILL. If the container doesn't stop within the grace period, SIGKILL is sent. Long-running request draining or database connections may need 60-120 seconds. The grace period includes preStop execution time.

##### spec.activeDeadlineSeconds (int64, optional)

Maximum duration of the Pod relative to `startTime`. After this, the Pod is killed. Primarily used by Jobs.

##### spec.serviceAccountName (string, optional, default `default`)

References a ServiceAccount in the same namespace. The kubelet mounts the projected service account token at `/var/run/secrets/kubernetes.io/serviceaccount/`. The token audience, expiration, and path are configurable via projected volumes. RBAC policies bound to the ServiceAccount determine what API calls the Pod can make.

##### spec.automountServiceAccountToken (bool, optional, default true)

If `false`, no service account token is mounted. Security best practice for Pods that don't need Kubernetes API access. Can also be set on the ServiceAccount object itself.

##### spec.nodeName (string, optional)

If set, the scheduler is bypassed and the Pod is assigned directly to the named node. The kubelet on that node picks it up. If the node doesn't exist or can't run the Pod, it stays in `Pending` with a failure event. Used by DaemonSet controller.

##### spec.nodeSelector (map[string]string, optional)

Simple label matching for node selection. The Pod is only scheduled to nodes with ALL specified labels. Less expressive than `nodeAffinity` but simpler. Commonly used for `kubernetes.io/os: linux`, instance types, or availability zones.

##### spec.affinity (Affinity, optional)

- **nodeAffinity**:
  - `requiredDuringSchedulingIgnoredDuringExecution`: Hard constraint. Pod is not scheduled if no node matches. Contains `nodeSelectorTerms` (OR logic between terms, AND logic between expressions within a term).
  - `preferredDuringSchedulingIgnoredDuringExecution`: Soft constraint with `weight` (1-100). Scheduler scores nodes higher if they match but will schedule elsewhere if needed.
- **podAffinity**: Schedule near other Pods matching labels on the same `topologyKey` (hostname, zone, region).
- **podAntiAffinity**: Schedule away from other Pods matching labels. Critical for HA: spread replicas across nodes (`topologyKey: kubernetes.io/hostname`) or zones (`topologyKey: topology.kubernetes.io/zone`).

##### spec.tolerations ([]Toleration, optional)

Allow the Pod to be scheduled on tainted nodes. Without a matching toleration, the scheduler excludes the node. Fields: `key`, `operator` (`Equal` or `Exists`), `value`, `effect` (`NoSchedule`, `PreferNoSchedule`, `NoExecute`), `tolerationSeconds` (for `NoExecute`: how long the Pod stays after the taint is applied). Default tolerations for `node.kubernetes.io/not-ready` and `node.kubernetes.io/unreachable` are automatically added with 300s tolerance.

##### spec.topologySpreadConstraints ([]TopologySpreadConstraint, optional)

Fine-grained control over how Pods are spread across topology domains (zones, nodes, regions). Fields: `maxSkew` (maximum allowed difference in Pod count between domains), `topologyKey`, `whenUnsatisfiable` (`DoNotSchedule` or `ScheduleAnyway`), `labelSelector`, `minDomains`. More expressive than podAntiAffinity for even distribution.

##### spec.priorityClassName (string, optional)

References a PriorityClass object. Sets the Pod's scheduling priority. Higher priority Pods can preempt lower priority Pods when resources are scarce. If omitted, defaults to the PriorityClass marked as `globalDefault` or priority 0.

##### spec.priority (int32, set by admission controller)

Numeric priority value. Set automatically from `priorityClassName`. Can be set directly but `priorityClassName` takes precedence. Value range: -2147483648 to 1000000000. System Pods use values above 1000000000.

##### spec.schedulerName (string, default `default-scheduler`)

Allows using a custom scheduler. Multiple schedulers can run in a cluster. The Pod sits in Pending until the named scheduler claims and binds it.

##### spec.dnsPolicy (string, default `ClusterFirst`)

- `ClusterFirst`: Use cluster DNS (CoreDNS). Falls back to node's DNS for external names.
- `Default`: Inherit the node's DNS configuration.
- `ClusterFirstWithHostNet`: Same as `ClusterFirst` but for Pods using `hostNetwork: true`.
- `None`: No auto-configured DNS. Must set `dnsConfig` manually.

##### spec.dnsConfig (PodDNSConfig, optional)

Merges with the DNS configuration selected by `dnsPolicy`. Fields: `nameservers` (list of DNS server IPs), `searches` (DNS search domains), `options` (list of name/value pairs). Critical tuning: `ndots` controls when a name is considered absolute vs. relative. Default `ndots: 5` in cluster DNS causes 4-5 DNS lookups per external name resolution. Setting `ndots: 2` reduces unnecessary lookups in production.

##### spec.hostNetwork (bool, default false)

Pod uses the host's network namespace. The Pod gets the node's IP. Port conflicts become possible. Required for some infrastructure Pods (kube-proxy, CNI agents). Breaks Pod-to-Pod networking assumptions.

##### spec.hostPID (bool, default false)

Pod shares the host's PID namespace. Can see and signal all processes on the host. Security-sensitive. Required for some monitoring or debugging agents.

##### spec.hostIPC (bool, default false)

Pod shares the host's IPC namespace. Can access host shared memory segments. Rarely needed.

##### spec.shareProcessNamespace (bool, default false)

Containers within the Pod share a single PID namespace. Processes in all containers are visible to each other. PID 1 in the Pod is the pause container (infrastructure container). Useful for sidecar patterns where a sidecar needs to signal the main container.

##### spec.enableServiceLinks (bool, default true)

Injects environment variables for each Service in the namespace (Docker-link style). For namespaces with many Services, this creates hundreds of env vars and slows container startup. Set to `false` in production. Use DNS for service discovery instead.

##### spec.overhead (ResourceList, set by RuntimeClass admission)

Resources consumed by the Pod infrastructure (e.g., VM overhead for Kata Containers). Added to container requests for scheduling. Not user-configurable directly; set by the RuntimeClass.

##### spec.volumes ([]Volume, optional)

Defines the volumes available to containers. Each volume has a `name` and a source:

- **emptyDir**: Temporary directory, empty at Pod start. Lifetime tied to the Pod. `medium: Memory` creates a tmpfs (RAM-backed). `sizeLimit` caps usage.
- **hostPath**: Mounts a path from the host node. Types: `Directory`, `DirectoryOrCreate`, `File`, `FileOrCreate`, `Socket`, `CharDevice`, `BlockDevice`. Security risk; restricted by PodSecurityStandards. Avoid in multi-tenant clusters.
- **configMap**: Mounts ConfigMap data as files. `items` selects specific keys. `defaultMode` sets file permissions. Updates propagate (delay depends on kubelet sync period, ~60-90 seconds) unless `subPath` is used.
- **secret**: Like configMap but for Secrets. Backed by tmpfs by default (never written to disk on the node). Same update propagation behavior.
- **projected**: Combines multiple volume sources (serviceAccountToken, configMap, secret, downwardAPI) into a single mount.
- **persistentVolumeClaim**: References a PVC. Decouples Pod spec from storage provisioner details.
- **csi**: Direct CSI driver reference. For advanced cases bypassing PVC abstraction.
- **nfs, iscsi, fc, cephfs, glusterfs, etc.**: Legacy in-tree volume plugins. Migrating to CSI equivalents.
- **downwardAPI**: Exposes Pod/container metadata as files.

##### spec.imagePullSecrets ([]LocalObjectReference, optional)

References Secrets of type `kubernetes.io/dockerconfigjson` for authenticating with private registries. The kubelet uses these credentials during image pull.

### 5. Status Section

The Pod status is written by the kubelet and updated in the API server. It is read-only from the user's perspective.

- **phase** (string)
  - High-level summary: `Pending`, `Running`, `Succeeded`, `Failed`, `Unknown`.
  - `Pending`: Pod accepted but not all containers running. Includes scheduling, image pulling, init containers.
  - `Running`: At least one container is running or is in the process of starting/restarting.
  - `Succeeded`: All containers exited with code 0. Terminal state. Applies to Pods with `restartPolicy: Never` or `OnFailure`.
  - `Failed`: All containers terminated, at least one with non-zero exit. Terminal.
  - `Unknown`: kubelet lost contact. Usually node failure.
  - The phase does NOT update in real-time during container crashes if `restartPolicy: Always`; the Pod stays in `Running` while containers restart.

- **conditions** ([]PodCondition)
  - `PodScheduled`: True when the Pod has been scheduled to a node. False during pending.
  - `Initialized`: True when all init containers have completed successfully.
  - `ContainersReady`: True when all containers pass readiness probes.
  - `Ready`: True when the Pod is ready to serve traffic. Combines `ContainersReady` AND all `readinessGates` conditions. This is what Services use to determine endpoint membership.
  - Each condition has: `type`, `status` (True/False/Unknown), `lastProbeTime`, `lastTransitionTime`, `reason`, `message`.
  - Custom readiness gates add conditions like `www.example.com/feature-gate` that must be True for the Pod to be Ready. Set by external controllers via the Pod status subresource.

- **hostIP** (string)
  - IP address of the node the Pod is running on. Set after scheduling.

- **hostIPs** ([]HostIP)
  - List of host IPs (for dual-stack nodes).

- **podIP** (string)
  - Primary IP assigned to the Pod from the Pod CIDR of the node. Set after the CNI plugin allocates the IP.

- **podIPs** ([]PodIP)
  - List of IPs (for dual-stack Pods).

- **startTime** (Time)
  - Timestamp of when the Pod was acknowledged by the kubelet.

- **containerStatuses** ([]ContainerStatus)
  - One per container in `spec.containers`. Fields:
  - `name`: Container name.
  - `state`: Current state: `waiting` (with `reason` and `message`), `running` (with `startedAt`), `terminated` (with `exitCode`, `signal`, `reason`, `message`, `startedAt`, `finishedAt`).
  - `lastState`: Previous state (useful for debugging restarts).
  - `ready`: Boolean, whether the readiness probe passes.
  - `restartCount`: Number of times the container has been restarted.
  - `image` and `imageID`: Resolved image reference and digest.
  - `containerID`: Runtime-specific container ID (e.g., `containerd://abc123`).
  - `started`: Boolean, set by the startup probe.

- **initContainerStatuses** ([]ContainerStatus)
  - Same structure as `containerStatuses`, one per init container.

- **ephemeralContainerStatuses** ([]ContainerStatus)
  - Same structure, for ephemeral containers added via `kubectl debug`.

- **qosClass** (string)
  - Computed from resource requests/limits: `Guaranteed`, `Burstable`, `BestEffort`. Affects OOM score and eviction priority.

- **nominatedNodeName** (string)
  - Set by the scheduler when the Pod is nominated for preemption on a node. The Pod waits for the preempted Pod's grace period before being scheduled.

- **observedGeneration** (int64, not present on Pods directly)
  - Not a standard Pod status field but present on controllers like Deployment. For Pods, `generation` changes are rare since spec is mostly immutable.

**Debugging with status:**

```bash
# Check why a Pod is Pending
kubectl get pod <name> -o jsonpath='{.status.conditions[?(@.type=="PodScheduled")]}'

# Check container restart reasons
kubectl get pod <name> -o jsonpath='{.status.containerStatuses[0].lastState.terminated.reason}'

# Check readiness gate status
kubectl get pod <name> -o jsonpath='{.status.conditions[?(@.type=="Ready")]}'

# Get OOM kill evidence
kubectl get pod <name> -o jsonpath='{.status.containerStatuses[0].lastState.terminated.exitCode}'
# 137 = SIGKILL (OOM), 143 = SIGTERM
```

### 6. Controller and Reconciliation Deep Dive

**Standalone Pods** have no controller. They are created directly and the kubelet runs them. If the node fails, the Pod is lost.

**Managed Pods** (by ReplicaSet, DaemonSet, etc.):

1. The workload controller creates a Pod object in etcd via the API server with `ownerReferences` pointing to itself.
2. The scheduler's informer sees the new unscheduled Pod. It evaluates filtering (resource fit, affinity, taints, topology constraints) and scoring (spread, resource balance, affinity preferences) to select a node.
3. The scheduler writes a Binding object, setting `spec.nodeName`.
4. The kubelet on the target node picks up the Pod via its watch. It calls the container runtime (via CRI) to pull images and start containers.
5. The kubelet updates Pod status in the API server as containers start, probes execute, and containers terminate.
6. The owning controller watches Pod status. If a Pod fails or is deleted, the controller creates a replacement.

**Event flow for Pod creation:**

```
User/Controller -> API Server (validation, admission, etcd write)
-> Scheduler informer detects unscheduled Pod
-> Scheduler selects node, creates Binding
-> Kubelet informer detects Pod bound to its node
-> Kubelet calls CRI to create sandbox and containers
-> Kubelet runs init containers sequentially
-> Kubelet starts app containers
-> Kubelet begins probing
-> Kubelet updates Pod status in API server
```

**Event flow for Pod termination:**

```
Delete request -> API Server sets deletionTimestamp
-> Endpoint controller removes Pod IP from endpoints (in parallel)
-> Kubelet receives update, begins termination:
   1. Runs preStop hooks (all containers in parallel)
   2. Sends SIGTERM to all containers
   3. Waits terminationGracePeriodSeconds
   4. Sends SIGKILL if still running
-> Kubelet reports terminal status
-> API Server removes object from etcd (if no finalizers)
```

**Race condition:** The endpoint removal and kubelet termination happen in parallel. This means traffic may still be routed to a Pod that's shutting down. The `preStop: sleep 5` pattern mitigates this by delaying the application shutdown, giving endpoints time to update.

### 7. Production Scenarios

**Real-world platform engineering use case:**
A platform team deploys a multi-tenant API gateway as a Pod (managed by Deployment) with: resource limits per tenant (enforced via ResourceQuota per namespace), network policies restricting Pod-to-Pod traffic, projected service account tokens with audience-scoped access, and topology spread across 3 AZs.

**Cloud environment example (AWS EKS):**
Pods running on Fargate profiles have no control over the underlying node. Pod resource requests directly determine the allocated vCPU/memory. Node selectors and affinity rules target Fargate profiles via `eks.amazonaws.com/fargate-profile` labels. ENI-based networking gives each Pod a VPC IP.

**Multi-tenant cluster scenario:**
Each tenant namespace has ResourceQuota limiting total Pod count and resource consumption. LimitRange sets default requests/limits so no Pod runs without resource constraints. PodSecurityStandards (restricted) enforce non-root, read-only root filesystem, and dropped capabilities. Network Policies isolate tenant traffic.

**Scaling scenario:**
Under load, HPA creates new Pods. The cluster autoscaler detects Pods in Pending state (insufficient resources), provisions new nodes. Pod topology spread constraints ensure even distribution. PodDisruptionBudgets prevent voluntary disruptions from violating availability guarantees during the scale-up.

**Failure scenario:**
A node running 12 Pods becomes unreachable. After 40 seconds, the node controller taints the node with `node.kubernetes.io/unreachable:NoExecute`. Pods without tolerations (or with `tolerationSeconds: 300`) are evicted after their tolerance window. The owning controllers (ReplicaSets) create replacement Pods on healthy nodes. Stateful workloads (StatefulSet) wait for the old Pod to be confirmed terminated before creating a replacement (at-most-one semantics).

**Misconfiguration example:**
A developer sets a liveness probe that checks database connectivity. When the database has a brief outage, ALL Pods fail liveness checks simultaneously, causing a rolling restart storm. As Pods restart, they flood the database with connection attempts, prolonging the outage. Fix: Use liveness probes only for process health. Use readiness probes for dependency checks.

### 10. Common Pitfalls and Production Failures

- **CrashLoopBackOff with exponential backoff**: Containers that crash immediately enter a restart loop with increasing delays (10s, 20s, 40s, 80s, 160s, 300s cap). During the backoff wait, the Pod is not serving traffic. If the underlying issue is a missing ConfigMap or Secret, the container keeps crashing until the dependency is created.

- **OOM kills misdiagnosed as application bugs**: Exit code 137 means SIGKILL, usually from the OOM killer. The container's memory limit was exceeded. Check `kubectl describe pod` for `OOMKilled` reason. Adjust limits or fix the memory leak. On cgroups v2, the entire Pod shares the memory limit if not set per-container.

- **Liveness probe causing cascading failures**: Liveness probes checking downstream services (databases, external APIs) trigger container restarts when the dependency is slow. All Pods restart simultaneously, amplifying load when the dependency recovers. Use readiness probes for dependency health and liveness probes only for process health.

- **Missing preStop hook causing 502 errors during deployment**: When a Pod terminates, the endpoint removal and SIGTERM delivery happen concurrently. If the application shuts down before the endpoints are updated, in-flight requests get 502. The `preStop: sleep 5` pattern gives the endpoints controller time to propagate the removal.

- **Immutable spec fields**: Most Pod spec fields are immutable after creation. Attempting to patch `containers[].image`, `resources`, or `command` on a Pod fails. These changes must be applied at the Deployment/controller level, which triggers a new rollout.

- **ImagePullBackOff in private registries**: Missing `imagePullSecrets`, expired registry tokens, or incorrect image references cause persistent image pull failures. The kubelet retries with exponential backoff. Verify with `kubectl describe pod` events section.

- **DNS resolution delays with high ndots**: Default `ndots: 5` in cluster DNS means names with fewer than 5 dots are tried with all search domains first. `api.example.com` generates 4-5 DNS queries before resolving. Set `ndots: 2` in `dnsConfig` for Pods making frequent external DNS lookups.

- **Resource quota exhaustion**: Pods fail to create with `forbidden: exceeded quota` when namespace ResourceQuota is exhausted. Monitor quota usage with `kubectl describe resourcequota -n <ns>`. The Pod stays in API server rejection, not Pending.

- **Eviction due to node pressure**: Kubelet evicts BestEffort Pods first, then Burstable, then Guaranteed when node disk or memory pressure is detected. Pods with no resource requests are first to go. Always set resource requests.

- **Volume mount shadowing**: Mounting a volume at a path that exists in the container image replaces the entire directory. If `/etc/config` has files in the image and you mount a ConfigMap there, only the ConfigMap files are visible. Use `subPath` to mount individual files without replacing the directory.

## ReplicaSet

### 1. Conceptual Overview

A ReplicaSet ensures that a specified number of Pod replicas are running at any given time. It is the successor to ReplicationController with support for set-based label selectors.

**What problem it solves:**
Individual Pods have no self-healing capability. If a Pod dies, nothing recreates it. ReplicaSet maintains a stable set of replica Pods, creating or deleting Pods as needed to match the desired count.

**Where it fits in cluster architecture:**
ReplicaSets are rarely created directly. They are created and managed by Deployments. A Deployment creates a new ReplicaSet for each revision, enabling rollouts and rollbacks. The ReplicaSet controller runs in the kube-controller-manager.

**Which controller manages it:**
The ReplicaSet controller within kube-controller-manager. When a ReplicaSet is owned by a Deployment, the Deployment controller manages the ReplicaSet's `spec.replicas` and creates/deletes ReplicaSets for rollout management.

**How reconciliation works:**
The ReplicaSet controller lists Pods matching its `spec.selector` and compares the count to `spec.replicas`. If there are fewer Pods, it creates new ones. If there are more, it deletes the excess (selecting candidates based on Pod phase, readiness, age, and co-located replica count). The controller uses the `controller` field in `ownerReferences` to claim Pods.

**Interaction with scheduler:**
The ReplicaSet controller creates Pod objects; it does not schedule them. The scheduler handles placement independently.

### 4. Complete Field Breakdown

#### metadata

Same structure as Pod metadata. Key differences for ReplicaSets:

- **ownerReferences**: When managed by a Deployment, contains a reference to the Deployment with `controller: true`. This enables cascade deletion and prevents other controllers from claiming the ReplicaSet.
- **annotations**: The Deployment controller sets `deployment.kubernetes.io/revision` to track the ReplicaSet's position in rollout history. `deployment.kubernetes.io/desired-replicas` and `deployment.kubernetes.io/max-replicas` are used during rolling updates.

#### spec

- **replicas** (int32, optional, default 1)
  - Desired number of Pods. The controller creates or deletes Pods to match. Setting to 0 scales down all Pods (useful for maintenance). When managed by a Deployment, this value is controlled by the Deployment controller and should not be manually changed on the ReplicaSet. Mutable. HPA modifies this field on the controller (Deployment, not ReplicaSet directly in most cases).

- **selector** (LabelSelector, required, immutable)
  - Determines which Pods are managed by this ReplicaSet. Supports `matchLabels` (AND logic) and `matchExpressions` (In, NotIn, Exists, DoesNotExist). **Immutable after creation.** The selector MUST match the template's labels, otherwise the API server rejects creation. The Deployment controller adds `pod-template-hash` to both selector and template labels to distinguish Pods from different revisions.

- **minReadySeconds** (int32, optional, default 0)
  - A Pod is considered available only after it has been ready for this many seconds without any container crashing. The ReplicaSet controller uses this when reporting `availableReplicas` in status. Affects how quickly the Deployment considers a rollout step complete. With `minReadySeconds: 30`, a newly ready Pod must stay ready for 30 seconds before counting as available.

- **template** (PodTemplateSpec, required)
  - The Pod template used to create new Pods. Contains `metadata` (labels, annotations) and `spec` (full Pod spec). Template labels MUST be a superset of `spec.selector.matchLabels`. Changes to the template do NOT affect existing Pods; only newly created Pods use the updated template. When managed by a Deployment, template changes trigger a new ReplicaSet creation (new rollout revision).

---

### 5. Status Section

- **replicas** (int32)
  - Actual number of Pods matching the selector (regardless of state). Updated by the ReplicaSet controller after each reconciliation.

- **readyReplicas** (int32)
  - Number of Pods with the Ready condition true. Used by Deployments to determine rollout progress.

- **availableReplicas** (int32)
  - Number of Pods that have been Ready for at least `minReadySeconds`. This is the metric used for determining if a rollout step is complete.

- **fullyLabeledReplicas** (int32)
  - Number of Pods with labels matching the ReplicaSet's selector. Should equal `replicas` unless labels were manually modified on Pods.

- **observedGeneration** (int64)
  - The most recent `metadata.generation` that the controller has processed. If `observedGeneration < generation`, the controller hasn't yet acted on the latest spec change.

- **conditions** ([]ReplicaSetCondition)
  - `ReplicaFailure`: True if the controller cannot create Pods (quota exhaustion, image pull failures, etc.). Contains `reason` and `message` with details.

**Debugging with status:**

### 6. Controller and Reconciliation Deep Dive

The ReplicaSet controller operates a continuous reconciliation loop:

1. **Watch**: Uses informers to watch Pod and ReplicaSet objects.
2. **Filter**: On Pod events, the controller checks if the Pod matches any ReplicaSet's selector. On ReplicaSet events, it enqueues the ReplicaSet for processing.
3. **Claim**: The controller adopts Pods matching its selector that have no `ownerReferences`. It releases Pods that no longer match the selector. This is the adoption/orphan mechanism.
4. **Count**: Counts active Pods (not in terminal phase) matching the selector with correct ownerReferences.
5. **Scale**: If count < desired, creates new Pods from the template (batch creation with exponential increase: 1, 2, 4, 8, 16... up to 500). If count > desired, deletes excess Pods.
6. **Status update**: Writes the updated replica counts to the ReplicaSet's status subresource.

**Pod deletion priority** (when scaling down): The controller ranks Pods for deletion using: unassigned Pods > Pending Pods > Pods on nodes with more replicas > newer Pods > Pods not ready > Pods without deletion timestamp. This maximizes availability during scale-down.

**Burst creation**: The controller creates Pods in batches. If a batch fails (e.g., quota limit), it stops and retries in the next reconciliation cycle, preventing thundering herd issues.

### 7. Production Scenarios

**Real-world use case:**
ReplicaSets are never managed directly in production. They are an implementation detail of Deployments. Platform engineers interact with ReplicaSets when debugging rollout issues, cleaning up stuck rollouts, or investigating why old ReplicaSets aren't scaled down.

**Orphan ReplicaSet cleanup:**
After deleting a Deployment with `--cascade=orphan`, the ReplicaSets persist. They continue managing their Pods but never receive updates. Clean up with: `kubectl delete rs -l app=<name> -n <ns>`.

**Stuck rollout investigation:**
A Deployment rollout stalls. The new ReplicaSet has `availableReplicas: 0` and Pods are in CrashLoopBackOff. The old ReplicaSet still has full replicas. The Deployment's `progressDeadlineSeconds` eventually marks it as failed. Debug: check the new RS's Pods, fix the image/config, and the Deployment resumes.

#### 10. Common Pitfalls and Production Failures

- **Selector overlap**: Two ReplicaSets with overlapping selectors fight over the same Pods, causing constant create-delete cycles. The Deployment controller prevents this with `pod-template-hash`, but manual ReplicaSet creation can cause this.

- **Manual Pod label changes**: Removing a label from a Pod that a ReplicaSet selects causes the RS to create a replacement. The orphaned Pod continues running unmanaged. This is actually a useful technique for debugging a failing Pod without affecting the ReplicaSet's replica count.

- **Scaling the ReplicaSet instead of the Deployment**: When a Deployment manages the RS, scaling the RS directly is reverted by the Deployment controller on its next reconciliation (typically within seconds).

- **Old ReplicaSets accumulating**: By default, Deployments keep `revisionHistoryLimit: 10` old ReplicaSets. Each has 0 replicas but occupies etcd space and creates noise. In high-churn environments, lower this value.

- **ReplicaFailure condition**: If a ReplicaSet cannot create Pods (quota exhaustion, invalid pod template), it enters a `ReplicaFailure` condition but does NOT stop trying. It continues attempting on each reconciliation, generating a flood of events.

## Deployment

### 1. Conceptual Overview

A Deployment provides declarative updates for Pods and ReplicaSets. It manages the lifecycle of application rollouts, rollbacks, scaling, and self-healing.

**What problem it solves:**
Direct ReplicaSet management doesn't support zero-downtime updates. Deployments orchestrate the transition between application versions by creating new ReplicaSets and scaling them up while scaling old ones down, implementing strategies like rolling updates and recreate.

**Where it fits in cluster architecture:**
Deployments are the most commonly used workload controller for stateless applications. They sit above ReplicaSets in the controller hierarchy: Deployment -> ReplicaSet -> Pod. The Deployment controller runs within kube-controller-manager.

**Which controller manages it:**
The Deployment controller within kube-controller-manager. It watches Deployment objects and their owned ReplicaSets.

**How reconciliation works:**
The Deployment controller compares the current ReplicaSet's pod template with the desired template. If they differ, it creates a new ReplicaSet and orchestrates scaling according to the strategy (`RollingUpdate` or `Recreate`). It monitors ReplicaSet status to track rollout progress and handles rollback by scaling up a previous ReplicaSet.

**Interaction with scheduler:**
The Deployment controller does not interact with the scheduler directly. It creates ReplicaSets, which create Pods, which the scheduler places.

### 4. Complete Field Breakdown

#### metadata

Same structure as other resources. Notable annotations for Deployments:

- **kubernetes.io/change-cause**: Set manually or by `kubectl apply --record` (deprecated). Displayed in `kubectl rollout history`. Critical for auditing which changes caused each revision.

#### spec

- **replicas** (int32, optional, default 1)
  - Desired Pod count. The Deployment controller sets this on the active ReplicaSet. HPA modifies this field via the scale subresource. Mutable. Setting to 0 scales down all Pods but preserves the Deployment and ReplicaSet objects.

- **selector** (LabelSelector, required, immutable)
  - Determines which Pods/ReplicaSets belong to this Deployment. Must match `template.metadata.labels`. Immutable after creation. Unlike ReplicaSets, the Deployment does not add `pod-template-hash` to its own selector; that label is added to the ReplicaSet's selector and Pod template.

- **template** (PodTemplateSpec, required)
  - The Pod specification template. Changes to any field within the template (including labels, annotations, container image, env vars, resource requests) trigger a new rollout. The Deployment controller computes a hash of the template and uses it to determine if a matching ReplicaSet already exists. Only changes to the template trigger rollouts; changes to `replicas`, `strategy`, or Deployment metadata do NOT create new ReplicaSets.

- **strategy** (DeploymentStrategy, optional)
  - **type** (string): `RollingUpdate` (default) or `Recreate`.
  - **Recreate**: Kills all existing Pods before creating new ones. Causes downtime. Use for workloads that cannot tolerate two versions running simultaneously (e.g., database schema incompatibility).
  - **RollingUpdate**: Gradually replaces old Pods with new ones.
    - **maxUnavailable** (IntOrString, default 25%): Maximum number/percentage of Pods that can be unavailable during update. 0 means all old Pods must stay running until new ones are ready.
    - **maxSurge** (IntOrString, default 25%): Maximum number/percentage of Pods above `replicas` during update. Controls how many extra Pods are created.
    - `maxUnavailable: 0` + `maxSurge: 1` = safest rolling update (always at full capacity, +1 Pod at a time).
    - `maxUnavailable: 1` + `maxSurge: 0` = resource-conservative (never more Pods than desired, but one less during transition).
    - Both 0 is invalid (no progress possible).
    - Percentages are rounded: maxUnavailable rounds down (more conservative), maxSurge rounds up.

- **revisionHistoryLimit** (int32, optional, default 10)
  - Number of old ReplicaSets to retain for rollback. Set to 0 to disable rollback capability. In high-churn environments, lower to 3-5 to reduce etcd objects. Each old RS retains the full Pod template for rollback.

- **progressDeadlineSeconds** (int32, optional, default 600)
  - If the rollout doesn't make progress for this many seconds, the Deployment is marked as failed (condition `Progressing: False` with reason `ProgressDeadlineExceeded`). This does NOT roll back automatically; it just sets the condition. Progress is defined as any change in new ReplicaSet's `availableReplicas`. Set higher for slow-starting apps.

- **minReadySeconds** (int32, optional, default 0)
  - Passed to the ReplicaSet. A Pod must be Ready for this duration before it's considered available. Slows down rollouts to catch immediate crashes. Useful for canary-like safety: if a Pod crashes within 30 seconds of becoming Ready, the rollout pauses (because `availableReplicas` doesn't increase).

- **paused** (bool, optional, default false)
  - Pauses the Deployment rollout. The Deployment controller stops scaling the new ReplicaSet up and the old one down. Useful for making multiple template changes as a single rollout (pause, make changes, unpause). `kubectl rollout pause/resume deployment <name>`.

### 5. Status Section

- **replicas** (int32): Total Pods across all ReplicaSets owned by this Deployment.
- **updatedReplicas** (int32): Pods matching the current template (in the newest ReplicaSet).
- **readyReplicas** (int32): Pods with Ready condition.
- **availableReplicas** (int32): Pods that have been Ready for `minReadySeconds`.
- **unavailableReplicas** (int32): Desired replicas minus available replicas.
- **observedGeneration** (int64): Latest `generation` processed by the controller.
- **collisionCount** (int32): Number of hash collisions encountered when creating ReplicaSet names.

- **conditions** ([]DeploymentCondition):
  - `Available`: True when `availableReplicas >= replicas - maxUnavailable`. Indicates the minimum availability threshold is met.
  - `Progressing`: True when the Deployment is scaling up/down, creating a new RS, or all replicas are updated. False with reason `ProgressDeadlineExceeded` when stuck.
  - `ReplicaFailure`: True when a ReplicaSet cannot create Pods.

### 6. Controller and Reconciliation Deep Dive

The Deployment controller loop:

1. **Watch**: Informers watch Deployments and ReplicaSets.
2. **Template comparison**: On Deployment update, the controller hashes the current Pod template and checks if a ReplicaSet with that hash exists.
3. **New RS creation**: If no matching RS exists, it creates a new ReplicaSet with `replicas: 0` and the `pod-template-hash` label.
4. **Scaling orchestration** (RollingUpdate):
   - Calculates maximum total Pods allowed (`replicas + maxSurge`).
   - Calculates minimum Pods that must be available (`replicas - maxUnavailable`).
   - Scales up new RS by as many as allowed while staying within `maxSurge`.
   - Scales down old RS by as many as allowed while staying above minimum available.
   - Repeats each reconciliation cycle until all Pods are on the new RS.
5. **Old RS cleanup**: After rollout completes, old ReplicaSets are retained (scaled to 0) up to `revisionHistoryLimit`. Excess old RSs are deleted (oldest first).
6. **Status update**: Reports replica counts and conditions.

**Rollback mechanism:**
`kubectl rollout undo` sets the Deployment's template back to a previous ReplicaSet's template. The controller detects the hash matches an existing RS and scales it up instead of creating a new one. The revision number still increments.

**Pause behavior:**
When paused, the controller processes the Deployment but skips scaling operations. It still updates status and claims ReplicaSets. Unpausing resumes the rollout from where it left off.

### 7. Production Scenarios

**Zero-downtime deployment:**
`maxUnavailable: 0, maxSurge: 1` with `minReadySeconds: 30` and proper readiness probes. PodDisruptionBudget with `minAvailable: 2` (for 3 replicas). `preStop` hook with `sleep 15`. This ensures at least full capacity at all times, new Pods are verified stable, and graceful connection draining.

**Blue-green deployment pattern:**
Create a second Deployment with the new version. Switch the Service selector to the new Deployment. If issues arise, switch back. Delete the old Deployment after verification. This is not native to Deployments but achievable with proper labeling.

**Canary deployment pattern:**
Run two Deployments (stable and canary) behind the same Service. The canary has fewer replicas (e.g., 1 out of 10 total). Traffic splits proportionally by Pod count. More sophisticated canary requires Istio or similar service mesh for weighted routing.

#### 10. Common Pitfalls and Production Failures

- **ProgressDeadlineExceeded with no automatic rollback**: Deployments do NOT auto-rollback when stuck. The condition is set, but the broken rollout remains. Use external tooling (Argo Rollouts, Flagger) or monitoring alerts to trigger manual rollback.

- **maxSurge and maxUnavailable both 0**: Invalid configuration. The controller cannot make progress because it can't create new Pods (maxSurge: 0) and can't remove old Pods (maxUnavailable: 0). API server rejects this.

- **Changing selector after creation**: Immutable. Attempting to modify the selector returns a validation error. The only recourse is to delete and recreate the Deployment.

- **HPA and manual scaling conflict**: If HPA is managing replicas, manually setting `spec.replicas` is overwritten by HPA within seconds. Use HPA `minReplicas`/`maxReplicas` to control bounds.

- **Rollout triggered by annotation-only changes in template**: Changing annotations in `spec.template.metadata.annotations` triggers a new rollout even though no functional change occurred. The hash changes, a new RS is created. Use this intentionally for restart triggers (`kubectl rollout restart`), but be aware of accidental triggers.

- **Revision history consuming etcd**: Each revision keeps a full ReplicaSet object in etcd. With frequent deployments (CI/CD pipelines deploying 50+ times/day), `revisionHistoryLimit: 10` may still accumulate significant etcd bloat. Lower to 3-5 in high-churn environments.

## DaemonSet

### 1. Conceptual Overview

A DaemonSet ensures that all (or some) Nodes run a copy of a Pod. As nodes join the cluster, Pods are added. As nodes leave, Pods are garbage collected.

**What problem it solves:**
Infrastructure agents that must run on every node: log collectors (Fluentd, Fluent Bit), monitoring agents (Prometheus Node Exporter, Datadog Agent), CNI plugins (Calico, Cilium), storage daemons (CSI node drivers), and security agents (Falco, Sysdig).

**Where it fits in cluster architecture:**
DaemonSets are cluster-level infrastructure components. They bypass the normal scheduler by default (the DaemonSet controller sets `spec.nodeName` directly, though modern Kubernetes uses the default scheduler). They run alongside all workload Pods on each node.

**Which controller manages it:**
The DaemonSet controller within kube-controller-manager. Since Kubernetes 1.12, DaemonSet Pods are scheduled by the default scheduler (not the DaemonSet controller directly). The controller creates Pod objects and relies on the scheduler for placement, but uses node affinity rules to target specific nodes.

**How reconciliation works:**
The controller lists all nodes and all Pods owned by the DaemonSet. For each eligible node (matching `nodeSelector`, node affinity, and tolerating taints), it ensures exactly one Pod is running. Missing Pods are created; extra Pods are deleted.

### 4. Complete Field Breakdown

#### spec

- **selector** (LabelSelector, required, immutable)
  - Same as ReplicaSet/Deployment. Must match template labels. Immutable.

- **template** (PodTemplateSpec, required)
  - Pod template. The DaemonSet controller injects tolerations for `node.kubernetes.io/unschedulable`, `node.kubernetes.io/not-ready`, `node.kubernetes.io/unreachable`, `node.kubernetes.io/disk-pressure`, `node.kubernetes.io/memory-pressure`, `node.kubernetes.io/pid-pressure`, and `node.kubernetes.io/network-unavailable` with `NoExecute` effect. This ensures DaemonSet Pods run even on unhealthy nodes (critical for infrastructure agents).

- **updateStrategy** (DaemonSetUpdateStrategy, optional)
  - **type**: `RollingUpdate` (default) or `OnDelete`.
  - `RollingUpdate`: Updates Pods automatically. `maxUnavailable` (IntOrString, default 1) controls how many Pods can be unavailable during update. `maxSurge` (IntOrString, default 0) allows creating new Pods before deleting old ones on the same node (requires Kubernetes 1.22+). Note: only one DaemonSet Pod per node, so `maxSurge: 1` means temporarily two Pods on a node during the update.
  - `OnDelete`: Pods are only updated when manually deleted. Old Pods are replaced with new-spec Pods when they terminate. Useful when you need manual control over the rollout on each node.

- **minReadySeconds** (int32, optional, default 0)
  - Same behavior as Deployment. Pod must be Ready for this duration before the DaemonSet considers it available and moves to the next node during a rolling update.

- **revisionHistoryLimit** (int32, optional, default 10)
  - Number of old ControllerRevisions to retain. DaemonSets use ControllerRevision objects (not ReplicaSets) to track template history.

### 5. Status Section

- **currentNumberScheduled**: Pods running on nodes where they should be running.
- **desiredNumberScheduled**: Total number of nodes that should run the DaemonSet Pod.
- **numberReady**: Pods with Ready condition.
- **numberAvailable**: Pods that have been Ready for `minReadySeconds`.
- **numberMisscheduled**: Pods running on nodes where they should NOT be running (node no longer matches selector).
- **numberUnavailable**: `desiredNumberScheduled - numberAvailable`.
- **updatedNumberScheduled**: Pods running the latest template.
- **observedGeneration**: Latest generation processed.
- **collisionCount**: Hash collision counter.
- **conditions**: Similar to Deployment conditions.

**Key debugging signal:** If `numberMisscheduled > 0`, there are orphaned DaemonSet Pods on nodes that no longer match the selector. The controller will clean these up.

### 6. Controller and Reconciliation Deep Dive

1. **Node enumeration**: The controller lists all nodes and filters by the DaemonSet's `nodeSelector` and node affinity.
2. **Pod enumeration**: Lists all Pods owned by the DaemonSet.
3. **Gap analysis**: For each eligible node, checks if a Pod exists. For each Pod, checks if it's on an eligible node.
4. **Create missing Pods**: Creates Pods for nodes missing them. The Pod template includes node affinity targeting the specific node (replacing the old `spec.nodeName` approach). The scheduler then places the Pod on the targeted node.
5. **Delete excess Pods**: Removes Pods on ineligible nodes.
6. **Rolling update**: During updates, the controller deletes old-template Pods one (or `maxUnavailable`) at a time, waiting for the replacement to become available before proceeding.

**ControllerRevision**: DaemonSets track revisions via ControllerRevision objects rather than ReplicaSets. Each revision stores the complete Pod template spec. Rollback reapplies a previous ControllerRevision's template.

### 7. Production Scenarios

**Log collection infrastructure:**
Fluent Bit DaemonSet with `hostPath` volumes mounting `/var/log` and `/var/lib/docker/containers`. Uses `tolerations: [{operator: Exists}]` to run on all nodes including tainted ones. Priority class `system-node-critical` ensures it survives eviction pressure.

**CNI plugin deployment:**
Calico or Cilium DaemonSet running in `kube-system` with `hostNetwork: true`, privileged containers (for iptables/eBPF), and init containers that install CNI binaries on the host. Uses `OnDelete` update strategy to control the rollout carefully (CNI disruption affects all Pods on the node).

**Node failure scenario:**
When a node fails, the DaemonSet controller does NOT create a replacement Pod on another node (each node gets exactly one). The missing Pod is expected until the node returns or is removed from the cluster. When the node is removed, the Pod is garbage collected. If a new node joins, a new Pod is created for it.

#### 10. Common Pitfalls and Production Failures

- **Missing tolerations**: DaemonSet Pods are auto-tolerated for standard taints, but custom taints (e.g., `dedicated=gpu:NoSchedule`) must be explicitly tolerated. Missing tolerations cause the Pod to be absent from tainted nodes, breaking infrastructure coverage.

- **Resource contention with workloads**: DaemonSet Pods consume resources on every node. If requests are too high, they reduce capacity for workload Pods. If too low, the DaemonSet Pod gets OOM-killed during load. Balance carefully.

- **hostPort conflicts**: Two DaemonSets using the same `hostPort` can't both run on the same node. The second Pod fails to start with a port binding error.

- **OnDelete strategy forgotten during upgrades**: With `OnDelete` strategy, updating the DaemonSet template has no immediate effect. Old Pods continue running until manually deleted. Operations teams forget this and wonder why the update didn't apply.

- **Privileged DaemonSets and PodSecurityStandards**: Infrastructure DaemonSets often need privileged access. PodSecurityStandard `restricted` or `baseline` profiles block this. Exempt the namespace or use PSA exemptions for specific DaemonSets.

## StatefulSet

### 1. Conceptual Overview

A StatefulSet manages stateful applications, providing stable, unique network identifiers, stable persistent storage, and ordered, graceful deployment and scaling.

**What problem it solves:**
Deployments treat Pods as interchangeable. Stateful applications (databases, message queues, distributed systems) require stable identity, persistent storage per replica, and ordered startup/shutdown. StatefulSets provide: (1) stable DNS names (`pod-0.svc`, `pod-1.svc`), (2) persistent volume claims per replica, (3) ordered rolling updates, and (4) ordered Pod creation/deletion.

**Where it fits in cluster architecture:**
StatefulSets sit alongside Deployments as workload controllers but with stronger identity and storage guarantees. They create Pods with ordinal indexes (0, 1, 2...) rather than random hashes. Each Pod gets a dedicated PVC that persists across rescheduling.

**Which controller manages it:**
The StatefulSet controller within kube-controller-manager.

**How reconciliation works:**
The controller maintains Pods with ordinal indexes from 0 to N-1 (where N is `replicas`). It creates Pods sequentially (by default) starting from 0. It deletes Pods in reverse order starting from N-1. During scale-up, it waits for each Pod to be Running and Ready before creating the next. During scale-down, it deletes one Pod at a time, waiting for termination to complete. This guarantees at-most-one semantics.

**Interaction with scheduler:**
StatefulSet Pods are scheduled normally by the default scheduler. However, PVC binding may constrain scheduling: if a PVC is bound to a PV in a specific zone, the Pod must be scheduled in that zone.

### 4. Complete Field Breakdown

#### spec

- **serviceName** (string, required)
  - Must reference an existing headless Service (ClusterIP: None). This Service provides DNS entries for each Pod: `<pod-name>.<serviceName>.<namespace>.svc.cluster.local`. For example, `postgresql-0.postgresql-headless.database.svc.cluster.local`. This is how Pods discover each other in distributed systems. The Service must exist before the StatefulSet is created. Immutable.

- **replicas** (int32, optional, default 1)
  - Number of replicas. Pods are named `{statefulset-name}-{ordinal}` from 0 to N-1. Mutable. Scale-up adds higher ordinals; scale-down removes the highest ordinal first.

- **podManagementPolicy** (string, optional, default `OrderedReady`)
  - `OrderedReady`: Pods are created sequentially (0, then 1, then 2) and deleted in reverse. Each Pod must be Running and Ready before the next is created. During scale-down, each Pod must terminate before the next is stopped.
  - `Parallel`: All Pods are created/deleted simultaneously, like a Deployment. Use when ordering doesn't matter (e.g., caching clusters where each instance is independent).
  - Immutable after creation.

- **updateStrategy** (StatefulSetUpdateStrategy, optional)
  - **type**: `RollingUpdate` (default) or `OnDelete`.
  - `RollingUpdate`:
    - **partition** (int32, default 0): Pods with ordinal >= partition are updated. Pods with ordinal < partition retain the old template. This enables canary-style updates: set partition to N-1 to update only the last Pod, verify, then lower partition. Setting partition to 0 updates all Pods. Pods are updated in reverse ordinal order (N-1, N-2, ..., 0).
    - **maxUnavailable** (IntOrString, default 1): Maximum Pods unavailable during rolling update. Requires Kubernetes 1.24+.
  - `OnDelete`: Pods are updated only when manually deleted.

- **persistentVolumeClaimRetentionPolicy** (StatefulSetPersistentVolumeClaimRetentionPolicy, optional)
  - **whenDeleted**: `Retain` (default) or `Delete`. What happens to PVCs when the StatefulSet is deleted.
  - **whenScaled**: `Retain` (default) or `Delete`. What happens to PVCs when the StatefulSet scales down.
  - Default behavior (Retain/Retain) means PVCs persist indefinitely. Manual cleanup required. This is the safe default for databases.

- **volumeClaimTemplates** ([]PersistentVolumeClaim, optional)
  - Templates for creating PVCs for each Pod. Each Pod gets its own PVC named `{template-name}-{statefulset-name}-{ordinal}` (e.g., `data-postgresql-0`). PVCs are created when the Pod is first created and persist across Pod rescheduling. The PVC follows the Pod: when `postgresql-0` is rescheduled to a different node, the PVC (and its PV) must be accessible from the new node (requires network-attached storage like EBS, PD, or NFS).
  - Immutable after StatefulSet creation (cannot add/remove/modify VCTs). Workaround: delete and recreate the StatefulSet with `--cascade=orphan`, then recreate with the new VCT.

- **minReadySeconds** (int32, optional, default 0)
  - Same as Deployment. Pod must be Ready for this duration before the StatefulSet considers it available.

- **revisionHistoryLimit** (int32, optional, default 10)
  - ControllerRevision objects to retain (like DaemonSet).

- **selector** (LabelSelector, required, immutable)
  - Same as other workload controllers.

- **ordinals** (StatefulSetOrdinals, optional)
  - **start** (int32, default 0): Starting ordinal for Pod naming. Set to 1 to start from `{name}-1` instead of `{name}-0`. Useful for migration scenarios.

### 6. Controller and Reconciliation Deep Dive

The StatefulSet controller maintains a strict ordering guarantee:

1. **Identity assignment**: Each Pod gets a sticky ordinal (0, 1, 2...). The Pod name, hostname, and PVC names are deterministic based on this ordinal.
2. **Sequential creation**: With `OrderedReady`, the controller creates Pod 0, waits for it to be Running and Ready, then creates Pod 1, etc. If Pod 0 fails, Pod 1 is never created.
3. **At-most-one guarantee**: Before creating a replacement Pod, the controller verifies the old Pod is completely terminated. This prevents split-brain scenarios in databases. If a node is unreachable, the Pod status remains `Unknown`, and the controller does NOT create a replacement until the old Pod is confirmed terminated (manually delete the Pod or wait for the node to be removed from the cluster).
4. **PVC lifecycle**: PVCs are created with the Pod but NOT deleted when the Pod is deleted (unless `persistentVolumeClaimRetentionPolicy` says otherwise). When a Pod is recreated (same ordinal), it reattaches to the existing PVC.
5. **Rolling update**: Pods are updated in reverse ordinal order. With `partition: 2` and 5 replicas, only Pods 4, 3, 2 are updated. Pods 1, 0 retain the old template.

**Network identity via headless Service:**
The headless Service creates DNS A/AAAA records for each Pod: `postgresql-0.postgresql-headless.database.svc.cluster.local`. These records point to the Pod's IP and are updated when the Pod is rescheduled. This provides stable network identity even as the underlying IP changes.

### 7. Production Scenarios

**PostgreSQL primary-replica cluster:**
StatefulSet with 3 replicas. Pod 0 is the primary (handles writes). Pods 1-2 are streaming replicas. The application reads the primary via `postgresql-0.postgresql-headless.database.svc.cluster.local` and replicas via a separate Service selecting all Pods. `podManagementPolicy: OrderedReady` ensures the primary starts first.

**Kafka cluster:**
StatefulSet with 3+ replicas. Each broker gets a stable identity (`kafka-0`, `kafka-1`, etc.) and persistent storage for log segments. Topology spread constraints distribute brokers across availability zones. `terminationGracePeriodSeconds: 120` allows time for partition leadership transfer during rolling updates.

**Scale-down data loss prevention:**
When scaling a StatefulSet from 5 to 3 replicas, Pods 4 and 3 are terminated. Their PVCs persist (default Retain policy). If you scale back to 5, Pods 3 and 4 reattach to their existing PVCs with all data intact. This is critical for distributed databases where each replica holds unique data.

**Node failure and the stuck Pod problem:**
If a node running `postgresql-0` becomes unreachable, the Pod status becomes `Unknown`. The StatefulSet controller will NOT create a replacement `postgresql-0` on another node because it cannot confirm the old Pod is terminated (at-most-one guarantee). Resolution: (1) Wait for the node to recover, (2) Confirm the node is truly dead and `kubectl delete node <name>`, (3) Force delete the Pod `kubectl delete pod postgresql-0 --force --grace-period=0` (risky: may cause split-brain if the old Pod is still running on a partitioned node).

#### 10. Common Pitfalls and Production Failures

- **Missing headless Service**: The StatefulSet requires the headless Service to exist before Pods are created. If the Service is missing, DNS records for Pods are not created, and inter-Pod communication fails. The StatefulSet controller still creates Pods, but they can't discover each other.

- **volumeClaimTemplates immutability**: You cannot change VCTs after creation. To resize PVCs, you must modify the PVC objects directly (if the StorageClass supports expansion). To change the StorageClass, you must delete the StatefulSet with `--cascade=orphan`, delete old PVCs, and recreate.

- **Stuck Pods on unreachable nodes**: The at-most-one guarantee means StatefulSet Pods on unreachable nodes block replacement creation. This can cause extended outages for database primaries. Automated solutions: use node-problem-detector with remediation scripts or configure `tolerationSeconds` to allow quicker eviction.

- **Zone-locked PVCs**: PVs backed by cloud block storage (EBS, PD) are zone-specific. If Pod 0's PVC is bound to `us-east-1a`, Pod 0 must always be scheduled in that zone. If that zone becomes unavailable, Pod 0 cannot be scheduled. Use multi-zone storage (EFS, GCS, cross-zone replication) for critical StatefulSets.

- **Parallel podManagementPolicy with ordered systems**: Setting `Parallel` on a system that requires ordered startup (e.g., a database that elects a primary from the first node) causes race conditions during initial bootstrap.

- **PVC leak on scale-down**: Default `Retain` policy means PVCs persist after scale-down. Over time, unused PVCs and their PVs accumulate, consuming storage and incurring cloud costs. Implement PVC cleanup automation or use `whenScaled: Delete` if the data is not critical.

## Job

### 1. Conceptual Overview

A Job creates one or more Pods and ensures that a specified number of them successfully terminate. Jobs are for batch workloads: one-time tasks, data processing, and computations.

**What problem it solves:**
Regular Pods with `restartPolicy: Always` keep running indefinitely. Jobs run a task to completion and track its success or failure. They handle retries, parallelism, and completion counting.

**Where it fits in cluster architecture:**
Jobs are the batch workload primitive. CronJobs create Jobs on a schedule. The Job controller runs within kube-controller-manager.

**Which controller manages it:**
The Job controller within kube-controller-manager.

**How reconciliation works:**
The controller creates Pods and tracks their completion. It creates new Pods until the desired number of completions is reached. Failed Pods are retried up to `backoffLimit`. The controller manages parallelism by ensuring no more than `parallelism` Pods are running concurrently.

### 4. Complete Field Breakdown

#### spec

- **completions** (int32, optional, default 1)
  - Number of Pods that must successfully complete for the Job to be considered done. For `completionMode: Indexed`, each index 0 to completions-1 must complete. For `NonIndexed`, any `completions` number of Pods must succeed.

- **parallelism** (int32, optional, default 1)
  - Maximum number of Pods running concurrently. For work-queue pattern, set `completions: null` and `parallelism: N`; the Job is complete when any Pod succeeds and the Pods coordinate among themselves.

- **backoffLimit** (int32, optional, default 6)
  - Number of retries before marking the Job as failed. Each Pod failure counts as one retry. With `restartPolicy: OnFailure`, container restarts within a Pod also count. Exponential backoff between retries: 10s, 20s, 40s, up to 6 minutes.

- **activeDeadlineSeconds** (int64, optional)
  - Maximum duration for the Job. After this, all running Pods are terminated and the Job is marked failed with reason `DeadlineExceeded`. Takes precedence over `backoffLimit`. Includes all retry time.

- **ttlSecondsAfterFinished** (int32, optional)
  - Automatic cleanup. The Job and its Pods are deleted this many seconds after the Job finishes (succeeded or failed). Without this, completed Jobs persist indefinitely, cluttering the namespace. Set to 86400 (24h) to allow time for log collection, then cleanup.

- **completionMode** (string, optional, default `NonIndexed`)
  - `NonIndexed`: Each Pod is interchangeable. Job succeeds when `completions` Pods finish.
  - `Indexed`: Each Pod gets a completion index (0 to completions-1) via the `JOB_COMPLETION_INDEX` env var and annotation. Each index must complete exactly once. Useful for parallel batch processing where each Pod handles a specific data partition.

- **suspend** (bool, optional, default false)
  - If true, the Job controller deletes all active Pods and stops creating new ones. Unsuspending resumes the Job. Useful for queue management, priority-based scheduling, or pausing expensive jobs.

- **podFailurePolicy** (PodFailurePolicy, optional)
  - Fine-grained failure handling. Rules match on exit codes or Pod conditions. Actions: `FailJob` (mark the Job as failed immediately), `Ignore` (don't count as a failure), `Count` (count toward backoffLimit, default behavior). Allows distinguishing between retriable failures (network timeout) and permanent failures (invalid input).

- **backoffLimitPerIndex** (int32, optional)
  - For `Indexed` completion mode. Maximum retries per index. When exceeded, that index is marked failed, but other indexes continue.

- **maxFailedIndexes** (int32, optional)
  - For `Indexed` mode. Maximum number of failed indexes before the entire Job is failed.

- **successPolicy** (SuccessPolicy, optional)
  - Allows the Job to be marked successful before all indexes complete. Rules define which indexes or how many must succeed.

- **template** (PodTemplateSpec, required)
  - Pod template. Must have `restartPolicy: OnFailure` or `Never`. `Always` is not allowed for Jobs. `OnFailure` restarts the container in-place; `Never` creates a new Pod for each retry. `OnFailure` is more efficient (no new Pod scheduling) but the container loses its filesystem (unless persistent volumes are used).

- **selector** (LabelSelector, auto-generated)
  - Automatically managed. The Job controller generates a unique label to prevent selector overlap between Jobs. Do not set manually unless you have a specific reason and understand the orphan adoption implications.

- **manualSelector** (bool, optional, default false)
  - If true, allows specifying `selector` manually. Used for compatibility with legacy Jobs or when migrating from another controller.

### 5. Status Section

- **startTime**: When the Job started (first Pod created).
- **completionTime**: When all completions finished.
- **active**: Number of actively running Pods.
- **succeeded**: Number of Pods that completed successfully.
- **failed**: Number of Pods that failed.
- **terminating**: Number of Pods in terminating state.
- **conditions**: `Complete` (Job finished successfully) or `Failed` (Job failed permanently). `Suspended` when suspended.
- **completedIndexes**: For Indexed mode, comma-separated list of completed index ranges (e.g., "0-3,5,7-9").
- **failedIndexes**: For Indexed mode with `backoffLimitPerIndex`, indexes that permanently failed.
- **ready**: Number of Pods with Ready condition.
- **uncountedTerminatedPods**: Pods that terminated but haven't been counted in `succeeded` or `failed` yet (optimistic bookkeeping to avoid race conditions).

---

### 6. Controller and Reconciliation Deep Dive

1. **Pod creation**: The controller creates up to `parallelism` Pods. Each Pod gets the Job's UID in `ownerReferences`.
2. **Completion tracking**: The controller watches for Pod completions. For `NonIndexed`, it counts total successes. For `Indexed`, it tracks which indexes have completed.
3. **Failure handling**: On Pod failure, the controller checks `podFailurePolicy` rules. If no rule matches, it increments the failure count. If `failed >= backoffLimit`, the Job is marked failed and remaining Pods are terminated.
4. **Parallelism management**: The controller ensures `active <= parallelism`. As Pods complete or fail, new Pods are created to maintain parallelism (up to remaining completions).
5. **Finalizers**: The Job controller uses the `batch.kubernetes.io/job-tracking` finalizer on Pods for accurate completion tracking, preventing race conditions between Pod completion and status updates.

**Data pipeline:**
An ETL Job with `completions: 100, parallelism: 10, completionMode: Indexed`. Each Pod processes a specific data partition based on `JOB_COMPLETION_INDEX`. Failed partitions are retried individually with `backoffLimitPerIndex: 3`.

**Database migration:**
A single-completion Job running a migration script. `backoffLimit: 0` because the migration is not idempotent. `activeDeadlineSeconds: 1800` to prevent hung migrations.

**Failure scenario:**
A Job with `backoffLimit: 6` keeps failing due to a misconfigured database connection string. Each retry takes 10s + backoff. After 6 failures, the Job is marked Failed. The Pods remain for debugging. `ttlSecondsAfterFinished` eventually cleans them up.

#### 10. Common Pitfalls and Production Failures

- **Forgetting ttlSecondsAfterFinished**: Completed Jobs and their Pods persist indefinitely by default. In CI/CD pipelines running many Jobs, this causes namespace clutter and etcd bloat.

- **restartPolicy: Always on Job Pods**: Validation error. Jobs require `OnFailure` or `Never`. The API server rejects `Always`.

- **Non-idempotent operations with retries**: A Job that inserts database records with `backoffLimit: 6` may create duplicate data if the operation succeeded but the Pod reported failure (e.g., timeout after commit). Make batch operations idempotent.

- **activeDeadlineSeconds including retry time**: The deadline is wall-clock time from Job start, not per-Pod time. A Job with `activeDeadlineSeconds: 300` and slow backoff may not get many retries before the deadline expires.

- **CronJob creating overlapping Jobs**: If a CronJob's Jobs take longer than the schedule interval, overlapping Jobs may conflict. Use `concurrencyPolicy: Forbid` to prevent this.

## CronJob

### 1. Conceptual Overview

A CronJob creates Jobs on a repeating schedule, defined using the cron format. It is the Kubernetes equivalent of the Unix cron daemon.

**What problem it solves:**
Scheduled batch processing: nightly backups, report generation, database maintenance, cleanup tasks, periodic data synchronization.

**Where it fits in cluster architecture:**
CronJobs sit above Jobs in the controller hierarchy: CronJob -> Job -> Pod. The CronJob controller runs within kube-controller-manager.

**Which controller manages it:**
The CronJob controller within kube-controller-manager.

**How reconciliation works:**
The controller checks CronJob schedules every 10 seconds. When a schedule tick fires, it creates a new Job from the `jobTemplate`. It manages Job retention based on `successfulJobsHistoryLimit` and `failedJobsHistoryLimit`. It enforces `concurrencyPolicy` when Jobs overlap.

### 4. Complete Field Breakdown

#### spec

- **schedule** (string, required)
  - Standard cron expression: `minute hour day-of-month month day-of-week`. Supports `*/5` (every 5 minutes), `1-5` (range), `1,15,30` (list). Also supports macros: `@yearly`, `@monthly`, `@weekly`, `@daily`, `@hourly`. Minimum granularity is 1 minute. No seconds support.

- **timeZone** (string, optional)
  - IANA timezone name (e.g., `America/New_York`). If not set, the schedule is interpreted in the kube-controller-manager's timezone (typically UTC). Always set explicitly in production to avoid confusion.

- **concurrencyPolicy** (string, optional, default `Allow`)
  - `Allow`: Multiple Jobs can run concurrently. No overlap prevention.
  - `Forbid`: If a previous Job is still running, the new scheduled Job is skipped. No new Job is created.
  - `Replace`: If a previous Job is still running, it is deleted and a new Job is created. Use with caution; the deleted Job's Pods are terminated immediately.

- **startingDeadlineSeconds** (int64, optional)
  - If the CronJob misses its scheduled time (e.g., controller was down), it still creates the Job if the missed time is within `startingDeadlineSeconds`. If more than 100 schedules have been missed, the CronJob is not scheduled and logs an error. Without this field, there is no deadline (the Job is created at the next opportunity).

- **successfulJobsHistoryLimit** (int32, optional, default 3)
  - Number of successful Jobs to retain. Older successful Jobs are deleted.

- **failedJobsHistoryLimit** (int32, optional, default 1)
  - Number of failed Jobs to retain. Older failed Jobs are deleted. Set higher in production for debugging.

- **suspend** (bool, optional, default false)
  - If true, no new Jobs are created from this CronJob. Existing Jobs are not affected.

- **jobTemplate** (JobTemplateSpec, required)
  - Template for creating Jobs. Contains the full Job spec. All Job fields apply.

---

### 5. Status Section

- **active** ([]ObjectReference): List of currently running Jobs.
- **lastScheduleTime** (Time): Last time a Job was created from this CronJob.
- **lastSuccessfulTime** (Time): Last time a Job completed successfully.

---

### 6. Controller and Reconciliation Deep Dive

The CronJob controller operates on a 10-second sync interval:

1. Lists all CronJobs.
2. For each CronJob, calculates the next scheduled time based on `schedule` and `lastScheduleTime`.
3. If the current time is past the scheduled time, determines whether to create a Job:
   - Checks `concurrencyPolicy` against active Jobs.
   - Checks `startingDeadlineSeconds` for missed schedules.
   - Checks `suspend` flag.
4. Creates the Job from `jobTemplate` with ownerReferences pointing to the CronJob.
5. Cleans up old Jobs beyond history limits.
6. Updates status with `lastScheduleTime`.

**Missed schedule handling:**
If the controller was down for 2 hours and the CronJob runs every 15 minutes, it counts 8 missed schedules. It creates one Job for the latest missed schedule. If more than 100 schedules were missed, it logs `Cannot determine if job needs to be started. Too many missed start time (> 100)` and does not create a Job.

**Database backup pipeline:**
A CronJob runs nightly at 2 AM EST, creates a `pg_dump`, and uploads to S3. `concurrencyPolicy: Forbid` prevents overlap if the backup takes longer than expected. `failedJobsHistoryLimit: 5` retains failed Jobs for investigation. Monitoring alerts if `lastSuccessfulTime` is older than 36 hours.

#### 10. Common Pitfalls and Production Failures

- **Timezone confusion**: Without `timeZone`, the schedule uses the controller's timezone. In managed Kubernetes, this is usually UTC. A schedule of `0 9 * * *` intended for 9 AM local time runs at 9 AM UTC.

- **Missing concurrencyPolicy**: Default `Allow` lets Jobs overlap. Long-running Jobs with short schedules create cascading resource consumption. Always set `Forbid` for non-idempotent operations.

- **100+ missed schedules**: After extended controller downtime, CronJobs with more than 100 missed schedules stop scheduling entirely. Set `startingDeadlineSeconds` to limit the window.

- **History limit cleanup removing debug evidence**: With `failedJobsHistoryLimit: 1`, failed Jobs are quickly cleaned up, losing logs and status information. Set higher for critical CronJobs.

- **Job name conflicts**: CronJobs generate Job names from the CronJob name and timestamp. Names must be under 63 characters. Long CronJob names combined with the timestamp suffix can exceed the limit.

## Service

### 1. Conceptual Overview

A Service is an abstraction that defines a logical set of Pods and a policy by which to access them. Services enable stable network endpoints for ephemeral Pods.

**What problem it solves:**
Pods are ephemeral; their IPs change on restart or rescheduling. Clients cannot rely on Pod IPs. Services provide a stable IP (ClusterIP), DNS name, and load balancing across a set of Pods. They decouple the client from the backing Pods.

**Where it fits in cluster architecture:**
Services are the primary networking primitive for Pod-to-Pod and external-to-Pod communication. They work with kube-proxy (or its replacement, e.g., Cilium) to program iptables/IPVS rules on each node. The Endpoints/EndpointSlice controllers populate the backend Pod IPs.

**Which controller manages it:**
The Endpoints controller and EndpointSlice controller within kube-controller-manager manage the association between Services and Pods. kube-proxy (or CNI plugin) implements the data plane (iptables, IPVS, or eBPF rules) on each node. The cloud controller manager manages cloud load balancers for `LoadBalancer` Services.

**How reconciliation works:**
The Endpoints controller watches Services and Pods. When a Service selector matches Pods, it creates/updates Endpoints objects listing the ready Pod IPs. kube-proxy watches Endpoints/EndpointSlices and programs data plane rules. When a Pod becomes unready, its IP is removed from Endpoints, and traffic stops being routed to it.

### 4. Complete Field Breakdown

#### spec

- **type** (string, optional, default `ClusterIP`)

  - `LoadBalancer`: Provisions an external load balancer (cloud-specific). Adds to NodePort and ClusterIP. The cloud controller manager creates the LB and configures it to route to NodePorts. In AWS: NLB/CLB/ALB. In GCP: Network/HTTP LB.
  - `ExternalName`: Maps the Service to a DNS CNAME. No proxying, no ClusterIP. `externalName` must be a valid DNS name. Used for aliasing external services.
  - Type is mutable (with caveats). Changing between `ClusterIP` and `NodePort` is straightforward. Changing to/from `LoadBalancer` triggers cloud LB creation/deletion.

- **clusterIP** (string, optional)
  - Assigned from the cluster's Service CIDR. `None` creates a headless Service (no ClusterIP; DNS returns Pod IPs directly). Can be set to a specific IP for deterministic addressing (e.g., `10.96.0.10` for CoreDNS). Immutable after creation.

- **clusterIPs** ([]string, optional)
  - List of ClusterIPs for dual-stack. First entry matches `clusterIP`.

- **selector** (map[string]string, optional)
  - Label selector matching backend Pods. Only Pods with ALL matching labels AND the Ready condition are included in Endpoints. If empty/nil, no Endpoints are created automatically; you must create them manually (useful for external service proxying).

- **ports** ([]ServicePort, required for non-ExternalName)
  - **name** (string): Required if multiple ports. Used in Ingress/NetworkPolicy references.
  - **port** (int32): The port exposed by the Service (what clients connect to).
  - **targetPort** (IntOrString): The port on the Pod (number or named port from container spec). If not set, defaults to `port` value.
  - **protocol** (string): TCP (default), UDP, SCTP.
  - **nodePort** (int32): For NodePort/LoadBalancer types. If not specified, automatically allocated from 30000-32767. Can be set manually for deterministic port allocation.
  - **appProtocol** (string): Application protocol hint (e.g., `http`, `https`, `grpc`). Used by Ingress controllers and service meshes.

- **externalTrafficPolicy** (string, optional)
  - `Cluster` (default): Traffic is distributed across all nodes via SNAT. Source IP is lost. Even distribution.
  - `Local`: Traffic is forwarded only to Pods on the receiving node. Preserves client source IP. If no Pods exist on a node, traffic to that node's NodePort is dropped. Creates uneven distribution. `healthCheckNodePort` allows the load balancer to health-check node readiness. Use `Local` when source IP preservation is required (security logging, geo-routing).

- **internalTrafficPolicy** (string, optional, default `Cluster`)
  - `Cluster`: Normal cluster-wide routing.
  - `Local`: Internal traffic prefers Pods on the same node. If no local Pod exists, traffic is dropped (with topology-aware hints enabled) or routed to another node (default behavior). Used for reducing cross-node traffic (latency-sensitive workloads, data locality).

- **sessionAffinity** (string, optional, default `None`)
  - `None`: Each request is independently load-balanced.
  - `ClientIP`: Requests from the same client IP are routed to the same backend Pod. Configured via `sessionAffinityConfig.clientIP.timeoutSeconds` (default 10800 = 3 hours). Implemented via iptables `recent` module or IPVS persistent connections.

- **externalIPs** ([]string, optional)
  - List of IPs that nodes will also accept traffic for this Service. Traffic arriving at these IPs on the Service port is routed to endpoints. The IPs are not managed by Kubernetes; they must be routed to nodes by external means. Security-sensitive; can be exploited for MITM if not controlled. Some clusters disable this via admission policies.

- **loadBalancerIP** (string, optional, deprecated)
  - Request a specific IP for the cloud load balancer. Deprecated in favor of annotations or `loadBalancerClass`-specific mechanisms.

- **loadBalancerSourceRanges** ([]string, optional)
  - CIDR ranges allowed to access the LoadBalancer. Implemented as security group rules (AWS) or firewall rules (GCP). Not all cloud providers support this field; use annotations for cloud-specific configuration.

- **loadBalancerClass** (string, optional)
  - Specifies which load balancer implementation to use. Allows multiple LB providers (e.g., `service.k8s.aws/nlb` for AWS Load Balancer Controller vs. the default cloud controller LB). Immutable after creation.

- **externalName** (string, for ExternalName type)
  - DNS name to CNAME to. No proxying occurs. CoreDNS returns a CNAME record. Port mapping is not supported (the full DNS name is returned). Used for transparent references to external services.

- **publishNotReadyAddresses** (bool, optional, default false)
  - If true, Pod IPs are published in DNS even when not Ready. Used by StatefulSet headless Services where client applications need to connect to Pods during initialization (e.g., database cluster bootstrap).

- **ipFamilyPolicy** (string, optional)
  - `SingleStack`, `PreferDualStack`, `RequireDualStack`. Controls IPv4/IPv6 behavior.

- **ipFamilies** ([]string, optional)
  - `IPv4`, `IPv6`. Order determines primary family.

- **allocateLoadBalancerNodePorts** (bool, optional, default true)
  - For LoadBalancer type. If false, NodePorts are not allocated. The LB routes directly to Pod IPs. Requires a LB implementation that supports direct routing (e.g., AWS NLB in IP mode via AWS Load Balancer Controller).

- **healthCheckNodePort** (int32, optional)
  - For LoadBalancer + `externalTrafficPolicy: Local`. The LB health-checks this port to determine if a node has ready backends. Automatically allocated if not specified.

### 6. Controller and Reconciliation Deep Dive

**Endpoints controller:**

1. Watches Services with selectors and all Pods.
2. For each Service, finds Pods matching the selector in the same namespace.
3. Filters to Pods in the Ready state (unless `publishNotReadyAddresses: true`).
4. Creates/updates the Endpoints object with the list of ready Pod IPs and ports.
5. When a Pod fails readiness, its IP is removed from Endpoints within ~1-2 seconds.

**EndpointSlice controller (preferred since 1.21):**
Same logic but uses EndpointSlice objects instead of Endpoints. EndpointSlices support 100 endpoints per slice (vs. one Endpoints object for all), improving scalability and reducing watch event size for Services with many backends.

**kube-proxy data plane:**

- **iptables mode**: Creates DNAT rules for each Service ClusterIP/NodePort to the backend Pod IPs. Round-robin via `iptables-extensions` random probability. Scales O(n) with number of Services. Rule updates block iptables briefly.
- **IPVS mode**: Uses Linux IPVS (IP Virtual Server) kernel module. Supports round-robin, least-connections, weighted, and other algorithms. Scales O(1) for connection setup. Better for large clusters (1000+ Services).
- **eBPF mode (Cilium)**: Replaces kube-proxy entirely. Handles service routing at the socket level or in XDP. Lower latency, better performance.

**Load balancer reconciliation (cloud controller):**
The cloud controller watches LoadBalancer Services. It creates/updates/deletes cloud LBs, configures health checks, security groups, and target groups. LB creation takes 1-5 minutes on most cloud providers. Health check convergence adds another 30-60 seconds.

#### 10. Common Pitfalls and Production Failures

- **Selector mismatch**: The Service selector does not match any Pod labels. Endpoints are empty. `kubectl get endpoints <svc>` shows no addresses. Most common cause of "Service not working."

- **externalTrafficPolicy: Local with uneven Pod distribution**: If Pods are concentrated on one node, that node receives a disproportionate share of traffic. Nodes without Pods drop traffic. Combine with topology spread constraints for even distribution.

- **LoadBalancer provisioning delay**: Cloud LBs take 1-5 minutes to provision. During this time, `status.loadBalancer.ingress` is empty. Health check convergence adds further delay. Total time from Service creation to traffic flowing: 2-7 minutes.

- **Headless Service with ClusterIP**: Setting `clusterIP: None` creates a headless Service. If you accidentally set `clusterIP: ""` (empty string), the API server allocates a ClusterIP. Be explicit.

- **Port vs targetPort confusion**: `port` is what clients connect to (on the ClusterIP). `targetPort` is the port on the Pod. If your app listens on 8080 but the Service `port` is 80, set `targetPort: 8080`.

- **Session affinity masking failures**: `ClientIP` affinity sends all requests from a client to one Pod. If that Pod is slow/broken, the client sees 100% error rate while other clients are fine. Difficult to diagnose.

- **ExternalName and TLS**: ExternalName returns a CNAME. The TLS certificate on the external service must match the original hostname, not the Kubernetes Service name. SNI/Host header must be set by the client.

- **stale endpoints during rolling updates**: There's a race between endpoint removal and Pod termination. Use `preStop` hooks and connection draining to mitigate.

## Ingress

### 1. Conceptual Overview

An Ingress exposes HTTP and HTTPS routes from outside the cluster to Services within the cluster. It provides URL-based routing, TLS termination, and virtual hosting.

**What problem it solves:**
Without Ingress, each externally-accessible Service needs its own LoadBalancer, which is expensive and lacks HTTP-level routing. Ingress consolidates external access behind a single entry point with path-based and host-based routing.

**Where it fits in cluster architecture:**
Ingress is an API object that describes routing rules. An Ingress controller (NGINX, Traefik, HAProxy, AWS ALB, Istio Gateway) implements the rules by configuring a reverse proxy or cloud load balancer. The Ingress resource alone does nothing without a controller.

**Which controller manages it:**
An Ingress controller, which is NOT a core Kubernetes component. It must be deployed separately. Common controllers: ingress-nginx, AWS Load Balancer Controller, Traefik, Istio, Contour. The controller watches Ingress objects and configures its data plane accordingly.

### 4. Complete Field Breakdown

#### spec

- **ingressClassName** (string, optional)
  - References an IngressClass object. Determines which Ingress controller handles this Ingress. Multiple controllers can coexist; `ingressClassName` routes to the correct one. If not specified, the default IngressClass (annotated `ingressclass.kubernetes.io/is-default-class: true`) is used. Replaces the deprecated `kubernetes.io/ingress.class` annotation.

- **tls** ([]IngressTLS, optional)
  - **hosts**: List of hostnames covered by the TLS certificate.
  - **secretName**: References a Secret of type `kubernetes.io/tls` containing `tls.crt` and `tls.key`. The Ingress controller loads this certificate for TLS termination. With cert-manager, the `cert-manager.io/cluster-issuer` annotation triggers automatic certificate provisioning and stores it in this Secret.
  - TLS termination happens at the Ingress controller. Backend traffic is typically HTTP (unencrypted) unless configured otherwise.

- **defaultBackend** (IngressBackend, optional)
  - Handles requests that don't match any rule. Serves as a catch-all. If not specified, the Ingress controller typically returns 404.

- **rules** ([]IngressRule, optional)
  - **host** (string): Hostname to match. Exact match only (no wildcards in standard Ingress; some controllers support `*.example.com`). If omitted, the rule matches all hosts.
  - **http.paths** ([]HTTPIngressPath):
    - **path** (string): URL path to match.
    - **pathType** (string, required): `Exact` (exact string match), `Prefix` (prefix match by path element, `/foo` matches `/foo`, `/foo/`, `/foo/bar` but not `/foobar`), `ImplementationSpecific` (controller-dependent).
    - **backend** (IngressBackend): Route target. References a Service and port (by name or number). Can also reference a `resource` (custom backend, e.g., S3 bucket via cloud-specific controllers).

### 5. Status Section

- **loadBalancer.ingress**: Similar to Service. Contains the external IP/hostname of the Ingress controller's load balancer. Populated by the Ingress controller, not the Kubernetes core.

---

### 6. Controller and Reconciliation Deep Dive

Ingress controllers operate outside the standard Kubernetes control plane:

1. The controller watches Ingress, Service, Secret, and Endpoints/EndpointSlice objects.
2. On change, it generates configuration (e.g., nginx.conf for ingress-nginx) based on all Ingress rules it manages.
3. It reloads/signals the reverse proxy to apply the new configuration.
4. For cloud-based controllers (AWS ALB), it calls cloud APIs to create/update load balancer rules, target groups, and listeners.

**ingress-nginx specifics:**

- Configuration changes trigger an nginx reload (brief connection disruption for some configurations).
- Lua-based dynamic upstreams avoid reloads for endpoint changes.
- Annotations control per-Ingress nginx directives.

**AWS ALB Ingress Controller:**

- Creates an Application Load Balancer per IngressClass (or per Ingress with `alb.ingress.kubernetes.io/group.name`).
- Each Ingress rule becomes an ALB listener rule.
- Target groups point to Pod IPs (IP mode) or NodePorts (instance mode).

### 7. Production Scenarios

**Multi-tenant platform:**
Single ingress-nginx instance with multiple Ingress resources per tenant namespace. Each tenant has its own hostname (`tenant1.platform.com`). TLS certificates managed by cert-manager with Let's Encrypt. Rate limiting and WAF rules via annotations.

**API versioning:**
Path-based routing: `/v1/*` to the v1 Service, `/v2/*` to the v2 Service. The default backend returns a version discovery document.

**Blue-green traffic switching:**
Two sets of Ingress rules pointing to blue/green Service backends. Switch traffic by updating the Ingress backend service name. Alternatively, use weighted annotations (controller-specific) for gradual traffic shift.

#### 10. Common Pitfalls and Production Failures

- **No Ingress controller installed**: Creating Ingress objects without a controller does nothing. The most common mistake for new cluster setups. Check for Ingress controller pods: `kubectl get pods -n ingress-nginx` or equivalent.

- **Wrong ingressClassName**: The Ingress is created but no controller picks it up because the class doesn't match. The Ingress sits with no address populated.

- **TLS Secret missing or malformed**: The Ingress controller cannot load the TLS certificate. It falls back to a default/fake certificate, causing browser trust errors. Verify: `kubectl get secret <secretName> -n <ns>`.

- **Path ordering matters**: Some controllers evaluate paths in order. More specific paths should come before less specific ones. `/api/v1` before `/api`. With `Prefix` type, `/` matches everything.

- **Annotation typos**: Ingress controller annotations are freeform strings. A typo (`nginx.ingress.kubernetes.io/proxy-body-siz` instead of `proxy-body-size`) is silently ignored.

- **502 during rolling updates**: Backend Pods terminate before the Ingress controller updates its upstream list. Implement `preStop` hooks and ensure readiness probes are configured.

- **Certificate renewal failures with cert-manager**: If cert-manager cannot complete the ACME challenge (DNS misconfiguration, rate limits), the TLS Secret is not renewed. The old certificate expires. Monitor cert-manager Certificate resources for Ready condition.

## NetworkPolicy

### 1. Conceptual Overview

A NetworkPolicy is a specification of how groups of Pods are allowed to communicate with each other and with other network endpoints. It provides network segmentation at the Pod level.

**What problem it solves:**
By default, all Pods in a Kubernetes cluster can communicate with each other (flat network). NetworkPolicies implement microsegmentation: restricting which Pods can talk to which, on which ports, and in which direction (ingress/egress).

**Where it fits in cluster architecture:**
NetworkPolicies are enforced by the CNI plugin (Calico, Cilium, Weave Net, Antrea). kube-proxy does NOT enforce NetworkPolicies. If the CNI plugin doesn't support NetworkPolicies, the objects are created but have no effect.

**Which controller manages it:**
The CNI plugin's policy agent (e.g., Calico Felix, Cilium agent). These agents watch NetworkPolicy objects and program iptables/eBPF/iptables rules on each node.

**How reconciliation works:**
The CNI policy agent watches NetworkPolicy objects and Pods. When a NetworkPolicy matches Pods via its `podSelector`, it enforces the specified ingress/egress rules by programming data plane rules (iptables or eBPF). Traffic not explicitly allowed by any policy applied to a Pod is denied.

**Key principle:** NetworkPolicies are additive. Multiple policies can apply to the same Pod. A connection is allowed if ANY policy allows it. There is no "deny" rule; the absence of an "allow" rule for a Pod with any policy applied results in denial.

metadata:
  name: default-deny-all
  namespace: production
spec:
  podSelector: {}
  policyTypes:
    - Ingress
    - Egress
```

---

### 4. Complete Field Breakdown

#### spec

- **podSelector** (LabelSelector, required)
  - Selects Pods in the same namespace to which this policy applies. Empty selector `{}` matches ALL Pods in the namespace. Pods not matched by any NetworkPolicy's `podSelector` have no restrictions (allow all).

- **policyTypes** ([]string, required in practice)
  - `Ingress`, `Egress`, or both. Determines which direction the policy restricts. If `policyTypes` includes `Ingress` but no `ingress` rules are specified, ALL ingress is denied. Same for `Egress`. This is how you create deny-all policies.

- **ingress** ([]NetworkPolicyIngressRule, optional)
  - Each rule allows traffic from specified sources on specified ports. Rules are OR'd (any rule can allow the connection).
  - **from** ([]NetworkPolicyPeer): Sources. OR'd. Each peer can be:
    - **podSelector**: Pods in the same namespace matching labels.
    - **namespaceSelector**: Pods in namespaces matching labels.
    - **podSelector + namespaceSelector** (combined in one peer): Pods matching `podSelector` in namespaces matching `namespaceSelector`. This is an AND condition. Be careful: two separate peers (one with podSelector, one with namespaceSelector) creates OR logic; combining them in one peer creates AND logic.
    - **ipBlock**: CIDR range with optional `except` exclusions. For traffic from outside the cluster.
  - **ports** ([]NetworkPolicyPort): Allowed ports. OR'd. `protocol` (TCP/UDP/SCTP), `port` (number or named port), `endPort` (port range upper bound, requires `port` as the lower bound).

- **egress** ([]NetworkPolicyEgressRule, optional)
  - Same structure as ingress but for outbound traffic.
  - **to** ([]NetworkPolicyPeer): Destinations. Same types as `from`.
  - **ports** ([]NetworkPolicyPort): Allowed destination ports.
  - Always allow DNS: Egress policies commonly include a rule allowing UDP/TCP port 53 to the cluster DNS (all namespaces or the kube-system namespace). Without DNS, almost nothing works.

---

### 5. Status Section

NetworkPolicy has no meaningful status section. The API server stores the object, but enforcement is entirely at the CNI layer. There is no feedback mechanism to indicate if the policy is actually enforced.

---

### 6. Controller and Reconciliation Deep Dive

NetworkPolicies are not managed by a Kubernetes controller. The CNI plugin's policy agent handles them:

1. The agent watches NetworkPolicy objects and Pod/Namespace label changes.
2. On any change, it recalculates the policy rules for affected Pods.
3. It programs the data plane:
   - **Calico**: iptables/ipsets rules or eBPF programs per Pod network namespace.
   - **Cilium**: eBPF programs attached to Pod veth interfaces. Cilium implements policies at L3/L4 and optionally L7 (HTTP, gRPC).
4. Rules are applied asynchronously. There's a brief window after policy creation where traffic may still be allowed.

**Pod identity:** The CNI maps Pod IPs to labels dynamically. When a Pod's IP changes (restart/reschedule), the ipsets are updated. Label changes on existing Pods also trigger rule updates.

---

### 7. Production Scenarios

**Default-deny with explicit allow (zero-trust):**
Apply a default-deny policy to every namespace (`podSelector: {}` with both policyTypes). Then create explicit allow policies for each communication path. This is the recommended production pattern.

**Multi-tenant isolation:**
Each tenant namespace has a default-deny policy. Cross-namespace communication is only allowed between specific labeled namespaces (e.g., `tenant: acme` namespace can reach `shared-services` namespace on port 443).

**Database access control:**
A NetworkPolicy on the database namespace allows ingress only from Pods in the application namespace with label `role: api` on port 5432. All other traffic to the database Pods is denied.

#### 10. Common Pitfalls and Production Failures

- **CNI doesn't support NetworkPolicy**: Flannel (without Calico) does not enforce NetworkPolicies. Objects are created but have no effect. Verify your CNI supports policies.

- **AND vs OR confusion in peers**: A single peer with both `namespaceSelector` and `podSelector` is AND (Pods matching labels in matching namespaces). Two separate peers is OR (any Pod matching labels OR any Pod in matching namespaces). This subtle difference causes unintended access.

- **Forgetting DNS egress**: A default-deny egress policy without a DNS allow rule breaks everything. Pods can't resolve Service names. Always include UDP/TCP 53 in egress policies.

- **No status feedback**: There's no way to know from the API if a NetworkPolicy is actually enforced. Use connectivity testing tools (e.g., `kubectl exec` with `wget`/`curl`) to verify.

- **ipBlock for cluster-internal IPs**: `ipBlock` rules do not match Pod IPs in some CNI implementations (Calico applies policies before NAT for some flows). Use `podSelector` for cluster-internal traffic and `ipBlock` for external.

- **Policies are namespace-scoped**: A NetworkPolicy in namespace A cannot directly select Pods in namespace B as its `podSelector` target. It can only allow traffic from/to namespace B's Pods using `namespaceSelector` in `ingress`/`egress` rules.

## Endpoints and EndpointSlice

### 1. Conceptual Overview

Endpoints and EndpointSlice objects store the IP addresses and ports of Pods backing a Service. They are the bridge between the Service abstraction and the actual backend Pods.

**Endpoints** is the legacy resource. A single Endpoints object contains all backend IPs for a Service. For Services with hundreds/thousands of backends, updates become expensive (every Pod change triggers a full object write).

**EndpointSlice** is the modern replacement. It shards endpoints into slices of up to 100 endpoints each, reducing the size of API watch events and improving scalability.

**Which controller manages it:**
The Endpoints controller and EndpointSlice controller within kube-controller-manager create and update these objects based on Service selectors and Pod readiness.

---

| EndpointSlice | discovery.k8s.io | v1      | none        |

        nodeName: worker-3

          kind: Pod
          name: api-server-ghi789
          namespace: production

        port: 8080
        protocol: TCP
```

#### EndpointSlice

### 4. Production Relevance

- EndpointSlice `zone` field enables topology-aware routing (traffic prefers same-zone backends).
- `conditions.terminating` allows distinguishing between healthy backends and those in graceful shutdown.
- For large Services (1000+ Pods), Endpoints object updates become a bottleneck. EndpointSlice scales better.
- Manual Endpoints are used for proxying to external databases, legacy services, or cross-cluster communication.

## PersistentVolume

### 1. Conceptual Overview

A PersistentVolume (PV) is a piece of storage in the cluster that has been provisioned by an administrator or dynamically provisioned using a StorageClass. It is a cluster-level resource (not namespaced) that represents physical or cloud storage.

**What problem it solves:**
Pod volumes are ephemeral (emptyDir) or node-specific (hostPath). PVs provide durable, portable storage that outlives individual Pods. They decouple storage provisioning from consumption.

**Where it fits in cluster architecture:**
PVs are cluster-scoped. PersistentVolumeClaims (PVCs) are namespace-scoped requests for storage. The PV controller binds PVCs to PVs. Pods reference PVCs in their volume spec.

**Which controller manages it:**
The PersistentVolume controller (PV binder) within kube-controller-manager. For dynamic provisioning, the external provisioner (CSI driver) creates PVs. The attach/detach controller handles volume attachment to nodes.

---

### 2. API Information

| Field                    | Value                |
| ------------------------ | -------------------- |
| **API Group**            | core (`""`)          |
| **Version**              | v1                   |
| **Kind**                 | PersistentVolume     |
| **Scope**                | Cluster-scoped       |
| **Short names**          | `pv`                 |
| **kubectl explain path** | `kubectl explain pv` |

---

### 3. Full Production YAML Example

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-database-prod-01
  labels:
    type: ssd
    environment: production
    topology.kubernetes.io/zone: us-east-1a
  annotations:
    pv.kubernetes.io/provisioned-by: ebs.csi.aws.com
spec:
  capacity:
    storage: 100Gi
  volumeMode: Filesystem
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  storageClassName: gp3-encrypted
  mountOptions:
    - noatime
    - nodiratime
  csi:
    driver: ebs.csi.aws.com
    volumeHandle: vol-0123456789abcdef0
    fsType: ext4
    volumeAttributes:
      encrypted: "true"
      kmsKeyId: "arn:aws:kms:us-east-1:123456789:key/abc-def"
  nodeAffinity:
    required:
      nodeSelectorTerms:
        - matchExpressions:
            - key: topology.kubernetes.io/zone
              operator: In
              values:
                - us-east-1a
```

---

### 4. Complete Field Breakdown

#### spec

- **capacity.storage** (Quantity, required)
  - Total storage size. For dynamic provisioning, this matches the PVC request. For static provisioning, this is the actual volume size. Binary units (Gi, Mi) or decimal (G, M).

- **volumeMode** (string, optional, default `Filesystem`)
  - `Filesystem`: Volume is formatted and mounted as a directory. `Block`: Volume is presented as a raw block device. Block mode is used for databases that manage their own filesystem (e.g., some distributed storage systems).

- **accessModes** ([]string, required)
  - `ReadWriteOnce` (RWO): Mounted as read-write by a single node. Most common for block storage (EBS, PD).
  - `ReadOnlyMany` (ROX): Mounted as read-only by many nodes.
  - `ReadWriteMany` (RWX): Mounted as read-write by many nodes. Requires network filesystems (NFS, EFS, CephFS).
  - `ReadWriteOncePod` (RWOP): Mounted as read-write by a single Pod (even if multiple Pods are on the same node, only one can mount it). Kubernetes 1.27+.
  - Access modes are constraints, not enforcement for all volume types. Some volume types don't enforce access modes at the storage layer.

- **persistentVolumeReclaimPolicy** (string, optional)
  - `Retain` (default for static PVs): PV is not deleted when the PVC is deleted. Data is preserved. The PV transitions to `Released` state and must be manually cleaned and re-bound.
  - `Delete` (default for dynamic PVs): The PV and its backing storage are deleted when the PVC is deleted. The CSI driver handles the deletion.
  - `Recycle` (deprecated): Runs `rm -rf /thevolume/*` and makes the PV available again. Only supported for NFS and hostPath.

- **storageClassName** (string, optional)
  - Links the PV to a StorageClass. PVCs requesting this StorageClass can bind to this PV. If empty string `""`, the PV only binds to PVCs with no StorageClass. If not set, the PV can bind to PVCs with no StorageClass or the default StorageClass (depending on configuration).

- **mountOptions** ([]string, optional)
  - Filesystem mount options (e.g., `noatime`, `nfsvers=4.1`). Not validated by Kubernetes; invalid options cause mount failure.

- **nodeAffinity** (VolumeNodeAffinity, optional)
  - Constrains which nodes can access this PV. Required for zone-specific volumes (EBS, GCE PD). The scheduler uses this to place Pods on nodes where the PV is accessible.

- **csi** (CSIPersistentVolumeSource)
  - **driver**: CSI driver name (e.g., `ebs.csi.aws.com`, `pd.csi.storage.gke.io`).
  - **volumeHandle**: Unique identifier for the volume in the storage system (e.g., AWS EBS volume ID).
  - **fsType**: Filesystem type (ext4, xfs, etc.).
  - **volumeAttributes**: Driver-specific key-value pairs.
  - **nodeStageSecretRef**, **nodePublishSecretRef**: Secrets for authentication with the storage system.

- **claimRef** (ObjectReference, optional)
  - Pre-binds the PV to a specific PVC. Set during binding. Can be set manually for static pre-binding (ensure the PVC exists or will exist).

---

### 5. Status Section

- **phase** (string):
  - `Available`: Not yet bound to a PVC.
  - `Bound`: Bound to a PVC.
  - `Released`: PVC was deleted, PV is released but not yet reclaimed.
  - `Failed`: Automatic reclamation failed.
- **lastPhaseTransitionTime**: When the phase last changed.

---

### 6. Controller and Reconciliation Deep Dive

The PV controller (PV binder) runs a continuous loop:

1. **Binding**: Matches unbound PVCs to available PVs based on: storage class, access modes, capacity (PV capacity >= PVC request), label selector, and volume mode. If a matching PV is found, it sets `claimRef` on the PV and `spec.volumeName` on the PVC. This is an atomic operation.
2. **Dynamic provisioning**: If no matching PV exists and the PVC's StorageClass has a provisioner, the PV controller triggers the external provisioner (CSI driver), which creates the storage and a corresponding PV object.
3. **Release**: When a bound PVC is deleted, the PV transitions to `Released`. Based on `reclaimPolicy`, it is retained, deleted, or recycled.

**Attach/detach controller:**
When a Pod referencing a PVC is scheduled to a node, the attach/detach controller calls the CSI driver's `ControllerPublishVolume` to attach the volume to the node. The kubelet then calls `NodeStageVolume` and `NodePublishVolume` to mount it into the Pod.

---

### 7. Production Scenarios

**Static provisioning for legacy storage:**
An administrator creates PVs representing existing NFS shares or SAN LUNs. Application teams create PVCs that bind to these PVs. Useful when storage cannot be dynamically provisioned.

**Data recovery from Released PVs:**
A PVC is accidentally deleted. The PV transitions to Released with `Retain` policy. Data is preserved. Recovery: remove `claimRef` from the PV (it becomes Available), create a new PVC that matches the PV's attributes, or create a PVC with `volumeName` pointing to the PV.

#### 10. Common Pitfalls and Production Failures

- **PVC stuck in Pending**: No PV matches the PVC's requirements (storageClass, accessModes, capacity). Check with `kubectl describe pvc <name>` for binding errors.

- **Zone mismatch**: PV in `us-east-1a` cannot be mounted by a Pod scheduled in `us-east-1b`. Use `nodeAffinity` on PVs and topology constraints on workloads.

- **Retain policy causing storage leaks**: With `Retain`, PVs persist after PVC deletion, consuming cloud storage costs. Implement periodic cleanup automation for Released PVs.

- **Delete policy causing data loss**: With `Delete`, deleting a PVC permanently destroys the underlying storage. No recovery possible. Use `Retain` for critical data and implement backup strategies.

- **Volume already attached errors**: A PV with RWO access mode can only be attached to one node. If a Pod is rescheduled to a different node while the old node hasn't detached the volume, the new Pod waits. Force detach may be needed: `kubectl delete volumeattachment <name>`.

## PersistentVolumeClaim

### 1. Conceptual Overview

A PersistentVolumeClaim (PVC) is a request for storage by a user. It claims a PersistentVolume and makes it available to Pods. PVCs are namespace-scoped.

**What problem it solves:**
Decouples storage consumption from provisioning. Application teams request storage without needing to know the underlying storage system. Platform teams manage PVs and StorageClasses.

---

### 2. API Information

| Field           | Value                 |
| --------------- | --------------------- |
| **API Group**   | core (`""`)           |
| **Version**     | v1                    |
| **Kind**        | PersistentVolumeClaim |
| **Scope**       | Namespaced            |
| **Short names** | `pvc`                 |

---

### 3. Full Production YAML Example

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data-postgresql-0
  namespace: database
  labels:
    app.kubernetes.io/name: postgresql
  annotations:
    volume.kubernetes.io/storage-provisioner: ebs.csi.aws.com
  finalizers:
    - kubernetes.io/pvc-protection
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: gp3-encrypted
  volumeMode: Filesystem
  resources:
    requests:
      storage: 100Gi
  selector:
    matchLabels:
      type: ssd
  dataSource:
    kind: VolumeSnapshot
    name: postgresql-snapshot-20251115
    apiGroup: snapshot.storage.k8s.io
```

---

### 4. Complete Field Breakdown

#### spec

- **accessModes** ([]string, required): Same as PV. Must match an available PV.
- **storageClassName** (string, optional): References a StorageClass. If not set, the default StorageClass is used. If set to `""`, only PVs with no StorageClass are matched.
- **volumeMode** (string, optional, default `Filesystem`): Must match the PV.
- **resources.requests.storage** (Quantity, required): Minimum storage requested. The bound PV must have capacity >= this value.
- **selector** (LabelSelector, optional): Additional filtering for PV binding. Restricts which PVs can be bound based on labels.
- **volumeName** (string, optional): Pre-binds to a specific PV by name. Used for static binding when you know exactly which PV to use.
- **dataSource** (TypedLocalObjectReference, optional): Clone from an existing PVC or restore from a VolumeSnapshot. The provisioner creates a new volume with the source data.
- **dataSourceRef** (TypedObjectReference, optional): Like `dataSource` but supports cross-namespace references and custom resources.

**PVC protection finalizer:**
The `kubernetes.io/pvc-protection` finalizer prevents deletion of PVCs that are in use by Pods. If you try to delete a PVC mounted by a running Pod, it enters `Terminating` state and is only deleted after the Pod releases it.

---

### 5. Status Section

- **phase**: `Pending` (no PV bound), `Bound` (PV bound), `Lost` (bound PV deleted).
- **accessModes**: Actual access modes of the bound PV.
- **capacity.storage**: Actual capacity of the bound PV (may be larger than requested).
- **conditions**: Including resize conditions (`FileSystemResizePending`).
- **allocatedResources**: Storage allocated by the volume plugin.
- **allocatedResourceStatuses**: Status of resize operations per resource.

---

### 6. Key Operations

**Volume expansion:**
If the StorageClass has `allowVolumeExpansion: true`, you can increase `spec.resources.requests.storage`. The CSI driver expands the underlying volume. For Filesystem mode, the kubelet resizes the filesystem on the next mount (some CSI drivers support online expansion). You cannot shrink a PVC.

```bash
kubectl patch pvc data-postgresql-0 -n database \
  -p '{"spec":{"resources":{"requests":{"storage":"200Gi"}}}}'
```

## StorageClass

### 1. Conceptual Overview

A StorageClass provides a way for administrators to describe the "classes" of storage they offer. Different classes may map to quality-of-service levels, backup policies, or storage tiers. StorageClasses enable dynamic provisioning of PersistentVolumes.

**What problem it solves:**
Without StorageClasses, administrators must pre-create PVs. StorageClasses enable on-demand PV creation when a PVC requests storage, with parameters specific to the storage backend.

---

### 2. API Information

| Field           | Value          |
| --------------- | -------------- |
| **API Group**   | storage.k8s.io |
| **Version**     | v1             |
| **Kind**        | StorageClass   |
| **Scope**       | Cluster-scoped |
| **Short names** | `sc`           |

---

### 3. Full Production YAML Example

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: gp3-encrypted
  annotations:
    storageclass.kubernetes.io/is-default-class: "false"
provisioner: ebs.csi.aws.com
parameters:
  type: gp3
  iops: "3000"
  throughput: "125"
  encrypted: "true"
  kmsKeyId: "arn:aws:kms:us-east-1:123456789:key/abc-def"
  fsType: ext4
reclaimPolicy: Retain
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer
mountOptions:
  - noatime
  - nodiratime
allowedTopologies:
  - matchLabelExpressions:
      - key: topology.kubernetes.io/zone
        values:
          - us-east-1a
          - us-east-1b
          - us-east-1c
```

---

### 4. Complete Field Breakdown

- **provisioner** (string, required)
  - The CSI driver or in-tree provisioner that creates PVs. Examples: `ebs.csi.aws.com`, `pd.csi.storage.gke.io`, `kubernetes.io/aws-ebs` (legacy). Immutable.

- **parameters** (map[string]string, optional)
  - Provisioner-specific parameters. For AWS EBS CSI: `type` (gp2, gp3, io1, io2), `iops`, `throughput`, `encrypted`, `kmsKeyId`. For GCE PD: `type` (pd-standard, pd-ssd, pd-balanced), `replication-type`. Immutable.

- **reclaimPolicy** (string, optional, default `Delete`)
  - Applied to PVs created by this StorageClass. `Delete` destroys the storage when the PVC is deleted. `Retain` preserves it. Use `Retain` for production databases.

- **allowVolumeExpansion** (bool, optional, default false)
  - If true, PVCs using this StorageClass can be expanded by editing `spec.resources.requests.storage`. Not all provisioners support expansion.

- **volumeBindingMode** (string, optional, default `Immediate`)
  - `Immediate`: PV is provisioned and bound as soon as the PVC is created. The volume may be created in a zone that doesn't match where the Pod will be scheduled, causing scheduling failures.
  - `WaitForFirstConsumer`: PV provisioning is delayed until a Pod referencing the PVC is scheduled. The volume is created in the same zone as the scheduled node. Strongly recommended for topology-constrained storage.

- **mountOptions** ([]string, optional): Default mount options for PVs.
- **allowedTopologies** ([]TopologySelectorTerm, optional): Restricts which zones/regions volumes can be provisioned in.

---

### 5. Common Pitfalls

- **Immediate binding with topology constraints**: Creates volumes in the wrong zone. Always use `WaitForFirstConsumer` for cloud block storage.
- **Default StorageClass**: If `storageclass.kubernetes.io/is-default-class: "true"` is set on multiple StorageClasses, PVC creation fails with an error. Only one default.
- **Immutable parameters**: You cannot change `provisioner` or `parameters` after creation. Delete and recreate. Existing PVs are not affected.
- **Delete reclaimPolicy for production databases**: Data loss risk. Changing the StorageClass doesn't change existing PVs' reclaimPolicy. Patch existing PVs individually.

## ServiceAccount

### 1. Conceptual Overview

A ServiceAccount provides an identity for processes running in a Pod. It is used for authenticating to the Kubernetes API and optionally to external systems via workload identity federation.

**What problem it solves:**
Pods need an identity to interact with the Kubernetes API (or external services). ServiceAccounts, combined with RBAC, control what a Pod can do. They replace shared credentials with per-workload identity.

---

### 2. API Information

| Field           | Value          |
| --------------- | -------------- |
| **API Group**   | core (`""`)    |
| **Version**     | v1             |
| **Kind**        | ServiceAccount |
| **Scope**       | Namespaced     |
| **Short names** | `sa`           |

---

### 3. Full Production YAML Example

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: api-server-sa
  namespace: production
  labels:
    app.kubernetes.io/name: api-server
  annotations:
    eks.amazonaws.com/role-arn: "arn:aws:iam::123456789:role/api-server-role"
    iam.gke.io/gcp-service-account: "api-server@project.iam.gserviceaccount.com"
automountServiceAccountToken: false
imagePullSecrets:
  - name: registry-credentials
secrets: []
```

---

### 4. Key Fields

- **automountServiceAccountToken** (bool, default true): If false, no token is mounted into Pods using this SA. Can be overridden at Pod level. Set to false for Pods that don't need API access.
- **imagePullSecrets** ([]LocalObjectReference): Default pull secrets for Pods using this SA. Merged with Pod-level `imagePullSecrets`.
- **secrets** ([]ObjectReference): Legacy. Previously referenced auto-generated long-lived tokens. Since Kubernetes 1.24, long-lived tokens are no longer auto-created. Use projected service account tokens (bound, short-lived) instead.

**Projected ServiceAccount tokens:**
Modern Kubernetes mounts a short-lived, bound token via a projected volume. The token is automatically rotated by the kubelet (before it expires). It contains audience, expiration, and the ServiceAccount identity. This is more secure than legacy long-lived tokens.

**Cloud IAM integration:**

- **AWS EKS**: `eks.amazonaws.com/role-arn` annotation enables IRSA (IAM Roles for Service Accounts). The Pod receives temporary AWS credentials via an OIDC-based token exchange.
- **GKE**: `iam.gke.io/gcp-service-account` annotation enables Workload Identity. The Pod authenticates as a GCP service account.
- **AKS**: Azure Workload Identity uses annotations for federated credential exchange.

---

### 5. Key Commands

```bash
kubectl create serviceaccount api-server-sa -n production
kubectl get sa -n production
kubectl describe sa api-server-sa -n production
kubectl create token api-server-sa -n production --duration=1h
kubectl annotate sa api-server-sa -n production \
  eks.amazonaws.com/role-arn=arn:aws:iam::123456789:role/api-role
```

## Role and ClusterRole

### 1. Conceptual Overview

Roles and ClusterRoles define sets of permissions (verbs on resources). A Role is namespace-scoped; a ClusterRole is cluster-scoped.

**What problem it solves:**
RBAC authorization requires permission definitions. Roles define what actions are allowed on which resources within a namespace. ClusterRoles define permissions across the cluster or for cluster-scoped resources.

---

### 2. API Information

| Resource                             | Scope       | Short names |
| ------------------------------------ | ----------- | ----------- |
| Role                                 | Namespaced  | none        |
| ClusterRole                          | Cluster     | none        |
| API Group: rbac.authorization.k8s.io | Version: v1 |             |

---

### 3. Full Production YAML Examples

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: production
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "watch", "list"]
  - apiGroups: [""]
    resources: ["pods/log"]
    verbs: ["get"]
  - apiGroups: [""]
    resources: ["pods/exec"]
    verbs: ["create"]
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list"]
    resourceNames: ["api-server"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: node-viewer
  labels:
    rbac.authorization.k8s.io/aggregate-to-view: "true"
rules:
  - apiGroups: [""]
    resources: ["nodes"]
    verbs: ["get", "list", "watch"]
  - apiGroups: ["metrics.k8s.io"]
    resources: ["nodes"]
    verbs: ["get", "list"]
  - nonResourceURLs: ["/healthz", "/readyz"]
    verbs: ["get"]
```

---

### 4. Complete Field Breakdown

#### rules

- **apiGroups** ([]string): API groups. `""` for core API (pods, services). `"apps"` for deployments, etc. `"*"` matches all.
- **resources** ([]string): Resource types. `pods`, `deployments`, `secrets`, etc. Subresources: `pods/log`, `pods/exec`, `pods/portforward`, `deployments/scale`, `nodes/status`.
- **resourceNames** ([]string, optional): Restrict to specific named resources. Useful for limiting access to specific Secrets or ConfigMaps.
- **verbs** ([]string): Allowed operations. `get`, `list`, `watch`, `create`, `update`, `patch`, `delete`, `deletecollection`. `*` matches all.
- **nonResourceURLs** ([]string, ClusterRole only): Non-resource URL paths (e.g., `/healthz`, `/api`, `/metrics`). Only `get` verb applies.

**ClusterRole aggregation:**
ClusterRoles can aggregate rules from other ClusterRoles using `aggregationRule.clusterRoleSelectors`. The built-in `admin`, `edit`, `view` ClusterRoles use aggregation, so custom ClusterRoles labeled `rbac.authorization.k8s.io/aggregate-to-view: "true"` automatically have their rules added to the `view` ClusterRole.

---

### 5. CKA-Oriented Scenarios

**Scenario 1: Create a Role allowing Pod management**

```bash
kubectl create role pod-manager -n exam \
  --verb=get,list,watch,create,delete \
  --resource=pods
```

**Scenario 2: Create a ClusterRole for reading nodes**

```bash
kubectl create clusterrole node-reader \
  --verb=get,list,watch \
  --resource=nodes
```

## RoleBinding and ClusterRoleBinding

### 1. Conceptual Overview

RoleBindings and ClusterRoleBindings grant the permissions defined in a Role or ClusterRole to users, groups, or ServiceAccounts.

- **RoleBinding**: Grants permissions within a specific namespace. Can reference a Role (same namespace) or a ClusterRole (reuses cluster-wide role definition but limits scope to the namespace).
- **ClusterRoleBinding**: Grants permissions cluster-wide. References a ClusterRole.

---

### 2. Full Production YAML Examples

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: pod-reader-binding
  namespace: production
subjects:
  - kind: ServiceAccount
    name: api-server-sa
    namespace: production
  - kind: User
    name: developer@example.com
    apiGroup: rbac.authorization.k8s.io
  - kind: Group
    name: platform-engineers
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: node-viewer-binding
subjects:
  - kind: Group
    name: sre-team
    apiGroup: rbac.authorization.k8s.io
  - kind: ServiceAccount
    name: monitoring-sa
    namespace: monitoring
roleRef:
  kind: ClusterRole
  name: node-viewer
  apiGroup: rbac.authorization.k8s.io
```

---

### 3. Key Fields

- **subjects** ([]Subject): Who gets the permissions. `kind`: `User`, `Group`, `ServiceAccount`. For ServiceAccounts, `namespace` is required.
- **roleRef** (RoleRef): Which Role/ClusterRole to bind. **Immutable after creation.** To change the role, delete and recreate the binding.

---

### 4. CKA-Oriented Scenarios

```bash
# Create a RoleBinding
kubectl create rolebinding pod-reader-binding -n exam \
  --role=pod-reader \
  --serviceaccount=exam:my-sa

# Create a ClusterRoleBinding
kubectl create clusterrolebinding node-viewer-binding \
  --clusterrole=node-viewer \
  --group=sre-team

# Verify permissions
kubectl auth can-i get pods -n exam --as=system:serviceaccount:exam:my-sa
kubectl auth can-i list nodes --as=system:serviceaccount:monitoring:monitoring-sa
```

---

### 5. Common Pitfalls

- **roleRef immutability**: Cannot change the referenced Role/ClusterRole. Must delete and recreate the binding.
- **ServiceAccount namespace**: Must specify `namespace` for ServiceAccount subjects, or the binding doesn't match.
- **ClusterRoleBinding with Role**: Invalid. ClusterRoleBindings can only reference ClusterRoles, not Roles.
- **RoleBinding with ClusterRole**: Valid and useful. Grants the ClusterRole's permissions but only within the RoleBinding's namespace. Common pattern for reusing role definitions across namespaces.
- **Privilege escalation prevention**: Users cannot create RoleBindings granting more permissions than they themselves have. The API server's RBAC authorizer prevents this.

## SecurityContext and PodSecurityContext

### 1. Conceptual Overview

SecurityContext (container-level) and PodSecurityContext (Pod-level) define privilege and access control settings for Pods and containers.

---

### 2. PodSecurityContext (spec.securityContext)

```yaml
securityContext:
  runAsNonRoot: true
  runAsUser: 1000
  runAsGroup: 3000
  fsGroup: 2000
  fsGroupChangePolicy: OnRootMismatch
  supplementalGroups: [4000]
  seccompProfile:
    type: RuntimeDefault
  sysctls:
    - name: net.core.somaxconn
      value: "1024"
```

- **runAsUser/runAsGroup**: Default UID/GID for all containers.
- **fsGroup**: GID applied to all volumes. Files created use this GID. The kubelet `chown`s volume files to this GID at mount time. `fsGroupChangePolicy: OnRootMismatch` only changes ownership if the root of the volume doesn't match, avoiding slow recursive chown on large volumes.
- **supplementalGroups**: Additional GIDs for container processes.
- **seccompProfile**: Seccomp filtering profile. `RuntimeDefault` uses the runtime's default (recommended). `Localhost` uses a custom profile.
- **sysctls**: Kernel parameters. `safe` sysctls (e.g., `net.core.somaxconn`) are per-namespace. `unsafe` sysctls require node-level configuration to allow.

---

### 3. Container SecurityContext (spec.containers[].securityContext)

```yaml
securityContext:
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true
  runAsNonRoot: true
  runAsUser: 1000
  runAsGroup: 3000
  privileged: false
  capabilities:
    drop: ["ALL"]
    add: ["NET_BIND_SERVICE"]
  seccompProfile:
    type: RuntimeDefault
  procMount: Default
```

Container-level settings override Pod-level where applicable.

---

### 4. PodSecurityStandards (PSS)

PodSecurityStandards are enforced by the PodSecurity admission controller (replacing PodSecurityPolicies which are removed in 1.25):

- **Privileged**: Unrestricted. No enforcement.
- **Baseline**: Minimally restrictive. Prevents known privilege escalations. Allows most container configurations.
- **Restricted**: Heavily restricted. Requires: `runAsNonRoot: true`, `allowPrivilegeEscalation: false`, `drop: ALL`, seccomp RuntimeDefault, no hostPath, no hostNetwork, no privileged.

Applied via namespace labels:

```bash
kubectl label namespace production \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/audit=restricted \
  pod-security.kubernetes.io/warn=restricted
```

## ResourceQuota

### 1. Conceptual Overview

ResourceQuota limits the total resource consumption in a namespace. It prevents a single namespace from consuming all cluster resources.

---

### 2. Full Production YAML Example

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: compute-quota
  namespace: production
spec:
  hard:
    requests.cpu: "100"
    requests.memory: 200Gi
    limits.cpu: "200"
    limits.memory: 400Gi
    requests.ephemeral-storage: 500Gi
    limits.ephemeral-storage: 1Ti
    pods: "200"
    count/deployments.apps: "50"
    count/services: "30"
    count/secrets: "100"
    count/configmaps: "100"
    persistentvolumeclaims: "50"
    requests.storage: 1Ti
    services.loadbalancers: "5"
    services.nodeports: "10"
  scopeSelector:
    matchExpressions:
      - scopeName: PriorityClass
        operator: In
        values:
          - high-priority
```

---

### 3. Key Fields

- **hard**: Resource limits. Categories:
  - Compute: `requests.cpu`, `limits.cpu`, `requests.memory`, `limits.memory`
  - Storage: `requests.storage`, `persistentvolumeclaims`, `<storageclass>.storageclass.storage.k8s.io/requests.storage`
  - Object count: `pods`, `count/<resource>`, `services`, `secrets`, `configmaps`
  - Service types: `services.loadbalancers`, `services.nodeports`
- **scopeSelector**: Apply quota only to Pods matching a scope (e.g., specific PriorityClass, BestEffort/NotBestEffort QoS).
- **scopes**: Predefined scope filters: `Terminating`, `NotTerminating`, `BestEffort`, `NotBestEffort`, `PriorityClass`, `CrossNamespacePodAffinity`.

When a ResourceQuota is present, all Pods must specify resource requests/limits for the resources being quota'd, unless a LimitRange provides defaults.

---

### 4. Key Commands

```bash
kubectl create quota compute-quota -n production \
  --hard=requests.cpu=100,requests.memory=200Gi,pods=200
kubectl describe resourcequota compute-quota -n production
kubectl get resourcequota -n production -o yaml
```

## LimitRange

### 1. Conceptual Overview

A LimitRange sets default, minimum, and maximum resource constraints for Pods, containers, and PVCs within a namespace.

---

### 2. Full Production YAML Example

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: default-limits
  namespace: production
spec:
  limits:
    - type: Container
      default:
        cpu: 500m
        memory: 256Mi
      defaultRequest:
        cpu: 100m
        memory: 128Mi
      min:
        cpu: 50m
        memory: 64Mi
      max:
        cpu: "4"
        memory: 8Gi
      maxLimitRequestRatio:
        cpu: "10"
        memory: "4"
    - type: Pod
      max:
        cpu: "16"
        memory: 32Gi
    - type: PersistentVolumeClaim
      min:
        storage: 1Gi
      max:
        storage: 500Gi
```

---

### 3. Key Fields

- **type**: `Container`, `Pod`, `PersistentVolumeClaim`.
- **default**: Default limits applied to containers without limits. Only for `Container` type.
- **defaultRequest**: Default requests applied to containers without requests. Only for `Container` type.
- **min/max**: Minimum and maximum allowed values. Pods exceeding these are rejected.
- **maxLimitRequestRatio**: Maximum ratio of limit to request. `cpu: "10"` means limits can be at most 10x requests. Prevents burstable workloads from hogging resources.

LimitRanges are enforced by an admission controller. They apply at creation/update time, not retroactively. Existing Pods that violate a new LimitRange continue running.

## Namespace

### 1. Conceptual Overview

A Namespace provides a scope for resource names and a boundary for RBAC, ResourceQuota, NetworkPolicy, and LimitRange enforcement. Namespaces are the primary isolation mechanism in Kubernetes.

---

| **Kind**        | Namespace      |

### 3. Key Fields

apiVersion: v1

## Node

### 1. Conceptual Overview

A Node is a worker machine in Kubernetes. It runs the kubelet, container runtime, and kube-proxy. Nodes are managed by the control plane but represent actual infrastructure (VMs, bare metal).

### Taints and Tolerations

---

### 1. Conceptual Overview

Taints are applied to Nodes to repel Pods. Tolerations are applied to Pods to allow scheduling on tainted nodes. Together they control which Pods can run on which nodes.

---

### 2. Taint Structure

```bash
kubectl taint node worker-3 key=value:effect
```

- **key**: Taint key (e.g., `dedicated`, `special-hardware`).
- **value**: Optional value.
- **effect**: `NoSchedule` (prevent scheduling new Pods), `PreferNoSchedule` (prefer not to schedule but allow if necessary), `NoExecute` (evict existing Pods that don't tolerate).

---

### 3. Toleration Structure

```yaml
tolerations:
  - key: dedicated
    operator: Equal
    value: gpu
    effect: NoSchedule
  - key: node.kubernetes.io/not-ready
    operator: Exists
    effect: NoExecute
    tolerationSeconds: 300
  - operator: Exists # Tolerates ALL taints
```

- **operator**: `Equal` (key, value, and effect must match) or `Exists` (key and effect must match, any value).
- **tolerationSeconds**: For `NoExecute`, how long the Pod stays after the taint is applied. If omitted, the Pod stays indefinitely.

---

### 4. Common Taints

- `node.kubernetes.io/not-ready`: Applied when node condition Ready is False.
- `node.kubernetes.io/unreachable`: Applied when node is unreachable.
- `node.kubernetes.io/disk-pressure`: Applied under disk pressure.
- `node.kubernetes.io/memory-pressure`: Applied under memory pressure.
- `node.kubernetes.io/pid-pressure`: Applied under PID pressure.
- `node.kubernetes.io/unschedulable`: Applied when node is cordoned.
- `node-role.kubernetes.io/control-plane:NoSchedule`: Prevents workloads on control plane nodes.

---

### Affinity and Anti-Affinity

---

### 1. Conceptual Overview

Affinity rules provide more expressive scheduling constraints than `nodeSelector` and taints/tolerations. They support soft/hard constraints and can target nodes (nodeAffinity) or other Pods (podAffinity/podAntiAffinity).

---

### 2. Node Affinity

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - key: topology.kubernetes.io/zone
              operator: In
              values: ["us-east-1a", "us-east-1b"]
            - key: node.kubernetes.io/instance-type
              operator: In
              values: ["m5.xlarge", "m5.2xlarge"]
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        preference:
          matchExpressions:
            - key: node-type
              operator: In
              values: ["compute-optimized"]
      - weight: 50
        preference:
          matchExpressions:
            - key: spot
              operator: DoesNotExist
```

- `required`: Hard constraint. Pod is NOT scheduled if no node matches.
- `preferred`: Soft constraint with weight (1-100). Scheduler prefers matching nodes.
- `IgnoredDuringExecution`: Existing Pods are NOT evicted if node labels change.
- Operators: `In`, `NotIn`, `Exists`, `DoesNotExist`, `Gt`, `Lt`.

---

### 3. Pod Affinity / Anti-Affinity

```yaml
affinity:
  podAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchExpressions:
            - key: app
              operator: In
              values: ["cache"]
        topologyKey: kubernetes.io/hostname
        namespaces: ["production"]
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchExpressions:
            - key: app
              operator: In
              values: ["api-server"]
        topologyKey: kubernetes.io/hostname
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchExpressions:
              - key: app
                operator: In
                values: ["api-server"]
          topologyKey: topology.kubernetes.io/zone
```

- **topologyKey**: The node label used to define the topology domain. `kubernetes.io/hostname` = per-node. `topology.kubernetes.io/zone` = per-zone.
- **podAffinity**: Schedule near matching Pods (same node, same zone).
- **podAntiAffinity**: Schedule away from matching Pods. Critical for HA: spread replicas across failure domains.
- **namespaces**: Restrict which namespaces to search for matching Pods.
- **namespaceSelector**: Label-based namespace filtering.

---

### 4. Performance Note

Pod affinity/anti-affinity is computationally expensive. For large clusters (1000+ nodes), `required` anti-affinity with `topologyKey: kubernetes.io/hostname` causes the scheduler to evaluate every node. Consider topology spread constraints as a more scalable alternative.

---

## PriorityClass

### 1. Conceptual Overview

A PriorityClass defines a priority for Pods. Higher priority Pods can preempt lower priority Pods when cluster resources are scarce.

---

### 2. Full Production YAML Example

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority
value: 1000000
globalDefault: false
preemptionPolicy: PreemptLowerPriority
description: "High priority for production workloads"
---
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: low-priority
value: 100
globalDefault: false
preemptionPolicy: Never
description: "Low priority for batch workloads, no preemption"
```

---

### 3. Key Fields

- **value** (int32, required): Priority value. Higher = more important. Range: -2147483648 to 1000000000. Values above 1000000000 are reserved for system components (`system-cluster-critical`: 2000000000, `system-node-critical`: 2000001000).
- **globalDefault** (bool, optional, default false): If true, this is the default PriorityClass for Pods without `priorityClassName`. Only one PriorityClass should have `globalDefault: true`.
- **preemptionPolicy** (string, optional, default `PreemptLowerPriority`):
  - `PreemptLowerPriority`: The scheduler can evict lower priority Pods to make room.
  - `Never`: The Pod waits in the scheduling queue without preempting others. Used for batch workloads that shouldn't disrupt production.
- **description** (string, optional): Human-readable description.

---

### 4. Preemption Mechanics

When a high-priority Pod can't be scheduled:

1. The scheduler identifies nodes where the Pod would fit if lower-priority Pods were removed.
2. It selects the node with the least disruption (fewest evictions, lowest total priority of victims).
3. It nominates the node (sets `status.nominatedNodeName` on the Pod).
4. It sends graceful deletion to victim Pods (they get their `terminationGracePeriodSeconds`).
5. Once victims are gone, the high-priority Pod is scheduled.

PodDisruptionBudgets (PDBs) are respected during preemption. If evicting a Pod would violate a PDB, the scheduler avoids that node.

---

### 5. Common Pitfalls

- **Preemption cascades**: A high-priority Pod preempts a medium-priority Pod, which triggers its controller to create a replacement, which preempts a low-priority Pod, creating a cascade. Design priority tiers carefully.
- **System priority values**: Don't use values above 1000000000 for user workloads. These are reserved for `system-cluster-critical` and `system-node-critical` components.
- **No PriorityClass = priority 0**: Pods without a PriorityClass get priority 0. They can be preempted by any Pod with a positive priority.
- **PDB interactions**: Preemption respects PDBs. If all potential victims are protected by PDBs, the high-priority Pod stays Pending.
