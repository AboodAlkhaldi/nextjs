## 1. Identity & Multi-Account Governance

This domain is the foundation of every well-architected AWS deployment. At the Professional level, identity is not about "how to create a user" — it is about cross-account trust chains, policy evaluation logic, permission boundaries, and organizational governance at scale.


### 1.1 AWS Identity and Access Management (IAM)

#### Core Definition

IAM is the **global** authorization and authentication control plane for all AWS API calls. Every single AWS API request — whether from the console, CLI, SDK, or another AWS service — is evaluated by the IAM policy engine.

- **Scope**: Global. IAM entities (users, roles, policies) are not region-scoped. However, some IAM-related features (like Access Analyzer) operate regionally.
- **Control Plane vs Data Plane**: IAM itself IS the control plane for authorization. It has no data plane. The IAM control plane is hosted in `us-east-1` with global replication. During a `us-east-1` outage, existing cached credentials continue to work (data plane continuity), but you cannot create or modify IAM entities (control plane disruption).
- **SLA**: IAM does not have a standalone SLA. It is a dependency of every other service. AWS does not publish a separate IAM availability commitment.
- **Pricing**: Free. There is no charge for IAM users, groups, roles, or policies. You pay for the services those identities access.
- **Architectural Abstraction**: Centralized policy evaluation engine with eventually consistent replication across all AWS regions.

#### Core Capabilities

**Policy Evaluation Logic** (critical for SAP-C02):
The IAM policy evaluation order is:
1. **Explicit Deny** — if any policy says Deny, the request is denied. Period.
2. **Organizations SCP** — if the account is in an Organization, SCPs are evaluated. SCPs do not grant permissions; they set the maximum permission boundary.
3. **Resource-based policies** — evaluated next. A resource-based policy that grants access to a principal in the SAME account can grant access even without an identity-based policy. For CROSS-account, both the resource policy AND the identity policy must allow.
4. **Permission Boundaries** — if set, the effective permission is the intersection of the identity policy and the permission boundary.
5. **Session Policies** — for federated/assumed-role sessions, the effective permission is the intersection of the role policy and the session policy.
6. **Identity-based policies** — the actual Allow statements on the user/role.

Exception: Resource-based policies that specify a principal (not `*`) bypass permission boundaries for same-account access.

**Scaling Model**:
- Up to 5,000 IAM users per account (hard limit, cannot be increased).
- Up to 10,000 managed policies per account.
- Up to 10 managed policies attached per user/role/group.
- Policy document size: 6,144 characters (managed), 2,048 characters (inline).
- Role trust policy: 2,048 characters (can be increased to 4,096).
- Path length for role session: 64 characters.
- Tags per IAM entity: 50.

**Security Integration**:
- MFA: Virtual, U2F, hardware TOTP.
- ABAC (Attribute-Based Access Control): Use tags on principals and resources to create fine-grained policies without enumerating every resource ARN.
- Condition keys: `aws:SourceIp`, `aws:SourceVpc`, `aws:SourceVpce`, `aws:PrincipalOrgID`, `aws:PrincipalTag/*`, `aws:RequestedRegion`, `aws:CalledVia`, etc.
- `aws:PrincipalOrgID` is critical for restricting access to principals within your AWS Organization without listing every account ID.

#### Architectural Design Patterns

**Multi-Account Role Chaining**: Account A user assumes role in Account B, which then assumes role in Account C. Maximum session duration is 1 hour when role chaining (cannot be extended). This is a hard constraint that affects automation pipelines.

**ABAC at Scale**: Instead of maintaining separate policies per team/project, tag IAM roles with `team=data-engineering` and resources with `team=data-engineering`, then write a single policy with `"Condition": {"StringEquals": {"aws:PrincipalTag/team": "${aws:ResourceTag/team}"}}`. Reduces policy management overhead from O(n) to O(1).

**Break-Glass Access**: Create a highly privileged role with MFA requirement and CloudTrail alert. Do not create permanent admin users. Use permission boundaries to prevent privilege escalation — even an admin cannot create a role that exceeds their own permission boundary.

**Service-Linked Roles**: Some AWS services require service-linked roles (SLRs). These cannot be modified. They are created automatically or via `iam:CreateServiceLinkedRole`. SLRs are critical in Organizations because SCPs cannot restrict service-linked role actions performed by the service itself.

#### When to Use

- Always. IAM is not optional. Every architecture decision involves IAM.
- Use IAM roles (not users) for all machine-to-machine authentication.
- Use IAM roles for cross-account access instead of sharing credentials.
- Use ABAC when you have dynamic, tag-driven environments.
- Use permission boundaries when delegating admin capabilities to teams.

#### When NOT to Use

- Do NOT use IAM users for application authentication. Use Cognito or IAM Identity Center.
- Do NOT use IAM for managing more than 5,000 human identities. Use IAM Identity Center with an external IdP.
- Do NOT use long-lived access keys. Use IAM roles with temporary credentials via STS.
- Do NOT use inline policies for anything beyond one-off exceptions. They are not reusable and hard to audit.

#### Trade-Offs vs Similar Services

| Aspect | IAM Users | IAM Identity Center | Cognito |
|---|---|---|---|
| Use case | Machine identities, legacy | Human workforce SSO | Customer-facing apps |
| Scale | 5,000 per account | Unlimited (IdP-backed) | Millions of users |
| Federation | Manual STS calls | Built-in SAML/OIDC | Built-in SAML/OIDC/Social |
| MFA | Per-user config | Centralized | Per-user pool config |
| Multi-account | Role chaining | Native multi-account | Single pool, multi-app |

#### Failure & Edge Case Behavior

- **us-east-1 outage**: Cannot create/modify IAM entities. Existing credentials and cached policies continue to work. STS `AssumeRole` calls may fail if they route to us-east-1. Regional STS endpoints (`sts.us-west-2.amazonaws.com`) mitigate this — ALWAYS use regional STS endpoints.
- **Eventual consistency**: IAM changes propagate globally but with eventual consistency. A policy change may take seconds to propagate. In rare cases, a newly created role may not be assumable for a few seconds. Mitigation: build retry logic.
- **Throttling**: IAM API calls are throttled. `GetUser`, `AssumeRole`, etc. have per-account rate limits. High-volume automation can hit these. Use exponential backoff.
- **Policy size exceeded**: If you exceed policy size limits, requests fail with `MalformedPolicyDocument`. This often happens with complex ABAC policies. Mitigation: use managed policies, break into multiple policies, or use policy variables to reduce size.

#### Security & Compliance Implications

- **Encryption**: IAM does not encrypt data at rest in a customer-visible way — it is an AWS-managed service. All API calls are over TLS.
- **CloudTrail**: All IAM API calls are logged in CloudTrail. `AssumeRole` events are logged in both the source and destination account.
- **Access Analyzer**: IAM Access Analyzer identifies resources shared with external principals. It operates regionally — you must enable it in every region you use.
- **Credential Report**: CSV export of all IAM users and their credential status. Useful for compliance audits. Generated on-demand, cached for 4 hours.
- **Data Residency**: IAM metadata is stored globally by AWS. You cannot restrict IAM data to a specific region.

#### Cost Model & Optimization

- IAM is free. No cost traps.
- However, misconfigured IAM (overly broad `*` policies) leads to security incidents, which are expensive.
- STS `AssumeRole` calls are free but throttled.

#### Advanced Professional-Level Exam Traps

1. **Role chaining limits session to 1 hour**. If a question describes a pipeline that assumes Role A → Role B, the maximum session is 1 hour regardless of the roles' configured max session duration.
2. **SCPs do not affect the management account**. This is tested repeatedly. The management account is EXEMPT from all SCPs.
3. **Resource-based policies bypass SCPs for same-account access** — but NOT for cross-account. A resource policy on an S3 bucket in Account B granting access to a role in Account A is still subject to Account A's SCPs.
4. **Permission boundaries do not grant permissions**. They restrict. A permission boundary of `s3:*` and an identity policy of `ec2:*` results in NO permissions (empty intersection).
5. **`aws:PrincipalOrgID` vs `aws:PrincipalOrgPaths`**: `OrgID` matches any account in the org. `OrgPaths` allows OU-level filtering. Questions may test whether you can restrict to a specific OU.
6. **Cross-account AssumeRole**: The trust policy must allow the principal, AND the principal's identity policy must allow `sts:AssumeRole` on the target role. Both sides must agree UNLESS the trust policy specifies the root account, in which case account-level delegation applies.


### 1.2 AWS Organizations

#### Core Definition

AWS Organizations is a **global** account management service that provides centralized governance over multiple AWS accounts. It is not merely "account grouping" — it is the foundational service for implementing AWS Landing Zones, policy guardrails, and consolidated billing.

- **Scope**: Global. The management account is the root of the organization.
- **Control Plane**: Global, hosted alongside IAM infrastructure. During a control plane outage, existing SCPs continue to be enforced (cached), but you cannot modify the organization structure.
- **Data Plane**: SCPs are evaluated as part of IAM policy evaluation, which is distributed.
- **Pricing**: Free for the service itself. You pay for the resources in each account.
- **SLA**: No standalone SLA.
- **Architectural Abstraction**: Hierarchical tree of accounts with policy inheritance.

#### Core Capabilities

**Organizational Units (OUs)**:
- Accounts are organized into a tree structure with OUs.
- OUs can be nested up to 5 levels deep.
- An account can belong to exactly ONE OU at a time.
- Policies (SCPs, Tag Policies, Backup Policies, AI Services Opt-out Policies) inherit down the tree.
- Maximum 1,000 accounts per organization (soft limit, can be increased).

**Service Control Policies (SCPs)**:
- SCPs define the MAXIMUM permissions for accounts in the organization.
- SCPs do NOT grant permissions. They are filters.
- SCPs do not affect the management account. EVER.
- SCPs do not affect service-linked roles.
- SCP evaluation: Deny takes precedence. Then, the effective permission is the intersection of all SCPs from the root down to the OU containing the account.
- SCP document size: 5,120 characters. This is tight. Complex deny lists can exceed this.
- Maximum 5 SCPs per OU/account attachment point.
- Strategy: Use a deny-list approach (start with `FullAWSAccess` SCP, then add deny SCPs for specific actions). An allow-list approach (remove `FullAWSAccess` and explicitly allow only needed actions) is more secure but harder to manage and the 5,120 character limit becomes painful.

**Delegated Administrator**:
- Instead of running services (like GuardDuty, Security Hub, Config) from the management account, designate a member account as the delegated administrator.
- Best practice: the management account should have minimal workloads. Use delegated administrators for security tooling.
- Not all services support delegated administrators.

**Consolidated Billing**:
- All accounts in the organization are billed through the management account.
- Volume discounts (S3, EC2 data transfer) are aggregated across accounts.
- Reserved Instances and Savings Plans are shared across accounts by default (can be disabled).
- Credit sharing: AWS credits applied to one account are shared org-wide (can be disabled).

**AWS CloudFormation StackSets**:
- Deploy CloudFormation stacks across multiple accounts and regions in the organization.
- Uses Organizations-trusted access (no need to create cross-account roles manually).
- Critical for deploying baseline configurations (VPC, logging, security tooling).

#### Architectural Design Patterns

**Multi-Account Landing Zone**:
```
Root
├── Security OU
│   ├── Log Archive Account (centralized CloudTrail, Config logs)
│   ├── Security Tooling Account (GuardDuty, Security Hub delegated admin)
│   └── Audit Account
├── Infrastructure OU
│   ├── Network Hub Account (Transit Gateway, shared VPC)
│   └── Shared Services Account (AD, CI/CD)
├── Workload OU
│   ├── Production OU
│   │   ├── App A Production Account
│   │   └── App B Production Account
│   └── Non-Production OU
│       ├── App A Dev Account
│       └── App B Staging Account
├── Sandbox OU
│   └── Developer Sandbox Accounts
└── Suspended OU (for decommissioned accounts)
```

**SCP Guardrails**:
- Deny `organizations:LeaveOrganization` on all accounts.
- Deny `cloudtrail:StopLogging` and `cloudtrail:DeleteTrail`.
- Deny all access in regions you don't use: `"Condition": {"StringNotEquals": {"aws:RequestedRegion": ["us-east-1", "eu-west-1"]}}`.
- Deny disabling EBS default encryption.
- Deny creating IAM users with console access (force SSO).
- Deny modifying VPC Flow Logs.

**Account Vending Machine**: Use Control Tower Account Factory, Service Catalog, or custom automation (Lambda + Organizations API) to automate account creation with baseline configurations applied via StackSets.

#### When to Use

- Always, for any organization with more than one AWS account.
- Required for implementing least-privilege at the account level.
- Required for consolidated billing and cost allocation.
- Required for deploying SCPs, tag policies, and backup policies.
- Essential for meeting compliance requirements (separate blast radius per workload, data isolation).

#### When NOT to Use

- There is no scenario where you would NOT use Organizations if you have multiple accounts.
- Do NOT run workloads in the management account. It is exempt from SCPs and should be tightly controlled.

#### Failure & Edge Case Behavior

- **Management account compromise**: Most critical failure scenario. The management account controls the entire org. It can remove accounts, modify SCPs, dissolve the org. Mitigation: minimal access, MFA everywhere, no workloads, heavy CloudTrail monitoring.
- **SCP lockout**: If you remove `FullAWSAccess` SCP from the root without attaching a replacement, all member accounts lose ALL permissions. Recovery requires the management account to re-attach the SCP. The management account itself is not affected.
- **Account limit reached**: Default 10 accounts, soft limit to 1,000+. If you hit the limit, account creation fails. Plan ahead and request increases.
- **Delegated admin removal**: If you remove a delegated administrator account, the service may lose its cross-account configuration. Plan migration carefully.

#### Security & Compliance Implications

- **CloudTrail**: Organization-level trail captures all API activity across all accounts. Logs go to the Log Archive account. Member accounts cannot delete or modify the organization trail.
- **Tag Policies**: Enforce standardized tagging (e.g., `CostCenter`, `Environment`). Non-compliant tags are reported but NOT blocked (tag policies are not enforcing by default — only certain services respect enforcement).
- **Backup Policies**: Define backup schedules at the OU level. Member accounts inherit and cannot override.
- **AI Services Opt-out Policies**: Prevent AWS from using your data for AI training.

#### Cost Model & Optimization

- Organizations is free.
- Consolidated billing provides volume discounts and RI/SP sharing.
- Cost Allocation Tags: Enable at the management account level. Tags propagate to Cost and Usage Reports.
- Linked account isolation: If you do NOT want RI/SP sharing across accounts, disable it in the management account billing preferences.

#### Advanced Professional-Level Exam Traps

1. **SCPs do not affect the management account**. Repeated because it is tested constantly.
2. **SCPs do not grant permissions**. If a question says "attach an SCP that allows S3 access," that alone does NOT grant access. The identity policy must also allow it.
3. **Moving an account between OUs changes its effective SCPs immediately**. There is no propagation delay for SCP evaluation at the account level.
4. **You cannot nest OUs more than 5 levels deep**. Architecture questions may test this.
5. **Service-linked roles are not affected by SCPs**. If a question asks how to prevent a service from acting, SCPs on the service's SLR actions won't work.
6. **Consolidated billing aggregates data transfer**. If two accounts in the same AZ communicate via private IP and are in the same org, some data transfer charges may be reduced. But cross-AZ and cross-region charges still apply.


### 1.3 AWS IAM Identity Center (formerly AWS SSO)

#### Core Definition

IAM Identity Center is the **recommended** service for managing workforce (human) access to multiple AWS accounts and business applications. It replaces the manual process of creating IAM users in every account.

- **Scope**: Regional deployment but operates across the organization. Deployed in a single home region.
- **Control Plane**: Regional (the home region you choose during setup).
- **Data Plane**: Authentication tokens are validated regionally.
- **Pricing**: Free for AWS account access. SCIM provisioning is free. Some external IdP integrations are free.
- **SLA**: Covered under the general AWS SLA for the region.
- **Managed vs Customer-Managed**: Fully managed. AWS handles the identity store, unless you connect an external IdP.
- **Architectural Abstraction**: SAML 2.0 federation hub with a built-in identity store or connection to external IdPs (Okta, Azure AD, Ping Identity, etc.).

#### Core Capabilities

**Identity Sources** (choose ONE):
1. **IAM Identity Center directory**: Built-in user store. Good for small orgs or testing.
2. **Active Directory**: Via AWS Managed Microsoft AD or AD Connector. Supports on-premises AD via AD Connector (no trust relationship needed) or AWS Managed AD (two-way trust).
3. **External IdP**: SAML 2.0 or SCIM 2.0. Connect Okta, Azure AD, etc. SCIM provides automatic user/group sync.

You can only have ONE identity source at a time. Changing it disrupts all existing permission sets and assignments.

**Permission Sets**:
- Define what a user/group can do in an AWS account.
- Under the hood, a permission set creates an IAM role in each assigned account.
- Maximum session duration: 1–12 hours (configurable per permission set).
- You can attach up to 10 AWS managed policies + 1 customer managed policy + 1 inline policy per permission set.
- Permission sets are deployed to accounts. The IAM roles created have the naming convention `AWSReservedSSO_<PermissionSetName>_<random>`.

**Multi-Account Permissions**:
- Assign permission sets to users/groups for specific accounts.
- Users see a portal listing their account assignments.
- Supports attribute-based access control (ABAC) — pass user attributes from the IdP as session tags.

**Application Assignments**:
- SSO into business applications (Salesforce, Slack, custom SAML apps).
- Pre-integrated application catalog.

#### Architectural Design Patterns

**Centralized Access Management for Landing Zones**: All human access goes through IAM Identity Center. No IAM users are created in member accounts. SCPs deny `iam:CreateUser` and `iam:CreateLoginProfile` in all accounts.

**ABAC with IdP Attributes**: User in Okta has attribute `department=engineering`. This is passed as a session tag via ABAC configuration. Permission sets use `"Condition": {"StringEquals": {"aws:PrincipalTag/department": "engineering"}}` to scope access dynamically without per-team permission sets.

**Emergency Access Pattern**: Create a break-glass IAM user in the management account (outside SSO) with MFA. This handles scenarios where the IdP is unavailable or IAM Identity Center has an outage.

#### When to Use

- For ALL human access to AWS accounts in an organization.
- When you need centralized, auditable access management.
- When integrating with corporate directories (AD, Okta, Azure AD).
- When you need temporary, time-limited credentials (no long-lived access keys).

#### When NOT to Use

- Not for machine-to-machine access. Use IAM roles.
- Not for customer-facing identity. Use Cognito.
- Not for accounts outside your Organization (it requires Organizations).
- Cannot use multiple IdP sources simultaneously.

#### Trade-Offs vs Similar Services

| Aspect | IAM Identity Center | Custom SAML Federation | IAM Users |
|---|---|---|---|
| Setup complexity | Low | High (manual STS, AssumeRoleWithSAML) | Low |
| Scalability | High (IdP-backed) | High | 5,000 per account |
| Multi-account | Native | Custom per account | Manual per account |
| Session duration | Up to 12 hours | Up to 12 hours | Permanent credentials |
| Auditability | Centralized | Custom CloudTrail parsing | Per-account |
| MFA | Centralized/IdP-managed | IdP-managed | Per-user |

#### Failure & Edge Case Behavior

- **Home region outage**: If the home region goes down, IAM Identity Center is unavailable. Users cannot authenticate. Existing sessions continue until their token expires. Mitigation: break-glass IAM users in the management account.
- **IdP outage**: If your external IdP (Okta, Azure AD) is down, users cannot authenticate. Mitigation: break-glass accounts.
- **SCIM sync failure**: If SCIM sync from external IdP fails, new users/group changes are not reflected. Existing access continues. Monitor SCIM sync status.
- **Permission set provisioning failure**: If CloudFormation fails to create the IAM role in a target account (e.g., role name conflict), the permission set shows a failed status for that account.

#### Security & Compliance Implications

- **CloudTrail**: All SSO authentication events are logged. `Authenticate`, `Federate`, and `AssumeRole` events.
- **MFA**: Can enforce MFA at the IAM Identity Center level (if using built-in directory) or rely on the external IdP's MFA.
- **Access to management account**: Be extremely careful. Limit who has permission sets assigned to the management account.
- **Session duration**: Longer sessions are more convenient but increase the blast radius of a compromised session.

#### Cost Model & Optimization

- Free. No charges for IAM Identity Center.
- Cost is in the IdP licensing (Okta, Azure AD P1/P2, etc.) — that's outside AWS.

#### Advanced Professional-Level Exam Traps

1. **IAM Identity Center requires AWS Organizations**. It cannot be used with standalone accounts.
2. **Only one identity source at a time**. Switching from AD to external IdP removes all existing user/group assignments. This is destructive.
3. **Home region is set during first configuration and cannot be changed** without disabling and re-enabling the service.
4. **Permission sets create IAM roles**. If a question asks about the mechanism, it is SAML federation creating IAM roles in each account.
5. **ABAC requires SAML attribute mapping**. The IdP must send the right attributes, and the ABAC configuration must map them to session tags.


### 1.4 Amazon Cognito

#### Core Definition

Amazon Cognito provides **customer-facing** identity management. It handles sign-up, sign-in, and access control for web and mobile applications. It is not for workforce identity — that is IAM Identity Center.

Two components:
1. **User Pools**: User directory with sign-up/sign-in. Returns JWT tokens (ID token, access token, refresh token). Supports SAML, OIDC, and social IdPs (Google, Facebook, Apple, Amazon).
2. **Identity Pools** (Federated Identities): Exchange tokens (from User Pools, social IdPs, SAML, or custom) for temporary AWS credentials (STS). Maps users to IAM roles.

- **Scope**: Regional.
- **Control Plane**: Regional.
- **Data Plane**: Regional.
- **Pricing**: User Pools: first 50,000 MAUs free (Essentials tier), then $0.015–$0.0055/MAU depending on tier and volume. Identity Pools: Pay-per-authentication (based on usage).
- **SLA**: 99.9% monthly uptime.
- **Architectural Abstraction**: Managed identity provider with OAuth 2.0 / OIDC endpoints.

#### Core Capabilities

**User Pools**:
- Custom user attributes, required attributes, attribute verification (email, phone).
- Password policies, MFA (SMS, TOTP, email).
- Lambda triggers at every lifecycle event: pre-sign-up, post-confirmation, pre-authentication, post-authentication, pre-token-generation (customize JWT claims), custom message, user migration (migrate users on-the-fly from legacy systems), define/create/verify auth challenge (custom auth flows).
- Hosted UI: Pre-built sign-in/sign-up pages. Customizable with CSS.
- Advanced security features: adaptive MFA, compromised credential detection, risk-based authentication.
- User Pool groups: Map to IAM roles for Identity Pool integration. Group precedence determines which IAM role is assigned.
- Quotas: 50 user pools per region (soft limit). 40,000 user read/write operations per second (soft limit).

**Identity Pools**:
- Authenticated identities: Users who have signed in via a User Pool or external IdP.
- Unauthenticated identities: Guest access with limited IAM permissions.
- Role mapping: Default role, rules-based (match token claims to roles), or token-based (use Cognito group's associated role).
- Basic (classic) flow vs Enhanced (simplified) flow: Enhanced flow calls STS directly from Cognito; classic flow requires a `GetOpenIdToken` + `AssumeRoleWithWebIdentity` two-step.

#### Architectural Design Patterns

**Serverless Web App Authentication**: CloudFront → S3 static site → Cognito User Pool for auth → API Gateway with Cognito Authorizer → Lambda → DynamoDB.

**Multi-Tenant SaaS Isolation**: Use Cognito custom attributes for `tenant_id`. Pre-token-generation Lambda injects `tenant_id` into the access token. API Gateway extracts the claim and routes/filters accordingly. Identity Pool maps tenant groups to IAM roles with scoped-down policies for DynamoDB leading key isolation (`dynamodb:LeadingKeys`).

**Social Identity Federation**: User signs in with Google/Facebook → Cognito User Pool → Identity Pool → temporary AWS credentials → S3 access scoped to user prefix (`s3:prefix/${cognito-identity.amazonaws.com:sub}/*`).

**User Migration**: Legacy database auth → Cognito user migration Lambda trigger → on first sign-in, Lambda authenticates against legacy DB, creates user in Cognito, returns success. Seamless migration without forcing password resets (if passwords can be verified).

#### When to Use

- Customer-facing web/mobile applications.
- When you need OAuth 2.0 / OIDC token-based authentication.
- When you need social sign-in (Google, Facebook, Apple).
- When you need to exchange user identity for temporary AWS credentials.
- When you need serverless, managed user directory.

#### When NOT to Use

- Not for workforce/employee access to AWS accounts. Use IAM Identity Center.
- Not for machine-to-machine authentication. Use IAM roles or STS.
- Not ideal when you need full control over the authentication server (use custom OIDC provider).
- Avoid for very high-volume, low-latency token validation where you need sub-ms response (validate JWTs locally instead of calling Cognito APIs).
- Avoid when your compliance requires user data to remain entirely on-premises.

#### Trade-Offs vs Similar Services

| Aspect | Cognito User Pools | Auth0 (3rd party) | Custom OIDC |
|---|---|---|---|
| Managed | Fully | Fully | Self-managed |
| AWS integration | Native | Custom | Custom |
| Social IdPs | Yes | Yes | Manual |
| Customization | Lambda triggers, limited UI | Extensive UI/flows | Unlimited |
| Pricing | Per MAU | Per MAU (higher) | Compute costs |
| JWT customization | Pre-token-generation Lambda | Rules engine | Full control |

#### Failure & Edge Case Behavior

- **Region failure**: Cognito is regional. If the region goes down, authentication fails. Mitigation: Cognito does NOT support multi-region natively. You would need a custom failover solution (two User Pools, custom DNS routing, user sync via Lambda/streams).
- **Throttling**: API rate limits per user pool. `AdminInitiateAuth`, `InitiateAuth` have hard limits. Burst traffic (e.g., marketing event) can trigger throttling. Request limit increases in advance.
- **Lambda trigger timeout**: Each trigger has a 5-second timeout. If your pre-token-generation Lambda takes too long, authentication fails. Keep triggers lightweight.
- **Token expiration**: ID/access tokens expire in 5 minutes to 24 hours (configurable). Refresh tokens: 1 hour to 3,650 days. If refresh token expires, user must re-authenticate.
- **Eventual consistency**: User attribute changes may take a few seconds to propagate.

#### Security & Compliance Implications

- **Encryption**: Data at rest encrypted with AWS-managed keys. Cannot use customer-managed KMS keys for User Pool data.
- **Compliance**: Cognito is HIPAA eligible, SOC, PCI DSS.
- **Advanced Security**: Adaptive authentication analyzes sign-in attempts (IP, device, location) and requires MFA or blocks access for risky sign-ins.
- **Token security**: Always validate JWTs server-side (verify signature against Cognito JWKS endpoint). Never trust client-side token claims without verification.

#### Cost Model & Optimization

- First 50,000 MAUs free (Essentials tier).
- Cost driver: MAUs (Monthly Active Users), not total users. Inactive users are free.
- Advanced Security features (adaptive auth, compromised credentials) add $0.050/MAU.
- SAML/OIDC federation costs more per MAU than direct Cognito auth.
- Cost trap: If your app has millions of MAUs with Advanced Security, costs grow quickly.

#### Advanced Professional-Level Exam Traps

1. **User Pools vs Identity Pools**: User Pools authenticate and return JWTs. Identity Pools exchange tokens for AWS credentials. Many questions conflate these. Know the difference.
2. **Cognito authorizer vs Lambda authorizer on API Gateway**: Cognito authorizer validates the JWT automatically but does not support custom logic. Lambda authorizer gives full control but requires you to manage caching and token validation.
3. **Unauthenticated Identity Pool access**: Be cautious with permissions granted to unauthenticated identities. Questions may test whether guest access can be exploited.
4. **Custom scopes in access tokens**: You can define resource servers and custom scopes in Cognito User Pools. Access tokens include these scopes. API Gateway can validate scopes.
5. **ALB integration**: ALB can authenticate users via Cognito User Pools directly (OIDC integration). This offloads auth from the application. The ALB adds user claims as HTTP headers to the backend.


### 1.5 AWS Security Token Service (STS)

#### Core Definition

STS provides **temporary security credentials** for IAM identities, federated users, and cross-account access. It is the mechanism behind every `AssumeRole` call.

- **Scope**: Global service with regional endpoints.
- **Pricing**: Free.
- **Architectural Abstraction**: Token issuance service that creates time-limited credential sets (access key, secret key, session token).

#### Core Capabilities

**Key APIs**:
- `AssumeRole`: Assume a role in the same or different account. Requires trust policy on the target role.
- `AssumeRoleWithSAML`: Assume a role using a SAML assertion from an IdP.
- `AssumeRoleWithWebIdentity`: Assume a role using a web identity token (OIDC). Cognito Identity Pools use this under the hood.
- `GetSessionToken`: Get temporary credentials for an IAM user (used for MFA-protected API access).
- `GetFederationToken`: Get temporary credentials for a federated user. Longer duration than AssumeRole.
- `GetCallerIdentity`: Returns the account ID, ARN, and user ID of the caller. Useful for debugging. No permissions required to call this.
- `DecodeAuthorizationMessage`: Decode an encoded authorization failure message. Requires `sts:DecodeAuthorizationMessage` permission.

**Session Duration**:
- `AssumeRole`: 15 minutes to 12 hours (configurable on the role, default 1 hour).
- `AssumeRole` with role chaining: **Maximum 1 hour**, regardless of role configuration.
- `AssumeRoleWithSAML`: 15 minutes to 12 hours.
- `AssumeRoleWithWebIdentity`: 15 minutes to 12 hours.
- `GetSessionToken`: 15 minutes to 36 hours (12 hours default for IAM users, 1 hour for root).
- `GetFederationToken`: 15 minutes to 36 hours.

**Regional Endpoints**: STS has a global endpoint (`sts.amazonaws.com`) which maps to `us-east-1`, and regional endpoints (`sts.<region>.amazonaws.com`). **Always use regional endpoints** to reduce latency and improve availability during regional outages.

#### When to Use

- Every cross-account access scenario.
- Every federation scenario.
- Every service-to-service authentication (EC2 instance profiles, Lambda execution roles, ECS task roles all use STS under the hood).
- MFA-protected API access.

#### Failure & Edge Case Behavior

- **Global endpoint outage**: If `sts.amazonaws.com` (us-east-1) is down, and you're using the global endpoint, `AssumeRole` fails. Regional endpoints continue to work. This has actually happened in real AWS outages.
- **Credential expiration during long-running tasks**: If a session expires mid-operation (e.g., large S3 upload), the operation fails. Use credential refresh or longer sessions.
- **Role chaining limit**: You CANNOT extend the 1-hour limit on role-chained sessions. This breaks automation that chains multiple roles and runs long tasks.

#### Advanced Professional-Level Exam Traps

1. **Regional vs global STS endpoints**: Exam questions may describe a scenario where `AssumeRole` fails during a us-east-1 outage. The fix is to use regional STS endpoints.
2. **Role chaining = 1 hour max**. Cannot be increased.
3. **`ExternalId` in cross-account AssumeRole**: Prevents the "confused deputy" problem. When a third-party service assumes a role in your account, the `ExternalId` ensures that the third party cannot reuse your role ARN on behalf of someone else.
4. **Session policies**: When you pass a session policy during `AssumeRole`, the effective permissions are the intersection of the role's policies and the session policy. Session policies cannot escalate permissions.


### 1.6 AWS Resource Access Manager (RAM)

#### Core Definition

RAM enables **sharing AWS resources across accounts** within or outside an Organization without creating duplicate resources. Instead of copying a resource to each account, you share it.

- **Scope**: Regional.
- **Pricing**: Free (you pay for the underlying resources).
- **Architectural Abstraction**: Resource sharing control plane that modifies resource policies or creates cross-account associations.

#### Core Capabilities

**Shareable Resources** (commonly tested):
- VPC Subnets (critical — allows multi-account VPC architectures)
- Transit Gateway
- Route 53 Resolver Rules
- License Manager configurations
- Aurora DB clusters (cross-account cloning)
- AWS Outposts
- EC2 Capacity Reservations
- Prefix Lists
- Network Firewall policies
- Systems Manager Incident Manager

**Sharing Models**:
- **Within Organization**: Sharing is automatic if enabled at the organization level. No invitation needed.
- **Outside Organization**: Requires an invitation that the receiving account must accept.
- **Sharing with OUs**: You can share with an entire OU; all current and future accounts in that OU get access.

**VPC Subnet Sharing** (critical for SAP-C02):
- Share subnets across accounts in the same Organization.
- Participant accounts can launch resources (EC2, RDS, etc.) into the shared subnet.
- The subnet owner account owns the subnet, route tables, NACLs, and Internet Gateway.
- Participant accounts own their resources (EC2 instances, ENIs, security groups) within the shared subnet.
- Participant accounts CANNOT modify the subnet, route tables, or NACLs.
- Resources in shared subnets communicate via private IPs without peering or Transit Gateway.
- This pattern reduces IP address consumption and simplifies network architecture.

#### Architectural Design Patterns

**Shared VPC Architecture**: Network account owns the VPC and subnets. Application accounts launch workloads into shared subnets. Reduces VPC count, simplifies routing, centralizes network management. Trade-off: less blast-radius isolation at the network level.

**Transit Gateway Sharing**: Network account owns the Transit Gateway. All spoke accounts attach their VPCs via RAM-shared Transit Gateway. Centralizes routing without Transit Gateway duplication.

#### When to Use

- Multi-account architectures where resources need to be shared.
- Centralized networking (shared VPCs, Transit Gateways).
- Avoiding resource duplication.
- Cross-account Aurora cloning for dev/test.

#### When NOT to Use

- When full isolation is required between accounts (regulated workloads that must not share network infrastructure).
- When the receiving account needs to modify the shared resource (subnet owners control route tables).

#### Advanced Professional-Level Exam Traps

1. **Shared subnets: owner vs participant permissions**. Owner controls network infra. Participant controls their resources. Questions test this boundary.
2. **RAM sharing within org doesn't require invitation acceptance**. Outside org does.
3. **Security groups**: Each account manages its own security groups even in shared subnets. Account A's security group can reference Account B's security group by ID within the same VPC.
4. **RAM does not share IAM policies or roles**. Each account maintains its own IAM permissions for resources it launches in shared subnets.


### 1.7 AWS Control Tower

#### Core Definition

Control Tower is an **opinionated orchestration service** that automates the setup of a multi-account AWS environment following best practices. It sits on top of Organizations, IAM Identity Center, CloudFormation, Config, and CloudTrail.

- **Scope**: Regional (landing zone deployed in a home region, with optional governed regions).
- **Pricing**: Free (you pay for underlying services: Config rules, CloudTrail, S3 storage, etc.).
- **Architectural Abstraction**: Landing zone orchestrator with pre-packaged guardrails.

#### Core Capabilities

**Landing Zone**: Automatically sets up:
- AWS Organizations with a recommended OU structure (Security OU, Sandbox OU).
- Log Archive account (centralized S3 buckets for CloudTrail and Config logs).
- Audit account (cross-account audit access, SNS notifications for guardrail violations).
- IAM Identity Center for federated access.
- CloudTrail organization trail.
- Config rules for guardrails.

**Guardrails**:
- **Preventive guardrails**: Implemented as SCPs. Block non-compliant actions (e.g., "Disallow deletion of the log archive"). Enforcement: Enforced or Not Enabled.
- **Detective guardrails**: Implemented as AWS Config rules. Detect non-compliant resources (e.g., "Detect whether S3 buckets have versioning enabled"). Enforcement: Clear, In Violation, or Not Enabled.
- **Proactive guardrails**: Implemented as CloudFormation hooks. Check resources before creation. Block non-compliant resources from being provisioned.
- Guardrails are categorized: Mandatory (always on), Strongly Recommended, Elective.
- Guardrails can be applied at the OU level.

**Account Factory**:
- Self-service account provisioning for end users.
- Backed by Service Catalog.
- Accounts are created with baseline configurations (VPC, guardrails, SSO access).
- Customization: Account Factory Customization (AFC) uses CloudFormation to apply custom templates during provisioning.

**Drift Detection**: Control Tower detects when the landing zone has drifted from its expected configuration (e.g., SCP modified manually, OU deleted). It can repair drift automatically or alert.

#### Architectural Design Patterns

**Enterprise Landing Zone**: Control Tower sets up the foundation. Customization Pipelines (CfCT — Customizations for Control Tower) extend the landing zone with organization-specific CloudFormation templates (e.g., Transit Gateway, custom Config rules, shared service VPCs).

**Nested OUs**: Control Tower supports registering existing OUs and nested OUs. You can extend the default structure with workload-specific OUs.

#### When to Use

- New AWS deployments that need a well-architected multi-account setup quickly.
- Organizations that want pre-built guardrails without building everything from scratch.
- When you want to provide self-service account provisioning with governance.

#### When NOT to Use

- Highly customized landing zones that deviate significantly from Control Tower's opinions. In this case, build on raw Organizations + CloudFormation.
- When you need guardrails in regions that Control Tower does not support.
- When the organization structure does not fit Control Tower's OU model.

#### Trade-Offs vs Raw Organizations

| Aspect | Control Tower | Raw Organizations + CloudFormation |
|---|---|---|
| Setup time | Hours | Weeks/months |
| Flexibility | Opinionated | Unlimited |
| Guardrails | Pre-built | Build your own |
| Drift detection | Built-in | Custom (Config/Lambda) |
| Account vending | Account Factory | Custom (Step Functions/Lambda) |
| Maintenance | AWS-managed updates | You manage everything |

#### Failure & Edge Case Behavior

- **Drift**: Manual changes to SCPs or OUs cause drift. Control Tower alerts and can repair.
- **Region limitations**: Control Tower supports a subset of regions. Newly launched regions may not be supported immediately.
- **Decommissioning**: Disabling Control Tower is complex. SCPs, Config rules, and IAM roles are left behind. Manual cleanup required.

#### Advanced Professional-Level Exam Traps

1. **Control Tower does NOT replace Organizations**. It uses Organizations under the hood.
2. **Preventive guardrails = SCPs. Detective guardrails = Config rules. Proactive guardrails = CloudFormation hooks.** Know the mapping.
3. **Account Factory uses Service Catalog**. If a question mentions self-service account creation with governance, Account Factory is the answer.
4. **CfCT (Customizations for Control Tower)** is the mechanism for extending Control Tower beyond its defaults. It is a CI/CD pipeline that deploys CloudFormation StackSets.
5. **Control Tower cannot be deployed in every region**. Exam questions may present scenarios in unsupported regions.


### 1.8 AWS Directory Service

#### Core Definition

AWS Directory Service provides managed Microsoft Active Directory (AD) and directory-related services in the AWS cloud.

Three flavors:
1. **AWS Managed Microsoft AD**: Full Microsoft AD, managed by AWS. Two domain controllers in different AZs. Supports AD trusts, Group Policy, LDAP, Kerberos.
2. **AD Connector**: Proxy to on-premises AD. Does NOT store any directory data in AWS. Forwards authentication requests to on-premises AD.
3. **Simple AD**: Samba 4-based, basic AD features. No trust relationships. Limited use cases.

- **Scope**: Regional (VPC-based).
- **Pricing**: Managed AD: $0.146/hr (Standard), $0.312/hr (Enterprise) per directory. AD Connector: $0.05/hr (Small), $0.133/hr (Large).
- **SLA**: 99.9% for Managed AD.

#### Core Capabilities

**Managed AD**:
- Supports multi-AZ (2+ domain controllers).
- Trust relationships: one-way or two-way trusts with on-premises AD or other AWS Managed AD directories.
- Multi-region replication: Extend a single Managed AD to multiple regions (directory shared, latency reduced for region-local authentication).
- Supports MFA (RADIUS integration).
- Integrates with: RDS SQL Server (Windows Auth), FSx for Windows File Server, WorkSpaces, WorkDocs, IAM Identity Center, EC2 domain join.
- Schema extensions supported.
- Up to 500,000 objects (Enterprise edition).

**AD Connector**:
- No directory data in AWS. All auth proxied to on-premises.
- Requires VPN or Direct Connect to on-premises.
- Supports IAM Identity Center integration.
- Does NOT support trust relationships.
- Cannot be shared via RAM.
- If on-premises AD is unavailable, authentication fails.

#### Architectural Design Patterns

**Hybrid AD**: On-premises AD trusts AWS Managed AD. Users on-premises authenticate against on-prem DCs. Users in AWS authenticate against Managed AD DCs. Replication happens between the directories.

**Multi-Region AD**: Deploy Managed AD in primary region. Add replica regions for lower latency and higher availability. Primary region manages the directory; replicas are read-only.

**WorkSpaces with Existing AD**: AD Connector points to on-premises AD. WorkSpaces authenticate against on-premises AD without storing user data in AWS.

#### When to Use

- **Managed AD**: When you need full AD features in AWS (trusts, Group Policy, LDAP, Kerberos, domain join).
- **AD Connector**: When you want to use existing on-premises AD credentials in AWS without replicating data.
- **Simple AD**: Small, basic directory needs without trust or schema extension requirements.

#### When NOT to Use

- Do NOT use AD Connector if your VPN/Direct Connect is unreliable (all auth depends on connectivity).
- Do NOT use Simple AD for anything requiring AD trusts or advanced Group Policy.
- Do NOT use Managed AD if you only need web app authentication (use Cognito).

#### Advanced Professional-Level Exam Traps

1. **Managed AD vs AD Connector**: If the question requires trust relationships, the answer is Managed AD. AD Connector cannot create trusts.
2. **AD Connector requires network connectivity to on-premises**. If that connectivity is unavailable, ALL authentication fails. This is a single point of failure.
3. **RDS SQL Server Windows Authentication requires Managed AD** (not AD Connector).
4. **Multi-region replica is available only for Managed AD**, not AD Connector.
5. **IAM Identity Center can use either Managed AD or AD Connector as its identity source**, but not Simple AD.

## 2. Networking & Hybrid Connectivity

Networking is the most tested domain on the SAP-C02 exam. You must understand packet-level routing decisions, DNS resolution chains, hybrid connectivity failure modes, and the cost implications of every data transfer path.


### 2.1 Amazon Virtual Private Cloud (VPC)

#### Core Definition

A VPC is a logically isolated virtual network within an AWS region. It is the foundational networking construct. Every compute resource (EC2, Lambda in VPC mode, RDS, EKS nodes, etc.) runs inside a VPC.

- **Scope**: Regional. A VPC spans all AZs in a region.
- **Control Plane**: Regional. VPC API calls are regional.
- **Data Plane**: Distributed across AZs. Each AZ has its own networking infrastructure.
- **Pricing**: VPCs are free. You pay for NAT Gateways, VPN connections, Elastic IPs, data transfer, and some VPC features.
- **SLA**: No standalone VPC SLA. Availability depends on the AZ infrastructure.
- **Architectural Abstraction**: Software-defined networking layer built on AWS's physical network fabric (Nitro, Blackfoot).

#### Core Capabilities

**CIDR and IP Addressing**:
- Primary CIDR: /16 (65,536 IPs) to /28 (16 IPs).
- Up to 5 CIDR blocks per VPC (can be increased to 50).
- IPv6: Optionally assign a /56 IPv6 CIDR (Amazon-provided or BYOIP).
- Each subnet gets a subset of the VPC CIDR.
- AWS reserves 5 IPs per subnet (first 4 + last 1): network address, VPC router (.1), DNS server (.2), future use (.3), broadcast (.255).
- Secondary CIDRs can be added to expand the VPC. They can be non-contiguous.
- **IPAM (IP Address Manager)**: Centralized IP address management across the organization. Allocate CIDR pools, enforce non-overlapping ranges.

**Subnets**:
- AZ-specific. A subnet exists in exactly one AZ.
- Public subnet: has a route to an Internet Gateway. Instances need public IP or EIP.
- Private subnet: no direct route to IGW. Uses NAT Gateway/instance for outbound internet.
- Isolated subnet: no route to internet at all.

**Route Tables**:
- Each subnet is associated with exactly one route table.
- Routes are evaluated using longest prefix match.
- Local route (VPC CIDR) is always present and cannot be removed.
- You can add routes to: IGW, NAT GW, VPC Peering, Transit Gateway, VPC Endpoint (Gateway), Network Interface, VPN Gateway.
- **Edge associations**: Route tables can be associated with an IGW or VGW to intercept inbound traffic (used for firewall appliances via Gateway Load Balancer or Firewall endpoints).

**Security**:
- **Security Groups**: Stateful firewalls at the ENI level. Allow rules only (no deny). Default: deny all inbound, allow all outbound. Can reference other security groups by ID (critical for cross-account shared VPCs). Up to 5 SGs per ENI (adjustable), 60 rules per SG (adjustable).
- **Network ACLs (NACLs)**: Stateless firewalls at the subnet level. Allow AND deny rules. Evaluated in rule number order (lowest first, first match wins). Default NACL allows all. Custom NACL denies all by default. NACLs are rarely used in modern architectures except for broad subnet-level blocking.

**NAT Gateway**:
- Managed NAT service for outbound internet access from private subnets.
- AZ-specific. Deploy one per AZ for HA.
- Bandwidth: up to 100 Gbps per NAT Gateway (scales automatically).
- Cost: $0.045/hr + $0.045/GB processed. This is a significant cost driver.
- Does NOT support security groups. Uses NACLs only.
- Cannot be used for inbound traffic initiation.
- Supports port forwarding? No. For inbound, use ALB/NLB or public instances.
- IPv6: NAT Gateway supports NAT64 (translate IPv6 to IPv4 for outbound) via egress-only configuration.

**VPC Endpoints**:
- **Gateway Endpoints**: S3 and DynamoDB only. Free. Route table entry that directs traffic to the service via AWS private network. Does not use ENIs. Controlled by endpoint policies (IAM-like). Regional only.
- **Interface Endpoints (PrivateLink)**: Create ENIs in your subnets with private IPs. Traffic to AWS services (or custom PrivateLink services) stays on AWS network. Cost: $0.01/hr per AZ + $0.01/GB processed. Support security groups. Enable private DNS to override the public service endpoint.
- **Gateway Load Balancer Endpoints**: For routing traffic to third-party virtual appliances (firewalls, IDS).

**VPC Flow Logs**:
- Capture IP traffic metadata (src/dst IP, port, protocol, action, bytes). Not packet content.
- Can be applied at VPC, subnet, or ENI level.
- Destination: CloudWatch Logs, S3, or Kinesis Data Firehose.
- Delay: ~10 minutes for aggregation.
- Custom format: select specific fields including VPC ID, subnet ID, instance ID, tcp flags, traffic type.
- Limitation: Does not capture DNS traffic to Route 53 Resolver, DHCP traffic, traffic to the instance metadata service (169.254.169.254), or NTP traffic.

#### Architectural Design Patterns

**Multi-AZ Architecture**: Deploy subnets in at least 2 AZs. Place ALB/NLB across AZs. Each AZ has its own NAT Gateway. This ensures that an AZ failure does not take down the entire application.

**Shared VPC (via RAM)**: Central network account owns the VPC. Application accounts launch resources into shared subnets. Reduces VPC sprawl and IP address waste. Trade-off: reduced blast radius isolation.

**Transit VPC / Transit Gateway Hub-and-Spoke**: Central VPC acts as a hub. Spoke VPCs connect via Transit Gateway. Centralizes routing, internet egress, and security inspection.

**Inspection VPC with Network Firewall**: All traffic (north-south and east-west) routes through an inspection VPC containing AWS Network Firewall. The inspection VPC sits between the Transit Gateway and the internet/on-premises.

#### When to Use

- Always. Every workload in AWS runs in a VPC (or default VPC).
- Use custom VPCs for production workloads. Never use the default VPC for production.

#### When NOT to Use

- Some serverless services (Lambda without VPC, API Gateway, DynamoDB, S3) operate outside your VPC. Don't place Lambda in a VPC unless it needs to access VPC resources (it adds cold start latency and consumes ENIs).

#### Failure & Edge Case Behavior

- **AZ failure**: Resources in the failed AZ become unreachable. Resources in other AZs continue. NAT Gateways are AZ-specific — if the AZ with your only NAT GW fails, private subnet internet access in other AZs fails (if they route to that NAT GW). Deploy one NAT GW per AZ.
- **IP exhaustion**: If a subnet runs out of IPs, new resource launches fail. Monitor available IPs. Use larger subnets or add secondary CIDRs.
- **ENI limits**: Each instance type has a limit on ENIs and IPs per ENI. Lambda in VPC mode consumes ENIs (with Hyperplane, this is largely mitigated).
- **Overlapping CIDRs**: VPCs with overlapping CIDRs cannot be peered or connected via Transit Gateway without IP translation (NAT or PrivateLink).

#### Security & Compliance Implications

- VPC Flow Logs for audit/compliance.
- Encryption in transit: not provided by VPC itself. Use TLS at the application layer. For encryption between VPCs/on-premises, use VPN or PrivateLink.
- Data residency: VPC is regional. Data stays in the region unless you explicitly transfer it.

#### Cost Model & Optimization

- VPC itself: Free.
- NAT Gateway: $0.045/hr + $0.045/GB. Major cost driver. Optimization: use VPC endpoints for S3/DynamoDB to avoid NAT GW charges. Use S3 Gateway Endpoint (free) instead of routing S3 traffic through NAT GW.
- Interface Endpoints: $0.01/hr/AZ + $0.01/GB. Deploy only in AZs where you have resources.
- Data transfer: Cross-AZ data transfer within VPC costs $0.01/GB each way ($0.02 round trip). Design for AZ affinity where possible.
- IPv4 public IPs: $0.005/hr per public IPv4 address (as of Feb 2024). Significant cost at scale.

#### Advanced Professional-Level Exam Traps

1. **Gateway endpoints are FREE for S3 and DynamoDB**. Interface endpoints cost money. If a question asks for the most cost-effective way to access S3 from a private subnet, the answer is Gateway Endpoint, not NAT Gateway or Interface Endpoint.
2. **NAT Gateway is AZ-specific**. One NAT GW does not provide HA across AZs.
3. **Security groups are stateful, NACLs are stateless**. Return traffic is automatically allowed by SGs but must be explicitly allowed by NACLs (ephemeral ports).
4. **VPC peering does not support transitive routing**. If VPC A is peered with VPC B, and VPC B is peered with VPC C, VPC A CANNOT reach VPC C through VPC B. Use Transit Gateway for transitive routing.
5. **Longest prefix match** determines route selection. A more specific route wins over a less specific one. This matters when overlapping routes exist (e.g., 10.0.0.0/16 to TGW vs 10.0.1.0/24 to peering connection).
6. **Public IPv4 addresses now cost money**. Questions about cost optimization may test this.


### 2.2 AWS Transit Gateway (TGW)

#### Core Definition

Transit Gateway is a **regional** network transit hub that connects VPCs, VPN connections, Direct Connect gateways, and Transit Gateway peering connections. It replaces the mesh of VPC peering connections.

- **Scope**: Regional. Transit Gateway Peering enables cross-region connectivity.
- **Control Plane**: Regional API.
- **Data Plane**: Distributed, high-performance network fabric.
- **Pricing**: $0.05/hr per attachment + $0.02/GB processed.
- **SLA**: 99.99% (high).
- **Architectural Abstraction**: Cloud router with route tables, route propagation, and attachment-based connectivity.

#### Core Capabilities

**Attachments** (how things connect to TGW):
- VPC attachment (one per VPC per TGW, subnet in each AZ).
- VPN attachment (IPSec VPN, supports ECMP for aggregate bandwidth).
- Direct Connect Gateway attachment (via Transit VIF).
- Peering attachment (cross-region TGW peering, static routes only).
- Connect attachment (GRE tunnels for SD-WAN appliances).

**Route Tables**:
- TGW has its own route tables, separate from VPC route tables.
- Each attachment is associated with ONE route table (for outbound routing from TGW perspective).
- Each attachment can propagate routes to multiple route tables.
- Default: single route table with all attachments associated and propagating. This creates full mesh connectivity.
- Segmented routing: Create multiple route tables. Associate subsets of attachments with different route tables. This creates network segmentation (e.g., production vs dev, or shared services vs isolated workloads).

**Routing Model**:
- Static routes: Manually configured.
- Propagated routes: Automatically learned from VPN/Direct Connect BGP or from VPC CIDR blocks.
- Route priority: static > propagated. For propagated routes, most specific prefix wins.
- Blackhole routes: Drop traffic to a specific CIDR. Useful for blocking routing between segments.

**Bandwidth**:
- Up to 50 Gbps per VPC attachment (burst).
- VPN: 1.25 Gbps per tunnel, but supports ECMP across multiple tunnels for aggregate bandwidth. With ECMP enabled, up to 50 Gbps via multiple VPN tunnels.
- Direct Connect: depends on the DX connection speed (1, 10, or 100 Gbps).
- Cross-region peering: limited by inter-region bandwidth (typically lower than intra-region).

**Multicast**: TGW supports multicast routing (IGMPv2). This is unique — no other AWS networking construct supports multicast natively.

#### Architectural Design Patterns

**Hub-and-Spoke**: All VPCs attach to a central TGW. Route tables control which VPCs can communicate. Shared services VPC (DNS, AD, monitoring) is routable from all spokes. Production and dev are isolated via separate route tables.

**Inspection Architecture**:
```
Internet → IGW → Firewall VPC (NW Firewall) → TGW → Spoke VPCs
```
TGW appliance mode must be enabled on the firewall VPC attachment to ensure symmetric routing (both directions of a flow go through the same firewall instance).

**Multi-Region Connectivity**: TGW in Region A peered with TGW in Region B. Cross-region traffic flows over AWS backbone. Note: peered TGW route tables require static routes (no dynamic propagation across peering).

**Transit Gateway + Direct Connect**: On-premises connects to Direct Connect Gateway, which associates with TGW. TGW distributes on-premises routes to VPCs. Supports up to 20 prefixes advertised from AWS to on-premises per Transit VIF (hard limit — plan prefix aggregation).

#### When to Use

- More than 2-3 VPCs that need connectivity.
- Centralized network routing and segmentation.
- VPN connections with ECMP for higher throughput.
- Multi-region network architectures.
- Multicast requirements.
- When you need transitive routing (which VPC peering cannot provide).

#### When NOT to Use

- Simple two-VPC connectivity: VPC Peering is cheaper and lower latency (no per-GB charge).
- When you need to connect hundreds of VPCs with simple routing: consider Cloud WAN for management at scale.
- If cost sensitivity is extreme: TGW's $0.02/GB charge on all traffic is significant.

#### Trade-Offs: VPC Peering vs Transit Gateway

| Aspect | VPC Peering | Transit Gateway |
|---|---|---|
| Transitive routing | No | Yes |
| Bandwidth | No aggregate limit (inter-AZ) | Up to 50 Gbps per attachment |
| Cost | Free (only data transfer) | $0.05/hr + $0.02/GB |
| Routing complexity | O(n²) peering mesh | O(n) hub-and-spoke |
| Cross-region | Yes (higher data transfer cost) | Yes (via TGW peering) |
| Network segmentation | Manual per peering | Route table-based |
| Multicast | No | Yes |
| Scale | 125 peering connections/VPC | 5,000 attachments/TGW |

#### Failure & Edge Case Behavior

- **AZ failure**: TGW is multi-AZ. If one AZ fails, traffic routes through other AZs. VPC attachments should have subnets in multiple AZs.
- **Asymmetric routing**: Without appliance mode, TGW may route forward and return traffic through different AZs, breaking stateful firewalls. Appliance mode ensures symmetric routing per-flow.
- **Route table misconfiguration**: Black hole routes or missing routes cause traffic drops. Use TGW Route Analyzer to diagnose.
- **Prefix limit on DX**: Only 20 prefixes can be advertised from TGW to on-premises per Transit VIF. Exceeding this causes BGP session reset. Aggregate routes.

#### Cost Model & Optimization

- **$0.02/GB processed** is the dominant cost. High-traffic architectures (e.g., centralized NAT/egress through TGW) can incur massive data processing charges.
- Optimization: For VPC-to-VPC traffic between two specific VPCs with high bandwidth, use VPC Peering instead of TGW.
- Optimization: For S3/DynamoDB access, use VPC endpoints instead of routing through TGW.

#### Advanced Professional-Level Exam Traps

1. **TGW peering uses static routes only**. No BGP propagation across peered TGWs. You must manually configure routes. This is a common gotcha in multi-region questions.
2. **Appliance mode**: Required for stateful inspection. Without it, firewalls see asymmetric traffic and drop connections.
3. **20 prefix limit on Transit VIF to on-premises**. If you advertise more, BGP session drops.
4. **ECMP is supported only for VPN attachments**, not for VPC attachments.
5. **TGW costs $0.02/GB in ADDITION to standard data transfer charges**. It's double-billed.


### 2.3 AWS Direct Connect (DX)

#### Core Definition

Direct Connect provides dedicated **private** network connections from on-premises to AWS. It bypasses the public internet, providing consistent latency, higher bandwidth, and reduced data transfer costs.

- **Scope**: Regional (connections terminate at a Direct Connect location/facility, associated with a specific AWS region).
- **Control Plane**: Regional API for creating connections and virtual interfaces.
- **Data Plane**: Physical layer 2 connection (Ethernet) between your router and AWS's router at the DX location.
- **Pricing**: Port-hour charges ($0.03–$0.285/hr depending on speed and location) + data transfer out ($0.02/GB for most regions, cheaper than internet data transfer).
- **SLA**: 99.99% if you follow the recommended resilient architecture (2 connections at 2 locations). 99.9% for single connection.
- **Lead time**: Provisioning takes weeks to months. This is a physical connection.
- **Architectural Abstraction**: Layer 2 dedicated connection with BGP-based Layer 3 routing.

#### Core Capabilities

**Connection Types**:
- **Dedicated Connection**: 1 Gbps, 10 Gbps, or 100 Gbps. Physical port dedicated to you. You request from AWS, then work with the co-location provider to complete the cross-connect.
- **Hosted Connection**: Provided by an AWS Direct Connect Partner. Speeds from 50 Mbps to 10 Gbps. Partner owns the physical connection and allocates bandwidth to you. Faster provisioning than dedicated.
- **Hosted VIF**: A virtual interface on a partner's connection. Legacy model being replaced by hosted connections.

**Virtual Interfaces (VIFs)**:
- **Private VIF**: Connects to a VPC (via VGW) or Direct Connect Gateway. Uses private IP addresses. BGP peering.
- **Public VIF**: Connects to AWS public services (S3, DynamoDB, etc.) over AWS's public IP space. Useful when you want to reach AWS public endpoints without going over the internet.
- **Transit VIF**: Connects to a Transit Gateway via Direct Connect Gateway. Enables connectivity to multiple VPCs through a single VIF. Maximum 3 Transit Gateways per Direct Connect Gateway.

**Direct Connect Gateway (DXGW)**:
- Global resource that connects a DX connection to VPCs or TGWs in any region (except China).
- You associate VGWs or TGWs with the DXGW.
- A single DXGW can be associated with up to 20 VGWs (in different regions) or 3 TGWs.
- DXGW does NOT provide VPC-to-VPC routing. It is a path from on-premises to AWS only.
- The DXGW is not a router. It doesn't support transitive routing between VPCs attached to it.

**Encryption**:
- DX connections are NOT encrypted by default. Traffic is private but not encrypted on the wire.
- For encryption: run a Site-to-Site VPN over the DX connection (IPSec). This provides encryption but adds VPN overhead.
- MACsec (802.1AE): Layer 2 encryption available on 10 Gbps and 100 Gbps dedicated connections. Hardware-based, no performance penalty. Requires MACsec-capable router.

**BGP**:
- DX uses BGP for route exchange.
- ASN: AWS side uses ASN 64512 (private) by default, or a specific public ASN.
- Customer side: provide your own ASN.
- BGP communities for route preference control (local preference, AS-path prepending).
- Route limits: 100 routes per BGP session for Private VIF/Transit VIF. 1,000 routes for Public VIF. Exceeding causes BGP session teardown.

**Link Aggregation Groups (LAG)**:
- Aggregate multiple DX connections (same speed) at the same location into a single logical connection.
- Uses LACP (Link Aggregation Control Protocol).
- All connections in a LAG must be the same speed and terminate at the same DX location.
- Minimum links threshold: configurable. If connections drop below threshold, the LAG goes down.

#### Architectural Design Patterns

**High Resiliency (Recommended)**:
- 2 DX connections at 2 different DX locations.
- Each location connects to a different AWS device.
- BGP with AS-path prepending for active/passive preference.
- Meets 99.99% SLA requirement.

**Maximum Resiliency**:
- 2 connections per location, 2 locations = 4 connections total.
- Protects against device failure AND location failure.

**DX + VPN Backup**:
- DX as primary, Site-to-Site VPN over internet as backup.
- BGP prefers DX (lower AS-path or higher local preference).
- If DX fails, traffic fails over to VPN.
- Trade-off: VPN has lower bandwidth and higher latency than DX. Suitable for non-latency-sensitive failover.

**DX + Transit Gateway**:
- DX → Transit VIF → DXGW → TGW → multiple VPCs.
- Single Transit VIF provides connectivity to all VPCs attached to the TGW.
- On-premises learns VPC routes via BGP propagation through TGW.
- 20 prefix limit from TGW to on-premises via DX.

#### When to Use

- Hybrid architectures requiring consistent, low-latency connectivity.
- High-bandwidth data transfer (database replication, backup, large-scale migration).
- Regulatory requirements prohibiting data traversal over public internet.
- Cost optimization for high-volume data transfer out of AWS (DX data transfer is cheaper).

#### When NOT to Use

- When you need connectivity in days, not weeks. DX provisioning takes time. Use VPN as an interim solution.
- For bursty, unpredictable workloads. DX is a fixed-cost, fixed-bandwidth pipe. You pay for the port whether you use it or not.
- For low-bandwidth requirements. VPN is more cost-effective at small scale.

#### Trade-Offs: Direct Connect vs Site-to-Site VPN

| Aspect | Direct Connect | Site-to-Site VPN |
|---|---|---|
| Setup time | Weeks/months | Minutes |
| Bandwidth | 1–100 Gbps | 1.25 Gbps per tunnel |
| Latency | Consistent, low | Variable (internet) |
| Encryption | Not default (MACsec or VPN overlay) | IPSec encrypted |
| Cost | Port-hour + data transfer | $0.05/hr per VPN connection + data transfer |
| Resiliency | Requires dual connections | Dual tunnels built-in |
| Use case | Production hybrid | Backup, low-volume |

#### Failure & Edge Case Behavior

- **Single connection failure**: If you have only one DX connection and it fails, all hybrid connectivity is lost. Always deploy redundant connections.
- **DX location failure**: If both connections are at the same location and the location has a power/network outage, connectivity is lost. Use two different locations.
- **BGP route limit exceeded**: If on-premises advertises more than 100 routes (Private VIF) or 1,000 routes (Public VIF), the BGP session is torn down. Monitor route counts. Use route aggregation.
- **Failover time**: BGP failover typically takes 30–90 seconds with BFD (Bidirectional Forwarding Detection). Without BFD, failover can take minutes (BGP hold timer default: 90 seconds, dead peer detection: 3x hold timer = 270 seconds). Always enable BFD for faster failover.

#### Security & Compliance Implications

- DX traffic is private but NOT encrypted. For sensitive data, use MACsec (10/100G dedicated) or VPN overlay.
- DX does not traverse the public internet. This satisfies many compliance requirements.
- VPC Flow Logs capture traffic from DX connections.

#### Cost Model & Optimization

- Port-hour charges are fixed regardless of utilization. Right-size the connection.
- Data transfer out via DX is cheaper than over the internet ($0.02/GB vs $0.09/GB for most regions).
- Cross-region data transfer via DX Gateway still incurs cross-region data transfer charges.
- Direct Connect data transfer IN is free (same as all inbound AWS data transfer).

#### Advanced Professional-Level Exam Traps

1. **DX is NOT encrypted by default**. If a question requires encryption, the answer involves MACsec or VPN over DX.
2. **DX provisioning takes weeks**. If a question needs connectivity "quickly" or "immediately," DX is not the answer. Use VPN.
3. **DXGW does not enable VPC-to-VPC routing**. It is only for on-premises-to-AWS. VPCs connected to the same DXGW cannot route to each other through it.
4. **Transit VIF: 20 prefix limit from AWS to on-premises**. Route aggregation is essential.
5. **BFD for fast failover**. Without BFD, failover takes too long for production SLAs.
6. **DX + VPN backup**: BGP path selection determines which link is preferred. Questions may test AS-path prepending or local preference configuration.
7. **100 Gbps DX** requires dedicated connection type and is available only at certain DX locations.


### 2.4 AWS Site-to-Site VPN

#### Core Definition

Site-to-Site VPN creates encrypted IPSec tunnels between your on-premises network and your AWS VPC (via Virtual Private Gateway or Transit Gateway).

- **Scope**: Regional.
- **Pricing**: $0.05/hr per VPN connection + data transfer out charges.
- **SLA**: Covered under VPC SLA.
- **Architectural Abstraction**: Two IPSec tunnels (for redundancy) terminating at AWS-managed VPN endpoints.

#### Core Capabilities

- Each VPN connection has 2 tunnels for HA (each tunnel terminates at a different AWS endpoint in different AZs).
- Bandwidth: 1.25 Gbps per tunnel. With ECMP on Transit Gateway, aggregate across multiple VPN connections for higher throughput.
- Supports static routing or dynamic (BGP) routing.
- Supports NAT Traversal (NAT-T).
- Supports Dead Peer Detection (DPD).
- Accelerated Site-to-Site VPN: Uses AWS Global Accelerator to route VPN traffic to the nearest AWS edge location, then over AWS backbone. Reduces internet path variability.

**VPN CloudHub**: Connect multiple on-premises sites to a single VGW. Sites can communicate with each other via the VGW (hub-and-spoke for on-premises networks through AWS).

#### When to Use

- Quick hybrid connectivity (minutes to set up).
- Backup for Direct Connect.
- Low-bandwidth hybrid workloads.
- Encrypted connectivity requirement (DX is not encrypted by default).

#### When NOT to Use

- High-bandwidth requirements (>1.25 Gbps per tunnel without ECMP, or >50 Gbps with ECMP on TGW).
- Latency-sensitive workloads (VPN over internet has variable latency).
- When consistent network performance is required (internet weather affects VPN).

#### Advanced Professional-Level Exam Traps

1. **Two tunnels per VPN connection**. Configure both tunnels on your on-premises device.
2. **ECMP requires Transit Gateway**. VPN connections on VGW do NOT support ECMP (only one tunnel active per connection).
3. **Accelerated VPN uses Global Accelerator**. Additional cost but significantly improves latency and jitter for internet-based VPN.
4. **BGP is recommended over static routing** for automatic failover and route management.


### 2.5 Amazon Route 53

#### Core Definition

Route 53 is AWS's **global** DNS service providing domain registration, DNS hosting, and health-checking/routing.

- **Scope**: Global. Hosted zones are replicated to Route 53 DNS servers worldwide.
- **Control Plane**: Global (us-east-1). Creating/modifying records is a control plane operation. During us-east-1 issues, you may not be able to modify records, but DNS resolution (data plane) continues globally.
- **Data Plane**: Globally distributed DNS servers. Extremely resilient. AWS offers a 100% SLA on Route 53 DNS resolution.
- **Pricing**: $0.50/month per hosted zone. $0.40 per million queries (standard), $0.60 per million for latency/geolocation/geoproximity.
- **SLA**: 100% for DNS resolution. This is the highest SLA of any AWS service.

#### Core Capabilities

**Hosted Zones**:
- Public Hosted Zone: Resolves DNS queries from the internet.
- Private Hosted Zone: Resolves DNS queries from within associated VPCs. Must associate the hosted zone with each VPC that needs resolution.

**Routing Policies**:
- **Simple**: Single resource. No health checks.
- **Weighted**: Distribute traffic by percentage. Use for canary deployments, A/B testing.
- **Latency-based**: Route to the region with lowest latency for the client. Based on AWS's latency measurements.
- **Failover**: Active-passive. Primary record with health check. If unhealthy, resolves to secondary.
- **Geolocation**: Route based on client's geographic location (continent, country, state). If no match, default record.
- **Geoproximity**: Route based on geographic distance. Supports bias to expand/shrink a region's traffic catchment area. Requires Route 53 Traffic Flow.
- **Multivalue Answer**: Return up to 8 healthy records. Client-side load balancing. NOT a substitute for ELB.
- **IP-based routing**: Route based on client IP address (CIDR blocks). Useful for ISP-specific routing.

**Health Checks**:
- Monitor endpoints (IP or domain), CloudWatch alarms, or calculated (aggregation of other health checks).
- Interval: 30 seconds (standard) or 10 seconds (fast, additional cost).
- Threshold: configurable number of consecutive failures.
- Health checkers are distributed globally. The endpoint must be accessible from the internet (for endpoint health checks). Private endpoints require CloudWatch alarm-based health checks.
- String matching: health checker can look for a specific string in the first 5,120 bytes of the response.

**Route 53 Resolver**:
- Default DNS resolver for VPCs (the .2 address in the VPC CIDR).
- **Resolver Endpoints**:
  - **Inbound Endpoint**: Allows on-premises DNS to resolve AWS private hosted zones (on-prem forwards to Resolver inbound endpoint ENIs).
  - **Outbound Endpoint**: Allows VPC resources to resolve on-premises DNS (Resolver forwards queries matching certain domains to on-prem DNS via outbound endpoint ENIs).
- **Resolver Rules**: Forwarding rules that specify which domains to forward to on-premises DNS servers. Can be shared across accounts via RAM.
- **Resolver DNS Firewall**: Filter/block DNS queries based on domain lists. Deny access to known-malicious domains.

**DNSSEC**: Route 53 supports DNSSEC signing for public hosted zones. Protects against DNS spoofing. Requires KMS key (asymmetric, ECC_NIST_P256) in us-east-1.

#### Architectural Design Patterns

**Multi-Region Active-Active**: Latency-based routing + health checks. Traffic goes to the lowest-latency healthy region. If a region fails, health check fails, traffic routes to the next best region.

**Multi-Region Active-Passive (DR)**: Failover routing policy. Primary region serves all traffic. If primary health check fails, DNS resolves to the DR region.

**Hybrid DNS Resolution**: Outbound Resolver endpoints forward on-premises domain queries to on-prem DNS. Inbound Resolver endpoints allow on-prem to resolve AWS hosted zones. Bidirectional resolution without custom DNS servers.

**Blue-Green Deployment**: Weighted routing with 100% to blue environment. Gradually shift weight to green. Rollback by shifting weight back.

#### Failure & Edge Case Behavior

- **DNS caching (TTL)**: Clients cache DNS responses for the TTL duration. If you failover, clients with cached records continue hitting the old endpoint until TTL expires. Use low TTLs (60 seconds) for failover records. Trade-off: lower TTL = more DNS queries = higher cost and load.
- **Health check false positive**: If Route 53 health checkers can't reach your endpoint (e.g., firewall blocks health checker IPs), the check fails, and DNS routes traffic away. Whitelist Route 53 health checker IP ranges.
- **Control plane outage (us-east-1)**: Cannot create/modify records, but existing records continue to resolve. Data plane is fully independent.

#### Cost Model & Optimization

- Hosted zones: $0.50/month each. Don't create unnecessary hosted zones.
- Query costs: $0.40–$0.70 per million queries. High-traffic domains can accumulate costs.
- Health checks: $0.50/month (AWS endpoints) to $0.75/month (non-AWS endpoints). Fast interval adds $1.00/month.
- Alias records: Queries to alias records pointing to AWS resources (ELB, CloudFront, S3) are FREE.

#### Advanced Professional-Level Exam Traps

1. **Alias records vs CNAME**: Alias records work at the zone apex (e.g., example.com). CNAME cannot be at zone apex. Alias records for AWS resources are free (no query charges). Always prefer Alias for AWS resources.
2. **Private hosted zones require VPC association**. If you create a private hosted zone and don't associate a VPC, it resolves nothing.
3. **Resolver inbound endpoints need to be accessible from on-premises** (via VPN or DX). They have security groups.
4. **DNSSEC**: The KMS key MUST be in us-east-1. Signing is only for public hosted zones.
5. **Geolocation routing**: If no match for the client's location and no default record, Route 53 returns "no answer." ALWAYS create a default record.
6. **Route 53 does NOT support multicast or anycast for records** — the service itself uses anycast for its name servers, but records resolve to unicast IPs.


### 2.6 AWS PrivateLink

#### Core Definition

PrivateLink enables private connectivity between VPCs, AWS services, and on-premises networks without exposing traffic to the public internet. It creates ENIs in your VPC that serve as entry points.

- **Scope**: Regional.
- **Pricing**: $0.01/hr per AZ + $0.01/GB processed (for interface endpoints). Endpoint services (NLB-backed): NLB pricing applies.
- **Architectural Abstraction**: Cross-VPC/cross-account private API exposure via ENIs.

#### Core Capabilities

**Consumer Side**: Interface VPC Endpoints. Creates ENIs with private IPs in your subnets. Traffic to the service goes through these ENIs.

**Provider Side**: Endpoint Service. Backed by a Network Load Balancer (NLB) or Gateway Load Balancer (GWLB). The provider exposes a service; consumers create endpoints to connect.

**Key Properties**:
- Unidirectional: Consumer initiates connections to the provider. Provider cannot initiate connections to the consumer.
- No overlapping CIDR issues: Because PrivateLink uses ENIs with consumer-side IPs, there's no routing overlap problem.
- Cross-account: A consumer in Account A can connect to a provider in Account B.
- Cross-region: NOT supported. PrivateLink is intra-region only. For cross-region, combine with TGW peering.
- DNS: Enable Private DNS to override the default public DNS of the service with private IPs.
- Security: Endpoint policies (IAM-like) control what actions/resources can be accessed through the endpoint. Security groups on the ENIs.

#### Architectural Design Patterns

**SaaS Integration**: SaaS provider exposes service via PrivateLink. Customer connects without internet exposure. IP overlap between provider and consumer is not an issue.

**Shared Services**: Central account hosts an NLB fronting a shared service (logging, monitoring). Other accounts consume via PrivateLink endpoints.

**Avoiding Transit Gateway for Service Access**: If you only need one-directional service access (consumer → provider), PrivateLink avoids the cost of Transit Gateway ($0.02/GB vs $0.01/GB for PrivateLink).

#### When to Use

- Exposing services privately to other VPCs/accounts without VPC peering or TGW.
- Consuming AWS services privately from your VPC.
- Multi-tenant SaaS connectivity with IP overlap.
- When security requirements prohibit public internet traversal.

#### When NOT to Use

- Bidirectional connectivity between VPCs. Use VPC Peering or TGW.
- Cross-region connectivity. PrivateLink is regional only.
- Very high throughput (>100 Gbps). Consider Direct Connect or TGW.

#### Advanced Professional-Level Exam Traps

1. **PrivateLink is unidirectional**. Consumer → Provider only.
2. **Does not require overlapping CIDR resolution** because it uses local ENIs. This is its key advantage over peering.
3. **Cross-region not supported**. Questions that require cross-region private connectivity need TGW peering or inter-region VPC peering.
4. **NLB is required as the provider backend**. ALB alone cannot be a PrivateLink endpoint service backend.


### 2.7 Elastic Load Balancing (ALB, NLB, GLB, CLB)

#### Core Definition

ELB distributes incoming traffic across multiple targets. Four types:

1. **Application Load Balancer (ALB)**: Layer 7 (HTTP/HTTPS). Content-based routing. WebSocket support.
2. **Network Load Balancer (NLB)**: Layer 4 (TCP/UDP/TLS). Ultra-low latency. Static IPs. PrivateLink support.
3. **Gateway Load Balancer (GLB)**: Layer 3 (GENEVE encapsulation). For inline virtual appliances (firewalls, IDS/IPS).
4. **Classic Load Balancer (CLB)**: Legacy. Layer 4/7. Do not use for new architectures.

- **Scope**: Regional. Deployed across AZs.
- **Pricing**: ALB/NLB: $0.0225/hr + LCU (Load Balancer Capacity Units). GLB: $0.0125/hr + GLCU.
- **SLA**: 99.99% for ALB/NLB.

#### Core Capabilities

**ALB**:
- Path-based routing (`/api/*`, `/images/*`).
- Host-based routing (`api.example.com`, `web.example.com`).
- HTTP header/method/query string routing.
- Weighted target groups (canary deployments).
- Lambda targets, EC2 instance targets, IP targets, container targets.
- Sticky sessions (cookie-based).
- Authentication: OIDC integration (Cognito, any OIDC IdP).
- WAF integration.
- HTTP/2, gRPC support.
- Cross-zone load balancing: enabled by default (no charge).
- Does NOT preserve source IP directly (use X-Forwarded-For header).

**NLB**:
- Handles millions of requests per second with ultra-low latency (\<100μs added latency).
- Static IP per AZ (one Elastic IP per AZ).
- Preserves source IP (for TCP).
- TLS termination at NLB level.
- Supports PrivateLink (can be an endpoint service backend).
- Cross-zone load balancing: disabled by default (enabled incurs cross-AZ data transfer charges).
- TCP/UDP/TLS protocols.
- Health checks: TCP, HTTP, HTTPS.
- Targets: EC2 instances, IP addresses, ALB (NLB → ALB chain for static IP + Layer 7 features).

**GLB**:
- GENEVE protocol (port 6081) for transparent inline inspection.
- Deploys virtual appliances (firewalls) as targets.
- VPC route table integration: traffic is redirected to GLB endpoint before reaching its destination.
- Appliance vendor support: Palo Alto, Fortinet, Check Point, etc.
- Cross-zone: disabled by default.

#### Architectural Design Patterns

**NLB → ALB Chain**: When you need static IPs (for whitelisting) AND Layer 7 routing. NLB provides static IPs, forwards to ALB target group for content routing.

**GLB for Centralized Inspection**: All VPC ingress/egress traffic routes through GLB → firewall fleet → GLB → destination. GLB handles HA and scaling of appliances.

**ALB + Cognito Authentication**: ALB handles OIDC authentication. Users are redirected to Cognito login. Upon successful auth, ALB adds user claims as headers to backend requests. Application doesn't need to implement auth.

#### When to Use

- **ALB**: Web applications, HTTP APIs, microservices, containerized apps, gRPC.
- **NLB**: TCP/UDP workloads, gaming, IoT, extreme performance, PrivateLink services, static IP requirements.
- **GLB**: Inline security appliances (firewall, IPS), traffic mirroring to appliances.

#### When NOT to Use

- **ALB**: Non-HTTP protocols (use NLB). Extreme low-latency requirements (NLB adds less latency).
- **NLB**: Complex routing logic (use ALB). WAF integration (NLB doesn't support WAF — chain with ALB).
- **GLB**: Standard load balancing (overkill, use ALB/NLB).

#### Trade-Offs: ALB vs NLB

| Aspect | ALB | NLB |
|---|---|---|
| OSI Layer | 7 (HTTP/HTTPS) | 4 (TCP/UDP/TLS) |
| Latency | ~ms | ~100μs |
| Static IP | No (use Global Accelerator or NLB→ALB) | Yes (EIP per AZ) |
| Source IP preservation | X-Forwarded-For header | Native (TCP) |
| WAF | Yes | No |
| PrivateLink backend | No | Yes |
| Authentication | Cognito/OIDC | No |
| gRPC | Yes | No (raw TCP only) |
| Cross-zone default | Enabled (free) | Disabled |
| WebSocket | Yes | Yes (raw TCP) |

#### Failure & Edge Case Behavior

- **AZ failure**: ELB stops sending traffic to targets in the failed AZ (if cross-zone is enabled, remaining AZs handle all traffic). If cross-zone is disabled, traffic to the failed AZ's IP is lost.
- **All targets unhealthy**: ALB/NLB returns 503 (ALB) or drops connections (NLB). NLB has a "failopen" behavior — if all targets are unhealthy, it sends traffic to all targets.
- **NLB cross-zone disabled**: If one AZ has more targets than another, traffic distribution is uneven. Each AZ gets equal DNS weight regardless of target count.

#### Cost Model & Optimization

- ALB charges by LCU: based on new connections/sec, active connections, bandwidth, rule evaluations. Complex routing rules increase cost.
- NLB charges by NLCU: based on new connections/sec, active connections, bandwidth. Cheaper for simple TCP pass-through.
- Cross-zone load balancing on NLB incurs cross-AZ data transfer charges. ALB cross-zone is free.

#### Advanced Professional-Level Exam Traps

1. **ALB cross-zone is enabled by default and free. NLB cross-zone is disabled by default and costs money.** Critical for cost and availability questions.
2. **NLB preserves source IP. ALB does not** (use X-Forwarded-For or Proxy Protocol v2).
3. **NLB supports PrivateLink. ALB does not.** For PrivateLink services, use NLB.
4. **GLB uses GENEVE protocol**, not IP-in-IP or GRE. Appliances must support GENEVE.
5. **ALB supports weighted target groups** for canary deployments (e.g., 90% to v1, 10% to v2).
6. **NLB health checks**: If using TCP health check, NLB only checks if the port is open, not if the application is healthy. Use HTTP health checks when possible.


### 2.8 AWS Network Firewall

#### Core Definition

Network Firewall is a managed, stateful network firewall service for VPCs. It provides deep packet inspection, intrusion prevention (IPS), and web filtering.

- **Scope**: Regional. Deployed per VPC.
- **Pricing**: $0.395/hr per firewall endpoint + $0.065/GB processed.
- **Architectural Abstraction**: Managed Suricata-based firewall engine deployed as endpoints in your VPC subnets.

#### Core Capabilities

- Stateful and stateless rule groups.
- Suricata-compatible IPS rules.
- Domain filtering (allow/deny lists for outbound DNS-based filtering).
- TLS inspection (decrypt, inspect, re-encrypt). Requires certificate management.
- Managed rule groups (AWS-managed threat intelligence).
- Centralized management via Firewall Manager (across accounts in an Organization).
- Logging: Flow logs, alert logs → S3, CloudWatch Logs, Kinesis Data Firehose.

#### Architectural Design Patterns

**Centralized Inspection VPC**: All traffic from spoke VPCs routes through TGW to a central inspection VPC containing Network Firewall. Return traffic also goes through the firewall. TGW appliance mode ensures symmetric routing.

**Per-VPC Inline Inspection**: Network Firewall endpoints in the workload VPC. Route table directs traffic to the firewall endpoint before the Internet Gateway. Simpler but doesn't consolidate firewall management.

#### When to Use

- Deep packet inspection, IPS/IDS in AWS.
- Domain-based filtering (block specific domains).
- Compliance requirements for network traffic inspection.
- Centralized firewall management across accounts.

#### When NOT to Use

- Simple IP/port filtering: Use Security Groups and NACLs (free).
- Web application layer attacks: Use WAF (Layer 7 HTTP-specific).
- Cost-sensitive environments with low risk: $0.395/hr + per-GB charges add up.

#### Trade-Offs: Network Firewall vs WAF vs Security Groups

| Aspect | Network Firewall | WAF | Security Groups |
|---|---|---|---|
| OSI Layer | 3/4/7 | 7 (HTTP) | 3/4 |
| Stateful | Yes | N/A (HTTP only) | Yes |
| IPS/IDS | Yes | No | No |
| Domain filtering | Yes | No | No |
| TLS inspection | Yes | No | No |
| Cost | High | Medium | Free |
| Scale | Per-GB | Per-request | Unlimited |
| Managed rules | Yes | Yes (marketplace) | No |

#### Advanced Professional-Level Exam Traps

1. **Network Firewall requires TGW appliance mode** for centralized inspection to maintain symmetric routing.
2. **Domain filtering requires DNS**. Firewall inspects DNS queries to match domain rules. Encrypted DNS (DoH/DoT) can bypass domain filtering.
3. **Cost**: $0.395/hr per endpoint + $0.065/GB. For high-traffic environments, this is expensive. Questions may test cost-aware alternatives.


### 2.9 AWS Shield (Standard and Advanced)

#### Core Definition

Shield provides DDoS protection for AWS resources.

- **Shield Standard**: Automatic, free, always-on. Protects against common Layer 3/4 attacks. Applied to all AWS customers.
- **Shield Advanced**: $3,000/month (1-year commitment) + data transfer fees. Layer 3/4/7 DDoS protection. DDoS Response Team (DRT) access. Cost protection (credits for scaling costs during DDoS). Advanced detection and mitigation.

#### Core Capabilities (Shield Advanced)

- Protects: CloudFront, Route 53, Global Accelerator, ALB, NLB, EC2, Elastic IP.
- Automatic DDoS detection and mitigation.
- Real-time attack visibility in CloudWatch.
- DDoS Response Team (DRT): 24/7 experts who can create WAF rules on your behalf during an attack.
- Cost protection: AWS credits your account for DDoS-related scaling costs (EC2, ELB, CloudFront, Route 53).
- Health-based detection: Uses Route 53 health checks to improve attack detection accuracy and reduce false positives.
- Proactive engagement: DRT reaches out to you when an attack is detected.
- Integration with Firewall Manager for centralized deployment.

#### When to Use

- **Shield Standard**: Always on. No action needed.
- **Shield Advanced**: High-profile public-facing applications. Financial/gaming/media companies. When DDoS cost protection is needed. When 24/7 DRT access is required.

#### Advanced Professional-Level Exam Traps

1. **Shield Advanced costs $3,000/month** with a 1-year commitment. Per-organization (covers all accounts in the org).
2. **Shield Advanced + WAF**: WAF charges are included (no additional WAF cost) for resources protected by Shield Advanced.
3. **Cost protection only covers DDoS-related scaling**. You must have auto-scaling configured for this to help.
4. **Shield Advanced health-based detection** requires Route 53 health checks to be configured on protected resources.


### 2.10 AWS WAF (Web Application Firewall)

#### Core Definition

WAF protects web applications from common Layer 7 (HTTP/HTTPS) exploits. Deployed on CloudFront, ALB, API Gateway, AppSync, Cognito User Pools, App Runner, and Verified Access.

- **Scope**: Regional (when on ALB/API Gateway/AppSync) or Global (when on CloudFront).
- **Pricing**: $5/month per Web ACL + $1/month per rule + $0.60 per million requests.

#### Core Capabilities

- **Web ACLs**: Container for rules. Associated with one or more resources.
- **Rules**: Match conditions → action (Allow, Block, Count, CAPTCHA, Challenge).
- **Rule types**: Rate-based (block IPs exceeding threshold), IP set match, geo match, regex match, string match, SQL injection detection, XSS detection, size constraints.
- **Managed Rule Groups**: AWS Managed Rules (core rule set, bot control, IP reputation), Marketplace rules (Fortinet, F5, etc.).
- **Bot Control**: Detect and manage bot traffic. Standard ($10/month + $1/M requests) and Targeted ($10/month + $25/M requests) tiers.
- **Account Takeover Prevention (ATP)**: Monitors login endpoints for credential stuffing.
- **Fraud Control**: Detect and prevent account creation fraud.
- **Logging**: Full request logs → S3 (prefixed with `aws-waf-logs-`), CloudWatch Logs, Kinesis Data Firehose.

#### Architectural Design Patterns

- **CloudFront + WAF**: WAF at the edge. Blocks attacks before they reach your origin. Most efficient for global applications.
- **ALB + WAF**: WAF at the regional level. Protects application entry points.
- **Rate limiting**: Block IPs exceeding request thresholds. Useful for API abuse prevention.

#### When to Use

- Public web applications exposed to the internet.
- API protection (SQL injection, XSS, bot management).
- Compliance requirements for web application firewalls.

#### When NOT to Use

- Non-HTTP traffic. Use Network Firewall or Shield.
- DDoS protection for Layer 3/4. Use Shield.

#### Advanced Professional-Level Exam Traps

1. **WAF on CloudFront is global; WAF on ALB is regional**. The Web ACL must be in the same region as the resource (or us-east-1 for CloudFront).
2. **Rate-based rules aggregate by IP** (default) or forwarded IP (behind a proxy). Threshold minimum: 100 requests per 5-minute window.
3. **WAF logging requires S3 bucket name starting with `aws-waf-logs-`** or CloudWatch log group starting with `aws-waf-logs-`.
4. **Rule evaluation order matters**. Rules in a Web ACL are evaluated in priority order. First match wins (for terminating actions).


### 2.11 AWS Cloud WAN

#### Core Definition

Cloud WAN is a managed wide-area networking service that builds, manages, and monitors a global network connecting resources across AWS regions, on-premises, and cloud environments. It simplifies management of complex multi-region Transit Gateway deployments.

- **Scope**: Global.
- **Pricing**: $0.05/hr per attachment + $0.02/GB per segment + peering costs.
- **Architectural Abstraction**: Global network policy engine on top of Transit Gateways.

#### Core Capabilities

- **Core Network**: Defined by a JSON policy document specifying regions, segments, and attachment policies.
- **Segments**: Logical isolation (similar to TGW route tables but across regions). Enforce routing domains globally.
- **Attachments**: VPCs, VPN, Direct Connect, Transit Gateway route table.
- **Policy-based automation**: Attachments auto-associate to segments based on tags. No manual route table management.

#### When to Use

- Large-scale multi-region networks (10+ regions, 100+ VPCs).
- When TGW management becomes complex.
- When policy-based, automated network segmentation is needed globally.

#### When NOT to Use

- Single-region or simple dual-region architectures. TGW is sufficient and cheaper.
- The service is relatively new; some features are still maturing.

#### Advanced Professional-Level Exam Traps

1. Cloud WAN uses Transit Gateways under the hood. It is an abstraction layer.
2. Cloud WAN supports **inter-segment routing** via shared segments. Understand how segment isolation works.
3. Pricing is additive on top of existing TGW-like charges.

## 3. Compute & Containers

The compute domain tests your ability to select the right compute model for a given constraint set: cost, latency, operational overhead, scaling speed, state management, and compliance. The SAP-C02 expects you to reason about when to use EC2 vs Lambda vs containers — and crucially, when each breaks down.


### 3.1 Amazon EC2 (Elastic Compute Cloud)

#### Core Definition

EC2 provides resizable virtual machines (instances) in the cloud. It is the most flexible compute service — you control the OS, networking, storage, and runtime environment.

- **Scope**: Regional (instances run in a specific AZ within a region).
- **Control Plane**: Regional API for launching, stopping, terminating instances.
- **Data Plane**: The instance itself runs on a physical host in an AZ. Powered by AWS Nitro System (hardware-based hypervisor, security chip, network/storage offload cards).
- **Pricing**: Multiple models — On-Demand, Reserved Instances (Standard/Convertible, 1yr/3yr), Savings Plans, Spot Instances, Dedicated Hosts, Dedicated Instances, Capacity Reservations.
- **SLA**: 99.99% for multi-AZ deployment. 99.5% for single-instance.
- **Architectural Abstraction**: Virtual machine on shared or dedicated hardware.

#### Core Capabilities

**Instance Types** (Professional-level requires understanding families):
- **General Purpose (M, T)**: Balanced compute/memory/network. T-series burstable (CPU credits).
- **Compute Optimized (C)**: High-performance processors. Batch, ML inference, gaming.
- **Memory Optimized (R, X, z)**: Large in-memory workloads. R: general memory-optimized. X: extreme memory (up to 4 TiB). z: high frequency + memory.
- **Storage Optimized (I, D, H)**: High sequential read/write to local storage. I: NVMe SSD. D: dense HDD. H: high throughput HDD.
- **Accelerated Computing (P, G, Inf, Trn, DL, F, VT)**: GPUs, FPGAs, custom ML accelerators. P: general GPU. G: graphics. Inf: AWS Inferentia (ML inference). Trn: AWS Trainium (ML training).
- **HPC Optimized (Hpc)**: High-performance computing with EFA (Elastic Fabric Adapter) support.

**Nitro System**: All modern instance types run on Nitro. Benefits: near bare-metal performance, hardware-based security (Nitro Security Chip), consistent network/storage performance via offload cards. Nitro Enclaves: isolated compute environments for processing highly sensitive data (no operator access, cryptographic attestation).

**Instance Store**: Ephemeral local NVMe storage physically attached to the host. Extremely high IOPS (millions). Data is LOST on stop/terminate/host failure. Use for temporary data, caches, scratch space. Not suitable for durable storage.

**Placement Groups**:
- **Cluster**: Instances packed close together in a single AZ. Low-latency, high-throughput inter-instance communication. HPC, tightly coupled workloads. Risk: hardware failure affects all instances.
- **Spread**: Instances on distinct hardware racks. Maximum 7 instances per AZ per group. HA for small critical instance sets.
- **Partition**: Instances spread across logical partitions (different racks). Each partition is failure-isolated. Up to 7 partitions per AZ. For large distributed systems (HDFS, HBase, Cassandra).

**Elastic Network Interfaces (ENI)**:
- Virtual network card. Has private IP, optional public IP, security groups, MAC address.
- Multiple ENIs per instance (depends on instance type).
- ENIs can be moved between instances (same AZ) for failover.
- Elastic Fabric Adapter (EFA): Specialized ENI for HPC. OS-bypass for inter-node communication. Used with MPI workloads.

**Auto Scaling**:
- Launch Templates (preferred over Launch Configurations — Launch Configurations are legacy and can't be modified).
- Auto Scaling Groups (ASG):
  - Scaling policies: Target Tracking (maintain metric at target, e.g., CPU at 50%), Step Scaling (scale in steps based on alarm thresholds), Simple Scaling (legacy), Scheduled Scaling, Predictive Scaling (ML-based forecast).
  - Cooldown period: prevents rapid scale in/out oscillation.
  - Lifecycle hooks: Pause instances during launch/terminate for custom actions (install software, drain connections).
  - Instance refresh: Rolling replacement of instances with new AMI/Launch Template.
  - Mixed instances policy: combine On-Demand and Spot, multiple instance types.
  - Warm pools: Pre-initialized instances in stopped state. Faster scale-out than cold launch.
  - Health checks: EC2 status checks, ELB health checks, custom health checks.
  - AZ rebalancing: ASG automatically rebalances instances across AZs.

**AMIs (Amazon Machine Images)**:
- Regional. Must be copied to use in another region.
- Can be shared cross-account or made public.
- Encrypted AMIs: Can copy to another encryption key. Cross-account sharing of encrypted AMIs requires sharing the KMS key.
- AMI lifecycle: Build with EC2 Image Builder. Automate with EventBridge + Lambda.

**EC2 Instance Connect & Session Manager**:
- Instance Connect: SSH key injection for temporary access. Requires port 22 open.
- Session Manager (SSM): Shell access without opening SSH/RDP ports. No inbound security group rules needed. Logged in CloudTrail. Requires SSM Agent and appropriate IAM role.

#### Architectural Design Patterns

**Immutable Infrastructure**: AMIs contain the full application stack. ASG launches new instances from updated AMIs. No in-place updates. Blue/green via ASG replacement.

**Spot + On-Demand Mixed Fleet**: ASG with mixed instances policy. On-Demand for baseline, Spot for peak. Multiple instance types to increase Spot pool diversity and reduce interruption risk.

**HPC Cluster**: Cluster placement group + EFA-enabled instances + FSx for Lustre (parallel file system). MPI or NCCL for inter-node communication.

**Hibernation**: Save in-memory state to root EBS volume. Resume without re-initialization. Useful for instances with long startup times. Constraints: EBS root volume must be encrypted, instance memory < 150 GB, hibernation < 60 days.

#### When to Use

- Full OS control required.
- Long-running, stateful workloads.
- GPU/FPGA/custom hardware requirements.
- High-performance computing.
- Applications with specific kernel or OS requirements.
- Lift-and-shift migrations.
- When third-party licensing is tied to vCPUs/sockets (Dedicated Hosts).

#### When NOT to Use

- Short-lived, event-driven functions (\<15 min). Use Lambda.
- When you want zero server management. Use Fargate or Lambda.
- Simple web applications. Consider App Runner or Lightsail.
- When workloads are extremely bursty and intermittent. Lambda scales to zero; EC2 doesn't.

#### Trade-Offs: EC2 vs Lambda vs ECS/EKS vs Fargate

| Aspect | EC2 | Lambda | ECS on EC2 | ECS on Fargate | EKS |
|---|---|---|---|---|---|
| Control | Full OS | Runtime only | OS + container | Container only | Full K8s |
| Scaling | Minutes (ASG) | Milliseconds | Minutes (ASG) | Seconds | Minutes (Karpenter) |
| Max runtime | Unlimited | 15 min | Unlimited | Unlimited | Unlimited |
| State | Stateful | Stateless | Both | Stateless pref | Both |
| Pricing | Per-instance-hr | Per-invocation+duration | Per-instance-hr | Per-vCPU-hr/GB-hr | Per-instance-hr + $0.10/hr/cluster |
| Ops overhead | High | None | Medium | Low | High |
| GPU | Yes | No | Yes | No (limited) | Yes |
| Max memory | ~24 TiB | 10 GB | Host-dependent | 120 GB (4 vCPU max: 30 GB) | Host-dependent |

#### Failure & Edge Case Behavior

- **Instance failure**: Hardware failure → instance terminated (if EBS-backed, EBS volumes persist). ASG replaces the instance. Instance store data is lost.
- **AZ failure**: All instances in the AZ become unavailable. ASG launches replacements in other AZs.
- **Spot interruption**: 2-minute warning before termination. Handle with interruption handler (drain connections, checkpoint state). Use diversified allocation strategy across instance types and AZs.
- **Insufficient capacity**: If the requested instance type is unavailable in an AZ, launch fails. Use multiple instance types in ASG and multiple AZs.
- **EC2 status checks**: System status check (hardware/AWS infrastructure). Instance status check (OS-level). Impaired status → auto-recovery (if configured) restarts on new hardware.

#### Security & Compliance Implications

- **Encryption**: EBS encryption at rest (AES-256 via KMS). In-transit encryption between EC2 and EBS is automatic for Nitro instances.
- **Instance Metadata Service (IMDSv2)**: Require IMDSv2 (token-based) to prevent SSRF attacks that exfiltrate IAM credentials from metadata. Disable IMDSv1 in production.
- **Nitro Enclaves**: Isolated compute for sensitive data processing. No persistent storage, no network access, no operator SSH. Cryptographic attestation verifies the enclave environment.
- **Inspector**: Automated vulnerability scanning for EC2 instances.
- **Systems Manager Patch Manager**: Automated OS patching.
- **Dedicated Hosts**: Full host visibility. Required for BYOL (Bring Your Own License) scenarios with CPU/socket-based licensing.

#### Cost Model & Optimization

- **On-Demand**: No commitment. Full price. Use for unpredictable workloads.
- **Reserved Instances (RI)**: 1yr or 3yr commitment. Standard RI: up to 72% discount, fixed instance type/AZ (can change AZ/size within family). Convertible RI: up to 66% discount, can change instance family. Capacity reservation with RIs requires zonal scope.
- **Savings Plans**: Compute SP: applies to EC2, Fargate, Lambda. Flexible across families/regions. EC2 Instance SP: specific family + region, deeper discount.
- **Spot**: Up to 90% discount. Interrupted with 2-minute notice. Use for fault-tolerant, batch, CI/CD, big data.
- **Dedicated Hosts**: Most expensive. Required for host-level licensing compliance. Allocation by instance family.
- **Cost traps**: Idle instances (use Compute Optimizer to right-size). Unattached EBS volumes. Old-generation instance types (previous gen costs same but slower). Underutilized RIs.
- **Compute Optimizer**: ML-based recommendations for right-sizing instances.

#### Advanced Professional-Level Exam Traps

1. **Spot interruptions**: Questions test whether you handle 2-minute warnings. Use diversified Spot fleets, checkpointing, and graceful drain.
2. **Launch Template vs Launch Configuration**: Launch Templates are the current standard. Support versioning, mixed instances, multiple instance types. Launch Configurations cannot be modified.
3. **Convertible vs Standard RI**: Convertible allows changing instance family but smaller discount. Standard is locked to the family.
4. **Savings Plans apply across EC2 + Fargate + Lambda**. Compute SP is more flexible than EC2 Instance SP.
5. **Dedicated Hosts vs Dedicated Instances**: Hosts give socket/core visibility for licensing. Dedicated Instances provide hardware isolation but no host-level visibility.
6. **Placement group limits**: Cluster = single AZ, high throughput. Spread = max 7 per AZ. Partition = max 7 partitions per AZ.
7. **IMDSv2**: Require it via Launch Template metadata options. Questions may describe SSRF vulnerabilities — the fix is IMDSv2.
8. **EC2 hibernation** requires encrypted EBS root volume and has memory limits.


### 3.2 AWS Lambda

#### Core Definition

Lambda is a **serverless** compute service that runs code in response to events without provisioning or managing servers. You upload code, define triggers, and AWS handles everything else.

- **Scope**: Regional.
- **Control Plane**: Regional API for function management.
- **Data Plane**: Regional execution environment (microVM-based, Firecracker).
- **Pricing**: $0.20 per 1M invocations + $0.0000166667 per GB-second (x86). ARM (Graviton): 20% cheaper.
- **SLA**: 99.95%.
- **Architectural Abstraction**: Event-driven function-as-a-service on Firecracker microVMs.

#### Core Capabilities

**Execution Model**:
- Maximum execution time: 15 minutes (hard limit).
- Memory: 128 MB to 10,240 MB (10 GB). CPU scales proportionally with memory. At 1,769 MB, you get 1 full vCPU.
- Ephemeral storage (`/tmp`): 512 MB to 10,240 MB (configurable).
- Deployment package: 50 MB (zipped, direct upload) or 250 MB (unzipped, including layers). Container image: up to 10 GB.
- Layers: reusable code/libraries shared across functions. Up to 5 layers per function, total 250 MB unzipped.
- Environment variables: up to 4 KB total.

**Concurrency**:
- Default: 1,000 concurrent executions per region per account (soft limit, can be increased to tens of thousands).
- Reserved concurrency: Guarantees a fixed number of concurrent executions for a function. Subtracts from the account pool.
- Provisioned concurrency: Pre-warms execution environments. Eliminates cold starts. Charged even when idle. Can auto-scale provisioned concurrency based on schedule or utilization.
- Burst concurrency: Initial burst of 500–3,000 (varies by region), then +500/minute.

**Cold Start**:
- First invocation of a new execution environment. Includes: downloading code, initializing runtime, running init code.
- Duration: 100ms–10s depending on runtime, package size, VPC configuration.
- VPC cold start: historically significant (~10s), now mitigated by Hyperplane ENI (shared ENI pool). Still adds some latency.
- Mitigations: Provisioned Concurrency (best), keep function warm with scheduled invocations (hack), minimize package size, use ARM/Graviton, use SnapStart (Java only — snapshots initialized state).

**SnapStart (Java)**: Caches initialized JVM state. Reduces cold start from ~5s to ~200ms for Java functions. Only works with Java (Corretto). Requires publishing a version. Has implications for uniqueness (random number generators, timestamps) — must restore unique state in afterRestore hooks.

**Event Sources** (synchronous vs asynchronous vs stream/queue):
- **Synchronous**: API Gateway, ALB, CloudFront (Lambda@Edge), Cognito triggers. Caller waits for response. Errors return to caller.
- **Asynchronous**: S3, SNS, EventBridge, SES, CloudFormation, CodeCommit. Lambda queues the event internally. Retries twice on failure. Dead-letter queue (SQS/SNS) for failed events. Supports event destination (on success/failure → SQS, SNS, Lambda, EventBridge).
- **Stream/Queue polling**: SQS, Kinesis, DynamoDB Streams, MSK, MQ. Lambda polls the source. Batch processing. Partial batch failure reporting (report which items failed, retry only those).

**VPC Integration**:
- Lambda can run inside a VPC to access private resources (RDS, ElastiCache, etc.).
- Uses Hyperplane ENIs (shared across functions in the same security group + subnet combination).
- Lambda in VPC has NO internet access by default (even with a public subnet). Must use NAT Gateway for internet access or VPC endpoints for AWS services.
- Performance: Hyperplane mitigated most VPC cold start penalty. Minor additional latency.

**Lambda Extensions**: Run additional processes alongside the function (monitoring agents, security agents). Up to 10 extensions. Extensions share the function's resources (memory, CPU, timeout).

#### Architectural Design Patterns

**API Backend**: API Gateway → Lambda → DynamoDB. Fully serverless. Scales to zero.

**Event-Driven Processing**: S3 upload → Lambda → process file → write to DynamoDB / put in SQS.

**Stream Processing**: Kinesis Data Stream → Lambda (batch consumer) → DynamoDB/S3. Use enhanced fan-out for dedicated throughput per consumer.

**Step Functions Orchestration**: Complex workflows with Lambda as task executors. Step Functions handles retries, error handling, parallel execution, wait states.

**Scheduled Tasks**: EventBridge scheduled rule → Lambda. Replaces cron jobs without EC2.

#### When to Use

- Event-driven, short-lived operations (\<15 min).
- APIs with unpredictable traffic patterns (scales to zero).
- Glue code between AWS services.
- Data transformation (ETL, image processing, log processing).
- Real-time stream processing.
- Scheduled tasks.

#### When NOT to Use

- Long-running processes (>15 min). Use ECS/Fargate or Step Functions with distributed processing.
- Consistent, high-throughput workloads. Lambda per-invocation pricing becomes expensive compared to EC2/Fargate at sustained high load. Typically, if you're running >1M invocations/day consistently at high memory, EC2/Fargate is cheaper.
- Workloads requiring GPUs. Lambda has no GPU support.
- Applications with very large binaries or dependencies that exceed 10 GB container image limit.
- Stateful applications requiring persistent local state between invocations.

#### Failure & Edge Case Behavior

- **Throttling**: If concurrent executions exceed the limit, Lambda throttles. Synchronous invocations get HTTP 429. Asynchronous invocations are queued for up to 6 hours. SQS-triggered Lambda uses SQS retry behavior.
- **Cold start storms**: Sudden spike → many cold starts simultaneously. Provisioned concurrency mitigates.
- **Function timeout**: After 15 minutes, Lambda kills the execution. No graceful shutdown. Ensure idempotency — the same event may trigger the function again (especially for async invocations with retries).
- **Poison pill (SQS trigger)**: A message that always fails processing blocks the batch. Use `maxReceiveCount` and dead-letter queue on the SQS queue. Use partial batch failure reporting (`ReportBatchItemFailures`).
- **Stream processing failures**: If Lambda fails on a Kinesis/DynamoDB Stream batch, it retries the same batch (blocking the shard). Use `bisectBatchOnFunctionError` to halve the batch and isolate the bad record. Use `maxRetryAttempts` and `destinationConfig.onFailure`.

#### Security & Compliance Implications

- **Execution role**: IAM role assumed by the function. Defines what AWS services it can access. Follow least privilege.
- **Resource-based policy**: Controls who/what can invoke the function. Critical for cross-account invocations.
- **Environment variable encryption**: Encrypted at rest with KMS (default AWS-managed key or customer-managed key). Can encrypt with a different key for transit encryption.
- **Code signing**: Verify that code hasn't been tampered with. Use AWS Signer.
- **VPC isolation**: Place function in VPC for network-level isolation.

#### Cost Model & Optimization

- **Free tier**: 1M invocations + 400,000 GB-seconds per month.
- **Cost drivers**: Invocations, duration × memory, provisioned concurrency (charged when idle).
- **Optimization**: Right-size memory (use Lambda Power Tuning tool). Use ARM/Graviton (20% cheaper, often faster). Minimize cold starts (reduce package size). Avoid over-provisioning concurrency.
- **Cost trap**: Provisioned concurrency for all functions. Only use for latency-sensitive paths.
- **Cost trap**: Lambda in VPC with NAT Gateway for internet access — NAT Gateway costs dwarf Lambda costs for low-traffic functions. Use VPC endpoints or avoid VPC when possible.

#### Advanced Professional-Level Exam Traps

1. **15-minute maximum execution time**. If a question describes a process that takes 20 minutes, Lambda alone is not the answer.
2. **Lambda in VPC cannot access the internet** without a NAT Gateway. Even in a public subnet with a public IP, Lambda doesn't use the public IP for outbound.
3. **Reserved concurrency = 0 disables the function**. Used as a kill switch.
4. **Synchronous invocation retries are the caller's responsibility**. Lambda does not auto-retry synchronous invocations.
5. **Asynchronous invocation retries twice** (3 total attempts). Then goes to DLQ if configured.
6. **Partial batch failure reporting for SQS** requires `FunctionResponseTypes: [ReportBatchItemFailures]` in the event source mapping.
7. **Lambda@Edge vs CloudFront Functions**: Lambda@Edge runs in regional edge caches (Node.js/Python, up to 30s viewer/5s origin trigger). CloudFront Functions run at all 400+ edge locations (JavaScript only, \<1ms, 2MB max, viewer request/response only). Use CloudFront Functions for simple header manipulation; Lambda@Edge for complex logic.
8. **SnapStart**: Only Java. Restores from snapshot. Must handle uniqueness in `afterRestore` hooks.


### 3.3 Amazon ECS (Elastic Container Service)

#### Core Definition

ECS is AWS's native container orchestration service. It manages the deployment, scheduling, and scaling of containerized applications.

- **Scope**: Regional.
- **Pricing**: ECS control plane is free. You pay for the compute: EC2 instances (ECS on EC2) or Fargate vCPU/memory (ECS on Fargate).
- **SLA**: 99.99%.
- **Architectural Abstraction**: Task scheduler and cluster manager for Docker containers.

#### Core Capabilities

**Launch Types**:
1. **EC2 Launch Type**: You manage EC2 instances (the cluster). ECS places containers (tasks) on your instances. You handle patching, scaling EC2 instances, and capacity management.
2. **Fargate Launch Type**: Serverless. No EC2 instances to manage. Specify CPU/memory per task. AWS manages the underlying infrastructure.
3. **External Launch Type (ECS Anywhere)**: Run ECS tasks on on-premises servers. Register on-prem instances as external instances. Management from AWS console/API.

**Key Concepts**:
- **Task Definition**: Blueprint for a task. Specifies container images, CPU/memory, networking mode, IAM role, volumes, port mappings, logging, health checks.
- **Task**: A running instantiation of a task definition. Can contain 1–10 containers (sidecar pattern).
- **Service**: Maintains a desired number of tasks. Handles deployment (rolling update or blue/green with CodeDeploy), load balancer integration, service discovery, auto-scaling.
- **Cluster**: Logical grouping of tasks/services. Contains the compute capacity (EC2 instances or Fargate).

**Networking Modes**:
- **awsvpc**: Each task gets its own ENI with private IP. Full VPC networking features (security groups per task). REQUIRED for Fargate. Best for production.
- **bridge**: Docker bridge networking. Port mapping from host to container. Multiple tasks share the host's IP.
- **host**: Container uses the host's network directly. Best performance but port conflicts.
- **none**: No external networking.

**Service Discovery**: Integrates with AWS Cloud Map. Tasks register DNS records (A records for `awsvpc`, SRV records for `bridge`). Other services discover tasks via DNS.

**Service Auto Scaling**: Target Tracking (CPU, memory, custom metrics), Step Scaling, Scheduled Scaling. Scales the number of tasks. Note: for EC2 launch type, you also need to scale the EC2 instances (ASG + Capacity Provider).

**Capacity Providers**:
- Fargate, Fargate Spot, and Auto Scaling Group capacity providers.
- Capacity provider strategy: Define a mix of capacity providers (e.g., 70% Fargate, 30% Fargate Spot).
- ASG capacity provider: ECS manages scaling the ASG based on task demand (Cluster Auto Scaler).

**ECS Exec**: Interactive shell access to running containers (similar to `kubectl exec`). Uses SSM Session Manager under the hood. Requires SSM agent in the container.

#### Architectural Design Patterns

**Microservices on Fargate**: Each microservice is a separate ECS service with its own task definition, auto-scaling policy, and ALB target group. Communication via ALB or Cloud Map DNS.

**Sidecar Pattern**: Task definition with multiple containers: main app container + sidecar for logging (Fluentbit), monitoring (Datadog agent), or service mesh proxy (Envoy/App Mesh).

**Blue/Green Deployment**: ECS service with CodeDeploy controller. Two target groups on ALB. CodeDeploy shifts traffic from blue to green target group. Supports canary, linear, and all-at-once traffic shifting.

**Batch Processing on Fargate Spot**: Fargate Spot for batch jobs. Up to 70% cost reduction. Tasks may be interrupted with 30-second warning. Handle checkpointing.

#### When to Use

- Containerized applications without Kubernetes requirements.
- Simpler container orchestration than EKS.
- Tight AWS service integration (ALB, CloudWatch, IAM, Secrets Manager, Parameter Store).
- Mixed EC2 + Fargate capacity strategies.

#### When NOT to Use

- If your team requires Kubernetes compatibility/portability. Use EKS.
- If you need the Kubernetes ecosystem (Helm, operators, CRDs). Use EKS.
- If you're running on-premises with Kubernetes already. Use EKS Anywhere.
- For simple, single-container apps. Consider App Runner.

#### Failure & Edge Case Behavior

- **Task failure**: If a task exits or fails health check, the service scheduler launches a replacement. Minimum healthy percent and maximum percent control rolling deployment behavior.
- **Capacity shortage (EC2)**: If there are no EC2 instances with sufficient resources, tasks stay PENDING. Capacity Providers + ASG auto-scaling resolves this.
- **Fargate capacity**: Rarely, Fargate may not have capacity in an AZ. Use multi-AZ placement.
- **Image pull failure**: If ECR is unreachable or the image doesn't exist, the task fails to start. Use VPC endpoints for ECR in private subnets.

#### Cost Model & Optimization

- ECS control plane: Free.
- **EC2 launch type**: Pay for EC2 instances. Bin-packing tasks onto instances for efficiency. Risk of wasted capacity if instances are underutilized.
- **Fargate**: Pay per vCPU-hour ($0.04048) and GB-hour ($0.004445). No waste (pay exactly for what each task uses). But ~20% more expensive than well-optimized EC2 at steady state.
- **Fargate Spot**: Up to 70% cheaper than Fargate. Interrupted with 30-second notice.
- **Cost trap**: Running many small tasks on Fargate (overhead per task). Consolidate where possible.
- **Savings Plans**: Compute Savings Plans apply to Fargate.

#### Advanced Professional-Level Exam Traps

1. **ECS control plane is free. EKS control plane costs $0.10/hr ($72/month).** ECS is cheaper for simple container orchestration.
2. **awsvpc mode is required for Fargate**. Each task gets its own ENI. This consumes IPs from your subnet — plan CIDR sizing.
3. **Task IAM roles (taskRoleArn)** provide AWS credentials to the container. **Execution role (executionRoleArn)** allows ECS agent to pull images and write logs. Different purposes.
4. **Fargate does not support all Linux capabilities**. `SYS_PTRACE` is supported (for ECS Exec). Others are restricted.
5. **ECS Anywhere**: Requires SSM agent on on-prem servers. Tasks are managed from AWS but run on-prem.


### 3.4 Amazon EKS (Elastic Kubernetes Service)

#### Core Definition

EKS is a managed Kubernetes service. AWS manages the Kubernetes control plane (API server, etcd, scheduler). You manage the worker nodes (or use Fargate).

- **Scope**: Regional.
- **Pricing**: $0.10/hr per cluster ($72/month) for the control plane + compute costs (EC2, Fargate, or Outposts).
- **SLA**: 99.95%.
- **Architectural Abstraction**: Managed Kubernetes control plane with customer-managed or serverless data plane.

#### Core Capabilities

**Control Plane**: AWS manages 3 etcd instances and 2+ API servers across 3 AZs. You cannot SSH into control plane nodes. Automatic Kubernetes version upgrades available.

**Data Plane Options**:
1. **Managed Node Groups**: EC2 instances managed by EKS (ASG under the hood). Automated provisioning, AMI updates, draining.
2. **Self-Managed Nodes**: You manage the EC2 instances and ASG. Full control, more operational burden.
3. **Fargate Profiles**: Serverless. Each pod runs on its own Fargate microVM. No node management. Constraints: no DaemonSets, no privileged containers, no GPU.
4. **Karpenter**: Open-source cluster autoscaler (alternative to Cluster Autoscaler). Provisions optimal EC2 instances based on pod requirements. Faster and more flexible than Cluster Autoscaler.
5. **EKS Anywhere**: Run EKS on-premises on VMware vSphere or bare metal. Separate licensing.

**Networking**:
- **Amazon VPC CNI**: Each pod gets an IP from the VPC subnet. Native VPC networking. Pods are directly addressable within the VPC. Limits: number of IPs per ENI × number of ENIs per instance = max pods per node. Mitigation: prefix delegation (assign /28 prefix per ENI slot, increases pod density).
- **Network Policies**: Calico or native VPC Network Policy (supported since EKS 1.25+).
- **Service Mesh**: AWS App Mesh (Envoy-based) or third-party (Istio, Linkerd).

**Security**:
- **IRSA (IAM Roles for Service Accounts)**: Associates Kubernetes service accounts with IAM roles. Pods assume IAM roles via OIDC federation. Fine-grained IAM per pod. Replaces the node IAM role for pod-level permissions.
- **EKS Pod Identity**: Simplified alternative to IRSA. Associates IAM roles with service accounts via EKS Pod Identity Agent addon.
- **Secrets Management**: Kubernetes secrets (base64, not encrypted by default). Integrate with AWS Secrets Manager or SSM Parameter Store via CSI Secrets Store Driver.
- **Envelope Encryption**: Encrypt Kubernetes secrets in etcd with a KMS key.

**Observability**:
- Container Insights (CloudWatch) for cluster/pod metrics.
- AWS Distro for OpenTelemetry (ADOT) for tracing.
- Prometheus-compatible metrics via Amazon Managed Prometheus (AMP).
- Logging: Fluentbit DaemonSet → CloudWatch Logs.

#### Architectural Design Patterns

**Multi-Tenant Kubernetes**: Namespace isolation, Network Policies, IRSA for per-tenant IAM. Resource quotas per namespace. OPA Gatekeeper for policy enforcement.

**Hybrid Kubernetes**: EKS in AWS + EKS Anywhere on-premises. GitOps with Flux or ArgoCD for consistent deployments across environments.

**Spot Instances for Workers**: Karpenter provisions Spot instances for non-critical workloads. On-Demand for system pods and critical workloads.

#### When to Use

- Existing Kubernetes expertise/tooling.
- Need for Kubernetes ecosystem (Helm, operators, CRDs, service mesh).
- Multi-cloud/hybrid portability requirements.
- Complex workloads needing Kubernetes scheduling features (affinity, taints, tolerations).

#### When NOT to Use

- Simple containerized applications without Kubernetes needs. Use ECS (cheaper, simpler).
- Serverless-first strategy. Use Lambda or ECS on Fargate.
- Small teams without Kubernetes expertise. EKS operational complexity is significant.

#### Trade-Offs: EKS vs ECS

| Aspect | EKS | ECS |
|---|---|---|
| Control plane cost | $0.10/hr ($72/mo) | Free |
| Ecosystem | Full Kubernetes | AWS-specific |
| Portability | High (Kubernetes standard) | Low (AWS-locked) |
| Complexity | High | Medium |
| Fargate support | Yes (limited) | Yes (full) |
| Community | Massive | AWS-focused |
| DaemonSets | Yes | No (sidecar containers instead) |
| Service Mesh | Any (Istio, Linkerd, App Mesh) | App Mesh |
| On-premises | EKS Anywhere | ECS Anywhere |

#### Advanced Professional-Level Exam Traps

1. **EKS control plane costs $0.10/hr**. ECS is free. Cost-sensitive questions may prefer ECS.
2. **IRSA vs node-level IAM**: IRSA provides pod-level permissions. Without IRSA, all pods on a node share the node's IAM role (overly broad). Questions may test this.
3. **VPC CNI IP limitations**: Pod density is limited by ENI/IP capacity per instance type. Prefix delegation or custom CNI plugins can increase density.
4. **Fargate on EKS**: No DaemonSets, no privileged pods, no GPU, no HostNetwork. If a question requires any of these, Fargate is not the answer.
5. **Kubernetes version lifecycle**: EKS supports 4 minor versions. You must upgrade regularly. End of support = forced upgrade.


### 3.5 AWS Fargate

#### Core Definition

Fargate is a **serverless compute engine** for containers. Not a standalone service — it is a launch type for ECS and EKS. You specify CPU and memory per task/pod; AWS manages the infrastructure.

- **Pricing**: Per vCPU-second and per GB-second. Fargate Spot: up to 70% discount.
- **Fargate for ECS**: Fully supported. All ECS features except daemon tasks.
- **Fargate for EKS**: Supported but with limitations (no DaemonSets, no privileged containers, no GPU, no EBS volumes for persistent storage — use EFS instead).

#### Key Constraints

- vCPU: 0.25 to 16 vCPU.
- Memory: 0.5 GB to 120 GB (valid combinations defined per vCPU).
- Ephemeral storage: up to 200 GB.
- No SSH access to underlying host.
- No Docker socket access.
- Cannot run with elevated privileges (no `--privileged` flag).

#### When to Use

- When you want zero infrastructure management for containers.
- Bursty container workloads (auto-scales, no idle capacity waste).
- Per-task isolation (each task runs on its own microVM).

#### When NOT to Use

- GPU workloads. Use EC2 with GPU instances.
- Workloads requiring specific OS kernel modules.
- Consistently high-utilization workloads where reserved EC2 is cheaper.
- When you need DaemonSets (EKS on Fargate doesn't support them).


### 3.6 AWS Batch

#### Core Definition

Batch runs batch computing workloads at any scale. It automatically provisions the optimal compute resources (EC2, Spot, Fargate) based on the volume and requirements of submitted jobs.

- **Scope**: Regional.
- **Pricing**: Free (pay for underlying compute).
- **Architectural Abstraction**: Job scheduler and resource manager for batch workloads.

#### Core Capabilities

- **Job Definitions**: Container image, vCPU, memory, command, IAM role, retry strategy.
- **Job Queues**: Priority-based queues. Multiple queues can map to different compute environments.
- **Compute Environments**: Managed (AWS provisions EC2/Fargate) or Unmanaged (you manage). Managed supports On-Demand, Spot, Fargate, Fargate Spot.
- **Array Jobs**: Submit thousands of related jobs as a single array. Each gets an index.
- **Job Dependencies**: Jobs can depend on other jobs (sequential pipelines).
- **Multi-node Parallel Jobs**: Distribute a single job across multiple EC2 instances for tightly coupled HPC workloads. Uses EFA for inter-node communication.
- **Scheduling**: FIFO within priority. Fair-share scheduling available for multi-tenant environments.

#### When to Use

- Batch processing: genomics, financial modeling, rendering, ETL.
- When you need automatic infrastructure scaling for variable batch workloads.
- Cost optimization via Spot instances for fault-tolerant batch jobs.

#### When NOT to Use

- Real-time processing. Use Lambda or ECS.
- Simple, periodic jobs. Use EventBridge + Lambda.
- Complex workflow orchestration. Use Step Functions.

#### Advanced Professional-Level Exam Traps

1. **Batch vs Lambda**: Batch for long-running (hours), large-memory jobs. Lambda for short (\<15 min), event-driven.
2. **Batch on Fargate**: Simpler, no EC2 management, but limited to 16 vCPU / 120 GB memory per job. For large jobs, use EC2 compute environment.
3. **Multi-node parallel jobs require EC2** (not Fargate).
4. **Spot interruption handling**: Batch automatically retries interrupted Spot jobs (up to retry count).


### 3.7 AWS App Runner

#### Core Definition

App Runner is a fully managed service for running containerized web applications and APIs at scale. No infrastructure management. Simplest container deployment option.

- **Scope**: Regional.
- **Pricing**: Per vCPU-second (active) + per GB-second (active) + per provisioned container instance (idle).
- **Architectural Abstraction**: Fully managed container platform (like Heroku/Cloud Run).

#### Core Capabilities

- Source: Container image (ECR) or source code (GitHub).
- Auto-scaling: Based on concurrent requests. Scale to zero is NOT supported — minimum 1 instance.
- Custom domain and HTTPS (automatic TLS).
- VPC integration: Connect to VPC resources (RDS, ElastiCache) via VPC connector.
- Observability: CloudWatch metrics and logs, X-Ray tracing.

#### When to Use

- Simple web apps and APIs. Teams that don't want to manage ECS/EKS.
- Rapid deployment from source code or container image.

#### When NOT to Use

- Complex microservice architectures. Use ECS/EKS.
- Non-HTTP workloads (batch, streaming). Not supported.
- When you need full control over networking, scaling policies, or deployment strategies.
- Scale-to-zero requirement. Use Lambda.


### 3.8 AWS Outposts

#### Core Definition

Outposts brings AWS infrastructure and services to on-premises. AWS delivers, installs, and manages physical racks in your data center.

- **Scope**: Extension of a specific AWS region/AZ. Treated as an extension of the parent region.
- **Pricing**: Rack-based (3-year commitment). Pay for the hardware configuration.
- **Services available**: EC2, EBS, S3 on Outposts, ECS, EKS, RDS, EMR, ALB.
- **Architectural Abstraction**: AWS-managed on-premises infrastructure connected to the parent region.

#### Core Capabilities

- Low-latency access to on-premises systems.
- Data residency: Keep data on-premises while using AWS APIs.
- Local compute and storage with cloud management.
- Requires reliable network connectivity back to the parent AWS region (for control plane operations).
- **S3 on Outposts**: Local S3 storage. 48 TB to 96 TB. Data stays on the Outpost.

#### When to Use

- Low-latency requirements for on-premises data.
- Data residency/sovereignty requirements.
- Hybrid workloads that need consistent AWS APIs on-premises and in cloud.

#### When NOT to Use

- If you can run entirely in an AWS region. Outposts is expensive and complex.
- If you don't need AWS-native APIs on-premises. Consider VMware or other on-prem solutions.
- Unreliable network to the parent region. Control plane operations fail without connectivity.

#### Advanced Professional-Level Exam Traps

1. **Outposts requires connectivity to the parent region**. If the network link is down, the control plane is unavailable (can't launch new instances), but existing workloads continue.
2. **Outposts is NOT the same as Local Zones**. Outposts = your data center. Local Zones = AWS-managed in a metro area.
3. **S3 on Outposts has limited capacity** and does not support all S3 features (no S3 Glacier, no cross-region replication, limited storage classes).

## 4. Storage

Storage choices on the SAP-C02 are never simple "which is cheapest?" questions. They test durability vs availability vs performance vs access pattern vs cost at scale. You must reason about consistency models, replication mechanics, lifecycle transitions, and cross-region implications.


### 4.1 Amazon S3 (Simple Storage Service)

#### Core Definition

S3 is an **object storage** service with virtually unlimited capacity. It stores objects (files up to 5 TB) in buckets. It is the foundational storage service in AWS.

- **Scope**: Global namespace (bucket names are globally unique), but data is stored in a specific region.
- **Control Plane**: Regional. Bucket creation and configuration are regional API calls. Exception: bucket creation defaults to us-east-1 unless you specify a region.
- **Data Plane**: Regional. Object reads/writes go to the region where the bucket exists.
- **Pricing**: Varies by storage class. S3 Standard: $0.023/GB/month (first 50 TB). PUT/GET requests charged separately. Data transfer out charged.
- **SLA**: 99.9% availability (Standard). 99.99% designed availability. 11 nines (99.999999999%) durability.
- **Architectural Abstraction**: Distributed object store with HTTP API. Objects are automatically replicated across at least 3 AZs (for most storage classes).

#### Core Capabilities

**Storage Classes** (critical for SAP-C02):

| Class | Durability | Availability | Min Storage | Retrieval | Use Case |
|---|---|---|---|---|---|
| **Standard** | 11 9s | 99.99% | None | Instant | Frequently accessed |
| **Intelligent-Tiering** | 11 9s | 99.9% | None | Instant (except Archive) | Unknown access patterns |
| **Standard-IA** | 11 9s | 99.9% | 30 days, 128 KB | Instant | Infrequent, rapid access needed |
| **One Zone-IA** | 11 9s | 99.5% | 30 days, 128 KB | Instant | Reproducible infrequent data |
| **Glacier Instant Retrieval** | 11 9s | 99.9% | 90 days, 128 KB | Instant (ms) | Archive, quarterly access |
| **Glacier Flexible Retrieval** | 11 9s | 99.99% (after restore) | 90 days, 40 KB | Minutes to hours | Archive, flexible retrieval |
| **Glacier Deep Archive** | 11 9s | 99.99% (after restore) | 180 days, 40 KB | 12-48 hours | Long-term archive, compliance |
| **S3 Express One Zone** | N/A (single AZ) | 99.95% | None | Single-digit ms | Lowest latency, ML, analytics |

**Key Storage Class Details**:
- **Intelligent-Tiering**: Automatic tiering based on access patterns. No retrieval fees. Small monitoring fee ($0.0025/1000 objects/month). Tiers: Frequent → Infrequent (30 days) → Archive Instant (90 days) → Archive (optional, 90 days) → Deep Archive (optional, 180 days). Best when access pattern is unpredictable.
- **IA classes**: Minimum 30-day storage charge. Objects smaller than 128 KB are charged for 128 KB. Retrieval fees apply. Cost trap: frequent access of IA data costs more than Standard.
- **One Zone-IA**: Data in a single AZ. If that AZ is destroyed, data is lost. Only use for data that can be recreated. Still 11 nines durability (within the AZ).
- **Glacier Flexible Retrieval tiers**: Expedited (1-5 min, expensive), Standard (3-5 hours), Bulk (5-12 hours, cheapest).
- **Glacier Deep Archive tiers**: Standard (12 hours), Bulk (48 hours).
- **S3 Express One Zone**: Directory buckets, single AZ, 10x faster than Standard. Purpose-built for compute-adjacent analytics.

**Versioning**:
- Bucket-level setting. Once enabled, can only be suspended (not disabled).
- Each version is a separate object with its own storage charge.
- Delete operation adds a delete marker (soft delete). Previous versions still exist.
- MFA Delete: Require MFA to permanently delete versions or change versioning state.
- Critical for data protection and compliance.

**Lifecycle Policies**:
- Transition objects between storage classes based on age.
- Expire (delete) objects after a specified period.
- Abort incomplete multipart uploads (important — incomplete uploads incur storage charges).
- Apply to prefix or tag filters.
- Transition waterfall: Standard → Standard-IA → Intelligent-Tiering → One Zone-IA → Glacier Instant → Glacier Flexible → Deep Archive. Cannot skip backwards. Minimum 30 days in Standard before transition to IA.

**Replication**:
- **Cross-Region Replication (CRR)**: Replicate objects to a bucket in a different region. For DR, compliance (data residency), latency reduction.
- **Same-Region Replication (SRR)**: Replicate within the same region. For log aggregation, live replication between production and test.
- Requirements: Versioning enabled on both source and destination. IAM role for replication.
- **Replication Time Control (RTC)**: 99.99% of objects replicated within 15 minutes. SLA-backed. Additional cost.
- Replication scope: all objects, prefix filter, or tag filter.
- Replication does NOT retroactively replicate existing objects. Use S3 Batch Replication for existing data.
- Delete markers are NOT replicated by default (can be enabled).
- Replication is one-directional. For bidirectional, configure replication in both directions (and handle conflict resolution carefully).

**Encryption**:
- **SSE-S3**: AWS-managed keys. Default encryption. No additional cost. No audit trail of key usage.
- **SSE-KMS**: AWS KMS-managed keys. CloudTrail logs every access. Supports CMK rotation. KMS API rate limits apply (key consideration for high-throughput workloads — GenerateDataKey calls are throttled).
- **SSE-C**: Customer-provided keys. You manage keys entirely. AWS does not store your key.
- **CSE (Client-Side Encryption)**: Encrypt before upload. AWS never sees plaintext.
- Bucket default encryption: Set the default encryption for all objects. Can be enforced via bucket policy denying unencrypted uploads.
- S3 Bucket Keys: Reduces KMS costs by generating a bucket-level data key, reducing per-object KMS API calls. Significant cost optimization for SSE-KMS with high object counts.

**Access Control**:
- **Bucket Policies**: Resource-based JSON policies. Control access at bucket and object prefix level. Can enforce encryption, restrict IP ranges, require VPC endpoints, restrict to organization accounts.
- **ACLs**: Legacy. Disabled by default for new buckets (Bucket Owner Enforced). Do not use for new architectures.
- **Access Points**: Simplified access management. Each access point has its own DNS name, policy, and VPC restriction. Useful for shared data lakes where different teams need different access patterns.
- **Object Lambda Access Points**: Transform data on read using a Lambda function (e.g., redact PII, resize images, decompress).
- **Block Public Access**: Account-level and bucket-level settings to prevent accidental public exposure. Enable at account level as a guardrail.
- **Pre-Signed URLs**: Time-limited URLs for temporary access. Upload or download. Respect the signer's permissions.

**Performance**:
- 3,500 PUT/COPY/POST/DELETE and 5,500 GET/HEAD requests per second per prefix.
- Scale across prefixes for higher throughput (parallelize across multiple prefixes).
- Multipart upload: Required for objects >5 GB. Recommended for objects >100 MB. Parallel uploads for higher throughput.
- S3 Transfer Acceleration: Uses CloudFront edge locations to accelerate uploads. Data enters at the nearest edge, then transfers to S3 over AWS backbone. Additional cost ($0.04–$0.08/GB).
- Byte-Range Fetches: Download specific byte ranges of an object. Useful for parallel downloads or reading specific sections of large files.

**Event Notifications**:
- Trigger on object creation, deletion, restore, replication.
- Destinations: SNS, SQS, Lambda, EventBridge.
- EventBridge destination enables advanced filtering, multiple targets, archive/replay.

**S3 Select / Glacier Select**: Query a subset of data within an object using SQL. Reduces data transfer. Supports CSV, JSON, Parquet. Being superseded by S3 Object Lambda and Athena for complex queries.

**S3 Object Lock**:
- WORM (Write Once Read Many) protection.
- **Governance Mode**: Users with special permissions can delete or overwrite. Audit-friendly.
- **Compliance Mode**: Nobody can delete or overwrite, including the root user. Immutable for the retention period. Required for SEC 17a-4, FINRA.
- **Legal Hold**: Indefinite lock. Independent of retention period. Apply/remove with IAM permission.
- Requires versioning.

**S3 Batch Operations**: Large-scale operations on billions of objects. Copy, invoke Lambda, restore from Glacier, apply tags, change ACLs, replicate. Uses S3 Inventory or manifest file as input.

#### Architectural Design Patterns

**Data Lake Foundation**: S3 as the central data lake. Raw zone (Standard), processed zone (Standard-IA), archive zone (Glacier). Athena, Redshift Spectrum, EMR query in-place. Glue for ETL and Data Catalog.

**Static Website + CloudFront**: S3 hosts static assets. CloudFront distributes globally. OAC (Origin Access Control) restricts direct S3 access.

**Cross-Account Data Sharing**: Bucket policy with `aws:PrincipalOrgID` condition. Access Points per team. CloudTrail and S3 server access logging for audit.

**Backup and Compliance Archive**: S3 Object Lock (Compliance mode) for regulatory data. Lifecycle to Glacier Deep Archive. Cross-region replication for DR.

#### When to Use

- Object storage for any file type at any scale.
- Data lake storage.
- Static website hosting.
- Backup and archive.
- Log storage.
- ML training data.

#### When NOT to Use

- Block storage needs (mounted filesystem). Use EBS or EFS.
- POSIX-compliant filesystem. Use EFS or FSx.
- Low-latency, single-digit millisecond database-like access. Use DynamoDB or ElastiCache. (Exception: S3 Express One Zone for certain workloads.)
- Frequently mutated small objects where you need strong consistency for reads and writes in parallel. S3 provides read-after-write consistency, but it's not a database.

#### Trade-Offs: S3 vs EBS vs EFS vs FSx

| Aspect | S3 | EBS | EFS | FSx Lustre | FSx Windows |
|---|---|---|---|---|---|
| Type | Object | Block | File (NFS) | File (Lustre) | File (SMB) |
| Access | HTTP API | EC2 mount | Multi-AZ mount | Multi-AZ mount | Multi-AZ mount |
| Max size | Unlimited | 64 TiB/vol | Petabytes | Petabytes | 64 TiB |
| Latency | ~10-100ms | \<1ms | ~1-10ms | \<1ms | \<1ms |
| Durability | 11 9s | 99.8-99.999% | 11 9s (Regional) | Varies | Varies |
| Concurrent access | Unlimited | 1 instance (io2 Multi-Attach: up to 16) | Thousands | Thousands | Thousands |
| Cost/GB | $0.023 | $0.08 (gp3) | $0.30 (Standard) | $0.14 | $0.13 |
| POSIX | No | Yes | Yes | Yes | No (SMB) |

#### Failure & Edge Case Behavior

- **Strong Read-After-Write Consistency**: Since Dec 2020, S3 provides strong consistency for PUT and DELETE operations. A GET after a successful PUT returns the latest version. A GET after a successful DELETE returns 404. No more eventual consistency issues for data path operations.
- **Bucket creation**: Eventually consistent for listing all buckets. A newly created bucket may not immediately appear in ListBuckets.
- **Replication lag**: CRR/SRR replication is asynchronous. Without RTC, replication timing is best-effort. RTC guarantees 15 minutes for 99.99% of objects.
- **Throttling**: 503 Slow Down errors if you exceed per-prefix request limits. Use exponential backoff. Distribute across prefixes.
- **Multipart upload cleanup**: Incomplete multipart uploads persist indefinitely and incur storage charges. Use lifecycle rules to abort them.
- **KMS throttling**: SSE-KMS at high throughput can hit KMS GenerateDataKey rate limits (5,500–30,000 requests/second depending on region). Use S3 Bucket Keys to reduce KMS calls.

#### Security & Compliance Implications

- **Block Public Access**: Enable at the account level. Use SCPs to prevent disabling it.
- **Bucket policies**: Use `aws:SecureTransport` condition to deny HTTP (require HTTPS).
- **VPC Endpoints**: Gateway endpoint for S3 to keep traffic private. Endpoint policy restricts which buckets/actions are accessible through the endpoint.
- **Access Logging**: S3 server access logs → another S3 bucket. Or use CloudTrail data events for API-level logging.
- **Macie**: Automated sensitive data discovery in S3 (PII, credentials, etc.).
- **Object Lock + Glacier Vault Lock**: For regulatory compliance (SEC, FINRA, HIPAA).

#### Cost Model & Optimization

- **Storage class selection**: Most impactful optimization. Use Intelligent-Tiering for unknown patterns. Use lifecycle policies for known patterns.
- **Requester Pays**: The requester (not bucket owner) pays for data transfer. Useful for shared datasets.
- **S3 Inventory**: Cheaper than LIST operations for large buckets. Use for auditing storage classes, encryption status, replication status.
- **Avoid small objects in IA/Glacier**: Minimum charge of 128 KB (IA) or 40 KB (Glacier). Aggregate small files before archiving.
- **Abort incomplete multipart uploads**: Use lifecycle rules (saves storage cost).
- **S3 Bucket Keys**: Reduces KMS costs dramatically for SSE-KMS workloads.
- **Transfer costs**: S3 data transfer IN is free. Transfer OUT to internet is tiered ($0.09/GB first 10 TB). Transfer to CloudFront is free. Transfer to same-region services is free. Cross-region transfer is charged.

#### Advanced Professional-Level Exam Traps

1. **S3 is strongly consistent** as of Dec 2020. Questions referencing eventual consistency for read-after-write are outdated. However, LIST operations on the bucket level can still show stale results briefly.
2. **Glacier Flexible Retrieval is NOT instant**. If a question requires immediate access to archived data, the answer is Glacier Instant Retrieval, not Glacier Flexible.
3. **Object Lock Compliance mode cannot be overridden by anyone**, including the root account. Governance mode can be overridden with specific permissions.
4. **CRR does not replicate existing objects**. Use S3 Batch Replication for backfill.
5. **S3 Transfer Acceleration vs Direct upload**: Acceleration is only beneficial for long-distance uploads. For same-region or nearby uploads, direct upload may be faster.
6. **KMS throttling with SSE-KMS**: High-throughput workloads can hit KMS limits. S3 Bucket Keys or SSE-S3 are alternatives.
7. **Minimum storage duration charges**: Deleting an IA object after 15 days still incurs 30-day charge. Same for Glacier (90/180 days).
8. **VPC Gateway Endpoint for S3 is free**. Interface endpoint costs money. For cost optimization, always use Gateway endpoint.
9. **Pre-signed URLs inherit the signer's permissions**. If the IAM user/role's permissions change or expire, the pre-signed URL stops working.


### 4.2 Amazon EBS (Elastic Block Store)

#### Core Definition

EBS provides persistent block storage volumes for EC2 instances. Think of it as a virtual hard drive that persists independently of the instance lifecycle.

- **Scope**: AZ-specific. An EBS volume exists in a single AZ and can only be attached to instances in that AZ.
- **Pricing**: Per-GB-month + IOPS provisioned (for io1/io2) + throughput provisioned (for gp3).
- **SLA**: 99.8–99.999% durability depending on volume type. 99.99% availability for io2 Block Express.
- **Architectural Abstraction**: Network-attached block storage replicated within an AZ.

#### Core Capabilities

**Volume Types**:

| Type | IOPS (max) | Throughput (max) | Latency | Use Case |
|---|---|---|---|---|
| **gp3** | 16,000 | 1,000 MB/s | Single-digit ms | General purpose (default) |
| **gp2** | 16,000 (burst) | 250 MB/s | Single-digit ms | General purpose (legacy) |
| **io2 Block Express** | 256,000 | 4,000 MB/s | Sub-ms | Critical databases, SAP HANA |
| **io1** | 64,000 | 1,000 MB/s | Single-digit ms | Databases, high IOPS |
| **st1** | 500 | 500 MB/s | Low | Throughput-intensive (logs, Kafka) |
| **sc1** | 250 | 250 MB/s | Low | Cold storage, infrequent access |

**Key Details**:
- gp3: Baseline 3,000 IOPS and 125 MB/s included. Independently provision IOPS (up to 16,000) and throughput (up to 1,000 MB/s). 20% cheaper than gp2 at baseline.
- gp2: IOPS scales with volume size (3 IOPS/GB, burst to 3,000). No independent IOPS provisioning.
- io2 Block Express: 99.999% durability (5 nines). Multi-Attach support. Up to 64 TiB.
- **Multi-Attach (io1/io2)**: Attach a single volume to up to 16 Nitro instances in the same AZ. Application must manage concurrent writes (cluster-aware filesystem required). NOT general-purpose file sharing.
- st1/sc1: Cannot be boot volumes. HDD-based. Optimized for sequential access.

**Snapshots**:
- Point-in-time backups stored in S3 (you don't see them in your S3 buckets).
- Incremental: Only changed blocks are stored after the first snapshot.
- Can be copied to other regions (for DR).
- Can be shared cross-account (including encrypted snapshots if you share the KMS key).
- Fast Snapshot Restore (FSR): Eliminate initialization penalty when creating a volume from a snapshot. $0.75/hr per AZ per snapshot. Expensive.
- EBS Snapshots Archive: Move snapshots to archive tier (75% cheaper). Retrieval takes 24-72 hours.
- Recycle Bin: Protect against accidental deletion. Retain deleted snapshots/AMIs for a configurable period.

**Encryption**:
- AES-256 encryption at rest and in transit (between EC2 and EBS).
- Uses KMS keys (AWS-managed or customer-managed).
- Encrypted volumes produce encrypted snapshots. Encrypted snapshots produce encrypted volumes.
- You cannot un-encrypt an encrypted volume directly. Workaround: create a snapshot, copy with a new key, create a new unencrypted volume (but this is unusual; you'd typically want everything encrypted).
- Default encryption: Enable at account/region level so all new volumes are encrypted automatically.

**Elastic Volumes**:
- Modify volume type, size, and IOPS on a live, attached volume without downtime.
- Size can only increase, not decrease.
- Modification takes time. Only one modification per 6 hours.

#### Architectural Design Patterns

**Boot + Data Volume Separation**: OS on gp3. Data on io2 (high IOPS) or st1 (throughput). Enables independent snapshot schedules and lifecycle management.

**RAID 0 for Performance**: Stripe multiple EBS volumes for aggregate IOPS and throughput. EBS doesn't natively support RAID; configure at OS level. Use for workloads exceeding single-volume limits.

**Cross-Region DR**: Automated EBS snapshots via AWS Backup or Data Lifecycle Manager (DLM). Copy snapshots to DR region. Automate volume creation from snapshots in DR.

#### When to Use

- EC2 boot volumes.
- Database storage (RDS uses EBS under the hood).
- Applications requiring persistent, low-latency block storage.
- When you need snapshot-based backup and recovery.

#### When NOT to Use

- Shared file storage across instances. Use EFS or FSx.
- Object storage. Use S3.
- Temporary/ephemeral data. Use instance store (faster, free).
- Cross-AZ shared storage. EBS is AZ-locked. Use EFS.

#### Failure & Edge Case Behavior

- **AZ failure**: EBS volumes in the failed AZ are unavailable. Data is replicated within the AZ for durability, but NOT across AZs. Snapshots (stored in S3) survive AZ failure.
- **Volume impairment**: Rare, but I/O can stall if underlying hardware degrades. EBS sends status events. Snapshot to another volume.
- **Snapshot consistency**: EBS snapshots are crash-consistent, NOT application-consistent. For databases, freeze I/O or flush buffers before snapshotting. Better: use application-level backup (e.g., RDS automated backups).

#### Cost Model & Optimization

- gp3 is almost always cheaper than gp2 for the same performance. Migrate gp2 → gp3.
- Delete unattached volumes (common waste).
- Use DLM/AWS Backup for snapshot lifecycle management. Delete old snapshots.
- EBS Snapshots Archive: 75% cheaper for long-retention snapshots.
- Fast Snapshot Restore: Only enable for critical volumes where initialization latency is unacceptable.

#### Advanced Professional-Level Exam Traps

1. **EBS is AZ-specific**. Cannot attach to an instance in a different AZ. Must use snapshots to move data across AZs.
2. **gp3 vs gp2**: gp3 is cheaper and allows independent IOPS/throughput provisioning. Exam may test migration scenarios.
3. **io2 Block Express**: 256,000 IOPS, sub-ms latency, 99.999% durability. For the most demanding database workloads.
4. **Multi-Attach requires cluster-aware filesystem**. Not ext4/xfs. Use GFS2 or similar. This is NOT a general file-sharing solution.
5. **Snapshots are incremental** but each snapshot is independently restorable. Deleting intermediate snapshots does NOT break later snapshots.
6. **Encryption is free**. No reason not to encrypt. Enable default encryption at account level.


### 4.3 Amazon EFS (Elastic File System)

#### Core Definition

EFS is a managed NFS file system that can be mounted by multiple EC2 instances, Lambda functions, and ECS/EKS tasks concurrently across multiple AZs.

- **Scope**: Regional (data replicated across AZs in a region). One Zone option available.
- **Pricing**: Standard: $0.30/GB/month. IA: $0.016/GB/month + $0.01/GB accessed. One Zone: 47% cheaper.
- **SLA**: 99.99% (Regional). 99.9% (One Zone).
- **Architectural Abstraction**: Managed NFS v4.1 distributed file system.

#### Core Capabilities

**Storage Classes**:
- **Standard**: Frequently accessed data. Multi-AZ.
- **Standard-IA**: Infrequent access. Multi-AZ. Lower storage cost, retrieval fee.
- **One Zone**: Frequently accessed, single AZ. 47% cheaper than Standard.
- **One Zone-IA**: Single AZ + infrequent access. Cheapest option.
- Lifecycle management: Automatically transition files between Standard and IA based on access patterns (configurable: 7, 14, 30, 60, 90, 180, 270, 365 days).

**Performance Modes**:
- **General Purpose**: Default. Low latency. Suitable for most workloads. Up to 35,000 read IOPS and 7,000 write IOPS.
- **Max I/O**: Higher aggregate throughput and IOPS. Higher latency. For highly parallelized workloads (big data, media processing). Legacy — Elastic Throughput is preferred.

**Throughput Modes**:
- **Elastic** (recommended): Automatically scales throughput. Pay per GB transferred. Up to 10 GB/s reads, 3 GB/s writes.
- **Bursting**: Throughput scales with file system size. Baseline: 50 KB/s per GB stored. Burst: up to 100 MB/s. Small file systems have limited throughput.
- **Provisioned**: Specify throughput independently of storage size. For workloads that need high throughput with small storage.

**Access**:
- NFS v4.1 protocol.
- Mount from EC2, Lambda (via EFS mount point), ECS (task storage), EKS (persistent volumes via EFS CSI driver).
- Cross-VPC access via VPC Peering or Transit Gateway (mount via IP address).
- Cross-region: Use EFS Replication (asynchronous, RPO in minutes).
- On-premises access: Via Direct Connect or VPN (NFS over the network).

**Security**:
- Encryption at rest (KMS) and in transit (TLS via EFS mount helper).
- POSIX file permissions (uid/gid).
- Security groups on mount targets.
- IAM authorization for NFS clients (EFS Access Points).
- **Access Points**: Application-specific entry points. Define a POSIX user/group and root directory. Enforces identity on all file operations through the access point.

#### Architectural Design Patterns

**Shared Application Storage**: Web server fleet mounts EFS for shared content (WordPress media, configuration files).

**Lambda Shared Storage**: Lambda functions mount EFS for shared data across invocations and functions. Useful for ML model files, reference data.

**Container Persistent Storage**: ECS/EKS tasks use EFS for persistent volumes. Survives task restarts. Shared across tasks.

#### When to Use

- Shared file storage across multiple instances/containers/Lambda.
- POSIX-compliant filesystem requirements.
- Workloads that need to scale storage automatically.
- Content management systems, web serving, development environments.

#### When NOT to Use

- Single-instance, high-IOPS block storage. Use EBS (lower latency, higher IOPS).
- Windows file shares. Use FSx for Windows.
- HPC with Lustre requirements. Use FSx for Lustre.
- Object storage. Use S3.
- Latency-sensitive databases. Use EBS or instance store.

#### Cost Model & Optimization

- EFS Standard is expensive ($0.30/GB). Use lifecycle policies to move infrequently accessed data to IA ($0.016/GB).
- One Zone is 47% cheaper but sacrifices multi-AZ durability.
- Elastic Throughput: Pay-per-use is cost-effective for bursty workloads.
- Bursting mode: Free throughput but limited by storage size. Small file systems with high throughput needs should use Provisioned or Elastic.

#### Advanced Professional-Level Exam Traps

1. **EFS is NFS (Linux only)**. Windows instances cannot mount EFS. Use FSx for Windows.
2. **EFS latency is higher than EBS**. For latency-sensitive databases, EBS is preferred.
3. **Bursting throughput depends on storage size**. A 1 GB file system gets minimal throughput. Switch to Elastic or Provisioned.
4. **EFS Replication is async**. Not suitable for RPO=0 requirements.
5. **Lambda + EFS**: Function must be in a VPC to mount EFS. EFS Access Points are used for Lambda mounts.
6. **Cross-region access is not direct**. Use EFS Replication for cross-region data availability, not cross-region NFS mounts.


### 4.4 Amazon FSx

AWS offers four FSx variants, each purpose-built:

#### 4.4.1 FSx for Windows File Server

**Core Definition**: Fully managed Windows-native file system. SMB protocol. Built on Windows Server.

- **Scope**: Single AZ or Multi-AZ deployment.
- **Pricing**: $0.13/GB/month (SSD) or $0.025/GB/month (HDD). Throughput capacity charged separately.
- Supports Microsoft DFS (Distributed File System) for namespace aggregation.
- Integrates with AWS Managed Microsoft AD or self-managed AD.
- VSS (Volume Shadow Copy): user-initiated backups, end-user file restore.
- Deduplication: Reduces storage for duplicated data (saves 50-80% for typical file shares).
- Quotas: File system size up to 64 TiB.

**When to Use**: Windows workloads needing SMB, Active Directory integration, DFS Namespaces, or NTFS features.

**When NOT to Use**: Linux workloads (use EFS). HPC (use FSx for Lustre).

#### 4.4.2 FSx for Lustre

**Core Definition**: Managed high-performance Lustre parallel file system. Sub-millisecond latency, hundreds of GB/s throughput.

- **Scope**: Single AZ only.
- **Pricing**: Persistent: $0.145/GB/month (SSD). Scratch: $0.14/GB/month.
- **Deployment types**: Scratch (temporary, higher performance, no replication — data lost on failure) and Persistent (replicated within AZ, for longer-term workloads).
- **S3 Integration**: Transparently linked to an S3 bucket. Data is lazy-loaded from S3 on first access. Write-back to S3 via `hsm_archive`.
- **Performance**: Up to 1 TB/s throughput, millions of IOPS. Designed for HPC, ML training, genomics, financial modeling.
- Data Compression: LZ4 compression reduces storage cost.

**When to Use**: HPC, ML training data, video processing, financial simulations. Any workload needing extreme throughput with POSIX.

**When NOT to Use**: General-purpose file sharing. Long-term storage (use S3 with Lustre as a cache). Multi-AZ durability (Lustre is single AZ).

#### 4.4.3 FSx for NetApp ONTAP

**Core Definition**: Managed NetApp ONTAP file system. Supports NFS, SMB, and iSCSI simultaneously. Full ONTAP feature set.

- Multi-protocol: Linux (NFS), Windows (SMB), and block (iSCSI) from the same file system.
- Snapshots, clones, replication (SnapMirror).
- Data tiering: Automatically tiers infrequently accessed data to a lower-cost capacity pool (S3-backed).
- Multi-AZ for HA.
- Ideal for lift-and-shift of on-premises NetApp workloads.

#### 4.4.4 FSx for OpenZFS

**Core Definition**: Managed OpenZFS file system. NFS protocol. High performance with ZFS features (snapshots, compression, cloning).

- Up to 1 million IOPS, sub-ms latency.
- NFS v3/v4.1.
- Instant snapshots, data cloning (zero-copy).
- Single AZ only.
- Good for Linux workloads requiring ZFS features or migrating from on-prem ZFS.

#### FSx Exam Traps

1. **FSx for Windows = SMB + AD. EFS = NFS + Linux.** Do not confuse them.
2. **FSx for Lustre = HPC + S3 integration.** For ML training pipelines reading from S3, Lustre is the answer.
3. **FSx for ONTAP = multi-protocol (NFS + SMB + iSCSI) + NetApp features.** Migration from on-prem NetApp.
4. **Lustre is single AZ only (even Persistent)**. If multi-AZ file system is needed, use EFS, FSx Windows (Multi-AZ), or FSx ONTAP (Multi-AZ).


### 4.5 AWS Storage Gateway

#### Core Definition

Storage Gateway is a hybrid storage service that provides on-premises applications with access to virtually unlimited cloud storage. It runs as a VM (VMware, Hyper-V, KVM) or hardware appliance on-premises.

Three gateway types:

**S3 File Gateway**: NFS/SMB interface on-premises → data stored as objects in S3. Local cache for low-latency access to frequently accessed data. Ideal for file shares, data lakes, backups.

**FSx File Gateway**: SMB interface on-premises → data stored in FSx for Windows. Local cache. For Windows file shares backed by FSx.

**Volume Gateway**:
- **Cached Volumes**: Primary data in S3. Frequently accessed data cached locally. Up to 32 volumes, 32 TiB each.
- **Stored Volumes**: Primary data on-premises. Asynchronous backup to S3 as EBS snapshots. Up to 32 volumes, 16 TiB each.

**Tape Gateway**: Virtual Tape Library (VTL). Presents iSCSI tape drives to backup software (Veeam, Veritas, etc.). Tapes stored in S3 (Virtual Tape Shelf in Glacier/Deep Archive). Drop-in replacement for physical tape infrastructure.

#### When to Use

- Hybrid storage: on-premises access to cloud storage.
- Cloud backup from on-premises applications.
- Migration from on-premises file shares to S3/FSx.
- Tape replacement.

#### When NOT to Use

- Cloud-native applications. Access S3/EFS/FSx directly.
- High-bandwidth, one-time migration. Use DataSync or Snow Family.
- Real-time low-latency requirements without local caching.

#### Advanced Professional-Level Exam Traps

1. **S3 File Gateway vs FSx File Gateway**: S3 FG stores data as S3 objects (no NTFS permissions). FSx FG preserves Windows permissions. For Windows ACLs, use FSx File Gateway.
2. **Cached vs Stored Volumes**: Cached = primary data in cloud, local cache. Stored = primary data local, cloud backup. If on-prem storage is limited, cached. If latency is critical for all data, stored.
3. **Tape Gateway**: If a question mentions "replace tape backup infrastructure," Tape Gateway is the answer.
4. **Gateway requires bandwidth** between on-premises and AWS. Saturated links degrade performance.


### 4.6 AWS Backup

#### Core Definition

AWS Backup is a centralized, policy-driven backup service for AWS resources across accounts and regions.

- **Supported Resources**: EC2 (AMI), EBS, EFS, FSx, RDS, Aurora, DynamoDB, S3, Neptune, DocumentDB, Redshift, Storage Gateway volumes, VMware (via Backup Gateway), SAP HANA on EC2.
- **Pricing**: Per-GB-month stored + per-GB restored (varies by resource type).

#### Core Capabilities

- **Backup Plans**: Define schedule, retention, lifecycle (transition to cold storage), cross-region copy, cross-account copy.
- **Backup Vault**: Storage container for backups. Vault access policy controls who can access. Vault Lock: WORM protection (Compliance mode = immutable, Governance mode = override with permissions).
- **Cross-Account Backup**: Copy backups to another account (requires Organizations). DR and security isolation.
- **Backup Audit Manager**: Evaluate backup compliance against controls (e.g., "all RDS instances must be backed up daily").
- **Organization-Level Backup Policies**: Apply backup plans at the OU/account level via Organizations backup policies. Member accounts cannot override.

#### When to Use

- Centralized backup management across the organization.
- Compliance requirements for backup retention and immutability.
- Cross-region and cross-account DR.

#### Advanced Professional-Level Exam Traps

1. **AWS Backup Vault Lock (Compliance mode)** is immutable. Even the root user cannot delete backups during the retention period.
2. **Cross-account backup requires Organizations**. The management account or delegated admin configures it.
3. **DynamoDB Backup via AWS Backup** is different from DynamoDB's native on-demand/PITR backup. AWS Backup provides centralized management and cross-account copy.
4. **S3 backup support** was added later. Backup can back up S3 buckets (including versioned objects). Not all S3 features are supported in backup.

## 5. Databases

Database questions on the SAP-C02 are among the hardest. You must understand consistency models, replication mechanics, failover behavior, read scaling vs write scaling, and when to choose SQL vs NoSQL vs purpose-built.


### 5.1 Amazon RDS (Relational Database Service)

#### Core Definition

RDS provides managed relational databases. AWS handles provisioning, patching, backups, and failover. You choose the engine.

- **Engines**: MySQL, PostgreSQL, MariaDB, Oracle, SQL Server.
- **Scope**: Regional (instances in a single AZ or Multi-AZ).
- **Pricing**: On-Demand, Reserved Instances (1yr/3yr). Per-instance-hour + storage + I/O (for some engines) + backup storage beyond free tier.
- **SLA**: 99.95% for Multi-AZ deployments.
- **Architectural Abstraction**: Managed EC2 instance + EBS storage running a database engine.

#### Core Capabilities

**Multi-AZ**:
- **Multi-AZ instance (classic)**: Synchronous standby in another AZ. Automatic failover (60-120 seconds DNS propagation). Standby is NOT readable. For HA, not read scaling.
- **Multi-AZ cluster (new, MySQL/PostgreSQL)**: One writer + two readable standbys across 3 AZs. Uses local NVMe-backed storage. Transaction log replication. Faster failover (~35 seconds). Readable standbys serve read traffic.

**Read Replicas**:
- Asynchronous replication from primary.
- Up to 15 read replicas (Aurora) or 5 (other engines).
- Cross-region read replicas for global read scaling and DR.
- Can be promoted to standalone instance (breaks replication permanently).
- Replica lag: eventual consistency. Depends on write workload and network.

**Storage**:
- gp3, io1, io2 EBS volumes.
- Storage auto-scaling: Automatically increases storage when nearing capacity.
- Maximum storage: 64 TiB.

**Backup**:
- Automated backups: Daily full backup + transaction logs every 5 minutes. Retention: 0-35 days. Point-in-time restore (PITR) to any second within the retention window.
- Manual snapshots: Persist beyond retention period. Must be manually deleted.
- Backups are stored in S3 (managed by AWS, not visible in your S3 console).
- Cross-region backup: Automated backups can be replicated to another region.

**Encryption**:
- At rest: KMS. Must be enabled at creation. Cannot encrypt an existing unencrypted DB.
- Workaround: Snapshot unencrypted DB → copy snapshot with encryption → restore from encrypted snapshot.
- In transit: SSL/TLS. Some engines support forcing SSL connections.

**RDS Proxy**:
- Managed database proxy for connection pooling and failover.
- Reduces failover time from ~60s to \<1s for Multi-AZ.
- Connection pooling: multiplexes thousands of application connections to fewer database connections. Critical for Lambda (which opens many short-lived connections).
- Supports IAM authentication and Secrets Manager integration.
- Pinning: Some SQL features (prepared statements, session variables) cause "pinning" — the proxy can't multiplex that connection. Monitor for pin events.

**RDS Custom**: Managed RDS with OS-level access. For Oracle and SQL Server workloads requiring custom OS settings (patches, agents, filesystem access). You manage the OS customizations; AWS manages the database.

#### When to Use

- Relational workloads with known query patterns.
- ACID compliance requirements.
- Lift-and-shift of on-premises databases (same engine compatibility).
- When you need managed backups, patching, and Multi-AZ failover.

#### When NOT to Use

- Read/write scaling beyond single-node capacity. Use Aurora or DynamoDB.
- Schemaless or key-value workloads. Use DynamoDB.
- Massive write throughput. Consider Aurora or DynamoDB.
- When you need full OS control beyond RDS Custom. Use EC2 + self-managed DB.

#### Advanced Professional-Level Exam Traps

1. **Multi-AZ standby is NOT a read replica**. Classic Multi-AZ standby cannot serve reads. Multi-AZ cluster standbys CAN.
2. **Read replicas use async replication**. There WILL be lag. For strongly consistent reads, read from the primary.
3. **RDS Proxy with Lambda**: Essential for Lambda → RDS because Lambda creates many connections rapidly. Without a proxy, connection exhaustion is common.
4. **Encrypting an unencrypted database requires snapshot → copy encrypted → restore**. It's a migration, not an in-place change.
5. **Cross-region read replica**: Can be promoted for DR. But it's a manual process and breaks replication.
6. **RDS does NOT support global tables** like Aurora or DynamoDB. Cross-region is limited to read replicas.


### 5.2 Amazon Aurora

#### Core Definition

Aurora is AWS's cloud-native relational database. Compatible with MySQL and PostgreSQL but re-architected for cloud performance and scalability. The storage layer is fundamentally different from RDS.

- **Scope**: Regional (with Global Database for multi-region).
- **Pricing**: On-Demand or Reserved per instance-hour + I/O charges + storage ($0.10/GB/month). Aurora I/O-Optimized: higher storage cost but no per-I/O charge.
- **SLA**: 99.99% for Multi-AZ.
- **Architectural Abstraction**: Compute-storage separation. Compute instances (writer/readers) attach to a shared distributed storage layer spanning 3 AZs.

#### Core Capabilities

**Storage Architecture** (key differentiator):
- Storage auto-scales from 10 GB to 128 TiB.
- Data is automatically replicated 6 ways across 3 AZs (2 copies per AZ).
- Fault tolerant: Can lose 2 copies without affecting writes. Can lose 3 copies without affecting reads.
- Storage is independent of compute. You can stop compute instances without losing data.
- Continuous backup to S3 (automatic, no performance impact).
- Backtrack: Rewind the database to a previous point in time WITHOUT restore (in-place). Aurora MySQL only. Maximum 72 hours.

**Compute**:
- Writer instance: Handles all writes.
- Up to 15 read replicas: Synchronous replication at the storage layer (not binlog). Millisecond replica lag. Can be promoted in \<30 seconds if writer fails.
- Auto-scaling of read replicas based on CPU/connections.
- Endpoints: Writer endpoint (DNS CNAME to current writer), Reader endpoint (load-balanced across read replicas), Custom endpoints (subsets of instances for different workloads).

**Aurora Serverless v2**:
- Scales compute in increments of 0.5 ACU (Aurora Capacity Units). 1 ACU ≈ 2 GB RAM.
- Range: 0.5 ACU to 256 ACU.
- Scales in seconds based on workload demand.
- Does NOT scale to zero (minimum 0.5 ACU). Aurora Serverless v1 could scale to zero but is deprecated for new workloads.
- Can mix provisioned and Serverless v2 instances in the same cluster (e.g., provisioned writer + Serverless v2 readers).
- Pricing: Per-ACU-hour ($0.12/ACU-hour).

**Aurora Global Database**:
- Primary region (read/write) + up to 5 secondary regions (read-only).
- Storage-level replication: ~1-second cross-region lag.
- Failover to secondary region: Promote a secondary to primary (RPO in seconds, RTO in minutes).
- Write forwarding: Secondary region readers can forward writes to the primary region (adds latency but simplifies global applications).

**Aurora Multi-Master**: DEPRECATED in favor of Global Database + write forwarding. Historically allowed multiple writer instances in a single region. Removed for Aurora MySQL.

**Aurora Machine Learning**: Invoke SageMaker or Comprehend from SQL queries. Augment relational data with ML predictions directly in the database.

#### Architectural Design Patterns

**Global Application with Low-Latency Reads**: Aurora Global Database. Primary in us-east-1, secondary in eu-west-1 and ap-southeast-1. Users read from the nearest region. Writes go to primary.

**Bursty Workload with Cost Optimization**: Aurora Serverless v2 for readers. Provisioned writer for consistent performance. Readers scale up during peak and down during off-peak.

**Blue/Green Deployment**: Aurora Blue/Green Deployments (native feature). Create a green cluster that is a clone of the blue cluster. Apply changes to green. Switch over with minimal downtime.

#### When to Use

- MySQL/PostgreSQL workloads requiring higher performance than RDS.
- Global relational database architectures.
- Applications needing fast failover (\<30 seconds).
- Variable or bursty workloads (Serverless v2).
- When storage auto-scaling and 6-way replication provide better durability than RDS.

#### When NOT to Use

- Oracle or SQL Server. Not compatible. Use RDS.
- Simple, low-traffic databases where RDS is sufficient and cheaper.
- Non-relational workloads. Use DynamoDB.
- When I/O costs exceed expectations (high-write workloads on Aurora standard billing). Consider Aurora I/O-Optimized or alternative.

#### Trade-Offs: Aurora vs RDS

| Aspect | Aurora | RDS |
|---|---|---|
| Storage | Distributed, auto-scaling, 6-way replication | EBS (gp3/io2), manual scaling |
| Replication | Storage-level, ms lag | Binlog-based, seconds lag |
| Max replicas | 15 | 5 |
| Failover time | \<30 seconds | 60-120 seconds |
| Max storage | 128 TiB | 64 TiB |
| Cost | ~20% more than RDS | Lower for simple workloads |
| Global | Global Database | Cross-region read replicas |
| Serverless | Serverless v2 | Not available |
| Backtrack | Yes (MySQL) | No |
| Engines | MySQL, PostgreSQL | MySQL, PostgreSQL, MariaDB, Oracle, SQL Server |

#### Advanced Professional-Level Exam Traps

1. **Aurora Serverless v2 does NOT scale to zero**. Minimum 0.5 ACU. If a question requires scale-to-zero, Aurora Serverless v2 is not the answer (consider Lambda + DynamoDB).
2. **Aurora Global Database replication lag is ~1 second**. For RPO=0, this is not sufficient. Use synchronous Multi-AZ within a single region.
3. **Backtrack is NOT a backup**. It rewinds the entire cluster. Not a point-in-time restore to a new instance.
4. **Aurora I/O-Optimized**: Eliminates per-I/O charges. Better for write-heavy workloads. Storage cost is higher. Break-even: if I/O > 25% of total Aurora cost, switch to I/O-Optimized.
5. **Custom endpoints**: Use for analytics workloads against specific larger read replicas, while smaller replicas handle operational reads.
6. **Writer endpoint always points to the current writer**. Applications should use the writer endpoint, not instance endpoints.


### 5.3 Amazon DynamoDB

#### Core Definition

DynamoDB is a fully managed, serverless NoSQL key-value and document database. Designed for single-digit millisecond latency at any scale.

- **Scope**: Regional (with Global Tables for multi-region).
- **Control Plane**: Regional.
- **Data Plane**: Regional (globally distributed with Global Tables).
- **Pricing**: On-Demand ($1.25/million WCU, $0.25/million RCU) or Provisioned ($0.00065/WCU-hour, $0.00013/RCU-hour). Storage: $0.25/GB/month.
- **SLA**: 99.999% for Global Tables. 99.99% for standard tables.
- **Architectural Abstraction**: Distributed hash table with consistent hashing, automatic partitioning.

#### Core Capabilities

**Data Model**:
- Tables, items, attributes. Primary key: Partition Key (PK) or Partition Key + Sort Key (PK + SK).
- Maximum item size: 400 KB.
- No fixed schema beyond the primary key.
- Secondary indexes: Local Secondary Index (LSI, same PK, different SK, max 5 per table, must be created at table creation) and Global Secondary Index (GSI, different PK and/or SK, max 20 per table, can be created anytime).

**Capacity Modes**:
- **On-Demand**: Pay per request. No capacity planning. Instantly scales to handle any traffic level. 2x previous peak as default limit. Good for unpredictable workloads.
- **Provisioned**: Specify read/write capacity units. Auto-scaling available (adjusts capacity based on utilization). More cost-effective for predictable workloads.
- Can switch between modes once every 24 hours.

**Consistency Models**:
- **Eventually Consistent Reads** (default): Reflects all writes that happened 1 second ago. Half the cost of strongly consistent.
- **Strongly Consistent Reads**: Returns the most up-to-date data. Requires read from the leader node. Double the RCU cost.
- **Transactional Reads/Writes**: ACID transactions across multiple items/tables. 2x the cost of standard operations.

**DynamoDB Streams**:
- Captures item-level changes (INSERT, MODIFY, DELETE) in near-real-time.
- Retention: 24 hours.
- Consumers: Lambda (event source mapping), Kinesis Data Streams (via Kinesis adapter), custom consumers.
- View types: KEYS_ONLY, NEW_IMAGE, OLD_IMAGE, NEW_AND_OLD_IMAGES.
- Used for: event-driven architectures, cross-region replication (Global Tables use Streams), materialized views, CDC (Change Data Capture).

**Global Tables**:
- Multi-region, multi-active (read/write in any region).
- Uses DynamoDB Streams for replication.
- Conflict resolution: Last Writer Wins (based on timestamp).
- Replication latency: typically \<1 second.
- Requires Streams enabled and On-Demand or auto-scaling provisioned capacity.
- All regions are equal (no primary region concept).

**DynamoDB Accelerator (DAX)**:
- In-memory cache for DynamoDB. Microsecond read latency.
- Read-through and write-through cache.
- Cluster-based (1-10 nodes).
- Compatible with DynamoDB API (drop-in replacement for read-heavy workloads).
- Not suitable for workloads needing strongly consistent reads (DAX returns eventually consistent).

**Point-in-Time Recovery (PITR)**:
- Continuous backups. Restore to any second within 35 days.
- Restores to a NEW table (not in-place).

**Time to Live (TTL)**:
- Automatically delete items after a specified timestamp.
- No cost. Items are deleted in background (may take up to 48 hours after expiry).
- Deleted items appear in DynamoDB Streams (useful for post-deletion processing).

**PartiQL**: SQL-compatible query language for DynamoDB. Allows SELECT, INSERT, UPDATE, DELETE using SQL syntax.

#### Architectural Design Patterns

**Single-Table Design**: Store multiple entity types in a single table using overloaded keys. Reduces cost and simplifies access patterns. Requires deep understanding of access patterns upfront. Trade-off: harder to maintain, steep learning curve.

**Event Sourcing**: DynamoDB as event store + Streams → Lambda → materialize views in other stores.

**Session Store**: TTL-enabled table for user sessions. Low latency, automatic cleanup.

**Global Application**: Global Tables for multi-region active-active. Route 53 latency-based routing to regional API endpoints.

#### When to Use

- Key-value or document access patterns.
- Single-digit millisecond latency at any scale.
- Serverless architectures.
- Highly variable or unpredictable traffic.
- Global multi-region active-active.
- Session management, leaderboards, IoT data, time-series (with proper key design).

#### When NOT to Use

- Complex queries with joins, aggregations, or ad-hoc analytics. Use RDS/Aurora or Redshift.
- Large items (>400 KB). Store large payloads in S3, reference from DynamoDB.
- Relational data with complex relationships. Use Aurora.
- Full-text search. Use OpenSearch.

#### Failure & Edge Case Behavior

- **Hot partition**: If a single partition key receives disproportionate traffic, it becomes a bottleneck. Mitigation: adaptive capacity (auto-rebalances), but extremely hot partitions can still throttle. Design keys for uniform distribution.
- **Throttling**: ProvisionedThroughputExceededException. Use exponential backoff. Switch to On-Demand for unpredictable spikes.
- **Global Table conflict**: Two regions write to the same item simultaneously. Last Writer Wins. No conflict detection or resolution. Application must handle this if it matters.
- **Eventual consistency**: Read after write in a different region may not reflect the latest write for up to 1 second (Global Tables).

#### Cost Model & Optimization

- **On-Demand vs Provisioned**: On-Demand is ~6.5x more expensive per request than Provisioned at steady state. Switch to Provisioned + Auto Scaling for predictable workloads.
- **Reserved Capacity**: Available for Provisioned mode. 1yr/3yr commitment for further savings.
- **GSI costs as much as the base table**. Every write to an item with a GSI incurs additional WCUs for the GSI. Minimize GSI projections (PROJECT only needed attributes).
- **Storage class**: Standard ($0.25/GB) vs Standard-IA ($0.10/GB but higher read/write cost). For infrequently accessed tables.
- **DAX**: Reduces read costs dramatically (microsecond reads for $0.269/hr per node). But adds infrastructure cost.
- **TTL is free**. Use it to avoid unbounded table growth.

#### Advanced Professional-Level Exam Traps

1. **DynamoDB is not a relational database**. No joins, no foreign keys, no SQL (except PartiQL for basic operations). Designing DynamoDB like a relational DB leads to poor performance and high cost.
2. **Global Tables ≠ strong consistency across regions**. Replication is async (~1s). Eventually consistent cross-region.
3. **LSI must be created at table creation time**. GSI can be added later. If a question mentions adding an index after the fact, it's a GSI.
4. **400 KB item size limit**. For larger data, store in S3 and reference.
5. **DAX does NOT support strongly consistent reads**. All DAX reads are eventually consistent.
6. **On-Demand mode absorbs spikes up to 2x previous peak instantly**. Beyond that, throttling may occur temporarily as DynamoDB pre-provisions more capacity.
7. **Transactional operations cost 2x** standard operations. Use only when ACID is required.
8. **DynamoDB export to S3**: Full table export in DynamoDB JSON or Ion format. Does NOT consume read capacity (reads from backups).


### 5.4 Amazon ElastiCache

#### Core Definition

ElastiCache provides managed in-memory data stores. Two engines:

1. **Redis (ElastiCache for Redis / MemoryDB for Redis)**: Data structures, pub/sub, Lua scripting, persistence, replication, cluster mode.
2. **Memcached**: Simple key-value caching. No persistence, no replication, multi-threaded.

- **Scope**: Regional.
- **Pricing**: Per-node-hour based on node type.
- **SLA**: 99.99% for Multi-AZ with auto-failover.

#### Core Capabilities

**Redis**:
- **Cluster Mode Disabled**: Single shard. 1 primary + up to 5 replicas. Up to ~6.1 TB (node memory × 1 shard). Good for simple caching.
- **Cluster Mode Enabled**: Up to 500 shards. Data partitioned across shards (hash slots). Up to 340 TB. Horizontal scaling. Required for large datasets.
- **Multi-AZ**: Replicas in different AZs. Auto-failover promotes replica to primary (~30 seconds).
- **Persistence**: RDB snapshots and AOF (Append Only File). Not durable like a database — use for cache, not primary data store (use MemoryDB for Redis if you need durable in-memory).
- **Encryption**: At rest (KMS) and in transit (TLS).
- **Global Datastore**: Cross-region replication for Redis. Active-passive (reads in secondary, writes in primary). Failover to secondary region manually. Replication lag: \<1 second typical.
- **Auth**: Redis AUTH token (password) or IAM authentication (newer, Redis 7+).

**Memcached**:
- Multi-threaded. Scales vertically better than Redis for simple caching.
- No persistence, no replication, no Multi-AZ failover.
- Auto-discovery of cluster nodes.
- Use when simplicity and multi-threaded performance matter.

#### When to Use

- **Redis**: Session stores, leaderboards, real-time analytics, pub/sub, geospatial, rate limiting, queue (simple), machine learning feature store.
- **Memcached**: Simple caching layer where persistence and replication aren't needed.
- **Either**: Database query caching, API response caching.

#### When NOT to Use

- Primary data store (unless using MemoryDB for Redis).
- Complex query workloads. Use a database.
- Large data that doesn't fit in memory economically.

#### Trade-Offs: ElastiCache Redis vs Memcached vs MemoryDB

| Aspect | ElastiCache Redis | Memcached | MemoryDB for Redis |
|---|---|---|---|
| Persistence | Optional (not durable) | No | Durable (Multi-AZ transaction log) |
| Replication | Yes | No | Yes |
| Multi-AZ | Yes | No | Yes |
| Data structures | Rich (sorted sets, streams, etc.) | Key-value only | Rich |
| Threads | Single-threaded (per shard) | Multi-threaded | Single-threaded (per shard) |
| Use case | Caching | Caching | Primary database |
| Durability | Not guaranteed | None | 11 nines (like S3) |

#### Advanced Professional-Level Exam Traps

1. **ElastiCache Redis is NOT a durable database**. For durable in-memory data store, use **MemoryDB for Redis** (Multi-AZ transaction log, 11 nines durability).
2. **Cluster Mode Enabled is required for horizontal scaling**. Without it, you're limited to a single shard.
3. **Global Datastore is active-passive**. Primary region handles writes. Secondary is read-only. Manual failover.
4. **Memcached has no replication**. Node failure = cache miss. Design for cache-aside pattern with database fallback.
5. **ElastiCache requires VPC**. No public access. Applications must be in the same VPC or connected via peering/TGW.
6. **Lazy loading vs write-through caching strategies**: Questions may test understanding of cache coherence patterns.


### 5.5 Amazon Redshift

#### Core Definition

Redshift is a petabyte-scale managed data warehouse optimized for OLAP (Online Analytical Processing) queries using columnar storage.

- **Scope**: Regional.
- **Pricing**: On-Demand ($0.25/hr for dc2.large), Reserved Instances, or Redshift Serverless ($0.375/RPU-hour).
- **SLA**: 99.9%.
- **Architectural Abstraction**: MPP (Massively Parallel Processing) columnar database. Leader node (query planning) + compute nodes (data storage/processing).

#### Core Capabilities

- **Columnar storage**: Optimized for analytics queries that scan few columns across many rows.
- **Compression**: Automatic column encoding (AZ64, LZO, ZSTD, etc.) reduces storage 3-4x.
- **Distribution styles**: KEY (by column value for co-located joins), EVEN (round-robin), ALL (full table copy on all nodes), AUTO (Redshift decides).
- **Sort keys**: Compound or interleaved. Optimizes range-based queries and zone maps.
- **Concurrency Scaling**: Automatically adds transient clusters to handle query spikes. First credit: 1 hour/day free per cluster.
- **Materialized Views**: Pre-computed query results. Auto-refreshed.
- **Redshift Spectrum**: Query data directly in S3 without loading into Redshift. Uses external tables (Glue Data Catalog). Pay per bytes scanned.
- **Redshift Serverless**: No cluster management. Specify base RPU (Redshift Processing Unit). Auto-scales. Pay per RPU-second used.
- **Data Sharing**: Share live data between Redshift clusters without copying. Cross-account and cross-region (preview).
- **AQUA (Advanced Query Accelerator)**: Hardware-accelerated cache on SSD-backed nodes (ra3). Pushes filtering/aggregation to storage layer. Up to 10x faster for some queries.
- **Federated Query**: Query data in RDS/Aurora PostgreSQL from Redshift. Join external operational data with warehouse data.
- **Snapshots**: Automated and manual. Cross-region snapshot copy for DR.
- **RA3 nodes**: Managed storage (separate from compute). Data stored in S3-backed managed storage. Hot data cached on local NVMe. Scale compute and storage independently.

#### When to Use

- Analytics and reporting on large datasets.
- Data warehouse workloads (star/snowflake schema).
- BI tool integration (Tableau, QuickSight, Looker).
- Complex SQL queries with joins, aggregations, window functions.

#### When NOT to Use

- OLTP (transactional) workloads. Use RDS/Aurora/DynamoDB.
- Real-time data ingestion with low-latency queries. Use Kinesis + Lambda or DynamoDB.
- Unstructured data processing. Use EMR or Glue.
- Small datasets (\<100 GB). Overkill and expensive.

#### Advanced Professional-Level Exam Traps

1. **Redshift Spectrum vs Athena**: Both query S3. Spectrum requires a Redshift cluster (additional cost but can join with warehouse data). Athena is serverless and standalone. For ad-hoc S3 queries without a warehouse, use Athena.
2. **RA3 nodes separate compute from storage**. If a question mentions scaling storage independently, RA3 or Serverless.
3. **Concurrency Scaling**: Handles burst read queries. Does NOT help with sustained high concurrency. For true elastic concurrency, use Serverless.
4. **Distribution key matters for join performance**. Incorrect distribution causes data shuffling across nodes (redistribute).
5. **Enhanced VPC Routing**: Forces all COPY/UNLOAD traffic through VPC (instead of AWS public network). Required for PrivateLink/VPC endpoint access to S3.


### 5.6 Other Purpose-Built Databases (Summary)

**Amazon Neptune**: Managed graph database. Property graph (Apache TinkerPop/Gremlin) and RDF (SPARQL). Use for social networks, knowledge graphs, fraud detection, recommendation engines. Multi-AZ, up to 15 read replicas.

**Amazon DocumentDB**: MongoDB-compatible managed document database. Not actual MongoDB — AWS-built storage layer (similar to Aurora). Use when you need MongoDB API compatibility without managing MongoDB. Up to 15 read replicas, Multi-AZ. Storage scales to 128 TiB.

**Amazon Keyspaces**: Managed Apache Cassandra-compatible service. Serverless. Use for IoT data, time-series, and workloads designed for Cassandra. On-Demand or Provisioned capacity.

**Amazon QLDB**: Quantum Ledger Database. Immutable, cryptographically verifiable transaction log. Centralized ledger (not blockchain). Use for supply chain, financial ledgers, system of record. Being deprecated — AWS recommends Aurora PostgreSQL with verifiable audit solutions.

**Amazon Timestream**: Managed time-series database. Serverless. Built-in time-series functions. Automatic tiering from memory to magnetic storage. Use for IoT telemetry, operational metrics, DevOps monitoring.

**Amazon MemoryDB for Redis**: Durable in-memory database compatible with Redis. Multi-AZ transaction log for durability (11 nines). Use as a primary database when you need Redis-compatible data structures with durability (not just caching).

## 6. Integration & Messaging

Decoupling is a first-class architectural principle at the Professional level. Every integration question tests whether you understand message delivery semantics, ordering guarantees, retry behavior, dead-letter handling, and service coupling trade-offs.


### 6.1 Amazon SQS (Simple Queue Service)

#### Core Definition

SQS is a fully managed message queuing service for decoupling producers and consumers. It buffers messages and provides at-least-once delivery.

- **Scope**: Regional.
- **Pricing**: $0.40 per million requests (first 1M free). $0.50 per million for FIFO. Data transfer charges for cross-region.
- **SLA**: 99.9%.
- **Architectural Abstraction**: Distributed message queue with at-least-once or exactly-once (FIFO) delivery semantics.

#### Core Capabilities

**Queue Types**:
- **Standard Queue**: Nearly unlimited throughput. At-least-once delivery (messages may be delivered more than once). Best-effort ordering (messages may arrive out of order). Use when throughput matters more than ordering.
- **FIFO Queue**: Exactly-once processing (deduplication within 5-minute window). Strictly ordered within a message group. 300 messages/second without batching, 3,000/second with batching. Higher throughput with high-throughput FIFO mode (up to 70,000 msgs/sec with multiple message group IDs).

**Key Features**:
- **Visibility Timeout**: After a consumer receives a message, it becomes invisible to other consumers for the visibility timeout (default 30s, max 12 hours). If not deleted within the timeout, it becomes visible again (retry). Tune based on processing time.
- **Long Polling**: `WaitTimeSeconds` up to 20 seconds. Reduces empty receives (and cost). Always use long polling.
- **Dead-Letter Queue (DLQ)**: Messages that exceed `maxReceiveCount` are moved to a DLQ. Essential for debugging failed messages. DLQ must be the same type (Standard DLQ for Standard queue, FIFO DLQ for FIFO queue). DLQ redrive: move messages back to the source queue after fixing the issue.
- **Delay Queue**: Messages are invisible for up to 15 minutes after being sent. Use for delayed processing.
- **Message Timer**: Per-message delay (up to 15 minutes). Only for Standard queues.
- **Message Retention**: 1 minute to 14 days (default 4 days).
- **Message Size**: Up to 256 KB. For larger messages, use SQS Extended Client Library (stores payload in S3, sends reference in SQS message).
- **Server-Side Encryption**: SSE-SQS (free, AWS-managed) or SSE-KMS (customer-managed keys, CloudTrail audit).
- **Access Policy**: Resource-based policy. Controls who can send/receive. Critical for cross-account access and service integration (e.g., allowing SNS to send to SQS).

**FIFO Specifics**:
- **Message Group ID**: Messages with the same group ID are ordered relative to each other. Different group IDs are processed in parallel (separate lanes).
- **Deduplication ID**: Prevents duplicate messages within a 5-minute window. Content-based deduplication: SQS generates dedup ID from message body hash. Or provide your own dedup ID.
- Queue name must end with `.fifo`.

#### Architectural Design Patterns

**Decoupled Processing**: Web tier → SQS → worker tier. Absorbs traffic spikes. Workers process at their own pace. ASG scales workers based on `ApproximateNumberOfMessagesVisible`.

**Fan-Out with SNS → SQS**: SNS topic → multiple SQS queues. Each queue has independent consumers. Ensures each subscriber gets every message.

**Request Buffering**: API Gateway → Lambda → SQS → backend processors. SQS absorbs bursts that would overwhelm the backend.

**Exactly-Once Processing Pipeline**: FIFO queue with deduplication + message group ordering. Each message processed exactly once in order.

#### When to Use

- Decoupling components.
- Absorbing traffic spikes (buffering).
- At-least-once or exactly-once message processing.
- Work queue for distributed workers.

#### When NOT to Use

- Fan-out to multiple subscribers from a single message. Use SNS (or SNS → SQS for each subscriber).
- Event routing with content-based filtering. Use EventBridge.
- Real-time streaming with replay. Use Kinesis.
- Pub/sub with topics. Use SNS.

#### Trade-Offs: SQS vs SNS vs EventBridge vs Kinesis

| Aspect | SQS | SNS | EventBridge | Kinesis Data Streams |
|---|---|---|---|---|
| Pattern | Queue (pull) | Pub/Sub (push) | Event bus (push) | Stream (pull/push) |
| Delivery | At-least-once / Exactly-once (FIFO) | At-least-once | At-least-once | At-least-once (per shard) |
| Ordering | FIFO available | FIFO with SQS sub | No | Per shard |
| Retention | Up to 14 days | None (immediate) | Archive up to indefinite | 1-365 days |
| Throughput | Nearly unlimited (Standard) | Nearly unlimited | Thousands/sec (default) | Unlimited (scale shards) |
| Consumers | Pull-based | Push (HTTP, SQS, Lambda, etc.) | Push (200+ targets) | Pull (consumers), push (enhanced fan-out) |
| Replay | No (once consumed) | No | Yes (archive) | Yes (within retention) |
| Filtering | No (app-level) | Attribute-based | Content-based (rich) | App-level |
| Cost | Per request | Per message + per delivery | Per event | Per shard-hour + per GB |

#### Failure & Edge Case Behavior

- **Poison pill**: Message that always fails processing. Without DLQ, it retries indefinitely. With DLQ, it moves after `maxReceiveCount`. ALWAYS configure DLQ.
- **Visibility timeout too short**: Consumer doesn't finish processing before timeout → message becomes visible → another consumer processes it → duplicate processing. Tune timeout to exceed processing time.
- **FIFO throttling**: Exceeding 300/3,000/70,000 msgs/sec throughput. Solution: use more message group IDs for parallelism.
- **Message deduplication**: If producer sends the same message twice within 5 minutes with the same dedup ID, SQS discards the duplicate (FIFO only). Standard queues have no deduplication.

#### Advanced Professional-Level Exam Traps

1. **SQS is pull-based**. Consumers poll SQS. SNS is push-based. Lambda polls SQS (event source mapping), but that's Lambda pulling from SQS on your behalf.
2. **FIFO ordering is per message group, not per queue**. Using a single message group ID forces all messages into one ordered lane, limiting throughput.
3. **DLQ must be same type as source queue**. Standard DLQ for Standard queue, FIFO DLQ for FIFO queue.
4. **Max message size is 256 KB**. For larger payloads, use the Extended Client Library with S3.
5. **SQS does not support message replay**. Once consumed and deleted, a message is gone. For replay, use Kinesis or EventBridge Archive.
6. **Auto Scaling based on SQS queue depth**: Use `ApproximateNumberOfMessagesVisible` as a CloudWatch metric. Target Tracking scaling policy with custom metric.


### 6.2 Amazon SNS (Simple Notification Service)

#### Core Definition

SNS is a fully managed pub/sub messaging service. Publishers send messages to topics; subscribers receive them.

- **Scope**: Regional.
- **Pricing**: $0.50 per million Standard publishes. FIFO: $0.50 per million. Delivery charges vary by protocol (SQS/Lambda: free, HTTP: $0.06/100,000, SMS: varies by country, email: $2/100,000).
- **SLA**: 99.9%.

#### Core Capabilities

- **Topics**: Standard (at-least-once, no ordering) and FIFO (ordering per message group, deduplication).
- **Subscribers**: SQS, Lambda, HTTP/S, Email, SMS, Kinesis Data Firehose, mobile push (APNs, FCM).
- **Message Filtering**: Subscriber-level filter policies based on message attributes. Reduces unnecessary message delivery (consumers only get relevant messages). Filter on attribute presence, exact match, prefix, numeric range, OR/AND logic.
- **Fan-Out**: Single publish → delivered to ALL subscribers. Combined with SQS for durable fan-out.
- **Message size**: 256 KB (same as SQS).
- **Large message payloads**: Use SNS Extended Client Library with S3 (up to 2 GB).
- **FIFO Topics**: Deliver messages in order to FIFO SQS subscribers. Deduplication. Only SQS FIFO queues and Lambda can subscribe to FIFO topics.
- **Cross-Account Subscriptions**: Topic policy allows other accounts to subscribe.

#### Architectural Design Patterns

**Fan-Out + Parallel Processing**: SNS topic → multiple SQS queues. Each queue feeds a different processing pipeline (e.g., order placed → inventory update, payment processing, notification, analytics).

**S3 Event Fan-Out**: S3 event notification → SNS → multiple SQS queues / Lambda functions. S3 supports only one event notification per event type per prefix. SNS enables multiple downstream consumers from that one notification.

**Mobile Push Notifications**: SNS → platform applications (APNs, FCM) → mobile devices.

#### When to Use

- Fan-out: One message to many subscribers.
- Push notifications (mobile, email, SMS, HTTP).
- Event-driven architectures where multiple downstream consumers need the same event.
- Decoupling with message filtering.

#### When NOT to Use

- Buffering / work queue. Use SQS.
- Ordered processing without SQS. Use SQS FIFO directly.
- Complex event routing. Use EventBridge.
- Streaming data with replay. Use Kinesis.

#### Advanced Professional-Level Exam Traps

1. **SNS + SQS fan-out** is the standard pattern for one-to-many event distribution. Know this cold.
2. **Message filtering** reduces cost and complexity. Subscribers only receive messages they care about.
3. **SNS FIFO can only deliver to SQS FIFO and Lambda**. Not HTTP, email, or SMS.
4. **SNS does NOT buffer messages**. If a subscriber is unavailable, SNS retries (with backoff) but eventually gives up. For durable delivery, use SNS → SQS.
5. **Cross-account SNS**: Publisher account's topic policy must allow the subscriber account. Subscriber account still needs to subscribe.


### 6.3 Amazon EventBridge

#### Core Definition

EventBridge is a serverless event bus for building event-driven architectures. It connects application events, AWS service events, and SaaS partner events to targets.

- **Scope**: Regional (with cross-region event buses).
- **Pricing**: $1.00 per million events (custom/partner). AWS service events routed to EventBridge are free.
- **SLA**: 99.99%.
- **Architectural Abstraction**: Serverless event router with content-based filtering and transformation.

#### Core Capabilities

**Event Buses**:
- **Default**: Receives all AWS service events for the account.
- **Custom**: Application-specific events.
- **Partner**: SaaS integrations (Zendesk, Datadog, Auth0, etc.).

**Rules**: Match events using patterns (JSON-based filtering on any field in the event). Route matched events to targets.

**Targets** (200+): Lambda, SQS, SNS, Kinesis, Step Functions, CodePipeline, ECS tasks, SSM Run Command, API Gateway, Redshift, API destinations (HTTP), CloudWatch Logs, another EventBridge bus (cross-account/cross-region).

**Event Patterns**: Match on event source, detail-type, and any field in the `detail` section. Supports exact match, prefix, numeric range, exists/does-not-exist, OR logic.

**Transformations**: Modify event before sending to target. Input transformer with JSON path extraction and template.

**Archive & Replay**: Archive events. Replay archived events to the bus. For testing, debugging, or reprocessing.

**Scheduling**: EventBridge Scheduler (separate feature). One-time or recurring schedules. Supports flexible time windows, retries, and DLQ. Replaces CloudWatch Events scheduled rules.

**Schema Registry**: Discover event schemas automatically. Generate code bindings for typed event handling.

**Pipes**: Point-to-point integration between sources (SQS, Kinesis, DynamoDB Streams, MQ, MSK, self-managed Kafka) and targets with optional filtering, enrichment (Lambda, API Gateway, Step Functions), and transformation.

**Global Endpoints**: Cross-region failover for event buses. Route events to a primary region, fail over to secondary region based on Route 53 health check. Active-passive event processing.

#### Architectural Design Patterns

**Event-Driven Microservices**: Each microservice emits events to a custom event bus. Other services subscribe to relevant events via rules. Loose coupling with content-based routing.

**Cross-Account Event Routing**: Central event bus in a shared services account. Workload accounts send events to the central bus (cross-account rules). Central bus routes events to appropriate targets.

**SaaS Integration**: Zendesk ticket created → EventBridge Partner bus → Rule → Lambda → create Jira ticket. No polling required.

**Scheduled Automation**: EventBridge Scheduler → Lambda (daily cleanup, report generation, compliance checks).

#### When to Use

- Complex event routing with content-based filtering.
- AWS service event reactions (EC2 state change, CodePipeline status, Config compliance change).
- SaaS event integration.
- Scheduled tasks.
- Cross-account/cross-region event distribution.
- When you need event replay.

#### When NOT to Use

- Simple queue-based work distribution. Use SQS.
- High-throughput streaming (millions/sec). Use Kinesis.
- Fan-out without filtering. SNS is simpler and cheaper for raw fan-out.

#### Advanced Professional-Level Exam Traps

1. **EventBridge default bus receives ALL AWS service events for free**. But custom events cost $1/million.
2. **EventBridge replaces CloudWatch Events**. Same underlying service, but EventBridge has more features (schema registry, partner buses, pipes). Exam may use either name.
3. **Archive and Replay**: Unique capability. Neither SNS nor SQS supports this natively.
4. **Cross-region event routing**: Use EventBridge rules to forward events to a bus in another region. Useful for centralized event processing.
5. **Global Endpoints**: Active-passive failover. Uses Route 53 health checks. Events automatically route to secondary region if primary is unhealthy.
6. **EventBridge Pipes vs Rules**: Pipes are point-to-point (source → transform → target). Rules are pattern-match-to-target on a bus. Pipes are for integration pipelines; rules are for event routing.
7. **EventBridge Scheduler vs EventBridge Rules**: Scheduler supports one-time schedules, time windows, and has better retry/DLQ support. Rules support only cron/rate expressions.


### 6.4 AWS Step Functions

#### Core Definition

Step Functions is a serverless workflow orchestration service. It coordinates multiple AWS services into visual workflows (state machines) with built-in error handling, retries, and parallelism.

- **Scope**: Regional.
- **Pricing**: Standard: $0.025 per 1,000 state transitions. Express: $0.00001667 per GB-second + $0.000001 per request.
- **SLA**: 99.9%.
- **Architectural Abstraction**: Finite state machine engine with durable execution history.

#### Core Capabilities

**Workflow Types**:
- **Standard Workflows**: Durable. Execution history persisted. Up to 1 year execution. Exactly-once execution. Up to 25,000 executions per second (with request). Ideal for long-running, auditable processes.
- **Express Workflows**: High-volume, short-duration. Up to 5 minutes. At-least-once execution. Up to 100,000 executions per second. Ideal for streaming data processing, IoT, API orchestration. Synchronous (wait for result) or Asynchronous (fire-and-forget).

**State Types**:
- **Task**: Invoke a service (Lambda, ECS, DynamoDB, SQS, SNS, Glue, SageMaker, Batch, etc.). Direct SDK integration (200+ AWS services) without Lambda glue code.
- **Choice**: Branching logic (if/else).
- **Parallel**: Execute branches in parallel.
- **Map**: Iterate over an array. Inline mode (up to 40 concurrent) or Distributed mode (up to 10,000 concurrent, for large-scale parallel processing like processing millions of S3 objects).
- **Wait**: Pause for a duration or until a timestamp.
- **Succeed/Fail**: Terminal states.
- **Pass**: Transform data or inject fixed values.

**Error Handling**:
- Retriers: Retry on specific error types with exponential backoff.
- Catchers: Catch errors and redirect to a fallback state.
- Heartbeat: For long-running tasks, heartbeat timeout detects stalled tasks.
- Built-in error types: `States.ALL`, `States.Timeout`, `States.TaskFailed`, `States.Permissions`.

**SDK Integration**: Call AWS services directly from a state machine definition (not just Lambda). Reduces the need for Lambda functions as glue code.

**Activity Tasks**: For tasks executed by external workers (on-premises systems, human approval). Worker polls for tasks, processes, and reports success/failure.

#### Architectural Design Patterns

**Data Processing Pipeline**: S3 upload → EventBridge → Step Functions → parallel Lambda invocations → aggregate results → write to DynamoDB.

**Human Approval Workflow**: Step Functions → send approval request (SES/SNS) → Wait state → API Gateway callback → approve/reject → continue workflow.

**Distributed Map for Large-Scale Processing**: S3 inventory of millions of objects → Step Functions Distributed Map → Lambda processes each object → aggregate results. Replaces custom batch orchestration.

**Saga Pattern**: Microservice transactions. Each step has a compensating transaction. If Step 3 fails, Step Functions executes compensating transactions for Step 2 and Step 1 (rollback).

#### When to Use

- Multi-step workflows with error handling and retries.
- Long-running processes (Standard: up to 1 year).
- Visual workflow definition and monitoring.
- Complex orchestration of multiple AWS services.
- Replacing custom state management code.

#### When NOT to Use

- Simple event-driven processing (one trigger → one action). Use Lambda directly.
- High-throughput, low-latency streaming. Use Kinesis.
- Cost-sensitive, very high-volume orchestration. Standard workflow charges per state transition can add up.

#### Advanced Professional-Level Exam Traps

1. **Standard vs Express**: Standard = durable, exactly-once, up to 1 year. Express = high throughput, at-least-once, up to 5 minutes. If a question mentions "high volume IoT event processing," Express is the answer.
2. **Distributed Map** can process millions of items in parallel. This is the answer for "process all objects in an S3 bucket at scale" type questions.
3. **SDK integrations reduce Lambda functions**. Instead of Lambda → DynamoDB, use a direct DynamoDB PutItem task state. Reduces cost and latency.
4. **State transition costs**: Standard workflows charge per state transition. A workflow with many states and iterations can become expensive.
5. **Wait state with callback**: Use `waitForTaskToken` for asynchronous integrations. Step Functions pauses until the task sends a callback with the token.


### 6.5 Amazon Kinesis

#### Core Definition

Kinesis is a family of services for real-time streaming data. It collects, processes, and analyzes data in real-time.

**Kinesis Data Streams (KDS)**: Real-time data streaming. Producers → shards → consumers.
**Kinesis Data Firehose**: Near-real-time data delivery to destinations (S3, Redshift, OpenSearch, Splunk, HTTP endpoints).
**Kinesis Data Analytics (now Amazon Managed Service for Apache Flink)**: Real-time analytics using Apache Flink (SQL or Java/Scala/Python).
**Kinesis Video Streams**: Real-time video streaming.

- **Scope**: Regional.
- **KDS Pricing**: On-Demand ($0.08/hr per GB/hr throughput) or Provisioned ($0.015/shard-hour + $0.014/million PUT payload units).
- **Firehose Pricing**: $0.029/GB ingested (first 500 TB/month).
- **SLA**: 99.9% for KDS and Firehose.

#### Core Capabilities (Kinesis Data Streams)

**Architecture**:
- Data is organized into **shards**. Each shard provides 1 MB/sec write, 2 MB/sec read.
- Records: Partition Key + Data Blob (up to 1 MB) + Sequence Number.
- Partition Key → hash → shard assignment. Uniform partition keys distribute data evenly.
- **Retention**: 24 hours (default), up to 365 days. Replay from any point.
- **Ordering**: Ordered within a shard (by sequence number). No ordering across shards.

**Capacity Modes**:
- **On-Demand**: Automatically scales shards. Default 4 MB/s write, scales to 200 MB/s. No capacity planning.
- **Provisioned**: Manually manage shard count. $0.015/shard-hour.

**Consumers**:
- **Shared throughput (Classic)**: Consumers share the 2 MB/s per shard. GetRecords API with polling.
- **Enhanced Fan-Out**: Dedicated 2 MB/s per consumer per shard. SubscribeToShard API (push via HTTP/2). Use when you have multiple consumers or need lower latency (\<200ms vs ~200ms–5s for classic).
- **Lambda as consumer**: Event source mapping. Lambda polls KDS. Supports batching, partial batch failure, bisection on error.
- **KCL (Kinesis Client Library)**: Java library for building consumer applications. Handles shard assignment, checkpointing, load balancing. One KCL worker per shard (max).

**Scaling**: Shard splitting (increase) and merging (decrease). On-Demand mode handles this automatically.

#### Core Capabilities (Kinesis Data Firehose)

- **Sources**: Direct PUT, Kinesis Data Streams, CloudWatch Logs, IoT rules, MSK, WAF logs.
- **Destinations**: S3, Redshift (via S3 intermediate), OpenSearch, Splunk, Datadog, HTTP endpoints, and more.
- **Transformation**: Lambda function for in-stream transformation before delivery.
- **Buffering**: Time-based (60-900 seconds) and size-based (1-128 MB). Whichever threshold is hit first triggers delivery.
- **Compression**: GZIP, Snappy, Zip (for S3).
- **Format Conversion**: Convert JSON to Parquet/ORC for S3 (using Glue schema).
- **Near-real-time**: Minimum latency is ~60 seconds (buffer interval). NOT real-time.
- **No retention**: Firehose is a delivery pipe, not a storage layer. No replay capability.
- **Automatic scaling**: No shards to manage. Scales automatically.

#### Architectural Design Patterns

**Real-Time Analytics Pipeline**: Producers → KDS → Apache Flink (Managed Flink) → real-time aggregation → DynamoDB/Redshift.

**Log Aggregation**: CloudWatch Logs → Kinesis Data Firehose → S3 (Parquet, partitioned by date). Athena queries the data lake.

**Click-Stream Processing**: Web/mobile → KDS → Lambda consumer → real-time aggregation → DynamoDB (dashboards) + Firehose → S3 (batch analytics).

#### When to Use

- **KDS**: Real-time processing with ordering guarantees. Multiple consumers needing independent read positions. Data replay requirement.
- **Firehose**: Near-real-time delivery to S3/Redshift/OpenSearch without managing consumers.
- **Managed Flink**: Real-time SQL or complex event processing.

#### When NOT to Use

- **KDS**: If you don't need real-time or ordering. SQS is simpler for queue-based workloads.
- **Firehose**: If you need real-time (\<60s latency). Use KDS with custom consumer or Lambda.
- **Either**: Simple event routing. Use EventBridge.

#### Trade-Offs: Kinesis vs SQS vs MSK

| Aspect | KDS | SQS | MSK (Kafka) |
|---|---|---|---|
| Pattern | Streaming | Queue | Streaming |
| Ordering | Per shard | FIFO per group | Per partition |
| Replay | Yes | No | Yes |
| Retention | Up to 365 days | Up to 14 days | Unlimited |
| Consumers | Multiple, independent | Single (per message) | Multiple, independent |
| Throughput | MB/s per shard, scale shards | Nearly unlimited | MB/s per broker |
| Latency | ~200ms (classic), ~70ms (EFO) | ~ms (long poll) | ~ms |
| Managed | Fully | Fully | Managed Kafka |
| Cost model | Per shard-hour | Per request | Per broker-hour |

#### Advanced Professional-Level Exam Traps

1. **Kinesis Data Streams retains data** (up to 365 days). SQS does not retain after consumption. For replay, use KDS.
2. **Firehose is near-real-time (≥60s latency)**. It is NOT real-time. For real-time, use KDS with Lambda.
3. **KDS ordering is per shard only**. If you need global ordering, use a single shard (limits throughput to 1 MB/s write).
4. **Enhanced Fan-Out** provides dedicated throughput per consumer. If a question mentions multiple consumers needing independent, low-latency access, EFO is the answer.
5. **KDS → Lambda**: Lambda gets records in batches per shard. One Lambda invocation per shard at a time (unless using parallelization factor to scale within a shard).
6. **Firehose cannot deliver to KDS**. It's a one-way pipe to destinations. KDS → Firehose is a valid pattern (Firehose as a consumer of KDS).


### 6.6 Amazon API Gateway

#### Core Definition

API Gateway is a fully managed service for creating, deploying, and managing APIs at any scale.

Three types:
1. **REST API**: Full-featured REST API. API keys, throttling, caching, request/response transformation, WAF, Cognito/Lambda authorizers, usage plans.
2. **HTTP API**: Lighter, cheaper, faster REST API. Supports OIDC/OAuth2, Lambda/HTTP backends. No caching, limited transformation. 70% cheaper than REST API.
3. **WebSocket API**: Full-duplex communication. Persistent connections. Chat apps, real-time dashboards, IoT.

- **Scope**: Regional or Edge-optimized (uses CloudFront at the edge) or Private (VPC only, via interface endpoint).
- **Pricing**: REST: $3.50/million requests. HTTP: $1.00/million requests. WebSocket: $1.00/million messages. Caching: $0.02–$3.80/hr by cache size.
- **SLA**: 99.95%.

#### Core Capabilities

- **Throttling**: Account-level: 10,000 requests/sec, 5,000 burst. Stage-level and method-level throttling configurable.
- **Caching** (REST API only): In-memory cache for responses. TTL 0-3600 seconds. Reduces backend invocations.
- **Authorization**: IAM, Cognito User Pools, Lambda authorizer (custom logic), API keys (for identification, not security).
- **Request/Response Transformation**: Velocity Template Language (VTL) mapping templates. Transform request/response format (REST API only).
- **Usage Plans & API Keys**: Rate limiting per API key. Tiered access for SaaS APIs.
- **Stages**: Deploy to stages (dev, staging, prod). Stage variables for environment-specific configuration.
- **Canary Deployments**: Route a percentage of traffic to a canary stage for testing.
- **Custom Domains**: Map custom domains with ACM certificates. Base path mapping to different APIs.
- **Integration Types**: Lambda (proxy or custom), HTTP (proxy or custom), AWS Service (direct DynamoDB/SQS/SNS/Step Functions/etc.), Mock, VPC Link (for private backends).

#### Architectural Design Patterns

**Serverless API**: API Gateway (REST or HTTP) → Lambda → DynamoDB. Zero infrastructure management.

**API Gateway as Facade**: API Gateway → VPC Link → NLB → EC2/ECS private backend. API Gateway handles auth, throttling, and SSL termination.

**Microservices API**: Custom domain → API Gateway → different Lambda functions per path/method. Or: API Gateway → VPC Link → NLB → ECS services.

#### When to Use

- Any HTTP API requiring managed throttling, authentication, and deployment management.
- Serverless backends with Lambda.
- API monetization with usage plans and API keys.
- WebSocket applications.

#### When NOT to Use

- Extreme low latency (\<10ms additional). API Gateway adds latency (~10-50ms for REST, ~5-10ms for HTTP API).
- Non-HTTP protocols (raw TCP, gRPC). Use NLB directly. (API Gateway supports gRPC for HTTP API.)
- Very high throughput at very low cost. At millions of requests, ALB may be cheaper.

#### Advanced Professional-Level Exam Traps

1. **REST API vs HTTP API**: REST has caching, WAF, request transformation, API keys. HTTP API is cheaper but has fewer features. Questions test whether you pick the right one.
2. **Private API Gateway**: Accessible only from within VPCs via interface endpoint. Useful for internal APIs.
3. **Lambda authorizer caching**: Authorizer results can be cached to avoid invoking the Lambda for every request. TTL configurable.
4. **29-second timeout**: API Gateway has a maximum integration timeout of 29 seconds. Longer operations need async patterns (API Gateway → SQS/Step Functions → callback).
5. **Usage plans enforce throttling per API key**, not per user identity. API keys are for tracking/throttling, not for authentication.
6. **Edge-optimized API Gateway uses CloudFront**, but you CANNOT customize the CloudFront distribution (no custom caching behaviors, no WAF on the CloudFront distribution itself — use WAF on the API Gateway stage).


### 6.7 Amazon MQ

#### Core Definition

Amazon MQ is a managed message broker service for Apache ActiveMQ and RabbitMQ. It is for migrating existing message broker workloads to AWS without rewriting application code.

- **Scope**: Regional.
- **Pricing**: Per-broker-instance-hour + storage + data transfer.
- **Protocols**: ActiveMQ: JMS, AMQP, MQTT, STOMP, OpenWire. RabbitMQ: AMQP.

#### When to Use

- Migrating from on-premises ActiveMQ/RabbitMQ.
- Applications that require JMS, AMQP, MQTT, STOMP protocols.
- When you can't rewrite applications to use SQS/SNS.

#### When NOT to Use

- Cloud-native applications. Use SQS/SNS/EventBridge (simpler, more scalable, fully serverless).
- High-scale serverless architectures. Amazon MQ requires broker instances.

#### Advanced Professional-Level Exam Traps

1. **MQ is for migration**. If a question mentions "migrate existing ActiveMQ/RabbitMQ," Amazon MQ is the answer.
2. **MQ is NOT serverless**. It runs on instances. SQS/SNS are serverless. For new cloud-native development, SQS/SNS are preferred.
3. **MQ supports MQTT** for IoT devices. If a question mentions MQTT and migration, MQ is the answer (though IoT Core is preferred for new IoT architectures).


### 6.8 AWS AppSync

#### Core Definition

AppSync is a managed GraphQL (and pub/sub) API service. It resolves GraphQL queries against multiple data sources (DynamoDB, Lambda, RDS, HTTP, OpenSearch, EventBridge).

- **Scope**: Regional.
- **Pricing**: $4.00 per million query/mutation operations. $2.00 per million real-time updates.

#### Key Capabilities

- **Real-time subscriptions**: WebSocket-based. Clients subscribe to data changes.
- **Offline sync**: Conflict detection and resolution for mobile apps.
- **Caching**: Server-side caching.
- **Authorization**: API Key, IAM, Cognito, OIDC, Lambda.
- **Merged APIs**: Combine multiple AppSync APIs into a single endpoint.
- **Pipeline resolvers**: Chain multiple data source operations.

#### When to Use

- GraphQL API requirements. Mobile apps with real-time sync. Applications needing to query multiple data sources in a single API call.

#### When NOT to Use

- REST APIs. Use API Gateway.
- Simple CRUD operations. API Gateway + Lambda is simpler.

## 7. Edge & Global Services

Edge services extend AWS to the global network edge, reducing latency for end users. Professional-level questions test subtle differences between CloudFront and Global Accelerator, caching strategies, and edge compute capabilities.


### 7.1 Amazon CloudFront

#### Core Definition

CloudFront is AWS's global Content Delivery Network (CDN). It caches content at 400+ Points of Presence (edge locations) and 13+ Regional Edge Caches worldwide.

- **Scope**: Global.
- **Pricing**: Per-GB data transfer out (varies by region: $0.085/GB US/EU, up to $0.170/GB in other regions) + per-request ($0.0075-$0.016 per 10,000 HTTP requests). Price Class can limit which edge locations are used (reduce cost).
- **SLA**: 99.9%.
- **Architectural Abstraction**: Reverse proxy cache at the network edge with programmable request/response handling.

#### Core Capabilities

**Origins**:
- S3 bucket (with Origin Access Control — OAC, which replaces legacy OAI).
- Custom HTTP origin (ALB, EC2, API Gateway, any HTTP server).
- MediaStore, MediaPackage.
- Lambda Function URLs.
- Origin Groups: Primary + failover origin. If primary returns 5xx/4xx, fail over to secondary. For HA.

**Caching Behavior**:
- Cache based on: path pattern, headers, query strings, cookies.
- Cache Policy: Defines what's included in the cache key and TTL.
- Origin Request Policy: Defines what's forwarded to the origin (separate from cache key).
- TTL: Default, min, max. `Cache-Control` and `Expires` headers from origin override defaults.
- Cache invalidation: Invalidate specific paths. First 1,000 invalidation paths/month free, then $0.005 per path. Use versioned file names instead of invalidation for cost optimization.

**Security**:
- **OAC (Origin Access Control)**: Restricts S3 access to CloudFront only. Supports SSE-KMS encrypted objects (OAI does not).
- **Signed URLs/Signed Cookies**: Restrict access to content. Time-limited. IP-restricted (optional). Signed URL for individual files. Signed Cookies for multiple files (streaming, subscriptions).
- **Geo Restriction**: Allow/block access by country (based on CloudFront's GeoIP database).
- **Field-Level Encryption**: Encrypt specific POST form fields at the edge before forwarding to origin. Ensures sensitive data is encrypted end-to-end.
- **HTTPS**: Viewer → CloudFront (TLS required or redirected). CloudFront → Origin (match viewer or HTTPS only). SNI-based custom SSL (free) or dedicated IP ($600/month per distribution — for legacy clients without SNI).
- **WAF integration**: Attach WAF Web ACL to CloudFront distribution.

**Edge Compute**:
- **CloudFront Functions**: JavaScript. Runs at ALL edge locations. \<1ms execution. Viewer request/response only. 2 MB max function size. 10 KB max output. Use for: header manipulation, URL rewrite, cache key normalization, JWT validation, A/B testing, simple redirects. $0.10 per million invocations.
- **Lambda@Edge**: Node.js/Python. Runs at Regional Edge Caches (not all 400+ edge locations). Up to 5s (viewer triggers) or 30s (origin triggers). 50 MB deployment package. Access to external network, SDK. All four trigger points: viewer request, viewer response, origin request, origin response. $0.60 per million invocations + $0.00000625125 per 128MB-ms.

**Real-Time Logs**: Stream access logs in real-time to Kinesis Data Streams. For real-time monitoring and analytics.

**Standard Logs**: Access logs to S3. Delayed (minutes to hours).

**Continuous Deployment**: Staging distribution with traffic-weighted routing. Canary deployments for CloudFront configuration changes.

#### Architectural Design Patterns

**Static Website Acceleration**: S3 + CloudFront with OAC. Global distribution with caching. Custom domain + ACM certificate.

**Dynamic API Acceleration**: API Gateway or ALB → CloudFront (with caching disabled or low TTL). Benefits: SSL termination at edge, HTTP/2/3, connection keep-alive to origin, Shield Advanced protection.

**Multi-Origin Architecture**: CloudFront behaviors route `/api/*` to ALB origin, `/static/*` to S3 origin, `/legacy/*` to on-premises origin.

**Origin Failover**: Origin Group with primary (us-east-1 ALB) + failover (eu-west-1 ALB). Automatic failover on 5xx errors.

#### When to Use

- Global content distribution (static and dynamic).
- Reducing latency for global users.
- Protecting origins from direct internet exposure.
- DDoS protection (Shield Advanced integration).
- Edge compute for request/response manipulation.

#### When NOT to Use

- Non-HTTP protocols (TCP/UDP). Use Global Accelerator.
- When content is not cacheable AND origin latency is acceptable. CloudFront adds complexity without benefit if there's no caching opportunity and no need for edge features.
- When all users are in a single region close to the origin.

#### Trade-Offs: CloudFront vs Global Accelerator

| Aspect | CloudFront | Global Accelerator |
|---|---|---|
| Protocol | HTTP/HTTPS | TCP/UDP (any protocol) |
| Caching | Yes | No |
| Edge compute | Yes (Functions, Lambda@Edge) | No |
| Anycast IPs | No (DNS-based) | Yes (2 static anycast IPs) |
| Origin types | S3, HTTP | ALB, NLB, EC2, EIP |
| Use case | Web content, APIs, streaming | Non-HTTP, gaming, IoT, VoIP |
| Failover | Origin Group (HTTP errors) | Endpoint health check (TCP/HTTP) |
| DDoS | Shield Standard/Advanced | Shield Standard/Advanced |
| WAF | Yes | No |

#### Advanced Professional-Level Exam Traps

1. **CloudFront Functions vs Lambda@Edge**: Functions run at all 400+ edge locations, are faster and cheaper, but limited to viewer triggers and JavaScript. Lambda@Edge has more capabilities but runs at Regional Edge Caches (fewer locations) and is more expensive.
2. **OAC (not OAI)** is the current best practice for S3 origins. OAC supports SSE-KMS; OAI does not.
3. **Cache invalidation costs money** after 1,000 paths/month. Use versioned file names (e.g., `app-v2.js`) instead.
4. **CloudFront does NOT support non-HTTP protocols**. For TCP/UDP workloads, use Global Accelerator.
5. **ACM certificates for CloudFront MUST be in us-east-1**. Even if your origin is in another region.
6. **Price Classes**: Restrict CloudFront to cheaper regions. Price Class 100 = US/EU only (cheapest). Price Class 200 = adds Asia. Price Class All = all edge locations.


### 7.2 AWS Global Accelerator

#### Core Definition

Global Accelerator provides static anycast IP addresses that route traffic to optimal AWS endpoints based on health, geography, and routing policies. It uses the AWS global network instead of the public internet.

- **Scope**: Global.
- **Pricing**: $0.025/hr per accelerator + data transfer premium ($0.015–$0.075/GB depending on region pair).
- **SLA**: 99.99%.
- **Architectural Abstraction**: Anycast IP addresses → AWS edge location → AWS backbone → regional endpoints.

#### Core Capabilities

- **Static IP Addresses**: 2 anycast IPs per accelerator. Never change. Useful for DNS caching issues, firewall whitelisting.
- **Endpoint Types**: ALB, NLB, EC2 instances, Elastic IP addresses. In one or more regions.
- **Traffic Dials**: Weight traffic distribution across regions (0-100%). Blue-green deployments.
- **Health Checks**: TCP, HTTP, HTTPS health checks on endpoints. Automatic failover to healthy endpoints in \<30 seconds.
- **Client Affinity**: Route a client to the same endpoint (by source IP). Useful for stateful applications.
- **Custom Routing Accelerator**: Map specific clients to specific EC2 instances behind the accelerator. For gaming, VoIP, IoT use cases requiring deterministic routing.

#### When to Use

- Non-HTTP/HTTPS applications (TCP/UDP workloads: gaming, VoIP, IoT).
- Multi-region active-active with instant failover (static IPs, no DNS caching issue).
- When you need static IP addresses for whitelisting.
- When internet path variability causes latency issues.

#### When NOT to Use

- HTTP content that benefits from caching. Use CloudFront.
- If you don't need static IPs or multi-region routing. Direct ALB is simpler and cheaper.

#### Advanced Professional-Level Exam Traps

1. **Global Accelerator provides static IPs**. CloudFront does not. If a question mentions "firewall whitelisting" or "static IP," Global Accelerator is likely the answer.
2. **Failover is \<30 seconds** because it's IP-based (no DNS TTL issue). CloudFront failover depends on DNS TTL.
3. **Global Accelerator + ALB** is a common pattern for HTTP applications when you need both static IPs and Layer 7 features.
4. **Data transfer through Global Accelerator costs more** than standard data transfer. Factor in cost.

## 8. Observability & Operations

Operations questions on SAP-C02 test your ability to design monitoring, alerting, automated remediation, and compliance validation systems across a multi-account organization.


### 8.1 Amazon CloudWatch

#### Core Definition

CloudWatch is the unified monitoring and observability service for AWS. It collects metrics, logs, and traces from AWS services and applications.

- **Scope**: Regional (some dashboards can be cross-region/cross-account).
- **Pricing**: Metrics: Free (basic, 5-min resolution). Detailed (1-min): $0.30/metric/month. Custom metrics: $0.30/metric/month. Logs: $0.50/GB ingested, $0.03/GB stored. Alarms: $0.10/alarm/month (standard).
- **Architectural Abstraction**: Time-series metrics database + log aggregation + alerting engine.

#### Core Capabilities

**Metrics**:
- AWS service metrics (EC2 CPU, RDS connections, Lambda duration, etc.).
- Custom metrics: Publish via PutMetricData API or CloudWatch Agent.
- High-resolution metrics: 1-second granularity (custom metrics). Standard: 1-minute or 5-minute.
- Metric Math: Combine metrics with expressions (e.g., `errors/requests * 100` for error rate).
- Anomaly Detection: ML-based expected band. Alert when metric is outside the band.
- Metric Streams: Real-time metric delivery to S3, Kinesis Data Firehose, or partner destinations (Datadog, Splunk). Near-real-time (2 minutes).

**Logs**:
- CloudWatch Logs: Centralized log storage. Log groups → log streams.
- Log Insights: Interactive SQL-like query language for searching/analyzing logs.
- Subscription Filters: Real-time streaming of log data to Lambda, Kinesis Data Streams, Kinesis Data Firehose.
- Metric Filters: Extract metric values from log data (e.g., count ERROR occurrences).
- Cross-Account Log Sharing: Share logs between accounts using subscription filters.
- Retention: Configurable per log group (1 day to indefinite). Default: never expire.
- Encryption: SSE-KMS for logs at rest.
- **Logs Insights**: Query across multiple log groups, visualize results, save queries. Very powerful for troubleshooting.

**Alarms**:
- Threshold alarms: Static threshold on a metric.
- Anomaly detection alarms: Trigger when metric is outside expected band.
- Composite alarms: Combine multiple alarms with AND/OR logic. Reduce alarm noise.
- Actions: SNS notification, EC2 action (stop/terminate/reboot/recover), Auto Scaling action, Systems Manager OpsItem/Incident, Lambda.
- OK/ALARM/INSUFFICIENT_DATA states.

**Dashboards**: Cross-account, cross-region dashboards. Widgets: metrics, logs, alarms, text, custom. Share dashboards publicly or with specific accounts.

**Application Signals**: APM (Application Performance Monitoring). Auto-instrument applications on EKS/ECS/EC2 for latency, error rate, request count. SLO monitoring.

**CloudWatch Agent**: Install on EC2/on-premises for:
- Detailed OS-level metrics (memory, disk, swap — not available in basic monitoring).
- Custom metrics.
- Log collection.
- StatsD and collectd integration.
- Unified agent replaces legacy logs agent and monitoring scripts.

**Contributor Insights**: Identify top contributors to a metric or log pattern. E.g., which API callers are generating the most errors.

**Synthetics (Canary)**: Automated scripts that monitor endpoints and APIs. Configurable schedule. Detect issues before users do. Supports screenshots for UI monitoring.

#### Architectural Design Patterns

**Cross-Account Observability**: Central monitoring account uses CloudWatch cross-account observability. Source accounts share metrics, logs, and traces with the monitoring account. Single pane of glass for the organization.

**Automated Remediation**: CloudWatch Alarm → SNS → Lambda → remediate (restart instance, flush cache, scale up). Or: CloudWatch Alarm → SSM Automation runbook.

**Log Analytics Pipeline**: Application → CloudWatch Logs → Subscription Filter → Kinesis Data Firehose → S3 → Athena for ad-hoc analysis.

#### Advanced Professional-Level Exam Traps

1. **EC2 basic monitoring does NOT include memory or disk metrics**. You need the CloudWatch Agent for those.
2. **CloudWatch Logs Insights vs Athena**: Logs Insights queries CloudWatch Logs directly (fast, simple). For large-scale, long-term log analysis, ship logs to S3 and query with Athena.
3. **Composite alarms** reduce alert fatigue. Use them for complex health conditions (e.g., only alert if BOTH CPU > 90% AND error rate > 5%).
4. **Metric resolution**: Standard metrics are 1 or 5 minutes. High-resolution custom metrics are 1 second. Alarms can evaluate at 10-second periods for high-resolution metrics.
5. **Cross-region dashboards**: A single dashboard can display metrics from multiple regions. Useful for global operations.
6. **CloudWatch Logs retention is infinite by default**. Set retention policies to control costs.


### 8.2 AWS CloudTrail

#### Core Definition

CloudTrail records all API calls made in your AWS account. It is the audit log for AWS.

- **Scope**: Regional or organizational (organization trail spans all accounts).
- **Pricing**: Management events: One trail is free. Additional trails: $2.00 per 100,000 events. Data events: $0.10 per 100,000 events. Insights: $0.35 per 100,000 events analyzed.
- **Architectural Abstraction**: API call journal stored in S3 with optional CloudWatch Logs integration.

#### Core Capabilities

**Event Types**:
- **Management events** (Control plane): API calls that manage AWS resources (CreateBucket, RunInstances, CreateUser). Always logged (in the free trail).
- **Data events** (Data plane): API calls that operate ON resources (GetObject, PutObject, InvokeFunction). NOT free. Must be explicitly enabled. High volume.
- **Insights events**: Detect unusual API activity (spike in write events, errors).

**Trail Configuration**:
- Single-region or all-regions (recommended: all-regions).
- Organization trail: Covers all accounts. Created from management account or delegated admin.
- S3 destination: Centralized S3 bucket (usually in the Log Archive account).
- CloudWatch Logs: Stream events to CloudWatch Logs for real-time alerting.
- SNS notification: Alert on each log file delivery.
- SSE-KMS encryption for log files.
- Log file integrity validation: SHA-256 hash chain. Detect tampering.
- CloudTrail Lake: Managed data lake for CloudTrail events. SQL-based querying. 7-year retention. Replaces the need to query raw S3 files with Athena for common use cases.

#### Architectural Design Patterns

**Organization-Wide Auditing**: Organization trail → centralized S3 bucket in Log Archive account (with bucket policy allowing all org accounts). CloudWatch Logs in Security Tooling account for real-time alerting.

**Compliance Monitoring**: CloudTrail → CloudWatch Logs → Metric Filter (detect `DeleteTrail`, `StopLogging`, `DisableKey`) → Alarm → SNS → Lambda → auto-remediate.

**Security Investigation**: CloudTrail Lake for SQL-based queries across all accounts and events. Investigate who did what, when, and from where.

#### Advanced Professional-Level Exam Traps

1. **CloudTrail events are delivered with ~15-minute delay**. It is NOT real-time. For real-time responses, use EventBridge (which receives CloudTrail events in near-real-time).
2. **Data events are expensive and high-volume**. Enable selectively (e.g., only for critical S3 buckets).
3. **Log file integrity validation** uses digest files with SHA-256 hashes. Used to prove logs haven't been tampered with (compliance/forensics).
4. **CloudTrail cannot be stopped by member accounts** if the organization trail is configured by the management account. This is a critical security guardrail.
5. **CloudTrail Lake vs Athena on S3**: Lake is managed, simpler, but costs more. Athena on S3 is cheaper at scale but requires more setup.
6. **CloudTrail logs cross-account AssumeRole events** in both the source and destination accounts.


### 8.3 AWS Config

#### Core Definition

Config continuously records and evaluates the configuration of AWS resources. It answers: "What was the configuration of resource X at time Y?" and "Is resource X compliant with rule Z?"

- **Scope**: Regional (with aggregator for cross-account/cross-region).
- **Pricing**: $0.003 per configuration item recorded. $0.001 per rule evaluation per region.
- **Architectural Abstraction**: Configuration database + compliance evaluation engine.

#### Core Capabilities

- **Configuration Items**: Snapshot of a resource's configuration at a point in time. Stored in S3 and queryable via Config API.
- **Configuration History**: Timeline of changes to a resource.
- **Config Rules**: Evaluate resource compliance. AWS Managed Rules (200+) or Custom Rules (Lambda-based or Guard policy). Triggered on config change or periodic.
- **Remediation**: Auto-remediation via SSM Automation documents when a rule is non-compliant.
- **Conformance Packs**: Collections of Config rules and remediation actions. Deploy as a package. Pre-built packs for CIS, NIST, PCI DSS, HIPAA.
- **Aggregator**: Cross-account, cross-region view. Aggregates compliance data from all accounts in an Organization.
- **Advanced Queries**: SQL-like queries on current configuration state across accounts.

#### Architectural Design Patterns

**Compliance Dashboard**: Config aggregator → centralized view of compliance across the organization. Non-compliant resources trigger auto-remediation.

**Resource Configuration Audit**: Config records all changes. Use Configuration History to investigate when a security group rule was modified or who changed a VPC route table.

**Auto-Remediation**: Config rule detects S3 bucket without encryption → auto-remediation via SSM Automation → enable default encryption. Runs automatically on detection.

#### Advanced Professional-Level Exam Traps

1. **Config records configuration, not API calls** (that's CloudTrail). Config answers "what was the state?" CloudTrail answers "who changed it?"
2. **Config must be enabled in every region** where you have resources. Or use an aggregator to see across regions.
3. **Conformance Packs** are the answer for "deploy compliance checks across the organization for HIPAA/PCI DSS."
4. **Custom Config rules can use Lambda or AWS CloudFormation Guard** (policy-as-code language).
5. **Config can trigger remediation**, but the remediation uses SSM Automation (not Config itself).


### 8.4 AWS Systems Manager (SSM)

#### Core Definition

Systems Manager is a management service for EC2 instances, on-premises servers, and other AWS resources. It provides a unified interface for operational tasks.

- **Scope**: Regional.
- **Pricing**: Most features are free. Some charges: Advanced parameters ($0.05/advanced parameter/month), OpsCenter OpsItems, and Change Manager approval requests.

#### Core Capabilities

**Session Manager**: Secure shell access without opening SSH/RDP ports. Logs sessions to S3/CloudWatch. IAM-controlled. No bastion hosts needed.

**Run Command**: Execute commands on managed instances (EC2, on-prem) at scale. No SSH needed. IAM-controlled.

**Patch Manager**: Automate OS and application patching. Patch baselines define which patches to approve. Maintenance windows define when to patch.

**State Manager**: Define desired state for instances (e.g., "anti-virus must be installed"). Automatically enforces compliance.

**Parameter Store**: Hierarchical key-value store for configuration data and secrets. Standard parameters free. Supports encryption with KMS (SecureString). Up to 10,000 standard parameters per account.

**Automation**: Define runbooks (documents) for automated operational tasks (restart instance, create AMI, deploy patch). Used for Config remediation. Approval workflows via Change Manager.

**Inventory**: Collect metadata about instances (installed software, OS version, network config). Useful for compliance and license tracking.

**Maintenance Windows**: Schedule tasks (Run Command, Automation, Lambda, Step Functions) during defined windows.

**OpsCenter**: Central location for operational issues (OpsItems). Integrates with CloudWatch alarms, Config, EventBridge.

**Fleet Manager**: Visual UI for managing instances at scale.

**Distributor**: Package software to managed instances (agents, drivers, custom packages).

#### Architectural Design Patterns

**Bastion-less Architecture**: Session Manager replaces bastion hosts. All EC2 access via Session Manager. IAM controls who can access which instances. Sessions logged for audit.

**Automated Incident Response**: CloudWatch Alarm → SSM Automation → restart instance, capture diagnostics, notify team.

**Centralized Configuration**: Parameter Store for application configuration. Applications read parameters at startup. Hierarchical naming: `/prod/app/database/endpoint`. Reference from Lambda, ECS task definitions, CloudFormation.

#### Trade-Offs: Parameter Store vs Secrets Manager

| Aspect | Parameter Store | Secrets Manager |
|---|---|---|
| Pricing | Free (standard) | $0.40/secret/month |
| Rotation | No native rotation | Native rotation (Lambda-based) |
| Cross-account | Limited | Supported |
| Max size | 8 KB (advanced) | 64 KB |
| KMS encryption | Optional (SecureString) | Always encrypted |
| CloudFormation | Dynamic reference | Dynamic reference |
| Use case | Configuration, non-rotating secrets | Database credentials, API keys (auto-rotation) |

#### Advanced Professional-Level Exam Traps

1. **Session Manager vs bastion host**: Session Manager is more secure (no SSH port, IAM-controlled, logged). Preferred answer in most scenarios.
2. **Parameter Store SecureString**: Encrypted with KMS. The application (Lambda, EC2) needs `ssm:GetParameter` and `kms:Decrypt` permissions.
3. **Patch Manager + Maintenance Windows**: For "automate patching during maintenance windows," this is the answer.
4. **SSM Agent**: Must be installed and running on instances. Amazon Linux 2, Ubuntu, and Windows AMIs have it pre-installed. Custom AMIs may not.
5. **Hybrid management**: SSM can manage on-premises servers if they have SSM Agent and are registered as managed instances (Advanced Instances tier).


### 8.5 AWS X-Ray

#### Core Definition

X-Ray provides distributed tracing for applications. It traces requests across microservices to identify performance bottlenecks and errors.

- **Scope**: Regional (with cross-account tracing).
- **Pricing**: $5.00 per million traces recorded. $0.50 per million traces retrieved/scanned.

#### Core Capabilities

- **Traces**: End-to-end path of a request through the application.
- **Segments**: Individual service's contribution to a trace.
- **Subsegments**: Downstream calls (database queries, HTTP calls).
- **Service Map**: Visual representation of the application's architecture and request flow.
- **Annotations**: Key-value pairs for filtering traces.
- **Groups**: Filter traces based on criteria.
- **Sampling**: Control how many requests are traced (reduce cost for high-traffic apps).
- **Integration**: Lambda, API Gateway, ECS, EKS, EC2, Elastic Beanstalk, AppSync.
- **X-Ray SDK or OpenTelemetry**: Instrument applications for tracing.

#### When to Use

- Microservices debugging. Identifying latency bottlenecks. Understanding request flow through distributed systems.

#### Advanced Professional-Level Exam Traps

1. **X-Ray integrates natively with Lambda and API Gateway**. Enable tracing with a configuration toggle.
2. **Sampling rules control cost**. Default: 1 request/second + 5% of additional requests. Customize for your needs.
3. **X-Ray daemon**: Must run alongside the application (sidecar for ECS, DaemonSet for EKS) for EC2/container tracing.

## 9. Security & Compliance

Security on the SAP-C02 permeates every question. This domain covers the services specifically focused on security posture, key management, threat detection, and compliance validation.


### 9.1 AWS KMS (Key Management Service)

#### Core Definition

KMS is a managed service for creating and controlling encryption keys used to encrypt data across AWS services and applications.

- **Scope**: Regional. Keys exist in a single region. Multi-region keys available for cross-region use.
- **Pricing**: $1.00/month per customer-managed key. $0.03 per 10,000 API requests. Free tier: AWS-managed keys have no monthly charge.
- **Architectural Abstraction**: Hardware Security Module-backed key management with envelope encryption.

#### Core Capabilities

**Key Types**:
- **AWS-managed keys**: Created automatically by AWS services (e.g., `aws/s3`, `aws/ebs`). Free. Cannot manage lifecycle or policies directly.
- **Customer-managed keys (CMK)**: You create and manage. Full control over policies, rotation, deletion. $1/month.
- **AWS-owned keys**: Used by AWS services internally. Not visible in your account.
- **Custom Key Store**: KMS backed by CloudHSM cluster (you own the HSMs). For regulatory requirements needing single-tenant HSMs.

**Key Specs**:
- Symmetric (AES-256): Default. Used by most AWS services. Never leaves KMS (you never see the plaintext key).
- Asymmetric (RSA, ECC): Key pair. Public key downloadable. Use for sign/verify, encrypt outside AWS.
- HMAC keys: For generating/verifying hash-based message authentication codes.

**Envelope Encryption**:
- KMS generates a data key. Data key encrypts the data. The encrypted data key is stored alongside the encrypted data. To decrypt, KMS decrypts the data key, then the data key decrypts the data.
- `GenerateDataKey` → returns plaintext + encrypted data key. Encrypt data with plaintext key. Store encrypted data + encrypted data key. Discard plaintext key.
- This avoids sending all data to KMS (which has a 4 KB limit for direct encryption).

**Key Policies**:
- Every KMS key has a key policy (resource-based). Default policy allows the root account full access and enables IAM policies to control key usage.
- If you remove root access from the key policy, you can lock yourself out. Recovery requires AWS Support.

**Key Rotation**:
- Automatic rotation for customer-managed symmetric keys: Rotates annually. Old key material is preserved (can decrypt data encrypted with previous versions). New encryptions use new material.
- Manual rotation: Create a new key, re-encrypt data with the new key, use aliases to swap keys transparently.

**Multi-Region Keys**: Primary key in one region → replica keys in other regions. Same key material. Encrypt in one region, decrypt in another without cross-region KMS calls. Use for DynamoDB Global Tables, S3 cross-region replication with client-side encryption.

**Grants**: Programmatic delegation of key usage. Temporary access to a key without modifying the key policy. Used by AWS services internally (e.g., EBS grants KMS access to encrypt/decrypt volumes).

#### Failure & Edge Case Behavior

- **KMS throttling**: `GenerateDataKey`, `Decrypt`, etc. have rate limits per key per second (varies by region: 5,500-30,000 requests/sec). High-throughput encryption (e.g., S3 with SSE-KMS) can hit these limits. Mitigate with S3 Bucket Keys, caching data keys, or requesting limit increase.
- **Key deletion**: Schedule key deletion (7-30 day waiting period). During this period, the key is disabled. After deletion, all data encrypted with the key is unrecoverable. CloudTrail alarms should monitor for `ScheduleKeyDeletion`.
- **Cross-account key access**: Key policy must allow the external account, AND the external account's IAM policy must allow KMS actions on the key. Both sides must agree.

#### Advanced Professional-Level Exam Traps

1. **KMS keys are regional**. Encrypting data in us-east-1 requires the key in us-east-1. For cross-region, use multi-region keys.
2. **Envelope encryption**: Understand the flow. KMS does NOT encrypt your data directly (except for \<4 KB). It encrypts the data key.
3. **Key policy is the primary access control**. Without a key policy that enables IAM policies, IAM policies alone cannot grant KMS access.
4. **Automatic rotation preserves old material**. You can still decrypt data encrypted with previous key versions. No re-encryption needed.
5. **Custom Key Store (CloudHSM-backed)**: For compliance requiring dedicated HSMs. More complex, more expensive.
6. **S3 Bucket Keys**: Reduce KMS API calls for SSE-KMS. A bucket-level data key is generated, reducing per-object KMS calls.
7. **KMS condition keys**: `kms:ViaService` (restrict key usage to specific AWS services), `kms:EncryptionContext` (require specific context for encryption/decryption).


### 9.2 AWS CloudHSM

#### Core Definition

CloudHSM provides dedicated, single-tenant Hardware Security Modules in the AWS cloud. You have full control over keys and cryptographic operations.

- **Scope**: Regional (cluster spans AZs).
- **Pricing**: $1.60/hr per HSM instance.
- **Architectural Abstraction**: FIPS 140-2 Level 3 validated HSMs under your exclusive control.

#### Key Differences from KMS

| Aspect | KMS | CloudHSM |
|---|---|---|
| Tenancy | Multi-tenant | Single-tenant |
| FIPS 140-2 | Level 2 (some Level 3) | Level 3 |
| Key control | AWS manages HSM | You manage HSM |
| Integration | Native to all AWS services | Limited (custom integration) |
| Pricing | Per-key + per-request | Per-HSM-hour |
| Key export | Never leaves KMS | You can export keys |
| Availability | Managed | You manage HA (multi-AZ cluster) |

#### When to Use

- Regulatory requirements for FIPS 140-2 Level 3.
- You must control and own HSM hardware exclusively.
- Oracle TDE (Transparent Data Encryption) or SSL/TLS offloading.
- Custom Key Store for KMS (CloudHSM-backed KMS).

#### Advanced Professional-Level Exam Traps

1. **CloudHSM is your responsibility**. If all HSMs fail, AWS cannot recover your keys. Deploy in at least 2 AZs.
2. **KMS Custom Key Store** allows using KMS API while keys are stored in CloudHSM. Best of both worlds.
3. **CloudHSM supports PKCS#11, JCE, CNG interfaces**. Application-level integration required.


### 9.3 AWS Secrets Manager

#### Core Definition

Secrets Manager stores, rotates, and retrieves secrets (database credentials, API keys, tokens).

- **Pricing**: $0.40/secret/month + $0.05 per 10,000 API calls.
- **Key differentiator from Parameter Store**: Native automatic rotation with Lambda.

#### Core Capabilities

- **Automatic Rotation**: Lambda function rotates secrets on a schedule (e.g., rotate RDS password every 30 days). Pre-built rotation Lambda functions for RDS, Redshift, DocumentDB, and generic secrets.
- **Cross-Account Access**: Resource policy on the secret allows other accounts to access.
- **Encryption**: Always encrypted with KMS.
- **Versioning**: AWSCURRENT, AWSPREVIOUS, AWSPENDING labels for rotation stages.
- **CloudFormation integration**: Dynamic references to secrets.
- **Replication**: Replicate secrets to other regions for DR or multi-region applications.

#### When to Use

- Database credentials with automatic rotation.
- API keys that need periodic rotation.
- Secrets shared across accounts.
- When compliance requires secret rotation.

#### When NOT to Use

- Non-secret configuration data. Use Parameter Store (free).
- Secrets that don't need rotation and cost sensitivity is high. Use Parameter Store SecureString (free).

#### Advanced Professional-Level Exam Traps

1. **Secrets Manager vs Parameter Store**: If the question mentions "automatic rotation" or "database credentials rotation," Secrets Manager is the answer.
2. **Rotation Lambda needs network access to both Secrets Manager and the database**. In a VPC, this means VPC endpoints or NAT Gateway.
3. **Cross-region secret replication**: For multi-region applications that need the same secret in each region.


### 9.4 Amazon GuardDuty

#### Core Definition

GuardDuty is a managed threat detection service that continuously monitors for malicious activity and unauthorized behavior.

- **Scope**: Regional (enable per region, per account). Organization-wide via delegated admin.
- **Pricing**: Based on volume of data analyzed (CloudTrail events, VPC Flow Logs, DNS logs, S3 data events, EKS audit logs, etc.).
- **Architectural Abstraction**: ML-based anomaly detection + threat intelligence feeds.

#### Core Capabilities

- **Data Sources**: CloudTrail management/data events, VPC Flow Logs, DNS queries, S3 data events, EKS audit logs, RDS login activity, Lambda network activity, runtime monitoring (ECS, EKS, EC2).
- **Finding Types**: Reconnaissance, instance compromise, account compromise, S3 compromise, Kubernetes compromise, malware detection.
- **Trusted and Threat IP Lists**: Whitelist known IPs. Blacklist custom threat IPs.
- **Suppression Rules**: Filter out known benign findings.
- **Multi-Account**: Organization-wide deployment via delegated admin. Findings from all accounts visible centrally.
- **Malware Protection**: Scans EBS volumes attached to EC2/ECS for malware.
- **EventBridge Integration**: Findings → EventBridge → Lambda/SNS/Security Hub for automated response.

#### Architectural Design Patterns

**Automated Threat Response**: GuardDuty finding → EventBridge → Lambda → isolate compromised instance (change SG to no ingress/egress), create forensic snapshot, notify security team.

**Organization-Wide Threat Detection**: Delegated admin account enables GuardDuty in all member accounts and regions. Centralized findings in Security Hub.

#### Advanced Professional-Level Exam Traps

1. **GuardDuty does NOT prevent threats**. It detects them. For prevention, use Network Firewall, WAF, or SGs/NACLs.
2. **GuardDuty must be enabled per region**. It does NOT automatically cover all regions.
3. **GuardDuty uses VPC Flow Logs and CloudTrail but does NOT require you to enable them separately**. GuardDuty accesses these data sources independently.
4. **GuardDuty + Security Hub**: GuardDuty findings flow into Security Hub for centralized security posture.
5. **30-day free trial** for new accounts. After that, cost is based on data volume.


### 9.5 AWS Security Hub

#### Core Definition

Security Hub provides a comprehensive view of security posture across AWS accounts. It aggregates findings from GuardDuty, Inspector, Macie, Firewall Manager, IAM Access Analyzer, and third-party tools.

- **Scope**: Regional (with cross-region aggregation).
- **Pricing**: $0.0010 per finding ingestion event per month (first 10,000 free).

#### Core Capabilities

- **Security Standards**: CIS AWS Foundations Benchmark, AWS Foundational Security Best Practices, PCI DSS, NIST 800-53. Automated compliance checks.
- **Automated Checks**: Runs Config-based checks against security standards. Generates findings for non-compliant resources.
- **Finding Aggregation**: Cross-account (via Organizations), cross-region.
- **Automated Remediation**: Findings → EventBridge → Lambda or SSM Automation → auto-fix.
- **ASFF (AWS Security Finding Format)**: Standardized JSON format for all findings.

#### When to Use

- Centralized security posture management.
- Compliance dashboards (CIS, PCI DSS, NIST).
- Aggregating findings from multiple security services.

#### Advanced Professional-Level Exam Traps

1. **Security Hub requires AWS Config** to be enabled. Many automated checks use Config rules.
2. **Enabling a security standard automatically creates Config rules** for that standard's checks.
3. **Cross-region aggregation region**: Designate one region to aggregate findings from all other regions.


### 9.6 Other Security Services (Summary)

**Amazon Inspector**: Automated vulnerability assessment. Scans EC2 instances (OS vulnerabilities), container images (ECR), and Lambda functions for known CVEs. Continuous scanning. Findings go to Security Hub and EventBridge.

**Amazon Macie**: Sensitive data discovery in S3. Uses ML and pattern matching to detect PII, credentials, financial data. Generates findings for sensitive data exposure.

**Amazon Detective**: Investigates security findings. Analyzes CloudTrail, VPC Flow Logs, and GuardDuty findings. Visualizes relationships between resources, IP addresses, and API calls. Use for root cause analysis.

**AWS Firewall Manager**: Centralized management of WAF rules, Shield Advanced protections, Security Groups, Network Firewalls, and Route 53 Resolver DNS Firewalls across accounts in an Organization. Requires Security Hub. Auto-applies policies to new resources.

**AWS Audit Manager**: Continuous evidence collection for audits. Maps to compliance frameworks (SOC 2, PCI DSS, HIPAA, GDPR). Automates evidence gathering from Config, CloudTrail, Security Hub.

**IAM Access Analyzer**: Identifies resources shared with external entities. External access findings (S3 buckets, IAM roles, KMS keys, Lambda functions, SQS queues exposed outside the account/organization). Also validates IAM policies for correctness and least privilege.

**AWS Certificate Manager (ACM)**: Managed SSL/TLS certificates. Free public certificates. Auto-renewal. Integration with ALB, CloudFront, API Gateway. For CloudFront, certificates MUST be in us-east-1. Private CA available for internal PKI ($400/month/CA).

## 10. Migration & Data Transfer

Migration questions test your ability to choose the right tool for the right scenario: size of data, time constraint, network bandwidth, ongoing vs one-time, and application compatibility.


### 10.1 AWS Database Migration Service (DMS)

#### Core Definition

DMS migrates databases to AWS with minimal downtime. Supports homogeneous (same engine) and heterogeneous (different engine) migrations.

- **Scope**: Regional.
- **Pricing**: Per-replication-instance-hour + storage + data transfer.
- **Architectural Abstraction**: Replication instance that reads from source and writes to target.

#### Core Capabilities

- **Continuous replication (CDC)**: Ongoing change data capture after initial full load. Enables near-zero-downtime migration (cutover after replication catches up).
- **Schema Conversion Tool (SCT)**: Converts schema from one engine to another (e.g., Oracle → PostgreSQL). Identifies incompatibilities.
- **Sources**: Oracle, SQL Server, MySQL, PostgreSQL, MariaDB, MongoDB, SAP ASE, Azure SQL, Amazon S3, RDS, Aurora.
- **Targets**: RDS, Aurora, DynamoDB, S3, Redshift, Kinesis, DocumentDB, Neptune, OpenSearch, Kafka, Redis.
- **DMS Serverless**: Auto-scaling replication without managing instances. Pay for capacity used.
- **Data Validation**: Validates migrated data matches source.
- **Premigration Assessment**: Identifies potential issues before migration.

#### When to Use

- Database migration to AWS (on-premises → RDS/Aurora/DynamoDB).
- Ongoing replication from source to target (CDC for analytics pipelines).
- Heterogeneous migrations (with SCT for schema conversion).

#### When NOT to Use

- Large-scale file/object migration. Use DataSync or Snow Family.
- One-time bulk data export/import (native dump/restore may be faster for homogeneous migrations).

#### Advanced Professional-Level Exam Traps

1. **Heterogeneous migration requires SCT** for schema conversion + DMS for data migration. Two separate tools.
2. **DMS does not migrate stored procedures, triggers, or secondary indexes** automatically. SCT handles some; others require manual work.
3. **Full load + CDC** is the standard pattern for minimal-downtime migration. Full load copies existing data; CDC captures changes during migration.
4. **DMS replication instance must have network connectivity to both source and target**. Often requires VPN/DX to on-premises source.
5. **DMS to S3**: Useful for creating data lake ingestion pipelines from relational databases.
6. **Multi-AZ replication instance**: For HA during migration. Recommended for production migrations.


### 10.2 AWS Application Migration Service (MGN)

#### Core Definition

MGN (formerly CloudEndure Migration) performs lift-and-shift (rehost) migration of servers to AWS. Continuous replication of source servers to AWS, then cutover.

- **Pricing**: Free for 90 days per server (after that, licensing applies).
- **Architectural Abstraction**: Block-level replication agent on source server → staging EC2 instances → launch target EC2 instances.

#### Core Capabilities

- Agentless or agent-based replication.
- Continuous block-level replication (RPO in seconds).
- Non-disruptive testing (launch test instances without affecting source).
- Automated conversion (handles boot loader, drivers, networking changes).
- Supports Linux and Windows.

#### When to Use

- Lift-and-shift server migration.
- Large-scale migrations (hundreds/thousands of servers).
- When you want continuous replication with near-zero RPO.

#### When NOT to Use

- Database migration. Use DMS.
- Re-platforming or refactoring. Use manual migration or container migration tools.
- Small, simple migrations where creating AMIs is sufficient.

#### Advanced Professional-Level Exam Traps

1. **MGN = rehost (lift-and-shift)**. DMS = database migration. Don't confuse them.
2. **MGN replaces Server Migration Service (SMS)**. SMS is legacy.
3. **Testing cutover** does not affect the source server or ongoing replication. Test repeatedly.


### 10.3 AWS DataSync

#### Core Definition

DataSync automates and accelerates data transfer between on-premises storage and AWS, or between AWS storage services.

- **Pricing**: $0.0125/GB transferred.
- **Architectural Abstraction**: Agent-based data transfer service with scheduling and validation.

#### Core Capabilities

- **Sources/Destinations**: NFS, SMB, HDFS, self-managed object storage, S3, EFS, FSx (all types), Snowcone.
- **Agent**: VM deployed on-premises. Connects to source storage.
- **Bandwidth throttling**: Control bandwidth usage.
- **Data integrity verification**: Automatic checksumming.
- **Incremental transfer**: Only changed data.
- **Scheduling**: Hourly, daily, weekly.
- **Encryption**: In-transit (TLS) and at-rest (KMS at destination).
- **Service-to-service** (agentless): S3 → EFS, EFS → S3, FSx → S3, etc. No agent needed for AWS-to-AWS transfers.

#### When to Use

- Recurring data transfer (daily sync) between on-premises and AWS.
- One-time migration of large file datasets to S3/EFS/FSx.
- AWS-to-AWS data movement (S3 → EFS, etc.).

#### When NOT to Use

- Real-time replication. Use Storage Gateway or DMS.
- Database migration. Use DMS.
- Multi-petabyte offline transfer. Use Snow Family.

#### Advanced Professional-Level Exam Traps

1. **DataSync vs Storage Gateway**: DataSync is for data transfer/migration (one-time or scheduled). Storage Gateway is for ongoing hybrid access (mount points, caching).
2. **DataSync vs S3 Transfer Acceleration**: DataSync transfers files/objects with metadata preservation, scheduling, and validation. Transfer Acceleration speeds up S3 uploads only.
3. **DataSync can transfer between AWS services** without an on-premises agent. Useful for cross-region or cross-account data movement.


### 10.4 AWS Snow Family

#### Core Definition

Snow Family provides physical devices for offline data transfer and edge computing.

- **Snowcone**: 8 TB (HDD) or 14 TB (SSD). Small, portable. Edge computing with EC2/IoT Greengrass. Can run DataSync agent.
- **Snowball Edge Storage Optimized**: 80 TB usable. EC2 compute, Lambda. Large-scale data transfer.
- **Snowball Edge Compute Optimized**: 42 TB usable + powerful compute (52 vCPUs, optional GPU). Edge processing.
- **Snowmobile**: 100 PB. Semi-trailer truck. Exabyte-scale data transfer.

#### When to Use

- **Network bottleneck**: When transferring data over the network would take too long (rule of thumb: if network transfer takes more than a week, consider Snow).
- **No network connectivity**: Remote locations (oil rigs, ships, field operations).
- **Edge computing**: Process data locally before sending to cloud.

#### When NOT to Use

- Small data volumes (\<10 TB). Use DataSync or direct upload.
- Ongoing/continuous transfer. Use DataSync, DX, or Storage Gateway.
- Databases. Use DMS.

#### Advanced Professional-Level Exam Traps

1. **Snowball Edge can run EC2 instances and Lambda functions locally**. For edge processing before uploading to S3.
2. **Snowmobile for >10 PB**. Below that, multiple Snowball Edges are more practical.
3. **Data goes to S3** when Snow devices are returned to AWS. You must have an S3 bucket configured.
4. **OpsHub**: Desktop application for managing Snow Family devices (no CLI needed).
5. **Snow devices support KMS encryption**. Data is encrypted before leaving your premises.


### 10.5 AWS Transfer Family

#### Core Definition

Managed SFTP, FTPS, FTP, and AS2 servers that transfer files to/from S3 or EFS.

- **Pricing**: $0.30/hr per endpoint + $0.04/GB transferred.

#### When to Use

- Partners/customers transfer files via SFTP/FTPS/FTP.
- Replacing on-premises SFTP servers.
- B2B file exchange (AS2 protocol).
- Preserving existing file transfer workflows while using S3/EFS as backend.

#### Advanced Professional-Level Exam Traps

1. **Transfer Family supports custom identity providers** (Lambda + API Gateway for auth against your directory).
2. **Each user can be scoped to a specific S3 prefix or EFS path** (logical directory mapping).
3. **FTP is unencrypted**. Only use within VPC. SFTP and FTPS are encrypted.

## 11. Cost Management

Cost questions at the Professional level go beyond "use Reserved Instances." They test understanding of pricing inflection points, data transfer charges, hidden costs, and organization-level cost governance.


### 11.1 AWS Cost Explorer

- Visualize, understand, and manage costs and usage over time.

- **EC2 Instance Savings Plans**: Locked to a specific instance family and region. Up to 72% savings.
- **SageMaker Savings Plans**: For ML workloads.

### 11.5 Reserved Instances

- **EC2 RIs**: Standard (up to 72% savings, limited flexibility) or Convertible (up to 66%, changeable).

- **ElastiCache RIs**, **Redshift RIs**, **OpenSearch RIs**.
- RIs are capacity reservations (zonal scope) or discount only (regional scope).
- RI Marketplace: Sell unused RIs (Standard only, not Convertible).

### 11.6 AWS Compute Optimizer

- ML-based recommendations for right-sizing EC2, EBS, Lambda, ECS on Fargate.
- Analyzes CloudWatch metrics to identify over-provisioned or under-provisioned resources.
- Enhanced recommendations with up to 3 months of metric data (requires opt-in).

#### Cost Management Exam Traps

1. **Data transfer costs are often the hidden expense**. Cross-AZ: $0.01/GB each way. Cross-region: $0.02/GB. Internet egress: $0.09/GB (first 10 TB). NAT Gateway: $0.045/GB processed. TGW: $0.02/GB processed. These stack.
2. **Savings Plans vs RIs**: Compute Savings Plans are more flexible than EC2 RIs. For most scenarios, Compute Savings Plans are the preferred answer.
3. **Consolidated billing shares RI/SP benefits across the organization**. Unless sharing is disabled.
4. **Cost Allocation Tags must be activated** in the management account. Only activated tags appear in cost reports.
5. **Budget Actions can enforce spend limits automatically** by applying SCPs or IAM policies.
6. **CUR + Athena is the most detailed cost analysis tool**. Cost Explorer is good for visualization but lacks per-resource granularity.

## 12. Management & Governance

This domain ties together the operational and governance services that enable enterprises to manage AWS at scale.


### 12.1 AWS CloudFormation

#### Core Definition

CloudFormation is infrastructure-as-code (IaC). Define AWS resources in JSON/YAML templates. CloudFormation provisions and manages the resources as stacks.

- **Scope**: Regional (StackSets for multi-account/multi-region).
- **Pricing**: Free (pay for provisioned resources). Third-party resource types: $0.0009 per handler operation.

#### Core Capabilities

- **Stacks**: A collection of resources defined by a template. Create, update, delete as a unit.
- **Change Sets**: Preview changes before applying. Shows what will be added, modified, or deleted.
- **Drift Detection**: Detect when actual resource configuration differs from the template.
- **StackSets**: Deploy stacks across multiple accounts and regions. Organization-integrated (trusted access). Auto-deploy to new accounts.
- **Nested Stacks**: Break large templates into reusable components. Parent stack references child stacks.
- **Cross-Stack References**: Export values from one stack, import in another. Avoid tight coupling.
- **Custom Resources**: Invoke a Lambda function during stack operations for unsupported resources or custom logic.
- **Dynamic References**: Reference SSM Parameter Store or Secrets Manager values in templates.
- **Stack Policies**: Prevent accidental update/deletion of critical resources.
- **Rollback**: Automatic rollback on failure. Can preserve successfully created resources (new feature).
- **Hooks**: Proactive controls. Evaluate resources before provisioning (used by Control Tower proactive guardrails).
- **CDK (Cloud Development Kit)**: Define CloudFormation templates in programming languages (TypeScript, Python, Java, C#, Go). Synthesizes to CloudFormation templates.
- **cfn-guard**: Policy-as-code tool. Validate templates against rules before deployment.
- **Import**: Import existing resources into a stack (adopt resources not originally created by CloudFormation).

#### Architectural Design Patterns

**Multi-Account Baseline**: StackSets deploy baseline resources (VPCs, IAM roles, Config rules, CloudTrail) to all accounts in the organization.

**Nested Stacks for Modularity**: Network stack (VPC, subnets) → Security stack (SGs, NACLs) → Application stack (ALB, ASG, RDS). Each managed independently.

**GitOps CI/CD**: Git repo → CodePipeline → CloudFormation deploy. Template changes trigger pipeline → change set → approval → deploy.

#### Advanced Professional-Level Exam Traps

1. **StackSets with Organizations trusted access** does NOT require IAM roles to be pre-created in target accounts. CloudFormation creates them automatically.
2. **Deletion policy**: `DeletionPolicy: Retain` keeps the resource when the stack is deleted. `DeletionPolicy: Snapshot` creates a snapshot (EBS, RDS) before deletion.
3. **CloudFormation does NOT handle all resources**. Some resources need Custom Resources (Lambda-backed). Check resource type support.
4. **Stack update replacement**: Some property changes require REPLACEMENT (delete and recreate resource). Change Sets show this. Critical for stateful resources (RDS instance name change = data loss).
5. **cfn-init vs user data**: cfn-init is a CloudFormation-specific configuration tool (metadata-driven). User data is a raw script. cfn-init supports update detection (cfn-hup).
6. **CDK vs raw CloudFormation**: CDK is more productive for developers. It generates CloudFormation. Both result in CloudFormation stacks.


### 12.2 AWS Service Catalog

#### Core Definition

Service Catalog enables organizations to create and manage catalogs of approved IT services (CloudFormation templates) that users can deploy in a self-service manner.

- **Pricing**: Free (pay for provisioned resources).

#### Core Capabilities

- **Portfolios**: Collections of products. Shared with specific accounts, OUs, or the organization.
- **Products**: CloudFormation templates wrapped with metadata, constraints, and launch roles.
- **Constraints**: Template constraints (restrict parameter values), launch constraints (IAM role for provisioning), notification constraints, tag update constraints.
- **TagOptions**: Enforce tagging on provisioned products.
- **Provisioned Products**: Instances of products deployed by users. Users can manage their provisioned products within the constraints.
- **Sharing**: Share portfolios across accounts via Organizations or account-level sharing.

#### When to Use

- Self-service infrastructure provisioning with governance.
- Standardized, approved resource configurations.
- Delegated provisioning without giving users direct CloudFormation/console access.
- Control Tower Account Factory (built on Service Catalog).

#### Advanced Professional-Level Exam Traps

1. **Launch constraints**: The IAM role used to provision the product. Users don't need broad IAM permissions — the launch role has the permissions. Users only need Service Catalog permissions.
2. **Service Catalog is how Control Tower Account Factory works**. Account creation is a Service Catalog product.
3. **Portfolio sharing with Organizations**: Automatic sharing to all accounts in the org or specific OUs.


### 12.3 AWS License Manager

- Track and manage software licenses (Oracle, SAP, Microsoft, etc.) across AWS and on-premises.
- Enforce license rules (core count, instance count).
- Integrates with EC2, RDS, Marketplace.
- Required for BYOL scenarios on Dedicated Hosts.

### 12.4 AWS Trusted Advisor

- Automated best practice checks across 5 categories: Cost Optimization, Performance, Security, Fault Tolerance, Service Limits.
- **Basic**: Limited checks (S3 public access, MFA on root, service limits). Free.
- **Business/Enterprise Support**: Full checks. Programmatic access via Support API.
- **Priority** (Enterprise): Personalized recommendations from AWS Technical Account Manager.

#### Exam Traps

1. **Trusted Advisor is NOT a replacement for Config**. Trusted Advisor provides recommendations; Config provides compliance evaluation and resource tracking.
2. **Service limit checks** are valuable for capacity planning. Trusted Advisor can alert before you hit limits.
3. **Full Trusted Advisor requires Business or Enterprise Support plan**.

### 12.5 AWS Well-Architected Tool

- Self-assessment against the 6 pillars of the Well-Architected Framework: Operational Excellence, Security, Reliability, Performance Efficiency, Cost Optimization, Sustainability.
- Generates improvement plans.
- Custom Lenses for domain-specific reviews (SaaS, IoT, etc.).
- Not tested deeply on the exam, but understanding the pillars is foundational.

### 12.6 AWS Proton

- Managed deployment service for container and serverless applications.
- Platform teams define templates (environment + service). Developers deploy using those templates.
- Handles infrastructure provisioning and CI/CD pipeline setup.

#### IAM Policy Evaluation Chain (Complete)

1. Explicit Deny in any policy → DENY
2. SCP boundary (Organizations) → must Allow (does not grant)
3. Resource-based policy → if it grants and same-account, ALLOW (bypasses permission boundary for same-account)
4. Permission boundary → must Allow (does not grant)
5. Session policy → must Allow if present (does not grant)
6. Identity-based policy → must have explicit Allow → ALLOW
7. If no Allow is found → implicit DENY

#### Disaster Recovery Patterns

| Pattern | RTO | RPO | Cost | Description |
|---|---|---|---|---|
| **Backup & Restore** | Hours | Hours | $ | Backup data to S3/Glacier. Restore on demand. |

| **Active/Active (Multi-Site)** | Near-zero | Near-zero | $$$$ | Full capacity in both regions. Route 53 routes traffic. |

#### Multi-Account Strategy Decision Tree

8. StackSets for baseline deployment.

## 13. Analytics & Data Lake

Analytics is a major question category on the SAP-C02. You must understand the full data pipeline — ingestion, cataloging, transformation, storage, querying, and visualization — and when each service is the right fit.


### 13.1 AWS Glue

#### Core Definition

Glue is a fully managed, serverless ETL (Extract, Transform, Load) service with a built-in Data Catalog. It discovers, transforms, and moves data between data stores.

- **Scope**: Regional.
- **Pricing**: ETL jobs: $0.44/DPU-hour (DPU = Data Processing Unit, ~4 vCPU + 16 GB RAM). Crawlers: $0.44/DPU-hour. Data Catalog: Free for first 1M objects, then $1/100K objects/month. Interactive sessions (Glue Studio notebooks): $0.44/DPU-hour.
- **SLA**: 99.9%.
- **Architectural Abstraction**: Serverless Apache Spark (ETL) + Hive Metastore-compatible catalog.

#### Core Capabilities

**Data Catalog**:
- Central metadata repository. Stores table definitions, schemas, partition information.
- Hive Metastore-compatible. Used by Athena, Redshift Spectrum, EMR, Lake Formation.
- One Data Catalog per AWS account per region.
- **Crawlers**: Automatically discover schema from data in S3, RDS, Redshift, DynamoDB, JDBC sources. Create/update tables in the Data Catalog. Schedule crawlers to keep schemas current.
- **Schema Registry**: Apache Avro and JSON Schema registry for streaming data. Validates schemas for Kinesis, MSK, Lambda. Prevents schema evolution from breaking consumers.
- **Cross-account catalog sharing**: Share catalogs via Lake Formation or resource-based policies.

**ETL Jobs**:
- **Spark ETL**: Apache Spark jobs for large-scale transformation. Python (PySpark) or Scala. Serverless — no cluster to manage.
- **Streaming ETL**: Process streaming data from Kinesis Data Streams or MSK in near-real-time.
- **Glue Studio**: Visual job editor. Drag-and-drop transformations. Generates Spark code.
- **Bookmarks**: Track processed data to avoid reprocessing. Enable incremental ETL (only process new data since last run).
- **Job types**: Spark (batch/streaming), Python Shell (lightweight scripts, no Spark overhead), Ray (Python-based distributed processing).
- **Workers**: Standard (4 vCPU, 16 GB), G.1X (4 vCPU, 16 GB, more memory), G.2X (8 vCPU, 32 GB), G.025X (2 vCPU, 4 GB — for Ray jobs). Autoscaling available (Glue 3.0+).
- **DPU allocation**: Minimum 2 DPUs for Spark jobs.
- **Connections**: Connect to data sources in VPCs (RDS, Redshift, Elasticsearch). Requires VPC configuration, security groups, subnet.

**FindMatches ML Transform**: Built-in ML for record deduplication and matching. No ML expertise required. Train on labeled examples.

**Data Quality**: Define data quality rules (completeness, uniqueness, freshness). Evaluate during ETL. Fail or warn on quality violations.

**Sensitive Data Detection**: Identify PII in data during ETL. Powered by pattern matching and ML.

#### Architectural Design Patterns

**Data Lake ETL Pipeline**: S3 raw zone → Glue Crawler (catalog schema) → Glue ETL job (clean, transform, partition) → S3 processed zone (Parquet, partitioned by date) → Athena/Redshift Spectrum for querying.

**Streaming ETL**: Kinesis Data Streams → Glue Streaming ETL → S3 (micro-batches in Parquet). Near-real-time transformation with continuous processing.

**Schema Evolution Management**: Glue Schema Registry validates schemas for Kinesis/MSK producers. Consumers are protected from breaking changes.

#### When to Use

- Serverless ETL at scale (GB to TB).
- Centralizing metadata in a Data Catalog for multiple query engines.
- Schema discovery (crawlers) for data in S3, RDS, Redshift.
- Streaming ETL from Kinesis or MSK.

#### When NOT to Use

- Simple file format conversion or small transformations. Lambda is cheaper and simpler.
- Real-time processing with sub-second latency. Use Lambda, Flink, or Kinesis.
- Complex DAG-based orchestration. Use Step Functions or Managed Airflow (MWAA).
- Large-scale Hadoop ecosystem workloads requiring Hive, Pig, Presto clusters. Use EMR.

#### Trade-Offs: Glue vs EMR

| Aspect | Glue | EMR |
|---|---|---|
| Management | Serverless | Managed cluster (you configure) |
| Customization | Limited (Spark, Python, Ray) | Full (Spark, Hive, Presto, Flink, HBase, etc.) |
| Scaling | Auto-scaling, DPU-based | Manual or auto-scaling EC2/Spot |
| Cost control | Per DPU-hour (no idle waste) | Per instance-hour (idle clusters cost money) |
| Startup time | Minutes (cold start) | Minutes (cluster launch) |
| Use case | ETL, catalog | Big data analytics, ML training, ad-hoc queries |
| Long-running | No (job-based) | Yes (persistent clusters) |

#### Advanced Professional-Level Exam Traps

1. **Glue Data Catalog is the metastore for Athena and Redshift Spectrum**. If a question mentions querying S3 with Athena, the schema is in the Glue Data Catalog.
2. **Glue Crawlers can be scheduled** but may create unwanted tables or update schemas incorrectly. Review crawler output in non-production first.
3. **Glue Bookmarks** prevent reprocessing. Without bookmarks, a Glue job processes ALL data on every run. Critical for incremental ETL.
4. **Minimum 2 DPUs for Spark jobs**. Python Shell jobs use 0.0625–1 DPU (much cheaper for simple scripts).
5. **Glue in VPC**: If a Glue job needs to access RDS or Redshift, it must be configured with VPC, subnet, and security group. It also needs a NAT Gateway or VPC endpoint for S3 and Glue service access.
6. **Glue vs Lambda for ETL**: Lambda is limited to 15 minutes and 10 GB memory. Glue handles larger datasets and longer processing. For small file transforms (\<100 MB, \<15 min), Lambda is cheaper.


### 13.2 Amazon Athena

#### Core Definition

Athena is a serverless, interactive SQL query engine for analyzing data in S3 using standard SQL (Presto/Trino engine).

- **Scope**: Regional.
- **Pricing**: $5.00 per TB scanned (queries). Provisioned capacity: $0.306/DPU-hour (reserved compute). Federated queries: additional charges.
- **SLA**: 99.9%.
- **Architectural Abstraction**: Serverless SQL-on-S3 engine using Presto/Trino.

#### Core Capabilities

- **Query data in S3**: CSV, JSON, Parquet, ORC, Avro, and more. No data loading required.
- **Schema from Glue Data Catalog**: Tables defined by Glue Crawlers or manually.
- **Partitioning**: Organize S3 data into partitions (e.g., `year=2024/month=01/day=15/`). Reduces data scanned → reduces cost.
- **Columnar formats**: Parquet and ORC dramatically reduce data scanned (only read needed columns). Always convert data to Parquet for cost optimization.
- **CTAS (Create Table As Select)**: Transform and store query results as new tables in S3. Useful for ETL.
- **Federated Queries**: Query data in RDS, DynamoDB, Redshift, CloudWatch Logs, HBase, and custom sources via Lambda-based connectors. Data stays in the source.
- **Views**: Standard SQL views over S3 data.
- **Workgroups**: Isolate users/teams. Set per-workgroup data scan limits. Separate query history and cost tracking.
- **Prepared Statements**: Parameterized queries for security and reuse.
- **Provisioned Capacity**: Reserve DPUs for consistent performance. Avoids per-query pricing variability.
- **Apache Iceberg / Delta Lake / Hudi**: Athena supports querying open table formats. Enables ACID transactions, time travel, row-level operations on S3 data.
- **Athena for Spark**: Run Apache Spark notebooks in Athena (serverless Spark).

#### Architectural Design Patterns

**Serverless Data Lake Query Layer**: S3 (Parquet, partitioned) + Glue Data Catalog + Athena. No infrastructure. Pay per query.

**CloudTrail Analysis**: CloudTrail → S3 → Athena table (partitioned by date/region). Query API activity with SQL.

**Cost-Effective Log Analytics**: VPC Flow Logs / ALB Access Logs / CloudFront Logs → S3 → Athena. Cheaper than CloudWatch Logs Insights for large-scale historical queries.

**Federated Query Dashboard**: Athena queries S3 data lake + live data from RDS (federated) → QuickSight dashboard.

#### When to Use

- Ad-hoc SQL queries on S3 data.
- Data lake query layer.
- Cost-effective alternative to Redshift for infrequent/exploratory queries.
- Log analysis (CloudTrail, VPC Flow Logs, ALB logs).

#### When NOT to Use

- Frequent, high-concurrency queries. Redshift is better for dashboarding workloads with many concurrent users.
- Sub-second query latency. Athena queries take seconds to minutes.
- Real-time analytics. Use Kinesis + Lambda or Flink.
- Complex transformations. Use Glue or EMR.

#### Trade-Offs: Athena vs Redshift vs Redshift Spectrum

| Aspect | Athena | Redshift | Redshift Spectrum |
|---|---|---|---|
| Infrastructure | Serverless | Cluster or Serverless | Requires Redshift cluster |
| Storage | S3 only | Managed storage (RA3) or S3 | S3 (external tables) |
| Pricing | Per TB scanned | Per instance-hour or RPU | Per TB scanned (+ cluster cost) |
| Concurrency | Limited (default 20) | High (concurrency scaling) | Cluster-dependent |
| Joins | S3-only or federated | Warehouse + S3 (Spectrum) | S3 + warehouse tables |
| Use case | Ad-hoc, infrequent | BI, dashboards, complex analytics | Extend warehouse to data lake |
| Latency | Seconds-minutes | Sub-second for cached data | Seconds-minutes |

#### Advanced Professional-Level Exam Traps

1. **Athena charges per TB scanned**. Unpartitioned, uncompressed CSV data is extremely expensive to query. Always: partition + Parquet/ORC + narrow column selection.
2. **Athena uses the Glue Data Catalog**. No separate catalog. If a question mentions Athena table definitions, it's Glue Data Catalog.
3. **Workgroup scan limits** prevent runaway queries from costing thousands. Set per-workgroup and per-query limits.
4. **Athena is NOT a database**. It does not store data. It queries data in S3.
5. **Federated queries add latency** and are rate-limited by the connector Lambda. Not suitable for high-volume federated queries.
6. **Athena vs CloudWatch Logs Insights**: For recent logs with low volume, Logs Insights is faster and simpler. For historical, large-scale log analysis, Athena on S3 is cheaper.


### 13.3 Amazon EMR (Elastic MapReduce)

#### Core Definition

EMR is a managed big data platform for running Apache Spark, Hive, Presto, Flink, HBase, and other Hadoop ecosystem frameworks at scale.

- **Scope**: Regional.
- **Pricing**: Per-instance-hour (EC2 price + EMR surcharge ~15-25%). EMR Serverless: per vCPU-second and per GB-second. EMR on EKS: per vCPU-second.
- **Architectural Abstraction**: Managed Hadoop/Spark cluster on EC2, EKS, or serverless.

#### Core Capabilities

**Deployment Options**:
1. **EMR on EC2 (Classic)**: Traditional managed cluster. Master, core, and task nodes. You choose instance types and count.
2. **EMR on EKS**: Run Spark jobs on existing EKS clusters. Share compute with other Kubernetes workloads.
3. **EMR Serverless**: Submit Spark or Hive jobs without managing clusters. Auto-scaling. Pay for resources used during job execution.
4. **EMR on Outposts**: Run EMR on-premises.

**Cluster Configurations**:
- **Transient clusters**: Launch, run job, terminate. Cost-efficient for batch workloads.
- **Persistent clusters**: Long-running for interactive queries (Presto/Hive), continuous processing, or HBase.
- **Instance Fleets**: Mix instance types and purchase options (On-Demand, Spot) for cost optimization.
- **Spot Instances**: Task nodes on Spot for cost savings. Core nodes on On-Demand for HDFS stability.
- **Auto-scaling**: Scale core and task nodes based on YARN metrics.
- **Managed Scaling**: EMR automatically scales based on workload (simpler than custom auto-scaling policies).

**Storage**:
- **EMRFS**: S3 as persistent storage for Hadoop (replaces HDFS for persistent data). Data survives cluster termination.
- **HDFS**: Local, ephemeral storage on cluster nodes. Faster I/O but data lost on termination. Use for intermediate processing.
- **Local storage**: Instance store for temporary data.

**Frameworks**: Spark, Hive, Presto/Trino, Flink, HBase, Pig, Tez, Mahout, Ganglia, ZooKeeper.

**Security**:
- Integration with Lake Formation for fine-grained data access.
- Kerberos authentication.
- Encryption at rest (EMRFS SSE-S3/SSE-KMS, LUKS for local disk) and in transit (TLS).
- Security configurations applied at cluster launch.
- Ranger integration for RBAC.

#### When to Use

- Large-scale data processing (TBs to PBs) with Spark, Hive, or Presto.
- Custom Hadoop ecosystem requirements.
- ML model training on Spark MLlib.
- HBase workloads (wide-column NoSQL).
- ETL jobs that are too large or complex for Glue.

#### When NOT to Use

- Simple ETL. Use Glue (serverless, simpler).
- SQL queries on S3. Use Athena (no cluster management).
- Real-time streaming with \<1s latency. Use Kinesis + Lambda or Managed Flink.
- If you don't need the Hadoop ecosystem. Glue or Athena is simpler.

#### Advanced Professional-Level Exam Traps

1. **EMR Serverless vs Glue**: Both are serverless Spark. Glue is simpler (visual editor, bookmarks, Data Catalog integration). EMR Serverless gives more Spark configuration control and supports Hive. For pure ETL, Glue. For complex Spark tuning, EMR Serverless.
2. **EMRFS vs HDFS**: EMRFS (S3) for persistent data that survives cluster termination. HDFS for fast intermediate storage during processing. Use both in the same cluster.
3. **Spot Instances**: Use for task nodes (no HDFS data). NEVER use Spot for core nodes with critical HDFS data (interruption = data loss).
4. **Transient vs persistent clusters**: Transient = batch, cost-effective. Persistent = interactive, higher cost. Questions may test when each is appropriate.
5. **Presto on EMR vs Athena**: Both use Presto/Trino. EMR gives you a dedicated cluster with tuning control. Athena is serverless and cheaper for ad-hoc. For high-concurrency dashboarding, EMR Presto may perform better.


### 13.4 Amazon OpenSearch Service

#### Core Definition

OpenSearch (formerly Elasticsearch Service) is a managed search and analytics engine. Used for log analytics, full-text search, application monitoring, and security analytics (SIEM).

- **Scope**: Regional.
- **Pricing**: Per-instance-hour + EBS storage + data transfer. OpenSearch Serverless: per OCU-hour (OpenSearch Compute Unit).
- **SLA**: 99.9%.
- **Architectural Abstraction**: Managed OpenSearch/Elasticsearch cluster with Kibana/OpenSearch Dashboards.

#### Core Capabilities

- **Domains**: Clusters of instances. Up to 80 data nodes per domain.
- **Multi-AZ**: 2-AZ or 3-AZ deployment for HA. 3-AZ recommended for production.
- **Dedicated Master Nodes**: Manage cluster state. 3 master nodes recommended. Don't use for data.
- **UltraWarm**: Warm storage tier using S3-backed nodes. Cheaper for infrequently queried data (logs older than 30 days).
- **Cold Storage**: Even cheaper for rarely accessed data. Detached from cluster, re-attached on demand.
- **OpenSearch Serverless**: No cluster management. Collection-based. Auto-scales. OCU-based pricing.
- **Ingestion**: OpenSearch Ingestion (managed pipelines). Sources: S3, Kinesis, DynamoDB, CloudWatch, HTTP. Replaces self-managed Logstash.
- **Index State Management (ISM)**: Automated lifecycle policies (transition indices to UltraWarm → Cold → delete).
- **Cross-Cluster Search**: Query across multiple domains.
- **Cross-Cluster Replication**: Replicate indices across domains (cross-region for DR).
- **Security**: Fine-grained access control (FGAC) with IAM, SAML, Cognito. Field-level and document-level security.
- **Alerting**: Built-in alerting on query results. Notify via SNS, Slack, custom webhooks.

#### Architectural Design Patterns

**Centralized Logging (ELK/EFK Stack)**: CloudWatch Logs → Subscription Filter → Kinesis Data Firehose → OpenSearch. Visualize with OpenSearch Dashboards.

**SIEM**: GuardDuty + CloudTrail + VPC Flow Logs → OpenSearch. Security analytics and threat hunting.

**Application Search**: DynamoDB → DynamoDB Streams → Lambda → OpenSearch. Full-text search over application data.

#### When to Use

- Log analytics and operational monitoring.
- Full-text search.
- Security analytics (SIEM).
- Real-time application monitoring.

#### When NOT to Use

- Primary data store. OpenSearch is a search index, not a database.
- Simple keyword search in S3. Use S3 Select or Athena.
- SQL-based analytics. Use Athena or Redshift.
- If you only need basic log searching. CloudWatch Logs Insights may suffice.

#### Advanced Professional-Level Exam Traps

1. **OpenSearch is NOT a replacement for a database**. It is a search and analytics engine. Use it alongside a database (DynamoDB + OpenSearch).
2. **UltraWarm for cost optimization**. Hot nodes (expensive, fast) → UltraWarm (cheaper, slower) → Cold (cheapest, on-demand). ISM automates transitions.
3. **OpenSearch Serverless** eliminates cluster management but has limitations (no custom plugins, limited index control).
4. **Cognito integration** for OpenSearch Dashboards authentication. This is a common exam question — Cognito provides user auth for the Dashboards UI.
5. **Firehose is the primary managed ingestion path to OpenSearch**. Questions about "stream logs to OpenSearch" typically involve Firehose.


### 13.5 AWS Lake Formation

#### Core Definition

Lake Formation is a service that simplifies building, securing, and managing data lakes. It provides centralized, fine-grained access control over data in S3.

- **Scope**: Regional.
- **Pricing**: No additional charge for Lake Formation itself. Pay for underlying services (S3, Glue, Athena).
- **Architectural Abstraction**: Fine-grained access control layer on top of Glue Data Catalog and S3.

#### Core Capabilities

- **Centralized Permissions**: Grant table-, column-, row-, and cell-level permissions. Replaces complex S3 bucket policies and IAM policies for data lake access.
- **Cross-Account Sharing**: Share databases and tables with other accounts via Lake Formation permissions (much simpler than S3 cross-account policies + Glue catalog resource policies).
- **TBAC (Tag-Based Access Control)**: Assign LF-Tags to databases, tables, and columns. Grant permissions based on tags. Scales better than individual grants.
- **Governed Tables**: ACID transactions on S3 data. Automatic compaction. Storage optimization.
- **Blueprints**: Pre-built workflows for ingesting data from databases (RDS, on-premises) into the data lake.
- **Data Filters**: Row-level and cell-level security. Different users see different rows/cells in the same table.

#### When to Use

- Multi-team, multi-account data lakes requiring fine-grained access control.
- When S3 bucket policies and IAM become unmanageable for data lake permissions.
- Cross-account data sharing for analytics.
- Column-level and row-level security.

#### When NOT to Use

- Simple, single-account data storage. S3 + IAM is sufficient.
- Non-tabular data. Lake Formation works with structured/semi-structured data in the Data Catalog.

#### Advanced Professional-Level Exam Traps

1. **Lake Formation permissions override IAM for data lake access** (when Lake Formation is enabled). Users need both Lake Formation permissions AND IAM permissions. This is a common confusion point.
2. **Cross-account data sharing via Lake Formation** is much simpler than the alternative (S3 bucket policy + Glue resource policy + IAM). If a question asks about sharing data lake tables cross-account, Lake Formation is the answer.
3. **LF-Tags for TBAC** scale permissions management. Instead of granting access per table/column, tag resources and grant access by tag (e.g., `classification=public`).
4. **Lake Formation requires Glue Data Catalog**. It IS the permission layer on top of the Data Catalog.
5. **Row-level and cell-level security** are unique to Lake Formation. Neither S3 policies nor IAM can provide this.


### 13.6 Amazon MSK (Managed Streaming for Apache Kafka)

#### Core Definition

MSK is a fully managed Apache Kafka service. It handles broker provisioning, patching, and cluster management.

- **Scope**: Regional.
- **Pricing**: Per-broker-instance-hour + storage + data transfer. MSK Serverless: per cluster-hour + per partition-hour + per GB data.
- **SLA**: 99.9%.
- **Architectural Abstraction**: Managed Kafka cluster (brokers, ZooKeeper) on EC2, or serverless.

#### Core Capabilities

- **MSK Provisioned**: You choose broker instance types and count. 3 AZ minimum recommended.
- **MSK Serverless**: No brokers to manage. Auto-scales. Pay per partition-hour and per GB. Limited to 200 MB/s per partition.
- **MSK Connect**: Managed Kafka Connect. Deploy connectors for S3, Redshift, OpenSearch, databases. Source and sink connectors.
- **Storage**: EBS-backed. Auto-scaling available. Unlimited retention supported with tiered storage (data moved to S3 automatically).
- **Security**: TLS in-transit, encryption at rest (KMS), IAM access control, SASL/SCRAM authentication, mTLS.
- **Schema Registry**: Glue Schema Registry integrates with MSK.
- **Multi-VPC connectivity**: PrivateLink-based connectivity for cross-VPC access without peering.
- **Topic replication**: MSK Replicator for cross-region replication (DR, geo-proximity).

#### When to Use

- Existing Kafka workloads migrating to AWS.
- Streaming architectures requiring Kafka ecosystem (Kafka Streams, Kafka Connect, KSQL).
- High-throughput, low-latency streaming with unlimited retention.
- When you need consumer groups, exactly-once semantics, and log compaction (Kafka features).

#### When NOT to Use

- New AWS-native streaming architectures without Kafka dependency. Use Kinesis Data Streams.
- Simple message delivery. Use SQS/SNS.
- Near-real-time delivery to S3/Redshift. Use Kinesis Data Firehose (simpler).

#### Trade-Offs: MSK vs Kinesis Data Streams

| Aspect | MSK | Kinesis Data Streams |
|---|---|---|
| Protocol | Kafka native | AWS proprietary |
| Management | Broker management (or Serverless) | Fully serverless |
| Ecosystem | Full Kafka (Connect, Streams, KSQL) | AWS ecosystem (Lambda, Firehose) |
| Retention | Unlimited (tiered storage) | Up to 365 days |
| Throughput | Per-broker, scale brokers | Per-shard, scale shards |
| Ordering | Per-partition | Per-shard |
| Pricing | Higher (broker instances) | Lower for moderate scale |
| Portability | High (standard Kafka) | Low (AWS-locked) |
| Consumer model | Consumer groups (native) | KCL or Lambda |

#### Advanced Professional-Level Exam Traps

1. **MSK for Kafka migration**. If a question mentions "existing Kafka" or "Kafka compatibility," MSK is the answer, not Kinesis.
2. **MSK Serverless limitations**: No multi-VPC, limited throughput per partition. For high throughput, use provisioned.
3. **MSK Connect replaces self-managed Kafka Connect**. For streaming to S3/OpenSearch/databases, MSK Connect is the managed option.
4. **Tiered storage** enables cost-effective unlimited retention. Hot data on EBS, warm data on S3.


### 13.7 Amazon QuickSight

#### Core Definition

QuickSight is a serverless, ML-powered BI (Business Intelligence) service for creating dashboards and visualizations.

- **Scope**: Regional.
- **Pricing**: Standard: $9/user/month. Enterprise: $18/user/month (author), $0.30/session for readers (up to $5/user/month).
- **Architectural Abstraction**: Serverless BI engine with SPICE in-memory storage.

#### Core Capabilities

- **SPICE**: Super-fast, Parallel, In-memory Calculation Engine. Imports data for fast querying. Up to 500 GB per user (Enterprise).
- **Data Sources**: S3, Athena, Redshift, RDS, Aurora, OpenSearch, DynamoDB (via Athena), Salesforce, on-premises databases (via Direct Connect/VPN).
- **ML Insights**: Anomaly detection, forecasting, auto-narratives.
- **Embedded Analytics**: Embed dashboards in applications. API-based embedding with per-session pricing.
- **Row-Level Security (RLS)**: Restrict data visibility per user/group.
- **Column-Level Security (CLS)**: Restrict column access per user/group.
- **Paginated Reports**: Pixel-perfect, printable reports (Enterprise).
- **Q (Natural Language Queries)**: Ask questions in plain English, get visualizations.
- **Themes & Branding**: Customize look and feel for embedded analytics.

#### When to Use

- Serverless dashboarding and reporting.
- Embedded analytics in SaaS applications (per-session pricing is cost-effective).
- Data lake visualization (Athena → QuickSight).
- When you don't want to manage a BI server (Tableau Server, etc.).

#### When NOT to Use

- Complex, highly customized BI with thousands of users and advanced data modeling. Consider Tableau or Looker.
- Real-time streaming dashboards with \<1s refresh. Use Grafana (Amazon Managed Grafana) or custom.

#### Advanced Professional-Level Exam Traps

1. **SPICE** enables fast queries without hitting the source. But SPICE has storage limits and needs refresh schedules.
2. **Reader pricing is per-session** ($0.30/session up to $5/month cap). Cost-effective for infrequent report consumers.
3. **Enterprise edition** is required for RLS, CLS, paginated reports, and embedded analytics. Standard does not support these.
4. **QuickSight + Athena** is the go-to serverless BI stack for data lake analytics.

## 14. CI/CD & Deployment Strategies

Deployment and CI/CD questions test your understanding of deployment patterns, rollback mechanisms, and blue/green vs canary vs rolling strategies across different compute platforms.


### 14.1 AWS CodePipeline

#### Core Definition

CodePipeline is a fully managed continuous delivery service that automates release pipelines.

- **Pricing**: $1.00/active pipeline/month (V1). V2 pipelines: Free tier for first pipeline, then action-type-based pricing.
- **Architectural Abstraction**: Pipeline orchestrator with stages and actions.

#### Core Capabilities

- **Stages**: Source → Build → Test → Deploy (customizable).
- **Actions**: Source (CodeCommit, GitHub, S3, ECR), Build (CodeBuild), Test (CodeBuild, third-party), Deploy (CodeDeploy, CloudFormation, ECS, S3, Elastic Beanstalk, Service Catalog), Invoke (Lambda, Step Functions), Approval (manual gate).
- **Cross-account deployment**: Deploy to another account using cross-account IAM roles. Artifacts stored in a shared S3 bucket with KMS encryption.
- **Cross-region deployment**: Deploy to multiple regions from a single pipeline.
- **Manual Approval**: Human gate between stages. SNS notification. Timeout configurable.
- **Pipeline triggers**: Source change, CloudWatch Events/EventBridge, webhook, manual.
- **V2 Pipelines**: Support triggers (PR-based, tag-based), Git-based change detection, improved pricing.

#### Advanced Professional-Level Exam Traps

1. **Cross-account CodePipeline** requires: artifact bucket accessible to both accounts, KMS key shared with deploying account, IAM roles in both accounts. Common complex scenario.
2. **Pipeline artifact bucket is encrypted with KMS**. Cross-account access requires sharing the KMS key.
3. **Manual approval stage** for production deployment governance. Combined with SNS for notification.


### 14.2 AWS CodeBuild

#### Core Definition

CodeBuild is a fully managed build service that compiles source code, runs tests, and produces deployable artifacts.

- **Pricing**: Per build-minute ($0.005–$0.20/min depending on compute type).
- **Architectural Abstraction**: Serverless build environment (Docker container on managed compute).

#### Core Capabilities

- **Build environments**: Pre-configured Docker images (Amazon Linux, Ubuntu, Windows) or custom Docker images (from ECR).
- **Buildspec.yml**: Defines build commands (phases: install, pre_build, build, post_build). Environment variables, artifacts, cache configuration.
- **Caching**: S3-based or local caching of dependencies (npm, Maven, pip) to speed up builds.
- **VPC access**: Place build environment in a VPC to access private resources (internal artifact repos, test databases).
- **Compute types**: 3 GB to 145 GB memory; 2 to 72 vCPU. GPU-enabled for ML builds.

#### Advanced Professional-Level Exam Traps

1. **CodeBuild is serverless**. No build servers to manage. Compare with Jenkins (self-managed on EC2).

### 14.3 AWS CodeDeploy

#### Core Definition

CodeDeploy automates application deployments to EC2, ECS, Lambda, and on-premises instances.

- **Pricing**: Free for EC2/on-premises. ECS/Lambda: $0.02 per deployment.

#### Core Capabilities

**Deployment Targets**:
- **EC2/On-Premises**: In-place (rolling update) or Blue/Green (new ASG, traffic shift). CodeDeploy agent required on instances.
- **ECS**: Blue/Green only. Two target groups on ALB. Traffic shifting: Canary, Linear, or AllAtOnce.
- **Lambda**: Traffic shifting between function versions. Canary, Linear, or AllAtOnce.

**Deployment Strategies**:

| Strategy | Description | Rollback |
|---|---|---|
| **AllAtOnce** | Deploy to all targets simultaneously | Fast but risky |
| **HalfAtATime** | 50% of targets at a time | Medium risk |
| **OneAtATime** | One target at a time | Safest but slowest |
| **Blue/Green (EC2)** | New ASG with new version. Switch ALB/NLB | Instant (switch back to blue ASG) |
| **Blue/Green (ECS)** | New task set. Shift traffic via target groups | Instant (route back to original task set) |
| **Canary (ECS/Lambda)** | 10% then 90% (configurable %, configurable wait) | Automatic on alarm |
| **Linear (ECS/Lambda)** | Shift N% every M minutes | Automatic on alarm |

**Hooks**: Lifecycle event hooks for custom validation (BeforeInstall, AfterInstall, ApplicationStart, ValidateService). Lambda functions as hooks for ECS/Lambda deployments.

**Rollback**: Automatic rollback on deployment failure or CloudWatch alarm trigger. For Blue/Green, rollback is instant (switch traffic back).

**AppSpec File**: Defines deployment lifecycle. For EC2: file locations, permissions, hooks. For ECS: task definition, container name, port. For Lambda: function version, alias, hooks.

#### Architectural Design Patterns

**ECS Blue/Green with Canary**: CodeDeploy shifts 10% of traffic to the new ECS task set. CloudWatch alarms monitor error rate. After 10 minutes with no errors, shift remaining 90%. On alarm, automatic rollback.

**Lambda Gradual Deployment**: New function version published. CodeDeploy shifts traffic on the alias from old to new version using Linear10PercentEvery1Minute strategy. Pre-traffic and post-traffic hooks validate the deployment.

**EC2 Blue/Green**: ASG with original version (blue). CodeDeploy creates a new ASG with new version (green). ALB target group switches from blue to green. Blue ASG kept for rollback window, then terminated.

#### Advanced Professional-Level Exam Traps

1. **Blue/Green on EC2 requires an ALB or NLB**. Classic Load Balancer is not supported for Blue/Green.
2. **ECS Blue/Green uses two target groups on the same ALB**. Traffic shifts between target groups.
3. **Canary vs Linear**: Canary = two steps (small % then rest). Linear = gradual increments over time.
4. **CodeDeploy agent**: Required on EC2/on-premises instances. Not needed for ECS/Lambda.
5. **CloudWatch Alarms for automatic rollback**: Configure alarms (error rate, latency) that trigger automatic rollback. This is the exam-preferred pattern.
6. **ECS deployments via CodeDeploy vs ECS rolling update**: CodeDeploy provides Blue/Green with canary/linear traffic shifting. ECS rolling update is simpler but doesn't support traffic shifting.


### 14.4 Amazon ECR (Elastic Container Registry)

#### Core Definition

ECR is a fully managed Docker container registry. Stores, manages, and deploys container images.

- **Pricing**: $0.10/GB/month storage. $0.09/GB data transfer out (after 500 MB free).

#### Core Capabilities

- **Private repositories**: Per-account, per-region. IAM-based access control.
- **Public repositories** (ECR Public): Free tier for public images.

## 15. Disaster Recovery — Deep Implementation

This section deepens the DR patterns with specific service configurations, which is what the exam actually tests.


### 15.1 AWS Elastic Disaster Recovery (DRS)

#### Core Definition

DRS (formerly CloudEndure Disaster Recovery) provides continuous block-level replication of source servers to AWS for disaster recovery. RPO in seconds, RTO in minutes.

- **Pricing**: $0.028/hr per replicating source server (~$20/month).
- **Architectural Abstraction**: Agent-based block replication to lightweight staging EC2 instances. On failover, launch full-size recovery instances.

#### Core Capabilities

- **Continuous replication**: Agent on source server replicates block-level changes to a staging area in AWS.
- **Staging area**: Low-cost EC2 instances and EBS volumes hold the replicated data. Minimal cost.
- **Recovery launch**: On DR event, launch full-sized EC2 instances from the replicated data. Minutes to recover.
- **Failback**: After recovery, replicate back to on-premises or primary region.
- **Non-disruptive testing**: Launch test instances without affecting replication. Test recovery regularly.
- **Sources**: On-premises physical servers, VMware VMs, Azure VMs, other cloud VMs, EC2 instances (cross-region DR).
- **Point-in-time recovery**: Recover from a specific point (useful for ransomware — recover to pre-infection state).

#### When to Use

- Server-level DR (not just database). Full OS + application state.
- Cross-region DR for EC2 workloads.
- On-premises to AWS DR.
- When RPO in seconds and RTO in minutes is required.

#### When NOT to Use

- Database-only DR. Use RDS Multi-AZ, Aurora Global Database, or DynamoDB Global Tables.
- Application-level DR that doesn't need full server replication. Use S3 CRR + CloudFormation.
- Stateless applications. Just redeploy in DR region (no replication needed).

#### Advanced Professional-Level Exam Traps

1. **DRS vs AWS Backup**: DRS provides continuous replication with seconds RPO. AWS Backup provides scheduled snapshots with minutes/hours RPO. DRS is for rapid failover; Backup is for data protection.
2. **DRS vs MGN (Application Migration Service)**: DRS is for ongoing DR (replicate continuously). MGN is for one-time migration (replicate, cut over, decommission source).
3. **DRS supports point-in-time recovery**. For ransomware scenarios, recover to a point before the infection.
4. **DRS staging area is low-cost**. You only pay for full-size instances during actual DR events or testing.


### 15.2 DR Pattern Implementation Details

#### Backup & Restore (RTO: Hours, RPO: Hours, Cost: $)

**Implementation**:
- AWS Backup for EBS, RDS, DynamoDB, EFS, FSx snapshots. Cross-region copy.
- S3 CRR for object data.
- CloudFormation templates stored in S3 (version-controlled in Git).
- AMIs copied to DR region.
- On DR: Deploy CloudFormation stack in DR region → restore databases from backups → update DNS.

**Key Services**: AWS Backup, S3 CRR, CloudFormation, Route 53 (failover routing).

#### Pilot Light (RTO: 10s of Minutes, RPO: Minutes, Cost: $$)

**Implementation**:
- Core database infrastructure running in DR region at minimum scale:
  - Aurora Global Database (secondary in DR region, read-only).
  - DynamoDB Global Tables (active in DR region).
  - RDS cross-region read replica.
- Everything else OFF (no EC2, no ECS tasks).
- AMIs and launch templates pre-configured in DR region.
- On DR: Promote Aurora secondary → Scale up compute (launch EC2/ECS from templates) → Update DNS.

**Key Services**: Aurora Global Database, DynamoDB Global Tables, ASG (min=0, increase on DR), Route 53 (failover).

#### Warm Standby (RTO: Minutes, RPO: Seconds-Minutes, Cost: $$$)

**Implementation**:
- Scaled-down replica of production running in DR region:
  - Aurora Global Database or RDS cross-region replica.
  - ECS/EKS running with minimum task count (1 replica per service).
  - ALB deployed but handling minimal traffic.
  - Route 53 weighted routing: 100% to primary, 0% to DR (or health-check-based failover).
- On DR: Promote database → Scale up compute (increase desired count) → Route 53 shifts traffic.

**Key Services**: Aurora Global Database, ECS/EKS with auto-scaling, Route 53 (failover), ALB.

#### Active/Active Multi-Site (RTO: Near-zero, RPO: Near-zero, Cost: $$$$)

**Implementation**:
- Full production capacity in both regions:
  - DynamoDB Global Tables (active-active read/write in both regions).
  - Aurora Global Database with write forwarding.
  - ECS/EKS running full capacity in both regions.
  - Route 53 latency-based routing to both regions.
  - CloudFront origin groups for failover.
- On failure: Route 53 automatically routes away from unhealthy region. DynamoDB continues accepting writes in surviving region. Aurora secondary promoted to primary.

**Key Services**: DynamoDB Global Tables, Aurora Global Database, Route 53 (latency + health checks), CloudFront, Global Accelerator.

#### DR Exam Decision Matrix

| Factor | Answer |
|---|---|
| RPO = 0 | Synchronous replication (Multi-AZ within region, NOT cross-region) |
| RPO < 1 second | DRS (server-level) or Aurora Global Database (database-level) |
| RPO < 1 minute | DynamoDB Global Tables, Aurora Global Database |
| RPO < 1 hour | S3 CRR with RTC, RDS cross-region read replica |
| RTO < 1 minute | Active/Active with Route 53, Global Accelerator |
| RTO < 15 minutes | Warm Standby with auto-scaling |
| RTO < 1 hour | Pilot Light |
| RTO < 24 hours | Backup & Restore |
| Lowest cost | Backup & Restore |
| Zero data loss within a region | Multi-AZ (RDS, Aurora, EBS snapshots) |

### 16.1 AWS Elastic Beanstalk

#### Core Definition

Beanstalk is a PaaS (Platform as a Service) that deploys and manages web applications. You upload code; Beanstalk handles provisioning (EC2, ALB, ASG, RDS), scaling, monitoring, and patching.

- **Pricing**: Free (pay for underlying resources).
- **Supported Platforms**: Java, .NET, Node.js, Python, Ruby, Go, PHP, Docker, Multi-container Docker.
- **Architectural Abstraction**: Managed application environment on top of EC2/ECS with auto-scaling and load balancing.

#### Core Capabilities

- **Environments**: Web server environment (HTTP) or Worker environment (SQS-based background processing).
- **Deployment policies**: All at once, Rolling, Rolling with additional batch, Immutable, Traffic splitting (canary), Blue/Green (via CNAME swap).
- **Configuration**: `.ebextensions` YAML files for customizing instances (packages, files, commands, services). Platform hooks for lifecycle scripts.
- **Managed platform updates**: Automatic minor/patch updates with scheduled maintenance window.
- **Custom platforms**: Build custom AMIs with Packer.
- **Docker support**: Single-container or multi-container (ECS-based).

#### When to Use

- Rapid deployment without managing infrastructure.
- Developers who want PaaS simplicity with AWS flexibility.

3. **Traffic splitting deployment**: Built-in canary. Routes a percentage of traffic to new instances for evaluation. Integrated with CloudWatch alarms.
4. **Beanstalk creates the resources** (EC2, ALB, ASG). You CAN modify them directly, but Beanstalk may overwrite changes on next deployment.
5. **Worker environment + SQS**: If a question describes background processing with a queue, Beanstalk worker tier is a valid answer.

### 17.2 Hybrid DNS Resolution — Complete Architecture

#### Scenario: Bidirectional DNS Between On-Premises and AWS

**AWS → On-Premises Resolution** (resolve `internal.corp` from VPC):
1. VPC DNS resolver (.2 address) receives query for `internal.corp`.
2. Route 53 Resolver Outbound Endpoint is configured with a forwarding rule: `internal.corp` → on-premises DNS server IPs.
3. Outbound Endpoint has ENIs in your VPC. Outbound DNS queries go through these ENIs → VPN/DX → on-premises DNS.
4. On-premises DNS responds. Resolver returns the answer to the VPC resource.

**On-Premises → AWS Resolution** (resolve `app.aws.internal` from on-premises):
1. On-premises DNS is configured with a conditional forwarder: `aws.internal` → Route 53 Resolver Inbound Endpoint IPs.
2. Inbound Endpoint has ENIs with private IPs in your VPC.
3. On-premises DNS forwards queries via VPN/DX to the Inbound Endpoint ENIs.
4. Resolver resolves against Private Hosted Zones associated with the VPC.
5. Answer returned to on-premises.

**Cross-Account DNS** (centralized DNS architecture):
1. Central network account has Private Hosted Zones.
2. Associate PHZs with VPCs in workload accounts (cross-account PHZ association).
3. Share Resolver Rules via RAM with workload accounts. Workload VPCs automatically use the shared rules.

#### Key Details

- Resolver Endpoints have Security Groups. Allow port 53 (TCP and UDP).
- Resolver Endpoints need ENIs in at least 2 AZs for HA.
- Resolver Rules can be shared via RAM to the entire Organization.
- DNS Firewall rules are evaluated before Resolver Rules. Use DNS Firewall to block malicious domains.
- Split-horizon DNS: Public Hosted Zone for external resolution, Private Hosted Zone for internal resolution. Same domain name, different records.


### 17.3 Cross-Account Data Sharing Patterns

#### S3 Cross-Account Access

**Option 1: Bucket Policy** — Simplest. Add principal from other account. Use `aws:PrincipalOrgID` condition for org-wide access. Bucket owner pays.

**Option 2: S3 Access Points** — Per-team access points with specific policies. Simplifies management for multiple teams/accounts.

**Option 3: Cross-Account IAM Role** — Other account assumes a role in the data-owning account. Role has S3 permissions. Bucket owner pays.

**Option 4: S3 Object Ownership** — Bucket Owner Enforced (default for new buckets). All objects owned by bucket owner regardless of who uploaded. Eliminates ACL complexity.

#### Redshift Cross-Account Data Sharing

- Redshift Data Sharing: Producer cluster shares databases/schemas/tables with consumer clusters. No data copying. Real-time. Consumer can be in a different account. Requires RA3 nodes or Serverless.

#### Lake Formation Cross-Account

- Grant permissions on databases/tables to external accounts via Lake Formation.
- External account's IAM principals receive access to Glue Data Catalog objects and underlying S3 data.
- Simpler than managing S3 + Glue + IAM policies separately.

#### DynamoDB Cross-Account

- No native cross-account sharing. Options:
  1. Cross-account IAM role to access the table.
  2. DynamoDB Streams → Lambda → replicate to another account's table.
  3. DynamoDB Export to S3 → share S3 bucket cross-account.

#### KMS Cross-Account for Encrypted Data

- Key policy must allow the external account.
- External account's IAM policy must allow KMS operations on the key.
- Use `kms:GrantIsForAWSResource` condition for service-level grants.
- For S3 SSE-KMS cross-account access: both S3 bucket policy AND KMS key policy must allow the external principal.


### 17.4 Container Image Management at Scale

#### ECR Architecture for Multi-Account, Multi-Region

**Centralized Image Repository**:
1. Shared Services account hosts ECR repositories.
2. CI/CD (CodeBuild) pushes images to Shared Services ECR.
3. Workload accounts pull images via cross-account ECR resource policy.
4. ECR Replication Rules replicate images to DR region and other deployment regions.
5. ECR Lifecycle Policies in all regions expire old images.

**Image Security Pipeline**:
1. Developer pushes to ECR.
2. ECR triggers scan-on-push (Inspector).
3. EventBridge rule triggers on CRITICAL/HIGH findings.
4. Lambda blocks deployment (update parameter in SSM to mark image as failed).
5. CodeDeploy/ECS checks parameter before deploying.

**ECS/EKS in Private Subnets — Required VPC Endpoints**:
- `com.amazonaws.<region>.ecr.api` (Interface)
- `com.amazonaws.<region>.ecr.dkr` (Interface)
- `com.amazonaws.<region>.s3` (Gateway — image layers are in S3)
- `com.amazonaws.<region>.logs` (Interface — for CloudWatch Logs)

Without these endpoints, container images cannot be pulled from private subnets (unless NAT Gateway is available).


### 17.5 Advanced Networking Scenarios

#### VPC Overlapping CIDR Solutions

When two VPCs (or on-premises networks) have overlapping CIDRs and need to communicate:

1. **PrivateLink**: Expose the service via NLB → PrivateLink endpoint service. Consumer creates interface endpoint. No IP overlap issue (consumer uses local ENI IPs). Best for unidirectional service access.

2. **NAT with Transit Gateway**: Transit Gateway with NAT instances/appliances translating overlapping addresses. Complex but bidirectional.

3. **AWS Cloud WAN with NAT**: Cloud WAN segments with NAT at segment boundaries.

4. **Application-level proxy**: ALB or API Gateway as intermediary. No direct IP communication.

#### VPC Peering vs Transit Gateway vs PrivateLink Decision

| Scenario | Best Option |
|---|---|
| 2 VPCs, simple connectivity | VPC Peering |
| 10+ VPCs, hub-and-spoke | Transit Gateway |
| Service-to-service, unidirectional | PrivateLink |
| Overlapping CIDRs | PrivateLink |
| Transitive routing needed | Transit Gateway |
| Centralized firewall inspection | Transit Gateway + Network Firewall |
| Multi-region connectivity | Transit Gateway Peering |
| High bandwidth, 2 VPCs | VPC Peering (no per-GB charge) |
| Cross-account service exposure | PrivateLink |


### 17.6 Common SAP-C02 Scenario Patterns — Quick Reference

#### "Migrate a database with minimal downtime"
→ DMS with full load + CDC. SCT if heterogeneous.

#### "Replace on-premises file server for Windows users"
→ FSx for Windows File Server + Storage Gateway (FSx File Gateway) for local caching.

#### "Global application with low-latency reads and writes"
→ DynamoDB Global Tables (active-active) + CloudFront + Route 53 latency routing.

#### "Process millions of S3 objects"
→ Step Functions Distributed Map + Lambda.

#### "Real-time dashboard from streaming data"
→ Kinesis Data Streams → Lambda or Managed Flink → DynamoDB → API Gateway WebSocket or QuickSight.

#### "Centralized logging across all accounts"
→ Organization CloudTrail + CloudWatch Logs (cross-account) + S3 centralized bucket + Athena or OpenSearch.

#### "Prevent data exfiltration from VPC"
→ VPC endpoints (no internet access) + S3 endpoint policy restricting to specific buckets + SCP denying S3 access outside VPC endpoint.

#### "Automate compliance remediation"
→ AWS Config rule (detect) → SSM Automation (remediate) → SNS (notify).

#### "Serve static website globally with custom domain"
→ S3 + CloudFront + Route 53 (Alias record) + ACM certificate (us-east-1).

#### "Decouple microservices with guaranteed ordering"
→ SNS FIFO → SQS FIFO (per-service queues).

#### "Reduce Lambda cold starts for Java"
→ SnapStart (if Java). Otherwise, Provisioned Concurrency.

#### "Encrypt data with customer-controlled keys and FIPS 140-2 Level 3"
→ CloudHSM or KMS Custom Key Store backed by CloudHSM.

#### "Share VPC infrastructure across accounts"
→ RAM (share subnets). Owner manages networking, participants launch resources.

#### "Track software licenses during migration to AWS"
→ License Manager + Dedicated Hosts (for BYOL with socket/core-based licensing).

#### "Migrate existing Kafka workloads"
→ Amazon MSK (native Kafka compatibility).

#### "Implement WORM compliance for financial records"
→ S3 Object Lock (Compliance mode) + Glacier Vault Lock.

#### "Federate corporate Active Directory for AWS console access"
→ IAM Identity Center + AWS Managed Microsoft AD (or AD Connector).

#### "Prevent accidental deletion of critical infrastructure"
→ CloudFormation Stack Policies + DeletionPolicy: Retain + AWS Backup Vault Lock.

#### "Multi-account tagging enforcement"
→ Organizations Tag Policies + SCP denying untagged resource creation + Config rules for tag compliance.
